Chapter 1 left a question open: if even the main loop is a plugin, where does control flow live?

This chapter gives both halves of the answer. **Service resolution** decides "whose implementation do I get". **Event dispatch** decides "who can intercept my decision". Both are defined in equally short code:

## 1. `ctx.tools` is not a property, it is a lookup

Chapter 1 established that `ctx` is a Proxy. Now look at what that Proxy's `get` trap actually does, in {{src:vendor/cordis/src/reflect.ts#L136-L171|ReflectService.handler.get}}:

```ts
get: (target, prop, ctx: Context) => {
  if (isSpecialProperty(prop)) {
    return Reflect.get(target, prop, ctx)
  }
  if (Reflect.has(target, prop)) {
    return getTraceable(ctx, Reflect.get(target, prop, ctx))
  }

  const error = new Error(`cannot get property "${prop}" without inject`)
  ...
```

The first two branches are fast paths. {{src:vendor/cordis/src/reflect.ts#L86-L91|isSpecialProperty}} defines what counts as special:

```ts
// - is a symbol
// - is a reserved word (prototype, then)
// - is a number string (0, 1, 2, ...)
// - starts with `_`
function isSpecialProperty(prop: string | symbol): prop is symbol {
  return typeof prop === 'symbol'
    || RESERVED_WORDS.includes(prop)
    || parseInt(prop).toString() === prop
    || prop.startsWith('_')
}
```

`then` is on the reserved list, and that bears directly on `await ctx.plugin(...)` from chapter 1: if `ctx.then` went through service resolution, any `await ctx` would trigger a lookup and throw. Classifying it as special means `ctx` can never be mistaken for a thenable.

Note the `error` object on the third line: it is constructed **before** the lookup starts. That is not waste, it is how the **caller's stack** gets captured here. Construct the error only after the lookup fails and the top of the stack is framework internals, leaving the user with nothing but cordis frames. Chapter 1 saw this same "build an error early just to keep the stack" trick in `buildOuterStack`.

### The actual lookup

Skipping the accessor branch, the core is this loop ({{src:vendor/cordis/src/reflect.ts#L153-L167|reflect.ts:153-167}}):

```ts
return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
  const key = target[symbols.isolate][prop]
  let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber
  while (true) {
    const impl = fiber.store?.[prop]
    if (impl) return getTraceable(ctx, impl.value)
    if (prop in fiber.inject) {
      error.message = `cannot get required service "${prop}" in inactive context`
      throw error
    }
    if (!fiber.runtime) throw error
    if (fiber.parent[symbols.isolate][prop] !== key) throw error
    fiber = fiber.parent.fiber
  }
})
```

**Reading a service name walks up the fiber chain.** Line by line:

1. `const key = target[symbols.isolate][prop]` takes this service name's **isolation label** in the current context. Section 4 covers it.
2. `fiber.store?.[prop]` checks the current fiber's service snapshot. A hit returns.
3. `if (prop in fiber.inject)` is the critical one: **the dependency was declared, but is not in the snapshot**. That can only happen while the fiber is not yet active (chapter 1: `store` is snapshotted from `_store` during `_reload`). Walking further up is wrong here, because it would hand back someone else's implementation while this plugin explicitly declared it wants its own. So it throws, worded `in inactive context` rather than `without inject`.
4. `if (!fiber.runtime) throw error` reached the root fiber (chapter 1: the root fiber's `runtime` is `null`), nothing found, so the original `without inject` message stands.
5. `if (fiber.parent[symbols.isolate][prop] !== key) throw error` the parent's isolation label differs from mine, **which means this is an isolation boundary**, and it must not be crossed.
6. `fiber = fiber.parent.fiber` only when none of the above applied.

:::key Why `inject` is mandatory
`fiber.store` only holds services this plugin **declared via `inject`** (chapter 1: that is exactly what `_refresh` fills by calling `_checkImpl` on each). Undeclared names are absent from the snapshot, the loop walks all the way to the root, and you get `cannot get property "x" without inject`.

So `inject` is not merely a scheduling hint meaning "wait for dependencies". It is simultaneously an **access declaration**. One `inject` table carries both jobs.
:::

## 2. provide: putting an implementation into the registry

The other direction. {{src:vendor/cordis/src/reflect.ts#L277-L305|ReflectService.provide()}}:

```ts
provide(name: string, value?: any, check?: () => boolean) {
  return this.ctx.fiber.effect(() => {
    ...
    this.ctx.root[symbols.isolate][name] ??= Symbol(name)
    const key = this.ctx[symbols.isolate][name]
    const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
    if (this.store[key]) {
      throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
    }
    this.store[key] = impl
    this.ctx.fiber.store![name] = impl
    if (this.ctx.fiber.state === FiberState.ACTIVE) {
      this.notify([name])
    }
    return async () => {
      delete this.store[key]
      const fibers = this.notify([name])
      await Promise.allSettled(fibers.map(fiber => fiber.await()))
      // ensure self access before dependencies cleanup
      delete this.ctx.fiber.store![name]
    }
  }, `ctx.provide(${JSON.stringify(name)})`)
}
```

The very first line honours chapter 1's hard rule: **the entire registration is wrapped in `ctx.fiber.effect()`**. When the plugin unloads, `store[key]` is deleted automatically.

Several details:

**`root[symbols.isolate][name] ??= Symbol(name)`** creates the default isolation label on the **root context**. So without any isolate declaration the whole tree shares one label, and a name has exactly one implementation in `store`.

**Providing the same name twice throws**, and the message names the first registrant's fiber. This is one instance of "misconfiguration fails loud": two plugins fighting over one service name is a configuration error, and the later one must not silently win.

**The order inside the disposer matters.** First `delete this.store[key]` (nobody can see me anymore), then `notify` to wake dependents so they unload, `await` all of them, and only **then** delete its own `fiber.store[name]`. The source comment says why: `ensure self access before dependencies cleanup`. Dependents may still need to read this service while running their own cleanup, and deleting our copy first would make their cleanup code fail to resolve it.

### The Service base class is sugar over provide

{{src:vendor/cordis/src/service.ts#L42-L59|The Service constructor}}:

```ts
constructor(protected ctx: Context, name: string) {
  name ??= this.constructor['provide'] as string
  let self = this
  const tracker: Tracker = { associate: name, property: 'ctx' }
  if (self[symbols.invoke]) {
    self = createCallable(name, joinPrototype(Object.getPrototypeOf(this), Function.prototype), tracker)
  }
  self.ctx = ctx
  self.name = name
  defineProperty(self, symbols.tracker, tracker)

  self.ctx.reflect.provide(name, self, this[symbols.check])
  return self
}
```

The last two lines are the whole point: `super(ctx, 'myService')` **is** a `provide`, and **the constructor may not return `this`** (chapter 1 saw the same trick in `Context`). When a service defines `[symbols.invoke]` it is wrapped into a callable object, which is where "the service itself can be called as a function", as in `ctx.logger('name')`, comes from.

Every DSH service is written this way. Here is a real one ({{src:packages/core/tools/src/index.ts#L787-L794|ToolRuntime}}):

```ts
export class ToolRuntime extends Service {
  static inject = ['systemPrompt']

  static Config: z<Config> = z.object({
    mode: z.union(['native', 'code', 'both'] as const).default('native'),
    maxParallelSubCalls: z.natural().min(1).default(10),
  })
```

`static inject` and `static Config` are the plugin metadata from chapter 1: a `Service` subclass is also a class plugin.

## 3. notify: a service changed, who wakes up

Chapter 1 covered the epoch mechanism: a changed dependency fingerprint triggers a reload. **Who changes the fingerprint** went unanswered. It is {{src:vendor/cordis/src/reflect.ts#L314-L336|notify()}}:

```ts
notify(names: string[], filter = (ctx, name) => ctx[symbols.isolate][name] === this.ctx[symbols.isolate][name]) {
  const fibers: Fiber[] = []
  for (const runtime of this.ctx.registry.values()) {
    for (const fiber of runtime.fibers) {
      let hasUpdate = false
      for (const name of names) {
        if (!(name in fiber.inject)) continue
        if (!filter(fiber.ctx, name)) continue
        hasUpdate = true
        fiber._checkImpl(name)
      }
      if (!hasUpdate) continue
      fiber._refresh()
      fibers.push(fiber)
    }
  }
  ...
}
```

It walks **every** fiber in the registry, picks the ones that declared this dependency and whose isolation label matches, refreshes each snapshot with `_checkImpl`, then recomputes the epoch with `_refresh`.

That closes chapter 1's loop:

```text
some plugin calls provide('llm', impl)
  -> notify(['llm'])
    -> for each fiber that injects llm: _checkImpl('llm')   update _store
    -> _refresh()          recompute the epoch fingerprint
      -> _setEpoch()       fingerprint changed
        -> _reload()       the plugin reloads, this time it can resolve llm
```

**This chain is the only automatic scheduling in Cordis.** No dependency-injection container, no topological sort, just "who provided what" triggering "who injected it" to recompute. Chapter 1 noted that a plugin's position in the config file does not determine load order, and this chain is why: order is decided at runtime.

## 4. isolate: several implementations of one name

So far `store` has been keyed by isolation label while we assumed there is only one label. {{src:vendor/cordis/src/context.ts#L121-L125|Context.isolate()}} breaks that assumption:

```ts
isolate(name: string, label?: symbol) {
  const shadow = Object.create(this[symbols.isolate])
  shadow[name] = label ?? Symbol(name)
  return this.extend({ [symbols.isolate]: shadow })
}
```

Three lines. Build a new label table inheriting the parent's, point `name` at a fresh label, and derive a child context with `extend` (chapter 1: `extend` is prototypal and never mutates the parent).

The effect: below the returned context, `ctx[isolate]['tools']` points at a new Symbol. Therefore

- `provide('tools', ...)` writes to `store[newSymbol]` without colliding with the outer one;
- when section 1's loop reaches the boundary, `fiber.parent[symbols.isolate]['tools'] !== key` holds, so it **stops walking up** and never sees the outer implementation.

In `cordis.yml` this is an entry option ({{src:vendor/loader/src/config/isolate.ts#L5-L13|the loader's EntryOptions}}):

```yaml
- name: my-plugin
  isolate:
    tools: true          # local realm: this entry only
    llm: shared-label    # named realm: shared by every entry using the same label
```

`true` produces a {{src:vendor/loader/src/config/isolate.ts#L47-L56|LocalRealm}} (label suffixed with `#<entry id>`), a string produces a named `GlobalRealm`.

### What DSH does with it

This is how "give one session a different capability set" is implemented. The comment in {{src:packages/preset/agent-presets/src/index.ts#L418-L428|agent-presets}} states it directly:

> A preset publishes services behind `isolate` realms, which are invisible outside the group that declares them, including to the host.

An agent preset mounts its own tools, prompts, and model adapters inside an isolate realm. So **within one process, two agents can each hold their own `ctx.tools` and never see each other's**.

:::key What this means for multi-agent research
"Give different agents different tool sets" requires no change to agent-loop in DSH, and no agent field in the tool registry to filter on. It is one line of configuration: put the service rows in an isolate realm.

Chapter 10 returns here for subagents, and the multi-agent arrangements you build in chapter 12 land here too.
:::

## 5. Events: five dispatch modes

Services answer "whose implementation do I get". The other half is "who can intercept my decision".

Cordis's event bus has five dispatch modes, differing only in **how they treat listener return values**:

| Mode | Synchrony | Stops when | Returns | Typical use |
|---|---|---|---|---|
| {{src:vendor/cordis/src/events.ts#L194-L196\|`emit`}} | sync, ignores promises | never | nothing | broadcast notification |
| {{src:vendor/cordis/src/events.ts#L183-L187\|`parallel`}} | concurrent, awaits all | never | nothing (errors become an AggregateError) | wait for all observers |
| {{src:vendor/cordis/src/events.ts#L204-L209\|`serial`}} | sequential await | first bail value | that value | async "who claims it" |
| {{src:vendor/cordis/src/events.ts#L217-L222\|`bail`}} | sequential sync | first bail value | that value | sync "who claims it" |
| {{src:vendor/cordis/src/events.ts#L234-L243\|`waterfall`}} | listener's choice | whoever skips `next()` | outermost return value | interceptable, rewritable decision chains |

A "bail value" is defined by {{src:vendor/cordis/src/events.ts#L13-L15|isBailed}}:

```ts
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

Returning `null` / `false` / `undefined` means "not mine, pass it on"; anything else means "claimed, stop". So a listener that **writes no return statement** passes through automatically.

### waterfall is this chapter's second focus

`emit` through `bail` are straightforward. `waterfall` deserves a line-by-line read ({{src:vendor/cordis/src/events.ts#L234-L243|events.ts:234-243}}):

```ts
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()
  const next = () => {
    const cb = cbs.shift() ?? inner
    return cb(...args)
  }
  args.push(next)
  return next()
}
```

Ten lines build an onion:

1. `const inner = args.pop()` takes the last argument off. **The caller's final argument is the built-in behavior**, meaning what happens when no listener intervenes.
2. The `next` closure calls `cbs.shift()` on every invocation. **That is destructive**, so the chain only moves forward; once drained it falls through to `inner`.
3. `args.push(next)` puts `next` back at the end of the argument list, so every listener receives `next` as its last argument.
4. `return next()` starts the chain.

**A listener that does not call `next()` breaks the chain there, and the built-in behavior does not run either.** That is the veto. DSH's guidelines make it a hard rule:

> **Waterfall listeners MUST call `next()`** to delegate; returning without it short-circuits the chain.

### Event filtering

{{src:vendor/cordis/src/events.ts#L165-L175|dispatch()}} filters listeners before delivery:

```ts
dispatch(type: string, args: any[]) {
  const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
  const name: string = args.shift()
  if (!name.startsWith('internal/')) {
    this.emit('internal/dispatch', type, name, args, thisArg)
  }
  const filter = thisArg?.[Context.filter]
  return (this._hooks[name] || [])
    .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
    .map(hook => hook.callback.bind(thisArg))
}
```

The first line is an optional-argument trick: if the first argument is an object or function it is taken as `thisArg`, otherwise the first argument is the event name. That makes both `ctx.emit('foo', a)` and `ctx.emit(carrier, 'foo', a)` valid.

`thisArg[Context.filter]` is the filter. Section 4's isolation does not leak events across realms because {{src:vendor/cordis/src/service.ts#L61-L63|Service's default filter}} compares isolation labels:

```ts
protected [symbols.filter](ctx: Context) {
  return ctx[symbols.isolate][this.name] === this.ctx[symbols.isolate][this.name]
}
```

Listeners registered with `global: true` bypass filtering, which is for diagnostics plugins that genuinely need a global view.

Finally, {{src:vendor/cordis/src/events.ts#L254-L260|register()}} is wrapped in an effect as always:

```ts
register(label: string, hooks: Hook[], callback: any, options: EventOptions): () => void {
  const method = options.prepend ? 'unshift' : 'push'
  return this.ctx.fiber.effect(() => {
    hooks[method]({ ctx: this.ctx, callback, ...options })
    return () => this.unregister(hooks, callback)
  }, label)
}
```

**Listeners registered with `ctx.on()` are removed when their plugin unloads.** That is chapter 1's rule honoured on the event side.

## 6. Back to DSH: approving one tool call

Put both halves together on a real path. Before dispatching a tool, DSH runs a waterfall ({{src:packages/core/tools/src/index.ts#L1474-L1478|tools/index.ts:1474}}):

```ts
const carrier = scopeTarget(this, exec.agent)
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)
```

Read those four lines against section 5's implementation:

- `carrier` is `thisArg`, built by `scopeTarget(this, exec.agent)`, and it **carries an agent-scoped filter**. Only listeners bound to this agent receive the event.
- `exec` is the argument: the pending tool call.
- The trailing arrow function is `inner`, and it **allows by default**.

That `inner` explains a design choice: **DSH's default is allow, and the ability to refuse comes entirely from plugins**. With no approval plugin installed the chain has no listeners, `next()` falls straight through to `inner`, and the result is `{ kind: 'allow' }`. With one installed, it listens on this event and can return `{ kind: 'ask' }` or `{ kind: 'deny' }` without calling `next()`, short-circuiting the chain.

The event's type declaration spells all of this out ({{src:packages/core/tools/src/index.ts#L144-L152|the declaration}}):

```ts
/**
 * Allow, deny, or ask before dispatch. `next()` delegates to allow; missing
 * approval support turns `ask` into denial. ...
 * @mode waterfall
 */
'tools/pre-execute'(this: Scoped<ToolRuntime>, exec: ToolExecution, next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
```

`@mode waterfall` is JSDoc that DSH mandates, because **the signature alone does not reveal which dispatch mode an event uses**, and the wrong mode changes listener behavior completely.

   ```text
   Error: failed to apply loader entry b141926e (@deepseek-ai/cordis-plugin-include):
     failed to apply loader entry 968fbe06 (./consumer.ts):
       cannot get property "greeter" without inject
   ```

   The innermost message is section 1's loop reaching the root fiber. The two outer layers are the loader's positional wrapping. Chapter 1 said "a failing plugin reports loudly rather than being skipped", and this is what that looks like.

2. **Restore inject and give consumer an isolate**:
   ```yaml
   - name: './consumer.ts'
     isolate:
       greeter: true
   ```
   Rerun. consumer now sits in its own realm and cannot see the outer greeter, so it stays PENDING forever, `apply` never runs, and nothing is printed. That is the `fiber.parent[symbols.isolate][prop] !== key` line in the lookup loop.

3. **Provide a second greeter inside the same realm** so consumer has something to resolve:
   ```yaml
   - name: './greeter.ts'
     config:
       name: outer
   - name: './consumer.ts'
     isolate:
       greeter: shared
   - name: './greeter.ts'
     config:
       name: inner
     isolate:
       greeter: shared
   ```
   The output becomes `hello from inner`. Two `ctx.greeter` implementations coexist in one process, and consumer resolves the one inside its realm.

Step 3 is the prototype of how DSH gives different agents different tool sets.

## 7. Looking back: these two chapters are a paper

Both halves of Cordis are now covered: chapter 1's revocable effects, chapter 2's service resolution and notification. This machinery was not improvised. There is a paper.

Line 7 of DSH's own {{src:README.md#L7|README}} says so:

> It uses an architecture where **everything is a plugin**, and is powered by Cordis, whose design is described in _A Programming Paradigm for Spatiotemporal Composability_.

The paper is at [github.com/cordiverse/paper](https://github.com/cordiverse/paper) ([direct PDF](https://github.com/cordiverse/paper/blob/main/paper.pdf)). Authors Yifan Shi, Wei Zhang, and Tianyi Cui, Peking University and DeepSeek-AI; 88 pages, draft of August 13, 2026, marked as a preprint under active revision. The abstract's first sentence names the motivation:

> Modern software—from plugin systems to self-evolving agent harnesses—increasingly requires *dynamic composition*, yet its formal foundations remain underdeveloped.

**From plugin systems to self-evolving agent harnesses.** §1.2.2 is titled Self-Evolving Agent Harnesses. DSH is this paper's application domain, not the other way around.

### Two dimensions

The paper splits dynamic composition into two orthogonal dimensions, which are exactly these two chapters:

| Dimension | Requirement | Static-case degeneration | This course |
|---|---|---|---|
| **Temporal composability** | on removal, every modification a component made to the shared environment must be completely and safely reversed | lexical scoping (RAII, bracket patterns) | chapter 1 |
| **Spatial composability** | components must declare, discover, and reactively resolve dependencies on one another at runtime | module import resolution | chapter 2 |

The difficulty is the word "dynamic". Statically both are solved at compile time; a plugin that arrives after deployment has no lexical scope to bound it and no compile-time context that could anticipate its dependencies. The paper's move is to take effects (how a program **modifies** its environment) and coeffects (how it **depends on** its environment), both of which are static-analysis theories, and lift them into runtime mechanisms.

The paper uses VSCode as the counterexample, and two numbers make the point: among the top 100 extensions by install count, **87 contain executable code**, so removing any of them requires restarting the whole extension host; and only **7 declare `extensionDependencies`**. The first number is the missing temporal dimension, the second the missing spatial one.

### Three things the paper explains that the code alone does not

**One: why reverse-order cleanup needs no precondition while concurrent cleanup does.**

Chapter 1 covered two cleanup orders: inside one `effect` it is reverse and **serial**, while across a fiber's effects it is reverse and **concurrent** (`Promise.all`). At the time the only available answer was "that is how it is written".

The paper supplies the difference. Definition 1 defines twisted composition:

```
(f₁, g₁) ∘ (f₂, g₂) := (f₁ ∘ f₂, g₂ ∘ g₁)
```

Forward transformations compose in order; inverses **accumulate in the opposite order**. That is the algebraic form of the line in `ctx.effect()` that prepends each new inverse onto the accumulator. Theorem 16 follows: reverting in the reverse of the application order needs **no additional assumption**, because each inverse meets exactly the state its own application produced.

Concurrent cleanup is not strictly reverse order. Making any order valid requires Definition 19's **independence**: two effects are independent when their transformations commute and neither disturbs the inverse the other yields. Only then does Corollary 21 hold: for a pairwise independent family, reverting in **any permutation** returns to the initial state.

So chapter 1's two orders were not arbitrary. Serial reverse order inside one effect takes Theorem 16's unconditional guarantee; concurrency across effects bets on independence. §6.1 discusses where that obligation lands: **the runtime does not verify that an inverse actually reverts its effect. That is the component author's obligation.**

**Two: `notify`'s three classifications have names.**

Definition 24 gives the satisfaction predicate and Definition 26 the classification:

```
σ ⊨ d  :=  ∀k ∈ d. k ∈ dom(σ)

notify_d(σ, σ') = activating    if σ ⊭ d and σ' ⊨ d
                | deactivating  if σ ⊨ d and σ' ⊭ d
                | neutral       otherwise
```

"An activating transition triggers execution of the component's effects, whereas a deactivating transition triggers recovery by applying the accumulator" is chapter 1's `_reload` and effect teardown, driven by chapter 2's {{src:vendor/cordis/src/reflect.ts#L314-L336|notify()}}. Algorithm 3's pseudocode is line-for-line isomorphic to that function: walk every fiber, test `key ∈ fiber.inject` and matching isolation label, refresh on a hit.

Chapter 2's epoch is called `target` in the paper, defined as a digest over the **uid of the provider fiber** each declared key resolves to. The paper explains the choice of uid over value: a uid is never reused, so "a different provider" and "the same provider changed its value" are distinguishable, and the latter by design **does not trigger a reload**.

**Three: isolate and intercept are one pair, not two features.**

Chapter 2 covered isolation realms and mentioned intercept only in passing. §3.2.3 puts them in one section titled Isolation and Interception and explains why they belong together.

Definition 28 defines the coeffect context with isolation as a two-layer map:

```
Σ^iso := (K ⇀ R) × ((r : R) ⇀ V_r)
```

The realm table ρ maps key k to a realm identifier r, then the value table σ yields σ(ρ(k)). That is chapter 2's two steps: read the label from `ctx[symbols.isolate][name]`, then the implementation from `store[key]`.

Definition 27 is the key distinction: a context transformation admits two **realizations**. *In-place* mutates the shared context and returns a nontrivial inverse. *Derived* leaves the input intact and returns a fresh child context, with the identity as its inverse. `provide` is the former (hence an effect that must be revoked); **isolate and intercept are both the latter** — they change only how a key resolves, never the table, so discarding the child context is the reversal and no inverse needs tracking. That is why `ctx.isolate()` returns a new context rather than a disposer.
