# Agent Loop：一次轮次的完整生命周期

上一章讲了事件怎么被记录。这一章讲事件是被谁 append 的。

`dsh-agent-loop` 的 README 第一段有一句话，值得先记住：

> This is the only package in the harness that contains concrete loop logic. Everything else is an abstract service or a plugin against extension points.

**整个 harness 里只有这一个包含有具体的循环逻辑。** 219 个包里，其他全部是抽象服务或者挂在扩展点上的插件。所以「DSH 的控制流在哪里」这个问题的最终答案，就是本章要走读的这 496 行。

先看它跑一次的产物。本章实验用一个假的模型适配器（第一次回工具调用，第二次回文本）跑一个真的 agent，日志是这 23 条：

## 一、三层循环

驱动器是三个嵌套的 `while`，每层的退出条件不同。

**最外层**是 {{src:packages/core/agent-loop/src/agent.ts#L210-L223|kick}}：

```ts
private async kick(): Promise<void> {
  try {
    while (await this.turn()) {}
  } catch (_error) {
    // Reported failures and cancellation are contained at the driver boundary.
  } finally {
    if (this.phase.kind === 'running') {
      const { turn, wakeRequested } = this.phase
      this.setPhase({ kind: 'idle', lastTurn: turn })
      if (wakeRequested && this.inbox.hasPending) this.wakeDriver()
    }
  }
}
```

`while (await this.turn()) {}` 一个空循环体。`turn()` 返回 `true` 表示队列里还有活，接着开下一轮；返回 `false` 就停下来变回 idle。

`catch` 是空的，这不是吞异常：失败已经在更内层通过 `agent/error` 事件报告过了，这里只是不让它冲出驱动器边界。第 4 章讲过 DSH 里「已提交的事情不能因为观察者失败而回滚」，这里是同一个思路的另一半：**驱动器是失败的终点**。

**中间层**是 {{src:packages/core/agent-loop/src/agent.ts#L246-L330|turn()}} 里的 `while (true)`，每转一圈是一个 step。

**最内层**是 {{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}} 里的 `while (true)`，它只为一件事存在：请求失败后重试。

## 二、Phase：三个状态和一个闩

{{src:packages/core/agent-loop/src/agent.ts#L38-L46|Phase}} 是个三态联合：

```ts
type Phase =
  | { kind: 'idle'; lastTurn: number }
  | { kind: 'maintenance'; abort: AbortController; lastTurn: number; wakeRequested: boolean }
  | { kind: 'running'; abort: AbortController; turn: number; step: number; wakeRequested: boolean }
```

对外暴露的 `status` 只有两种：`maintenance` 和 `idle` 都报 `'idle'`。maintenance 是「独占但不是模型轮次」的状态，压缩这类活跃在它里面跑。

有意思的是 `wakeRequested` 这个闩。看 {{src:packages/core/agent-loop/src/agent.ts#L172-L193|wakeDriver}}：

```ts
private wakeDriver(wakeAfterAbort = false): void {
  if (this.phase.kind !== 'idle') {
    const reason = this.phase.abort.signal.reason as AgentCancelCause | undefined
    if (reason?.kind !== 'disposed' && (this.phase.kind === 'maintenance' || wakeAfterAbort)) {
      this.phase.wakeRequested = true
    }
    return
  }
  ...
}
```

新消息到达时，如果驱动器正忙，通常不用管：活着的驱动器自己会在下一个 step 边界去 claim 队列。但有两种情况它不会来取：

1. 当前是 **maintenance**，根本没有 step 边界；
2. 当前驱动器**已经被 abort 了**，它正在往退出路径上走。

这两种情况就把 `wakeRequested` 置位，等收敛点（`kick` 的 `finally` 或 `runMaintenance` 的 `finally`）再重放一次唤醒。

`reason?.kind !== 'disposed'` 是例外中的例外：**销毁不留闩**。否则卸载时还会去起一轮新的模型调用。

### 一个被注释专门标出来的顺序

{{src:packages/core/agent-loop/src/agent.ts#L113-L120|send()}} 只有六行，但每一行都有讲究：

```ts
send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
  // Waking input cannot join an aborted activity, so it starts the next turn.
  // Captured before the insertion so a reentrant cancel from a splice observer cannot reclassify it.
  const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
  const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
  this.inbox.splice(resolvedTarget, Infinity, 0, [message])
  if (wakeup) this.wakeDriver(wakingAfterAbort)
}
```

`wakingAfterAbort` **在插入之前就算好**。原因写在第二行注释里：`inbox.splice` 会 append 一条 `agent/inbox/spliced` 事件，而第 4 章讲过，append 会同步调用一批 `session/event` 监听器。这些监听器里任何一个都可能反过来调 `agent.cancel()`。如果分类在插入之后算，同一条消息就会因为一个观察者的副作用而从「加入当前轮次」变成「另起一轮」。

先算后插，分类就锁死了。

## 三、inbox：两条队列

{{src:packages/core/agent/src/inbox.ts#L28-L40|Inbox}} 持有两条队列，语义完全不同：

| 队列 | 消费方式 | 用途 |
|---|---|---|
| `next-turn` | 一次取**一条**（FIFO） | 排队的用户提问，每条各占一个轮次 |
| `next-step` | 一次取**整批** | 步间插入：steering、工具产出的上下文、注入 |

三个公开方法是同一个 `send()` 的固定预设，区别只在 (目标 × 是否唤醒) 两个维度：

| 方法 | target | wakeup | 效果 |
|---|---|---|---|
| `followup()` | `next-turn` | 是 | 排一个新轮次并唤醒 |
| `steer()` | `next-step` | 是 | 挤进下一个 step 边界并唤醒 |
| `inject()` | `next-step` | 否 | 挤进下一个 step 边界，但不主动叫醒 |

`inject()` 不唤醒这一点很关键：文件变更通知、AGENTS.md、skill 内容这些都走 `inject()`，它们只在**已经有活跃轮次**的时候才有意义。agent 闲着的时候注入一条上下文却把它叫起来跑一次模型调用，是没人想要的行为。

{{src:packages/core/agent/src/inbox.ts#L71-L78|claim()}} 是步边界上的取件动作：

```ts
claim(target: InboxTarget, turn: number): UserMessage[] {
  const claimed = this.mutate('next-step', 0, this.nextStep.length, [], false)
  if (target === 'next-turn') {
    claimed.push(...this.mutate('next-turn', 0, 1, [], false))
  }
  for (const message of claimed) this.notifications.claimed(message, turn)
  return claimed
}
```

`next-step` 全取，`next-turn` 只取一条。最后那个 `false` 参数是 `discardRemoved`：**claim 是纯删除，不算取消**。这个区别落在日志上就是 `outcome` 字段有没有 `'canceled'`，重放时能分清「这条消息被用掉了」和「这条消息被撤了」。

### inbox 也是日志投影

{{src:packages/core/agent/src/inbox.ts#L158-L193|mutate()}} 的最后几行：

```ts
this.validate(splice)
const event = this.session.append('agent/inbox/spliced', splice)
const removed = inbox.splice(actualStart, actualDeleteCount, ...event.data.inserted)
```

**先写日志，再改内存。** 方法注释解释了为什么：

> The durable event commits before the live projection mutates, so synchronous `session/event` observers see the pre-splice lists and can reconstruct the removed messages from the normalized coordinates.

同步观察者看到的是**变更前**的队列加上一份规范化的坐标，两者相减就能算出被删掉的是哪几条。事件里不需要冗余地存一份被删的消息。

构造函数则反过来，从日志重放出内存状态：

```ts
for (const event of session.events.slice(session.header.seedLength ?? 0)) {
  if (event.type !== 'agent/inbox/spliced') continue
  this.apply(event.data)
}
```

所以 resume 一个持久化的会话时，没来得及处理的排队消息会一起回来。inbox 和第 4 章的 surface 是同一种东西：**日志的一个增量投影**。

## 四、turn()：边界一定成对

{{src:packages/core/agent-loop/src/agent.ts#L246-L330|turn()}} 是本章最该逐句读的函数。骨架是这样：

```ts
const turn = phase.turn + 1
this.session.append('turn/start', { turn })
phase.turn = turn
let turnEnds: TurnEndReason | null = null
let target: InboxTarget = 'next-turn'
try {
  while (true) { /* 一圈一个 step */ }
} catch (error) {
  ...
} finally {
  this.session.append('turn/end', { turn, reason: turnEnds! })
}
```

**`turn/end` 写在 `finally` 里。** 无论正常结束、被拒绝、抛异常还是被取消，这条事件一定落日志。`step/end` 同样：

```ts
try {
  for (const message of decision.messages) {
    this.session.append('user/message', message, { surfaceOp: 'append' })
  }
  const stepEnd = await this.step(decision.assembly)
  if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
} finally {
  this.session.append('step/end', { turn, step })
}
```

于是日志里的 `turn/start` / `turn/end` 和 `step/start` / `step/end` 严格成对嵌套，重放的人不需要处理「开了没关」的情况。

### turnEnds 在哪里被赋值

这个变量决定 `turn/end` 里写什么理由，四个赋值点分别对应四种结局：

```ts
if (decision.kind === 'reject') {
  turnEnds = { kind: 'blocked' }
  return false
}
```

`agent/pre-step` 拒绝，轮次开了但一步没走。本章实验第 2 步会造一个出来，日志只有四条。

```ts
if (phase.step === 0 && decision.messages.length === 0) {
  turnEnds = { kind: 'completed' }
  return false
}
```

**唤醒消息被撤了，或者被插件改写成空**。注释说明了这里的取舍：

> A removed waking message or an enter decision rewritten to empty still owns the initial turn boundary, but it spends no model call.

轮次边界已经开了就得关，但不花模型调用。

```ts
if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
```

**max-tokens 是粘性的。** 一旦某一步撞了输出上限，后面的步骤即便正常完成也不能把整轮的结论降级。因为对调用方来说「这轮有内容被截断了」是必须知道的事实。

```ts
} catch (error: unknown) {
  if (signal.aborted) {
    turnEnds = { kind: 'aborted', reason: signal.reason as AgentCancelCause }
    throw error
  }
  turnEnds = {
    kind: 'error',
    error: error instanceof LlmError ? error.failure : { message: errorChain(error), code: 'UNKNOWN' },
  }
  this.throwError(error)
}
```

取消和失败分开。取消把 `signal.reason` 原样存进日志，所以重放时能看出是用户按的停、是 hook 拦的、还是父 agent 停的。失败则一律结构化：`LlmError` 保留原有事实，其余的压平成 `errorChain` 文本加 `UNKNOWN` 码。**日志里不会出现一个非结构化的错误。**

### 什么时候继续下一步

```ts
if (turnEnds && this.inbox.nextStep.length === 0) {
  await this.dispatch.serial('agent/turn-stopping', { turn, signal })
  signal.throwIfAborted()
}
if (turnEnds && this.inbox.nextStep.length === 0) break
target = 'next-step'
```

同一个条件判断了两次，中间夹一次 `agent/turn-stopping`。这不是笔误：`turn-stopping` 的监听器**可以往 `next-step` 里塞东西**，从而让轮次继续下去。第一次判断决定要不要问，问完之后再判断一次才作数。这是一个「最后挽留」扩展点，goal 模式的续轮就挂在这里。

注意 `target = 'next-step'`：**第二个 step 开始就不再消费排队的提问了**。开篇那 23 行日志里，seq 15 的 `step/start` 后面没有 `user/message`，就是这个原因——第二步的输入是上一步留在 surface 上的 `tool/result`。

最后：

```ts
if (!this.inbox.hasPending) return false
phase.abort = new AbortController()
phase.wakeRequested = false
phase.step = 0
return true
```

**换一个新的 AbortController。** 上一轮如果是被取消的，那个 controller 已经处于 aborted 状态，直接复用会让新轮次一开始就抛。同时把闩清掉，注释解释：活着的驱动器自己会去 claim 队列，旧 controller 上的闩已经过期了。

## 五、step()：一次模型调用

{{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}} 的一圈：

```ts
const { request, preparedCall } = await this.buildRequest(
  turn, step, assembly.tools, system, this.session.deriveMessages(), signal,
)
```

第五个参数就是第 4 章那个 `deriveMessages()`。**每一步都重新派生一次**，驱动器自己不维护任何消息数组。这是「日志是唯一真相」在调用侧的直接后果：一个压缩插件在两步之间往日志里 append 一条 replace 事件，下一步的请求自动就用上了压缩后的历史，不需要任何人通知驱动器。

```ts
const assembler = new BlockAssembler()
const chunkSeqs: number[] = []
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
for await (const chunk of stream) {
  signal.throwIfAborted()
  chunkSeqs.push(this.session.append('assistant/chunk', { turn, step, chunk }).seq)
  assembler.push(chunk)
}
```

每个 chunk 都落日志，`append` 的返回值提供 seq，攒成 `chunkSeqs`。开篇日志里 seq 7-10 就是这四条，而 seq 11 的 `assistant/message` 带着 `sourceEventSeqs: [7,8,9,10]`。第 4 章讲的溯源链在这里被填上。

`signal.throwIfAborted()` 在循环体第一行，**每收到一个 chunk 检查一次**。取消能在流的任何位置生效，已经落日志的 chunk 不回滚。

```ts
const finish = assembler.finish
if (finish.kind === 'error' || finish.kind === 'aborted') {
  const action = await this.dispatch.waterfall('agent/request-error', { ... },
    () => Promise.resolve<RequestErrorAction>(undefined))
  if (action?.kind !== 'retry') {
    throw new LlmError(finish.failure.message, finish.failure.code, finish.failure)
  }
  continue
}
```

**默认不重试。** 内置行为返回 `undefined`，只有插件明确回一个 `{ kind: 'retry' }` 才 `continue` 转第二圈。第 2 章讲的 waterfall 洋葱在这里又是「默认拒绝，能力由插件提供」的形状，和 `tools/pre-execute` 正好相反（那个是默认放行）。`dsh-llm-retry` 就是挂在这个点上的插件。

```ts
this.session.append('assistant/message', { turn, step, message, ...usage },
  { surfaceOp: 'append', sourceEventSeqs: chunkSeqs })
if (finish.kind === 'max-tokens') return { kind: 'max-tokens' }

const toolCalls = message.content.filter(block => block.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }
const { concluded } = await executeToolCalls(
  this.loopCtx, turn, step, toolCalls, signal,
  context => this.inbox.splice('next-step', this.inbox.nextStep.length, 0, [context]),
)
return concluded ? { kind: 'completed' } : null
```

三个返回值定义了外层循环的行为：

| 返回 | 含义 | turn() 的反应 |
|---|---|---|
| `{ kind: 'max-tokens' }` | 撞上输出上限 | 记为结束理由（且粘性） |
| `{ kind: 'completed' }` | 没有工具调用，或工具声明了结束 | 记为结束理由 |
| `null` | 工具跑完了，还得再问一次模型 | 继续下一个 step |

`null` 就是 ReAct 循环的那个「继续」。类名 `ReactLoopAgent` 里的 React 指的正是 reason-act 交替。

最后那个箭头函数是**工具产出的上下文的去向**：直接进 `next-step` 队列。所以一个工具可以在结果之外附带一条用户角色的上下文消息，它会在下一个 step 边界被 claim 进去。

## 六、buildRequest：请求头只在变化时写

{{src:packages/core/agent-loop/src/agent.ts#L407-L495|buildRequest}} 有 88 行，做四件事。

**一、算出这次的配置提案，交给插件改。**

```ts
const seedConfig = deepFreeze(structuredClone(
  this.requestHeaderLogged ? requestProposal(persistedHeader!) : { ...route, ...reasoningEffort, ...maxTokens }
))
const proposedConfig = await this.dispatch.waterfall('agent/request', { turn, step, signal },
  () => Promise.resolve(seedConfig))
```

`requestProposal` 那个小函数值得看：

```ts
function requestProposal(header: EpochHeader): LlmCallConfig {
  if (header.adapterDefaults === undefined) return header.config
  const proposal = { ...header.config }
  if (header.adapterDefaults.reasoningEffort === true) delete proposal.reasoningEffort
  if (header.adapterDefaults.maxTokens === true) delete proposal.maxTokens
  return proposal
}
```

**由适配器补全的默认值要先剥掉再给插件看。** 第 4 章提过 `adapterDefaults` 这个标记 map，它区分「用户明确设的值」和「适配器根据具体模型填的值」。如果不剥，插件看到的就是一个已经被上一次解析固化的配置，换模型时旧模型的默认值会跟着跑过去。

**二、把提案交给适配器解析。**

```ts
try {
  preparedCall = await this.loopCtx.llm.prepareCall(proposedConfig, signal)
  config = preparedCall.config
} catch (error) {
  if (!(error instanceof LlmError) || error.code !== 'NO_ADAPTER') throw error
  config = proposedConfig
}
```

`NO_ADAPTER` 被单独放行，注释解释：中间件可以服务一条没有注册适配器的路由。只有真正走到终端分发时才必须有适配器。

**三、写请求头，但只在变化时写。**

```ts
const baseline = this.session.requestHeader()
if (!this.requestHeaderLogged) {
  this.session.append('request/header', { header, reason: baseline === undefined ? 'initial' : 'resume' })
  this.requestHeaderLogged = true
} else if (baseline === undefined || !headerEquals(baseline, header)) {
  this.session.append('request/header', { header, reason: 'change' })
}
```

三种 reason 各有含义：`initial` 是全新会话的第一条，`resume` 是这个 loop 实例在一条已有日志上的第一条（进程重启、fork），`change` 是后来某次请求换了配置。`baseline` 来自第 4 章那个增量 fold `session.requestHeader()`。

请求头包含 system 提示词和工具 schema 全文，每一步都写一遍会让日志暴涨。只在变化时写，重放时靠 fold 取最新一条，两边都划算。开篇日志里 seq 5 只出现一次，第二步没有再写。

**四、冻结并打标。**

```ts
const request = markAgentLoopRequest(deepFreeze({ ...header.config, messages: boundaryMessages, ... }))
```

`markAgentLoopRequest` 把这个请求对象登记进 `dsh-llm` 持有的一个进程内 identity 集合。不变量companion 靠它区分「循环构建的请求」和「插件直接发的一次性调用」，因为只有前者才应该能从日志里重建出来。

## 七、工具调度：并发执行，模型序提交

{{src:packages/core/agent-loop/src/tool-calls.ts#L59-L101|executeToolCalls}} 把一个 step 的工具调用切成若干组：

```ts
while (next < planned.length) {
  const first = planned[next]!
  const mode = ctx.tools.executionMode(first.exec).kind
  const group = mode === 'parallel' ? planned.slice(next) : [first]
  const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
  next += outcome.consumed
  ...
}
```

`parallel` 的调用从当前位置一直切到末尾（后面会再细分），非 parallel 的每次只切一个，形成一道屏障。写文件、执行命令这类工具是独占的，读文件、搜索是并行的。

{{src:packages/core/agent-loop/src/tool-calls.ts#L121-L246|runGroup}} 是这一节的核心，两个不变式撑起它。

**不变式一：提交只沿连续的模型序前进。**

{{src:packages/core/agent-loop/src/tool-calls.ts#L146-L160|commitReady}}：

```ts
const commitReady = async (): Promise<void> => {
  while (committed < group.length) {
    const slot = slots[committed]
    if (slot === undefined) break
    ...
    appendToolResult(session, turn, step, call!.block, result, callSeqs[committed]!)
    for (const context of result.additionalContexts ?? []) acceptContext(context)
    concluded ||= result.concludesTurn === true
    committed++
  }
}
```

三个调用并发跑，第 3 个先完成也只能等着：`slots[committed]` 还是 undefined 就 `break`。等第 1 个和第 2 个到了才一路提交下去。

**执行可以乱序，日志必须有序。** 因为模型下一步看到的 `tool/result` 序列如果和它发出的 `tool/call` 顺序不一致，同样一组调用在两次运行里会得到两份不同的历史，重放就不确定了。

**不变式二：注册表变化能在中途造出屏障。**

{{src:packages/core/agent-loop/src/tool-calls.ts#L198-L213|fillPool}}：

```ts
while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
  const nextCall = group[nextToStart]!
  if (nextToStart > 0 && mode === 'parallel'
    && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
  await startCall(nextToStart)
  nextToStart++
  ...
}
```

每次要启动一个新调用之前**重新问一次** `executionMode`。因为前面的工具可能刚刚改了注册表（比如一个工具切换了权限模式），后面本来并行的调用应该立刻变成独占。`break` 出去之后，外层 `executeToolCalls` 的下一轮会用新的 mode 重新分组。

### 取消时怎么收场

{{src:packages/core/agent-loop/src/tool-calls.ts#L237-L245|runGroup 的收尾}}：

```ts
if (aborted) {
  for (const call of group.slice(started)) appendSkippedToolCall(session, turn, step, call.block)
  return { consumed: group.length, aborted: true, concluded }
}
```

已经启动的调用会被 drain 并正常提交结果，**没启动的则补一对合成的 call/result**（{{src:packages/core/agent-loop/src/tool-calls.ts#L249-L259|appendSkippedToolCall}}）：

```ts
appendToolResult(session, turn, step, block, {
  content: [{ type: 'text', text: 'Error: tool call aborted before dispatch' }],
  isError: true,
  error: { message: 'tool call aborted before dispatch', info: { name: 'AbortError', code: TOOL_ABORTED_BEFORE_DISPATCH } },
}, callSeq)
```

理由在模块注释里：

> Abort records synthetic error results for skipped calls so replay stays valid.

模型发出了 5 个工具调用，日志里就必须有 5 个结果。少一个，重放出来的历史里就有一次悬空的调用，模型会困惑。所以取消时宁可伪造一个「已取消」的结果，也要保住配对。

调度器自身失败则相反：**不伪造结果**，只保留已经记录的 `tool/call`。因为那不是一个「调用被取消了」的事实，而是 harness 自己坏了，伪造一个结果会掩盖问题。

本章实验第 3 步能看到取消的实际形态：工具已经启动，结果照常提交，然后 `turn/end` 记 `{"kind":"aborted","reason":{"kind":"user"}}`。

## 八、五个扩展点

驱动器里所有的 `dispatch.waterfall` / `dispatch.serial` 就是 DSH 给外部留的全部循环级扩展点：

| 事件 | 模式 | 时机 | 能做什么 | 默认行为 |
|---|---|---|---|---|
| {{src:packages/core/agent/src/runtime-types.ts#L222-L231\|`agent/pre-step`}} | waterfall | 每个 step 开始前 | 拒绝整个轮次，或改写进入这一步的消息 | 放行，消息原样 |
| {{src:packages/core/agent/src/runtime-types.ts#L236-L244\|`agent/request`}} | waterfall | 组装请求时 | 改 provider / model / 采样参数 | 用种子配置 |
| `agent/request-error` | waterfall | 请求失败后 | 要求重试 | 不重试，抛 |
| {{src:packages/core/agent/src/runtime-types.ts#L270-L278\|`agent/turn-stopping`}} | serial | 轮次即将结束时 | 往 `next-step` 塞东西让它继续 | 什么都不做 |
| `agent/error` | emit | 失败发生时 | 观察 | 无 |

这五个点覆盖了「拦一步、换个模型、重试、续一轮、看一眼」。第 4 章讲的 `session-checkpoint-policy` 就挂在 `agent/pre-step` 上做落盘检查点，本章实验第 2 步用同一个点做一个内容拦截。

:::key 循环没有第六个扩展点
想改变循环行为，只能从这五个点里选。工具层面的扩展（新工具、执行策略、审批）走的是第 8、9 章的 `tools/*` 事件，那是另一套。

第 12 章要做多智能体排布的话，`agent/pre-step` 和 `agent/turn-stopping` 是最直接的两个抓手。
:::

## 小结

一次轮次的完整链条：

```
followup() → inbox.splice → wakeDriver → kick
  → turn(): turn/start → preStep → claim → step/start → user/message
      → step(): buildRequest → llm.stream → chunk×N → assistant/message
          → executeToolCalls → tool/call / tool/result
      → step/end → 下一步 或 turn-stopping → turn/end
  → 队列空 → idle
```

三个结论：

**边界事件写在 `finally` 里。** `turn/end` 和 `step/end` 无论怎么退出都会落日志，所以重放的人永远不用处理「开了没关」。取消和失败各自把结构化的理由塞进 `turn/end`。

**执行可以乱序，日志必须有序。** 工具并发跑，但 `commitReady` 只沿连续的模型序提交；取消时给未启动的调用补合成结果保住配对。目的都是让同一组调用在任何一次重放里得到同一份历史。

**每一步重新 `deriveMessages()`。** 驱动器不持有消息数组。这让压缩、注入、steering 这些事情不需要通知驱动器就能生效，是第 4 章那个设计在调用侧的回报。

下一章往下走一层，讲 LLM 层：`llm.stream()` 背后的流式协议、适配器契约，以及 `BlockAssembler` 怎么把一串 delta 拼回消息块。
