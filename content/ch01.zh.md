## 一、插件是什么：三种形态，一个 callback

Cordis 接受三种插件写法。函数、带 `apply` 方法的对象、类：

```ts
// 1. 函数插件
export function apply(ctx: Context) {}

// 2. 对象插件
export const objectPlugin = { name: 'object-plugin', apply(ctx: Context) {} }

// 3. 类插件（Service 子类，第 2 章讲）
export class MyService extends Service {
  constructor(ctx: Context) { super(ctx, 'myTutorialService') }
}
```

这三种在框架内部会被归一成同一样东西。看 `resolve()`：

```srcref vendor/cordis/src/registry.ts#L222-L228
三种形态归一为一个 callback：函数直接用自己，对象用它的 apply 方法。
```

```ts
resolve(plugin: Plugin): Function | undefined {
  // plugin.apply may throw
  try {
    if (typeof plugin === 'function') return plugin
    if (isApplicable(plugin)) return plugin.apply
  } catch {}
}
```

注意这个 `try {} catch {}`：`plugin.apply` 是一次属性读取，而属性读取在有 getter 的对象上**可能抛异常**。框架选择静默吞掉并返回 `undefined`，让调用方报"不是合法插件"，而不是把一个陌生的 getter 错误抛给用户。这种写法在 Cordis 里很常见。后面你会反复看到"失败要失败得可解释"。

:::key 归一后的 callback 就是插件的身份
`resolve()` 返回的这个函数，是插件在注册表里的**唯一标识**。同一个函数被 `ctx.plugin()` 挂载十次，注册表里只有一条 `Runtime` 记录，但会有十个 `Fiber`。这个 1:N 关系是下一节的主题。
:::

## 二、`ctx.plugin()`：从调用到运行

这是整章最该先读的一段。{{src:vendor/cordis/src/registry.ts#L316-L336|RegistryService.plugin()}}，21 行：

```ts
plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
  // check if it's a valid plugin
  const callback = this.resolve(plugin)
  if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
  this.ctx.fiber.assertActive()

  let runtime = this._internal.get(callback)
  if (!runtime) {
    let name = plugin.name
    if (name === 'apply') name = undefined
    runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
    this._internal.set(callback, runtime)
  }

  const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
  const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
  wrapped.then = (onFulfilled, onRejected) => {
    return fiber.await().then(onFulfilled, onRejected)
  }
  return wrapped
}
```

逐句拆：

1. **`this.ctx.fiber.assertActive()`**：在一个已经卸载的上下文里挂新插件，直接抛 `INACTIVE_EFFECT`。这条守卫的存在本身就说明：上下文是有生命周期的，且可能死掉。
2. **`_internal` 是 `Map<Function, Runtime>`**：按 callback 查 Runtime，没有就新建。所以 Runtime 是**每个插件一份**，不是每次挂载一份。
3. **`new Fiber(...)`**：每次调用都新建一个 Fiber。这是**每次挂载一份**。
4. **最后三行的 `Object.create(fiber)` + `then`**：返回值不是 Promise，是一个"可以被 await 的 Fiber"。你可以立即同步读 `fiber.uid`，也可以 `await ctx.plugin(...)` 等它加载完。用原型继承而不是把 `then` 直接挂到 fiber 上，是为了不污染 Fiber 本身（否则 Fiber 自己会被当成 thenable，`await someFiber` 会陷入递归）。

## 三、`ctx` 是一个 Proxy

现在看插件收到的那个 `ctx`。{{src:vendor/cordis/src/context.ts#L71-L84|Context 的构造函数}}只有 14 行，但每一行都有讲究：

```ts
constructor() {
  this[symbols.isolate] = Object.create(null)
  this[symbols.intercept] = Object.create(null)
  const self = new Proxy<this>(this, ReflectService.handler)
  this.root = self
  this.baseUrl = undefined
  this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])
  this.reflect = new ReflectService(self)
  this.registry = new RegistryService(self)
  this.events = new EventsService(self)
  this.logger = new LoggerService(self)
  this.fiber._disposables.clear()
  return self
}
```

三处值得停下来：

**第一，`return self` 返回的是 Proxy，不是 `this`。** 构造函数返回对象时，`new Context()` 拿到的是那个返回值。所以你手里的 `ctx` 从来都不是 Context 实例本身，而是套了 `ReflectService.handler` 的代理。这就是为什么 `ctx.tools`、`ctx.llm` 这些属性能在"服务还没注册"时不存在、注册后凭空出现。读属性走的是代理的 `get` 陷阱，去服务表里查（第 2 章细讲）。

**第二，`new Fiber(self, {}, ..., null, ...)` 里的 `null`。** 第四个参数是 `runtime`，传 `null` 表示这是**根 fiber**。回头看 Fiber 构造函数，它对根 fiber 有一条完全不同的分支：

```srcref vendor/cordis/src/fiber.ts#L320-L332
根 fiber 分支：uid 固定为 0，状态直接是 ACTIVE，execute 是空函数。
```

根 fiber 不执行任何插件代码，它只是**整棵树的根**，用来持有那些直接挂在根上下文上的 effect。

**第三，最后那句 `this.fiber._disposables.clear()`。** 上面四个 `new XxxService(self)` 在构造时会注册各自的服务，注册就是 effect，effect 会被收集进根 fiber 的清理列表。这一句把它们清空，也就是说**四个内置服务被刻意设计成不可卸载**。根上下文没有"卸载自己"的语义，把它们留在清理列表里没有意义，反而会让 `getEffects()` 的诊断输出里永远挂着四条噪音。

### `extend()`：子上下文是原型链，不是拷贝

```srcref vendor/cordis/src/context.ts#L99-L107
extend()：子上下文通过 Object.create 继承父上下文。
```

```ts
extend(meta = {}): this {
  const shadow = Reflect.getOwnPropertyDescriptor(this, symbols.shadow)?.value
  const self = Object.create(getTraceable(this, this))
  for (const prop of Reflect.ownKeys(meta)) {
    Object.defineProperty(self, prop, Reflect.getOwnPropertyDescriptor(meta, prop)!)
  }
  if (!shadow) return self
  return Object.assign(Object.create(self), { [symbols.shadow]: shadow })
}
```

核心是 `Object.create(...)`：子上下文**原型继承**父上下文，`meta` 里的自有属性遮蔽继承来的。文档注释里那句 "The parent is not mutated" 是这个设计的全部要点：派生子上下文永远不会影响父级。

这解释了 Fiber 构造函数里的这一行（{{src:vendor/cordis/src/fiber.ts#L236|fiber.ts:236}}）：

```ts
this.ctx = this.context = parent.extend({ fiber: this })
```

**每个 Fiber 都给自己造了一个子上下文，唯一的区别就是 `fiber` 属性指向自己。** 于是插件代码里的 `ctx.fiber` 永远是"我自己这个插件的 fiber"，而 `ctx` 的其他一切都从父级继承下来。`ctx.effect()`、`ctx.on()` 这些方法之所以能自动把副作用记到正确的插件账上，靠的就是这一行。

:::key 一句话记住
`ctx` = 一条原型链 + 一个 Proxy。原型链决定了"我继承了谁的能力"，Proxy 决定了"读一个服务名时去哪里找实现"，而 `fiber` 属性决定了"我注册的东西记在谁的账上"。
:::

## 四、effect：本章的核心

现在到了那条硬规则的出处。DSH 的 {{src:AGENTS.md|AGENTS.md}} 写：

> **Registrations are effects**: every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

`ctx.effect()` 就是 {{src:vendor/cordis/src/fiber.ts#L418-L561|Fiber.effect()}}，143 行，是全文件最长的方法。它做的事一句话说得完：**跑一段代码，收集它产生的清理函数，保证这些清理函数在插件卸载时一定被执行。**

但这 143 行里有大量在处理边界情况。我们先看骨架，再看它到底在防什么。

### 4.1 接受什么

```srcref vendor/cordis/src/fiber.ts#L83-L93
Effect 的四种合法形态。
```

```ts
type SyncEffect<T = any> =
  | Disposable<T>                              // 直接返回一个清理函数
  | Iterable<Disposable<T>, void, void>        // 生成器，yield 多个清理函数

type AsyncEffect<T = any> =
  | Promise<Disposable<T>>                     // 异步返回一个
  | AsyncIterable<Disposable<T>, void, void>   // 异步生成器
```

生成器形态是个漂亮的设计。它让"我要注册五样东西，每样都有自己的清理逻辑"写起来是这样：

```ts
ctx.effect(function* () {
  yield openDatabase()
  yield startTimer()
  yield subscribeToEvents()
}, 'my-plugin-setup')
```

而不用手工组装一个大清理函数。分发这四种形态的是 {{src:vendor/cordis/src/fiber.ts#L356-L400|_execute()}}，它逐个判断类型并把产出的 disposer 交给 `collect`。

### 4.2 清理的顺序

这是本章最容易记错、也最值得记牢的一点。

**在一个 effect 内部**，多个 disposer 是**倒序、串行**执行的：

```srcref vendor/cordis/src/fiber.ts#L427-L442
单个 effect 的 dispose 闭包：splice(0).reverse() 决定倒序，task.then 链决定串行。
```

```ts
const dispose = () => {
  if (disposing) return disposalTask
  disposing = true
  let task!: void | Promise<void>
  for (const disposable of disposables.splice(0).reverse()) {
    if (task) {
      task = task.then(() => runDisposable(disposable))   // 串成一条链
    } else {
      const result = runDisposable(disposable)
      if (isObject(result) && 'then' in result) {
        task = result as any
      }
    }
  }
  return disposalTask = task
}
```

倒序是必须的：上面那个生成器例子里，`subscribeToEvents` 依赖数据库还开着，所以必须先退订、再停定时器、最后关数据库。串行也是必须的：如果并发执行，退订还没完成时数据库就关了。

开头那两行 `if (disposing) return disposalTask` 让**重复调用 disposer 是安全的空操作**，第二次调用直接拿到第一次的清理任务。这是公开契约的一部分，方法注释里明确写了 "Calling the disposer twice is a no-op"。

**但在 fiber 卸载时**，多个 effect 之间是**倒序、并发**的：

```srcref vendor/cordis/src/fiber.ts#L675-L686
_unload()：Promise.all 并发跑，但遍历顺序由 clear() 决定。
```

```ts
private async _unload() {
  await Promise.all(this._disposables.clear().map(async (dispose) => {
    try {
      await composeError(async (info) => { ... await runDisposable(dispose) }, ...)
    } catch (reason) {
      this.ctx.logger.error(reason)     // 一个 effect 清理失败，不影响其他
    }
  }))
  ...
}
```

倒序来自 {{src:vendor/cordis/src/utils.ts#L27-L31|DisposableList.clear()}}：

```ts
clear() {
  const values = [...this.map.values()]
  this.map.clear()
  return values.reverse()          // ← 就是这里
}
```

:::key 两种顺序，别搞混
| 场景 | 顺序 | 并发性 | 代码位置 |
|---|---|---|---|
| 一个 effect 内部的多个 disposer | 倒序 | **串行**（`.then` 链） | `effect()` 的 dispose 闭包 |
| 一个 fiber 的多个 effect | 倒序 | **并发**（`Promise.all`） | `_unload()` |

为什么后者敢并发？因为不同 effect 之间**不应该**有清理顺序依赖。有依赖的东西本来就该写在同一个 effect 的生成器里。这是框架用 API 形状表达的一条设计约束。
:::

还要注意 `_unload` 里那个 `try/catch`：**一个 effect 清理失败只记日志，不中断其他 effect 的清理**。卸载路径必须是尽力而为的，否则一个写坏的插件能让整棵树卸不干净。

### 4.3 那 143 行到底在防什么

剩下的代码几乎全在处理一件事：**清理请求可能在 setup 还没跑完时就到达**。

想象一个 effect 的 body 是 `async` 的，跑了 500ms 才返回 disposer。在这 500ms 里，父插件被卸载了。此时：

- disposer 还不存在，没东西可调用；
- 但 setup 正在进行中，它可能已经打开了 socket；
- 如果直接忽略，那个 socket 就泄漏了。

Cordis 的解法是 `setupBarrier` 加 `disposeAfter`：

```ts
const disposeAfter = (setup: PromiseLike<void>) => {
  return Promise.resolve(setup).then(
    () => dispose(),
    async (reason) => { await dispose(); throw reason },
  )
}
```

**先等 setup 结束，再执行清理**，无论 setup 是成功还是失败（注意 reject 分支里也调了 `dispose()`）。

还有一行值得单独指出，第 520 行：

```srcref vendor/cordis/src/fiber.ts#L516-L522
在跑任何插件代码之前，先把 wrapper 登记到 fiber 的清理列表里。
```

```ts
// Make the effect visible to a reentrant owner unload before execute()
// runs any plugin code.
removeWrapper = this._disposables.push(wrapper)
try {
  task = this._execute(runner)
```

顺序是：**先登记，后执行**。如果反过来（先执行、成功了再登记），那么在 `execute()` 内部同步触发卸载的场景下，这个 effect 对卸载流程是不可见的，必然泄漏。这类"先注册再干活"的模式在 Cordis 里到处都是，是它敢承诺"卸载一定干净"的底气。

:::key 这 143 行给出的契约
只要注册走了 `ctx.effect()`，无论插件在什么时刻、以什么方式被卸载（正常卸载、加载中途被卸、setup 抛异常），清理函数都会被调用恰好一次。DSH 的 219 个包全部建立在这个承诺上。
:::

驱动这台状态机的不是显式的 `setState`，而是一个叫 **epoch** 的字符串。看 {{src:vendor/cordis/src/fiber.ts#L611-L623|_refresh()}}：

```ts
_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE        // 有依赖缺失 → 整体失活
      break
    }
    epoch += ':' + impl.fiber.uid    // 把每个依赖的提供方 uid 拼进去
  }
  this._setEpoch(epoch)
}
```

epoch 是**当前依赖组合的指纹**：把每个被注入服务的提供方 fiber 的 uid 拼成一个字符串。然后 {{src:vendor/cordis/src/fiber.ts#L625-L639|_setEpoch()}} 只做一件事：比较新旧指纹，不同就触发重载或卸载。

这个设计的精妙之处：**依赖的提供方被换掉时，uid 变了，指纹就变了，插件自动重载**。你不需要写任何"监听依赖变化"的代码。`ctx.inject(['llm'], ...)` 里的回调之所以能在 LLM 适配器被替换时自动重跑，就是这个机制。

:::note 状态 vs epoch
`state` 字段是**给外部观察用的**（`internal/status` 事件、诊断输出）。真正决定"该加载还是该卸载"的是 epoch 比较。{{src:vendor/cordis/src/fiber.ts#L574-L579|_getState()}} 甚至是从 uid / _error / epoch 三者**反推**出 state 的，而不是反过来。
:::

## 六、回到 DSH

现在回头看那条规范，它不再是一句空话：

> **Registrations are effects**: every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

翻译成人话：**在 DSH 里注册一个工具、一个模型适配器、一个事件监听器，都必须返回一个撤销函数，并且这个撤销函数必须交给 effect 系统托管。**

这条规则换来的能力是具体的：

- **热插拔**：卸载一个插件，它注册的工具就从工具表里消失，不留残渣。
- **按 agent 隔离**：用 `agent.ctx` 注册的东西，随那个 agent 一起消失（第 5 章）。
- **HMR**：改一行代码，只有受影响的子树重载（第 2 章）。
- **模型自修改**：`packages/extensions` 让模型自己挂载/卸载插件。这在没有可靠卸载语义的框架里是不可想象的。

最后一条对你的研究方向特别重要：**你要做的"自进化"，在 DSH 里的落点就是让 agent 在运行时挂载新插件**。而这件事之所以安全，全靠本章这 143 行 effect 代码提供的清理保证。
