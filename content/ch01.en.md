# The Cordis plugin model: Context, Fiber, and revocable effects

The previous chapter said DSH has no privileged core. This chapter explains what replaced it.

By the end you should be able to answer: what actually happens when a plugin is mounted, why `ctx` is a Proxy, and why DSH's own guidelines dare to state "**registrations are effects**" as a hard rule.

The whole chapter revolves around three files, under 1200 lines total:

```srcref vendor/cordis/src/fiber.ts

```

```srcref vendor/cordis/src/registry.ts
RegistryService, 337 lines. The entry point of ctx.plugin().
```

## 1. What a plugin is: three shapes, one callback

Cordis accepts three plugin shapes: a function, an object with an `apply` method, or a class:

```ts
// 1. Function plugin
export function apply(ctx: Context) {}

// 2. Object plugin
export const objectPlugin = { name: 'object-plugin', apply(ctx: Context) {} }

// 3. Class plugin (a Service subclass, chapter 2)
export class MyService extends Service {
  constructor(ctx: Context) { super(ctx, 'myTutorialService') }
}
```

Internally all three collapse into the same thing. Look at `resolve()`:

```srcref vendor/cordis/src/registry.ts#L222-L228
Three shapes normalized to one callback: a function is itself, an object contributes its apply method.
```

```ts
resolve(plugin: Plugin): Function | undefined {
  // plugin.apply may throw
  try {
    if (typeof plugin === 'function') return plugin
    if (isApplicable(plugin)) return plugin.apply
  } catch {}
}
```

Note that `try {} catch {}`: reading `plugin.apply` is a property access, and property access **can throw** on an object with a getter. The framework deliberately swallows that and returns `undefined`, so the caller reports "not a valid plugin" rather than surfacing a stranger's getter error. This style recurs throughout Cordis. Failures must fail in an explainable way.

:::key The normalized callback is the plugin's identity
The function returned by `resolve()` is the plugin's **unique key** in the registry. Mount the same function ten times with `ctx.plugin()` and you get one `Runtime` record but ten `Fiber`s. That 1:N relationship is the next section.
:::

## 2. `ctx.plugin()`: from call to running

This is the passage to read first. {{src:vendor/cordis/src/registry.ts#L316-L336|RegistryService.plugin()}}, 21 lines:

```ts
plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
  // check if it's a valid plugin
  const callback = this.resolve(plugin)
  if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
  this.ctx.fiber.assertActive()

  let runtime = this._internal.get(callback)
  if (!runtime) {
    let name = plugin.name
    if (name === 'apply') name = undefined
    runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
    this._internal.set(callback, runtime)
  }

  const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
  const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
  wrapped.then = (onFulfilled, onRejected) => {
    return fiber.await().then(onFulfilled, onRejected)
  }
  return wrapped
}
```

Line by line:

1. **`this.ctx.fiber.assertActive()`**: mounting a plugin in an already-unloaded context throws `INACTIVE_EFFECT`. The mere existence of this guard tells you contexts have a lifecycle and can die.
2. **`_internal` is a `Map<Function, Runtime>`**: keyed by callback, created on demand. So a Runtime is **one per plugin**, not one per mount.
3. **`new Fiber(...)`**: constructed on every call. That is **one per mount**.
4. **The last three lines, `Object.create(fiber)` plus `then`**: the return value is not a Promise but "a Fiber you can await". You can synchronously read `fiber.uid`, or `await ctx.plugin(...)` to wait for loading. Using prototypal inheritance rather than assigning `then` onto the fiber itself avoids polluting Fiber (otherwise Fiber becomes thenable and `await someFiber` recurses).

:::note Why separate Runtime from Fiber
Because the same plugin can be **mounted several times with different configs**. An HTTP-server plugin might be mounted twice to listen on two ports. They share one `Config` schema (Runtime's job) but each has its own port config, its own lifecycle, and its own open sockets (Fiber's job).
:::

## 3. `ctx` is a Proxy

Now the `ctx` a plugin receives. {{src:vendor/cordis/src/context.ts#L71-L84|The Context constructor}} is 14 lines, and nearly every one matters:

```ts
constructor() {
  this[symbols.isolate] = Object.create(null)
  this[symbols.intercept] = Object.create(null)
  const self = new Proxy<this>(this, ReflectService.handler)
  this.root = self
  this.baseUrl = undefined
  this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])
  this.reflect = new ReflectService(self)
  this.registry = new RegistryService(self)
  this.events = new EventsService(self)
  this.logger = new LoggerService(self)
  this.fiber._disposables.clear()
  return self
}
```

Three places worth stopping at:

**First, `return self` returns the Proxy, not `this`.** When a constructor returns an object, that object is what `new Context()` evaluates to. So the `ctx` you hold is never the Context instance itself. It is a proxy wrapping it with `ReflectService.handler`. That is exactly why `ctx.tools` and `ctx.llm` can be absent before their service registers and materialize afterwards: property reads go through the proxy's `get` trap and consult the service table (chapter 2).

**Second, the `null` in `new Fiber(self, {}, ..., null, ...)`.** The fourth argument is `runtime`, and `null` marks this as the **root fiber**. Back in the Fiber constructor there is a completely separate branch for it:

```srcref vendor/cordis/src/fiber.ts#L320-L332
The root-fiber branch: uid is fixed at 0, state starts ACTIVE, execute is a no-op.
```

The root fiber runs no plugin code. It is just **the root of the tree**, holding effects registered directly on the root context.

**Third, that final `this.fiber._disposables.clear()`.** The four `new XxxService(self)` calls above register their services during construction, registration is an effect, and effects get collected into the root fiber's cleanup list. This line empties it, meaning the four built-in services are **deliberately made non-unloadable**. A root context has no "unload myself" semantics, so leaving them in the cleanup list serves no purpose and would leave four permanent entries polluting `getEffects()` diagnostics.

### `extend()`: child contexts are a prototype chain, not a copy

```srcref vendor/cordis/src/context.ts#L99-L107
extend(): a child context inherits from its parent via Object.create.
```

```ts
extend(meta = {}): this {
  const shadow = Reflect.getOwnPropertyDescriptor(this, symbols.shadow)?.value
  const self = Object.create(getTraceable(this, this))
  for (const prop of Reflect.ownKeys(meta)) {
    Object.defineProperty(self, prop, Reflect.getOwnPropertyDescriptor(meta, prop)!)
  }
  if (!shadow) return self
  return Object.assign(Object.create(self), { [symbols.shadow]: shadow })
}
```

The heart is `Object.create(...)`: a child context **prototypally inherits** its parent, and own properties from `meta` shadow the inherited ones. The doc comment's "The parent is not mutated" is the entire point: deriving a child can never affect the parent.

This explains one line in the Fiber constructor ({{src:vendor/cordis/src/fiber.ts#L236|fiber.ts:236}}):

```ts
this.ctx = this.context = parent.extend({ fiber: this })
```

**Every Fiber builds itself a child context whose only difference is that `fiber` points at itself.** So `ctx.fiber` inside plugin code is always "my own plugin's fiber", while everything else on `ctx` is inherited from the parent. This single line is why `ctx.effect()` and `ctx.on()` can automatically bill side effects to the right plugin.

:::key One sentence to remember
`ctx` = a prototype chain + a Proxy. The chain decides "whose capabilities I inherit", the Proxy decides "where to look when a service name is read", and the `fiber` property decides "whose account my registrations are billed to".
:::

## 4. Effects: the core of this chapter

Now for the source of that hard rule. DSH's {{src:AGENTS.md|AGENTS.md}} says:

> **Registrations are effects**: every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

`ctx.effect()` is {{src:vendor/cordis/src/fiber.ts#L418-L561|Fiber.effect()}}, 143 lines, the longest method in the file. What it does fits in one sentence: **run some code, collect the cleanup functions it produces, and guarantee those cleanups run when the plugin unloads.**

But most of those 143 lines handle edge cases. Look at the skeleton first, then at what it is defending against.

### 4.1 What it accepts

```srcref vendor/cordis/src/fiber.ts#L83-L93
The four legal effect shapes.
```

```ts
type SyncEffect<T = any> =
  | Disposable<T>                              // return one disposer
  | Iterable<Disposable<T>, void, void>        // a generator yielding several

type AsyncEffect<T = any> =
  | Promise<Disposable<T>>                     // async, one disposer
  | AsyncIterable<Disposable<T>, void, void>   // async generator
```

The generator shape is an elegant touch. It turns "I need to register five things, each with its own cleanup" into:

```ts
ctx.effect(function* () {
  yield openDatabase()
  yield startTimer()
  yield subscribeToEvents()
}, 'my-plugin-setup')
```

instead of hand-assembling one big cleanup function. The dispatcher for all four shapes is {{src:vendor/cordis/src/fiber.ts#L356-L400|_execute()}}, which type-checks and hands each produced disposer to `collect`.

### 4.2 Cleanup order

This is the point most easily misremembered and most worth getting right.

**Inside a single effect**, multiple disposers run **in reverse, serially**:

```srcref vendor/cordis/src/fiber.ts#L427-L442
An effect's dispose closure: splice(0).reverse() gives reverse order, the task.then chain gives serial execution.
```

```ts
const dispose = () => {
  if (disposing) return disposalTask
  disposing = true
  let task!: void | Promise<void>
  for (const disposable of disposables.splice(0).reverse()) {
    if (task) {
      task = task.then(() => runDisposable(disposable))   // chained
    } else {
      const result = runDisposable(disposable)
      if (isObject(result) && 'then' in result) {
        task = result as any
      }
    }
  }
  return disposalTask = task
}
```

Reverse order is mandatory: in the generator example, `subscribeToEvents` depends on the database still being open, so you must unsubscribe first, stop the timer, then close the database. Serial is mandatory too: run them concurrently and the database could close while unsubscription is still in flight.

The opening `if (disposing) return disposalTask` makes **calling a disposer twice a safe no-op**, since the second call simply receives the first call's cleanup task. This is part of the public contract; the method's doc comment states "Calling the disposer twice is a no-op".

**But when a fiber unloads**, its multiple effects run **in reverse, concurrently**:

```srcref vendor/cordis/src/fiber.ts#L675-L686
_unload(): Promise.all runs them concurrently, while the iteration order comes from clear().
```

```ts
private async _unload() {
  await Promise.all(this._disposables.clear().map(async (dispose) => {
    try {
      await composeError(async (info) => { ... await runDisposable(dispose) }, ...)
    } catch (reason) {
      this.ctx.logger.error(reason)     // one failed cleanup does not block others
    }
  }))
  ...
}
```

The reverse order comes from {{src:vendor/cordis/src/utils.ts#L27-L31|DisposableList.clear()}}:

```ts
clear() {
  const values = [...this.map.values()]
  this.map.clear()
  return values.reverse()          // ← right here
}
```

:::key Two orders, don't mix them up
| Scope | Order | Concurrency | Where |
|---|---|---|---|
| Disposers within one effect | reverse | **serial** (`.then` chain) | the dispose closure in `effect()` |
| Effects within one fiber | reverse | **concurrent** (`Promise.all`) | `_unload()` |

Why is concurrency safe at the fiber level? Because distinct effects are assumed to have **no teardown-order dependency**. Anything with such a dependency belongs inside a single effect's generator in the first place. This is a design constraint the framework expresses through the shape of its API.
:::

Also note the `try/catch` inside `_unload`: **a failed cleanup is logged and does not interrupt the other effects**. The unload path has to be best-effort, or one badly written plugin could prevent the whole tree from unloading cleanly.

### 4.3 What those 143 lines are defending against

Nearly all the remaining code handles one thing: **a cleanup request can arrive before setup has finished**.

Picture an effect whose body is `async` and takes 500ms to return its disposer. During those 500ms, the parent plugin unloads. At that moment:

- the disposer does not exist yet, so there is nothing to call;
- but setup is in flight and may already have opened a socket;
- ignoring it leaks that socket.

Cordis solves this with `setupBarrier` and `disposeAfter`:

```ts
const disposeAfter = (setup: PromiseLike<void>) => {
  return Promise.resolve(setup).then(
    () => dispose(),
    async (reason) => { await dispose(); throw reason },
  )
}
```

**Wait for setup to finish, then clean up**, whether setup succeeded or failed (note that `dispose()` is called in the reject branch too).

One more line deserves singling out, line 520:

```srcref vendor/cordis/src/fiber.ts#L516-L522
Register the wrapper on the fiber's cleanup list before running any plugin code.
```

```ts
// Make the effect visible to a reentrant owner unload before execute()
// runs any plugin code.
removeWrapper = this._disposables.push(wrapper)
try {
  task = this._execute(runner)
```

The order is **register first, execute second**. Reversed (execute, then register on success), an unload triggered synchronously from inside `execute()` would not see this effect at all, and it would inevitably leak. This "register before you work" pattern is everywhere in Cordis, and it is what lets the framework promise that unloading is always clean.

:::key The contract these 143 lines provide
As long as a registration goes through `ctx.effect()`, its cleanup runs exactly once, no matter when or how the plugin unloads (normal unload, unloaded mid-load, setup threw). All 219 DSH packages are built on that promise.
:::

What drives this machine is not an explicit `setState` but a string called an **epoch**. See {{src:vendor/cordis/src/fiber.ts#L611-L623|_refresh()}}:

```ts
_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE        // any missing dep → deactivate entirely
      break
    }
    epoch += ':' + impl.fiber.uid    // fold each provider's uid into the fingerprint
  }
  this._setEpoch(epoch)
}
```

The epoch is a **fingerprint of the current dependency set**: the uid of each injected service's provider fiber, concatenated. {{src:vendor/cordis/src/fiber.ts#L625-L639|_setEpoch()}} then does exactly one thing: compare old and new fingerprints and trigger a reload or unload when they differ.

The elegance: **when a dependency's provider is swapped out, its uid changes, so the fingerprint changes, so the plugin reloads automatically**. You never write "watch for dependency changes" code. That is why a `ctx.inject(['llm'], ...)` callback re-runs by itself when the LLM adapter is replaced.

:::note state vs epoch
The `state` field exists **for external observers** (the `internal/status` event, diagnostics). What actually decides "load or unload" is the epoch comparison. {{src:vendor/cordis/src/fiber.ts#L574-L579|_getState()}} even **derives** state from uid / _error / epoch rather than the other way round.
:::

---

## 6. Back to DSH

Now reread the guideline; it is no longer an empty phrase:

> **Registrations are effects**: every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

In plain terms: **registering a tool, a model adapter, or an event listener in DSH must return a revoking function, and that function must be handed to the effect system.**

What this rule buys is concrete:

- **Hot swapping**: unload a plugin and the tools it registered vanish from the tool table, leaving no residue.
- **Per-agent isolation**: anything registered through `agent.ctx` disappears with that agent (chapter 5).
- **HMR**: change one line and only the affected subtree reloads (chapter 2).
- **Model self-modification**: `packages/extensions` lets the model mount and unmount plugins itself, which would be unthinkable in a framework without reliable unload semantics.

That last one matters especially for your research direction: **"self-evolution" in DSH lands on letting an agent mount new plugins at runtime**. What makes that safe is exactly the cleanup guarantee provided by this chapter's 143 lines of effect code.
