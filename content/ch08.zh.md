# 工具注册与受保护的执行流水线

第 5 章讲了循环怎么把工具调用排进日志，第 6 章讲了工具参数为什么保持原始 JSON 字符串。这一章讲中间那一段：一个 `tool-call` 块从模型嘴里出来，到一条 `tool/result` 落进日志，中间要穿过什么。

答案是七道关卡。本章实验第 3 步把它们逐条打印出来了：

```
=== 正常一次（text="hi"）===
   1. tools/pre-execute  name=echo args={"text":"hi"}
   2. guard  name=echo
   3. tools/execute（前）
   4. 工具体 execute()
   5. tools/execute（后）isError=false
   6. tools/post-execute  isError=false
   7. tools/result（emit，只能看）isError=false frozen=true
   → isError=false content=[{"type":"text","text":"HI"}]
```

「受保护」这个词有具体所指，本章拆成三层：

- **对模型的保护**：参数、返回值、渲染，三处都校验，任何一处不合规都变成一条结构化的 `isError` 结果，而不是抛异常。
- **对部署方的保护**：`pre-execute` 和 guard 两级准入，`restrict` 按 agent 裁剪可见工具，审批服务缺席时 `ask` 降级为拒绝。
- **对循环的保护**：这条流水线**从不抛异常**。第 5 章那句「工具并发跑但按模型序提交」能成立，前提是每一次调用都必然产出一个结果。

## 一、defineTool：一份声明，四种用途

{{src:packages/core/tools/src/schema.ts#L545-L617|defineTool()}} 接受一份紧凑的声明，产出一个 `ToolDefinition`。实验第 1 步注册了这个：

```js
defineTool({
  name: 'grep',
  description: 'Search files for a pattern.',
  parameters: {
    pattern: { type: 'string', required: true, description: 'the regex to search for' },
    path: { type: 'string', description: 'directory to search in' },
    maxResults: { type: 'number' },
  },
  output: {
    schema: { type: 'object', additionalProperties: false, properties: {
      matches: { type: 'array', required: true, items: { type: 'string' } },
      truncated: { type: 'boolean' },
    } },
    render: (_args, v) => [{ type: 'text', text: v.matches.join('\n') || '(no matches)' }],
  },
  execute: async (args) => ({ matches: [`a.ts: ${args.pattern}`], truncated: false }),
})
```

`parameters` 里逐个属性写 `required: true`，编译出来的却是标准 JSON Schema 的 `required` 数组：

```json
{
  "type": "object",
  "properties": {
    "pattern": { "type": "string", "description": "the regex to search for" },
    "path": { "type": "string", "description": "directory to search in" },
    "maxResults": { "type": "number" }
  },
  "required": ["pattern"]
}
```

这份 JSON 就是第 6 章 `GenerateOptions.tools` 里发给模型的东西。{{src:packages/core/tools/src/schema.ts#L449-L458|parameterSchemaSpecToJsonSchema()}} 做这个转换。

一份声明有四个下游：

| 字段 | 谁用 |
|---|---|
| `parameters` | 发给模型的 schema；同时是 `execute` 入口的参数校验器 |
| `output.schema` | 注册表校验工具**返回值**的依据 |
| `output.render` | 把结构化返回值投影成模型看到的 `ContentBlock[]` |
| `output.presentationMeta` / `presentCall` / `presentResult` | 界面展示，纯函数，可在重放时重算 |

注意 `output.schema` 里那个 `additionalProperties: false` 不是可选的。省掉它，注册就直接失败：

```
unsupported JSON schema: schema.additionalProperties must be explicitly true or false
```

而且失败发生在**加载期**，整棵插件树起不来（第 3 章讲过 `EntryGroup.update` 的全量回滚）。这是仓库那条「misconfiguration fails loud at load when self-contained」的直接体现：一个写坏的 schema 是自包含的错误，不该等到模型第一次调用时才炸。

### 校验放在 `execute` 入口，不放在注册表

`defineTool` 生成的 `execute` 是一层包装：

```ts
async execute(args: unknown, exec: ToolRunContext): Promise<JsonValue> {
  const violations = validate(args)
  if (violations.length > 0) throw new ToolArgsError(violations)
  return userExecute(args as InferArgs<S>, exec) as Promise<JsonValue>
},
```

参数校验是**工具自己的事**，不是注册表的事。`ToolDefinition` 的 JSDoc 说得明确：注册表把参数原样交给 `execute`，工具校验自己的 schema。为什么这么分？因为工具可以不用 `defineTool`，手写一个 `ToolDefinition` 完全合法，那时它自己决定怎么校验。注册表只强制它必须声明 `output`。

### 展示投影绝不抛异常

同一份 `validate`，在展示路径上的用法不一样：

```ts
// Presentation is display-only and may run on REPLAY of arbitrary logged args
// (possibly from an older schema), so it must never throw: validate softly and
// fall back to `undefined` (a generic UI presentation) on any mismatch, rather
// than the hard `ToolArgsError` the execute path raises.
if (userPresentCall) {
  tool.presentCall = (args: unknown): ToolCallView | undefined => {
    if (validate(args).length > 0) return undefined
    return userPresentCall(args as InferArgs<S>)
  }
}
```

执行路径校验失败就抛，展示路径校验失败就返回 `undefined`。理由在注释里：展示会在**重放**时对着历史日志里的参数重算，而那些参数可能来自一个旧版本的 schema。一年前的日志用今天的 schema 校验必然不过，但它仍然应该能显示出来。

## 二、三处校验，五种失败

实验第 2 步把五种失败并排跑了一遍。全部返回 `isError` 结果，没有一个抛到调用方：

```
[参数缺 required]
  error = {"message":"invalid arguments: missing required property \"pattern\"",
           "info":{"name":"ToolArgsError","code":"INVALID_ARGS"}}

[参数类型不对]
  error = {"message":"invalid arguments: \"pattern\" must be a string", ... "code":"INVALID_ARGS"}

[工具违反自己的 output schema]
  error = {"message":"tool \"liar\" returned invalid output: \"value.matches\" must be an array;
           \"value.extra\" is not a declared property (additionalProperties: false)",
           "info":{"name":"ToolOutputError","code":"INVALID_TOOL_OUTPUT"}}

[render 抛异常]
  error = {"message":"tool \"badrender\" returned invalid output: output.render failed: render blew up",
           "info":{"name":"ToolOutputError","code":"INVALID_TOOL_OUTPUT"}}

[未注册的工具]
  error = {"message":"unknown tool \"nope\"","info":{"name":"ToolNotFoundError","code":"UNKNOWN_TOOL"}}
```

第三、四种由 {{src:packages/core/tools/src/index.ts#L1793-L1823|createSuccessResult()}} 产生，它是工具体返回之后必经的一关：

```ts
private createSuccessResult(exec: ToolExecution, tool: ToolDefinition, candidate: unknown): ToolExecutionSuccess {
  const detached = snapshotToolValue(tool.name, candidate)
  const violations = validateJsonSchemaValue(tool.output.schema, detached, 'value')
  if (violations.length > 0) throw new ToolOutputError(tool.name, violations)
  const value = deepFreeze(detached)
  let rendered: ContentBlock[]
  try {
    rendered = tool.output.render(exec.arguments, value)
  } catch (error: unknown) {
    throw projectionError(tool.name, 'render', error)
  }
  const content = snapshotProjection(tool.name, 'render', rendered)
  ...
}
```

四步：**快照**（脱离工具可能还持有的引用）、**校验**、**冻结**、**投影**。顺序不能换。先快照才能保证校验的和最终用的是同一份数据；先冻结再 `render`，`render` 就改不动它。

`presentationMeta` 只在顶层调用时算：

```ts
if (exec.parent === undefined && tool.output.presentationMeta !== undefined) {
```

`exec.parent` 有值意味着这是 `run_code` 里的嵌套子调用，界面上没有它的位置，算了也没人看。

:::key 工具的返回值不被信任
工具是插件写的，`output.schema` 是它自己声明的，而注册表拿它来校验它自己。这不是防恶意，是防漂移：一个工具改了返回结构却忘了改 schema，会在第一次调用时以 `INVALID_TOOL_OUTPUT` 暴露，而不是把一个模型读不懂的对象送进日志。
:::

## 三、七道关卡的顺序，以及每种拒绝在哪一步终止

流水线的骨架是 {{src:packages/core/tools/src/index.ts#L1342-L1344|execute()}}，只有一行，把活分给三个阶段：

```ts
async execute(exec: ToolExecutionInput): Promise<ToolExecutionResult> {
  return this.prepareExecution(exec, prepared => this.completeScheduledExecution(prepared))
}
```

准入在 {{src:packages/core/tools/src/index.ts#L1463-L1507|prepareExecution()}}，派发在 `dispatchScheduledExecution()`，收尾在 `finalizeScheduledExecution()`。拆成三段是为了给外部调度器（`TOOL_RUNTIME_SCHEDULER`）逐阶段调用的能力，`execute()` 只是把三段串起来的便利入口。

准入这一段是本节的重点：

```ts
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)
const askResolution: ToolAskResolution = gate.kind === 'ask'
  ? await this.serviceAsk(exec, gate)
  : { decision: gate, approvalCancelled: false }
const { decision } = askResolution
if (this.callerCancelled(exec) && askResolution.approvalCancelled) {
  return await next({ kind: 'post-result', exec, result: toolAbortedBeforeDispatchResult() })
}
const denialReason = decision.kind === 'allow'
  ? this.guardReason(exec)
  : decision.reason
if (denialReason !== undefined) { ... }
```

三个判断依次落下：waterfall 的裁决、审批的裁决、guard 的裁决。最后一行的条件写法值得看：**只有 `allow` 才去问 guard**。已经被拒的调用不需要再问一遍，而 guard 也没有翻案的权力。

实验第 3 步的输出把每条路径的终止点标出来了：

| 场景 | 走到第几步 | 跳过了什么 |
|---|---|---|
| 正常 | 1→2→3→4→5→6→7 | 无 |
| `pre-execute` 拒绝 | 1→6→7 | guard、`tools/execute`、工具体 |
| guard 拒绝 | 1→2→6→7 | `tools/execute`、工具体 |
| 无审批服务时 `ask` | 1→6→7 | 同 pre-execute 拒绝 |
| `post-execute` 拦截 | 1→2→3→4→5→6→7 | 无，但结果被换成 `isError` |

一条规律：**无论怎么被拒，`post-execute` 和 `tools/result` 都会执行**。拒绝也是一次结果，观察者（审计、计费、界面）看得到。

### guard 和 pre-execute 的分工

两者都能拒，区别在能力：

```ts
/**
 * Register a monotonic guard after the extensible `tools/pre-execute`
 * waterfall. A plain-context guard applies globally; one registered through
 * `agent.ctx` applies only to that agent. Any matching guard may deny by
 * returning a reason, while no guard can force-allow a call another guard
 * denied.
 */
guard(guard: ToolGuard): () => void {
```

**单调**（monotonic）是关键词：guard 只能拒，不能放行。{{src:packages/core/tools/src/index.ts#L1119-L1128|guardReason()}} 遍历全局层然后 scope 链，任何一个返回字符串就终止：

```ts
private guardReason(exec: ToolExecution): string | undefined {
  const globalReason = this.layers.global.guardReason(exec)
  if (globalReason !== undefined) return globalReason
  if (exec.agent === undefined) return undefined
  for (const layer of this.layers.chainLayers(exec.agent)) {
    const reason = layer.guardReason(exec)
    if (reason !== undefined) return reason
  }
  return undefined
}
```

而 `tools/pre-execute` 是 waterfall，一个监听器不调 `next()` 就能替所有人做决定，包括**替所有人放行**。所以两者的用途不同：策略协商用 pre-execute，硬性禁止用 guard。第 9 章的安全边界基本都落在 guard 上。

`guard()` 注册时还带一个参数：

```ts
{ label: 'tools.guard()', notify: false }
```

`notify: false` 表示注册 guard **不触发 `tools/change`**。因为 guard 不改变工具的可见性，模型看到的 schema 列表没变，没必要让所有 agent 重新组装提示词。而 `register()` 和 `restrict()` 都会触发。

### ask 降级为拒绝

{{src:packages/core/tools/src/index.ts#L1689-L1729|serviceAsk()}} 处理 `{ kind: 'ask' }`：

```ts
const approval = this.ctx.get('approval')
if (approval === undefined) {
  return {
    decision: { kind: 'deny', reason: ask.reason ?? `tool "${exec.name}" requires approval (not yet supported)` },
    approvalCancelled: false,
  }
}
```

用 `ctx.get('approval')` 而不是声明式注入，是因为审批服务是可选的（第 2 章讲过这两种读法的区别）。没有它，`ask` 变成 `deny`。这是 fail-closed：一个说「需要人确认」的调用，在没人能确认的部署里，绝不能自己放行。

拿到审批服务之后，四种结局映射成三种不同的拒绝理由：

```ts
case 'allowed-once': return { decision: { kind: 'allow' }, approvalCancelled: false }
case 'rejected': return { decision: { kind: 'deny', reason: `the user rejected tool "${exec.name}"` }, ... }
case 'cancelled': return { decision: { kind: 'deny', reason: `approval for tool "${exec.name}" was cancelled` }, approvalCancelled: true }
case 'unavailable': return { decision: { kind: 'deny', reason: `tool "${exec.name}" requires approval, but no approval channel is available` }, ... }
```

JSDoc 解释了为什么要三种不同措辞：`so the model can tell a human "no" from an absent approval channel`。人明确说不，和根本没人可问，模型的下一步应该不同。前者该换个做法，后者该告诉用户「这个部署没配审批」。

## 四、注册表是分层的

`ToolRuntime` 用的还是第 7 章那套 `ScopedLayers`：一个全局层，加上按 agent 划分的 scoped 层。

{{src:packages/core/tools/src/index.ts#L1037-L1062|register()}} 落在**调用方的 scope**：全局 `ctx` 注册的是全局工具，`agent.ctx` 注册的只属于那个 agent。实验第 5 步验证了同名的行为：

```
[同一层重名注册]
  tool "read" is already registered (for a per-agent variant, register through that agent's `agent.ctx` instead)
[agent 层影子注册同名] 没报错
```

同层重名抛，跨层同名是**遮蔽**。和第 7 章的 `PERSONA_SECTION` 一个模式。

### restrict：只裁剪继承来的

{{src:packages/core/tools/src/index.ts#L1071-L1098|restrict()}} 的四条校验，实验第 5 步全跑出来了：

```
[全局 ctx 上调 restrict]
  tools.restrict() requires a scoped context (agent.ctx): a context-global restriction
  would mask every agent — deny the tool for the intended agent instead
[空 filter]
  tools.restrict({}) is a no-op: pass `allow` and/or `deny`
  (an empty filter is almost always a materialized-empty-config bug)
[restrict 一个不存在的名字]
  tools.restrict() names unknown global tool "nosuch"; known global tools: read
[restrict 保留名 run_code]
  tools.restrict() cannot name reserved Code Mode presentation transport "run_code";
  restrict end-capability tools instead
```

第二条那句「an empty filter is almost always a materialized-empty-config bug」值得记住：`restrict({})` 在语法上合法、语义上无害，但它几乎总是「配置项被物化成了空对象」的症状。与其静默地什么都不做，不如报错。

真正微妙的是 {{src:packages/core/tools/src/index.ts#L1152-L1193|view()}} 上那段注释，它记录了一次实际发生过的失效：

> A restriction filters what a scope inherits — the global layer and every ancestor layer on its chain — and never what its OWN layer registers. That exemption is what a per-child capability filter has to keep intact: the delegation runtime registers a child's reporting and structured-output tools into the child's own layer, and a filter naming the capabilities the child may use must not strip the machinery it answers through.
>
> Reading the exempt set as "the global layer" instead of "not mine" held only while every model-facing tool sat in the host composition. Once presets moved them onto the agent plane they became an ANCESTOR contribution, so a child's filter silently stopped constraining anything it was given.

限制作用于「继承来的」，豁免的是「自己注册的」。曾经的实现把豁免集理解成「全局层」，在所有模型工具都住在宿主组合里的时候，这两种理解等价。等 agent preset 把工具搬到 agent 平面上，它们变成了**祖先**的贡献，于是 subagent 的能力过滤器**静默地不再限制任何东西**。第 10 章讲 subagent 时会回到这里。

### 被限制掉的工具，对模型来说不存在

实验第 4 步：

```
--- restrict({deny:[bash,write]}) 之后 ---
   agent : flaky, read, search, slow
   全局  : bash, flaky, read, search, slow, write
   agent 里 get("bash") = undefined
   agent 调 bash → {"message":"unknown tool \"bash\"","info":{"name":"ToolNotFoundError","code":"UNKNOWN_TOOL"}}
```

不是「你没权限调 bash」，是 `unknown tool "bash"`。schema 列表里没有它，调它的报错也和调一个拼错的名字一样。模型没有办法从错误信息里推断出「这个部署有 bash，只是不给我用」。

这一条有一个刻意的例外，就是 Code Mode 的塌缩。{{src:packages/core/tools/src/index.ts#L1364-L1451|createExecution()}} 里：

```ts
// The name IS visible here, so the denial carries the route the model
// must take instead. Without it the model reads a bare `unknown tool`
// for a tool the prompt just declared and concludes the deployment is
// broken rather than correcting itself.
return {
  kind: 'final-result',
  exec: execution,
  result: toolErrorResult(new ToolNotFoundError(
    name,
    `only \`${RUN_CODE_NAME}\` is callable directly — call \`${name}\` from inside a \`${RUN_CODE_NAME}\` program instead`,
  )),
}
```

名字在提示词里出现过，只是不能直接调。这时给一个裸的 `unknown tool` 会让模型认为部署坏了，而不是纠正自己的调用方式。所以这条拒绝**带上了正确的路**。

同一段代码上方还有一句注释解释了为什么塌缩要在流水线**之前**终止：

> A collapsed call is deterministically denied, so it terminates BEFORE the extensible policy pipeline: pre-execute listeners, approval `ask`, and guards must never observe — or worse, approve — a call that can only fail.

一个注定失败的调用，不该走到审批那一步。否则用户会被问「是否允许执行 bash」，点了「允许」，然后调用照样失败。

## 五、tools/execute 包装器：signal 的所有权

{{src:packages/guard/timeout-policy/src/index.ts#L55-L81|timeout-policy}} 全文 27 行，是 `tools/execute` 包装器的范本：

```ts
ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs
  if (timeoutMs === undefined) return next()

  using d = deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)
  const upstream = exec.signal
  exec.signal = d.signal
  try {
    const result = await next()
    if (timeoutOf(d.signal, TOOL_TIMEOUT) !== undefined) {
      return toolTimeoutResult(timeoutMs)
    }
    return result
  } finally {
    exec.signal = upstream
  }
})
```

四件事，每一件都对应事件声明里的一句契约。

**一、只能改 `exec.signal`。** 事件 JSDoc：`wrappers may change only exec.signal, while call identity remains immutable`。callId、name、arguments 都不许动。改身份等于伪造一次调用。

**二、必须还回去。** `finally` 里 `exec.signal = upstream`。注释解释了为什么：`so post-execute listeners never see this plugin's (possibly already-aborted) timeout signal`。post-execute 拿到一个已经 abort 的 signal，会误以为整次调用被取消了。

**三、注册表会把调用方的原 signal 重新融回去。** 这是包装器改不掉的：

```ts
/**
 * Dispatch the registered body with the original caller signal fused back
 * into any around-wrapper replacement. Cancellation never abandons the body:
 * a started promise reaches quiescence before its outcome becomes `ABORTED`.
 */
private async dispatchToolBody(exec: MutableToolRunContext): Promise<ToolExecutionResult> {
  const state = this.cancellationStates.get(exec)
  const wrapperSignal = exec.signal
  const fused = fuseToolSignals(state.callerSignal, wrapperSignal)
  const signal = fused.signal
```

{{src:packages/core/tools/src/index.ts#L1532-L1560|dispatchToolBody()}} 把包装器给的 signal 和**原始调用方 signal** 融成一个。事件声明写的是 `The registry re-fuses the original caller signal before the body, so replacement cannot detach caller cancellation`。一个包装器不能通过换 signal 让工具听不见用户按的取消。

**四、只在自己的计时器响了才替换结果。** `timeoutOf(d.signal, TOOL_TIMEOUT)` 按**码**判定：

```ts
/**
 * The code owned by this plugin, used BOTH as the internal deadline
 * classification code AND as the structured error `code` on the replacement
 * tool result. Scoping timeoutOf to it keeps a nested outer deadline
 * (another `tools/execute` wrapper's timer that fired first) from being misread
 * as this plugin's own timeout — it reads as an ordinary upstream cancel.
 */
```

两个超时包装器叠在一起时，外层的计时器先响，内层不该把它报告成自己的超时。按码区分让每个包装器只认自己那一个。

实验第 4 步的结果：工具体 sleep 3000ms 并声明 `timeoutMs: 200`，实际耗时 203ms，结果是：

```
{"isError":true,"error":{"message":"tool call timed out after 200ms",
 "info":{"name":"ToolTimeoutError","code":"TOOL_TIMEOUT"}}}
```

注意工具体自己是**正常返回**的（它监听了 `exec.signal`，被 abort 之后 `return 'finished anyway'`）。包装器看到自己的计时器响过，把这个返回值换成了结构化的超时。工具的 promise 没有被抛弃，也没有被 race 掉，这就是注释里那句 `without racing or abandoning the tool promise`。

## 六、结果的规范化：canonicalResults

`tools/execute` 包装器可以**替换结果**，不只是改 signal。这带来一个问题：包装器伪造出来的成功结果，绕过了第二节那道 `output.schema` 校验吗？

没有。{{src:packages/core/tools/src/index.ts#L1826-L1844|normalizeDispatchResult()}}：

```ts
private normalizeDispatchResult(exec: ToolExecution, result: ToolExecutionResult): ToolExecutionResult {
  if (this.canonicalResults.get(result) === exec.token) return result
  if (result.isError) { ... }
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (tool === undefined) throw new ToolNotFoundError(exec.name)
  const normalized = this.createSuccessResult(exec, tool, result.value)
  ...
}
```

第一行是一张 `WeakMap<object, ToolExecutionToken>`：注册表自己造的结果会被 {{src:packages/core/tools/src/index.ts#L1787-L1790|markCanonical()}} 打上这次执行的 token。回来的结果如果**不是**注册表造的（包装器新造的对象），就重新走一次 `createSuccessResult`，也就是重新校验、重新渲染。

值得看的是 key：

```ts
private markCanonical<T extends ToolExecutionResult>(exec: ToolExecution, result: T): T {
  this.canonicalResults.set(result, exec.token)
  return result
}
```

记的是「这个结果对象属于**这一次**执行」，不是「这个结果对象是规范的」。token 是 {{src:packages/core/tools/src/index.ts#L1364-L1451|createExecution()}} 里 `Symbol()` 出来的，每次执行都不同。所以一个包装器把上一次调用的结果对象缓存下来返回，token 对不上，照样重新校验。

`tools/post-execute` 的 `accept` 也可以带 `value` 替换返回值，同样走 `createSuccessResult`：

```ts
if (Object.hasOwn(decision, 'value')) {
  if (result.isError) {
    throw new TypeError('tools/post-execute cannot replace the value of a failed result')
  }
  ...
  const replaced = this.createSuccessResult(exec, tool, decision.value)
```

上面那个 `Object.hasOwn(decision, 'content') && Object.hasOwn(decision, 'value')` 的检查也在同一个函数里：不许同时替换两者。因为 `content` 是 `value` 的投影，两个都给等于自相矛盾。

最后一关是 {{src:packages/core/tools/src/index.ts#L1847-L1862|materializeFinalResult()}}，在 `tools/result` 之前把结果冻结。实验第 3 步打印的 `frozen=true` 就是它。观察者只能看。

## 七、取消：body 有没有启动，决定错误码

流水线里有两个取消相关的常量：

```ts
export const TOOL_ABORTED = 'ABORTED'
export const TOOL_ABORTED_BEFORE_DISPATCH = 'ABORTED_BEFORE_DISPATCH'
```

选哪一个，由 {{src:packages/core/tools/src/index.ts#L1518-L1525|cancellationResult()}} 一行决定：

```ts
return state.bodyInvoked
  ? toolAbortedResult(prior)
  : toolAbortedBeforeDispatchResult(prior)
```

`bodyInvoked` 在 `dispatchToolBody` 里紧挨着 `tool.execute()` 之前置位。区分这两者是有实际后果的：**`ABORTED_BEFORE_DISPATCH` 意味着这个工具没有产生任何副作用**，重放和重试可以放心地当它没发生；`ABORTED` 意味着工具体跑过一部分，副作用未知。

`execute()` 的 JSDoc 把整条取消契约写全了：

> Cancellation arriving after entry and before final result materialization skips a not-yet-started body with `ABORTED_BEFORE_DISPATCH` or replaces a successful started outcome with `ABORTED`; already-started work is still drained and may retain a tool-owned structured error.

三句话三个规则。最后一句是关键：**已经启动的工作照样等它跑完**。这一层从不 race，从不抛弃 promise。第 5 章那句「取消到达时工具已经启动，`runGroup` 会 drain 已启动的调用并正常提交结果」，底下靠的就是这条。

而且注意 `!postResult.isError` 这个条件：

```ts
this.callerCancelled(exec) && !postResult.isError
  ? this.cancellationResult(exec, postResult)
  : postResult,
```

取消只替换**成功**的结果。工具自己报的结构化错误保留下来，因为那比一句「被取消了」信息量大。

## 八、并发：默认独占

循环侧怎么调度，第 5 章走读过。这里只补一个判据。{{src:packages/core/tools/src/index.ts#L1276-L1285|executionMode()}}：

```ts
executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
```

三条路全都通向保守的一边：没声明 `isConcurrencySafe` 是独占，声明了但返回非 `true` 是独占，谓词**抛异常**也是独占。实验第 4 步：

```
--- executionMode（默认独占）---
   read    {"kind":"exclusive"}
   search  {"kind":"parallel"}
   flaky   {"kind":"exclusive"}
```

`flaky` 的谓词 `throw new Error('boom')`，判定结果是独占而不是失败。`catch {}` 里没有日志也没有重抛，因为这不是错误处理，是**默认值**：一个不能确定安全的调用就当它不安全。

而且注意谓词接受 `arguments`：同一个工具可以按参数决定。`read` 一个文件是安全的，`write` 同一个文件不是；一个 `bash` 工具可以对只读命令返回 `true`，对别的返回 `false`。

五处对照：

1. **guard 排在 pre-execute 之后。** `DENY` 那次连 guard 都没跑到：已经被拒的调用不再问 guard。
2. **guard 拒得了 pre-execute 已经放行的调用。** `GUARD` 那次 pre-execute 返回了 `next()`，guard 照样拦下。这就是「单调」。
3. **`ASK` 在没装审批服务时变成拒绝**，理由用的是 pre-execute 给的那句。fail-closed。
4. **无论怎么被拒，6 和 7 都执行。** 拒绝也是一次结果。
5. `frozen=true`：`tools/result` 拿到的是深冻结的快照。

试着在 `tools/result` 里改 `result.content`，会抛 `TypeError`。

## 小结

一次工具调用的完整链条：

```
createExecution   快照参数 → 冻结 → 发 token；塌缩与不可序列化参数在这里就终止
  ↓
tools/pre-execute（waterfall）  allow / deny / ask
  ↓ 只有 allow 才继续
guard（单调）      任一层返回字符串就拒；无人能强行放行
  ↓
tools/execute（around）  可换 exec.signal 和结果；finally 必须还回去
  ↓
dispatchToolBody  融回调用方 signal → bodyInvoked = true → tool.execute()
  ↓
createSuccessResult  快照 → 校验 output.schema → 冻结 → render → presentationMeta
  ↓
tools/post-execute（waterfall）  accept / +content / +value（重新校验）/ block
  ↓
materializeFinalResult → 深冻结 → tools/result（emit，只能看）
```

三个结论：

**这条流水线从不抛异常。** 参数错、返回值错、render 崩、工具不存在、超时、取消，六种情况全部变成结构化的 `isError` 结果，带稳定的机器码。第 5 章那句「工具并发跑但按模型序提交」，前提就是每一次调用必然产出一个可提交的结果。

**拒绝分两级，能力不同。** `tools/pre-execute` 是 waterfall，可以拒也可以替所有人放行；`guard` 是单调的，只能拒。策略协商走前者，硬性禁止走后者。两者都不影响 `post-execute` 和 `tools/result` 的执行，所以拒绝是可审计的。

**不确定就往保守的一边倒。** 没装审批服务，`ask` 变 `deny`；`isConcurrencySafe` 没声明、返回非 `true`、甚至抛异常，都判独占；工具返回值不合自己的 schema，宁可报错也不送进日志。这几处都不是错误处理，是**默认值的选择方向**。

下一章沿着 guard 往下走，讲能力 seam 与安全边界：文件系统、shell、网络这些真正危险的能力是怎么被包起来的，以及 DSH 在哪里画了信任的线。
