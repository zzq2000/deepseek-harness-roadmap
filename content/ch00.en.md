# Run it first, then read the map

This chapter explains no mechanism. It does three things: say what DSH is, list the environment needed to run it, and teach you how to locate any implementation inside 200k lines of code.

---

## One claim

DeepSeek Harness (**DSH**) is an agent harness: the runtime layer that connects a large model to tools, a filesystem, a terminal, and a sandbox so it can actually do work. You have seen this category before: Claude Code, Codex, Cline.

But DSH makes one design decision that separates it from most of them, stated in the first line of {{src:AGENTS.md|AGENTS.md}}:

> **everything is a plugin**

In many projects that sentence is marketing. In DSH it is literal. {{src:docs/architecture.md#L11-L13|architecture.md}} puts it even more bluntly:

> There is no privileged core to patch: you extend dsh by mounting plugins alongside others, and every registration is an effect that is revoked when its plugin unloads.

Take "**no privileged core**" seriously. It means: model adapters are plugins, the tool registry is a plugin, the session log is a plugin, and **the agent loop itself is a plugin**. There is no `main()` orchestrating things from the top, and no `core` module that everything else must route around. A running `dsh` process is a tree of plugins assembled from configuration.

:::key The central question of this course
If even the main loop is a replaceable plugin, where does control flow actually live? The answer: in **events** and **service resolution**. That is what chapters 1 and 2 answer, and it is the prerequisite for everything after.
:::

What this means for you directly: **self-evolution, memory, and multi-agent arrangements require no changes to DSH's own code**. They are new plugins hanging off existing extension points. That is the goal of chapter 12.

This plugin model is not an engineering habit; it has a formal basis. Line 7 of DSH's {{src:README.md#L7|README}} points at a paper:

> _A Programming Paradigm for Spatiotemporal Composability_, by Yifan Shi, Wei Zhang, and Tianyi Cui, Peking University and DeepSeek-AI. 88 pages, draft of August 13, 2026. [Repository](https://github.com/cordiverse/paper) · [PDF](https://github.com/cordiverse/paper/blob/main/paper.pdf)

It splits "dynamic composition" into a temporal and a spatial dimension, which are exactly chapters 1 and 2 of this course, and the application domain its abstract names is the self-evolving agent harness. **No need to read it now**: the end of chapter 2 works through the full correspondence once you have read the source.

## How much code is this

An honest sense of scale, so you neither under- nor overestimate:

| Measure | Count |
|---|---|
| Package groups under `packages/` | 49 |
| Leaf packages (actual npm packages) | 219 |
| Product TypeScript (excluding tests) | about **207,000 lines** / 1292 files |
| Including tests and the full frontend | about 450,000 lines |
| The Cordis framework core (`vendor/cordis/src`) | **2693 lines** |

Note the last row. The entire "everything is a plugin" foundation (Context, plugin lifecycle, service resolution, the event bus) is **2693 lines**. Those 2693 lines are the highest-leverage part of this course: read them properly and the remaining 200k lines become "applications on top of a framework" rather than 200k lines of unfamiliar code.

So the course does not start at `main`. It starts at the **framework core**. Chapters 1 and 2 read the essential parts of those 2693 lines line by line.

## Prerequisites

Hands-on labs start in chapter 3 and require a working build of DSH. Check your environment against this table first:

| Component | Requirement | Check | Why |
|---|---|---|---|
| **Node.js** | `^22.19.0 \|\| >=24.0.0` | `node -v` | Runtime; pnpm refuses to install on a mismatched version |
| **pnpm** | 11.x | `pnpm -v` | The repo is a pnpm workspace, so npm/yarn will not install it |
| **Git** | any | `git --version` | Cloning the repo |
| **DeepSeek API key** | a valid key | see below | Running the agent; not needed to read source |
| Disk | about 3 GB | `df -h .` | `node_modules` plus build output |

The authoritative source for versions is the repo's `package.json`, not this page:

```srcref package.json#L7-L10
The packageManager and engines fields. These are the real requirements; the table above only restates them.
```

:::note You can read the first two chapters without installing anything
Chapters 1 and 2 read `vendor/cordis` source. Pure reading, no install required. The build only matters from chapter 3 onward. If you want to save time, start the install and build in the background now; it will be done by the time you finish chapter 2.
:::

### Install and build

```sh
corepack enable          # corepack ships with Node; the easiest way to get pnpm
cd deepseek-harness
pnpm install
pnpm run build           # the first build usually takes 10+ minutes
```

`corepack enable` prepares the exact pnpm version declared in `packageManager`, which is harder to get wrong than a global `npm i -g pnpm`.

### Run

```sh
pnpm dsh web             # Web UI, default http://127.0.0.1:3080
pnpm dsh --profile headless "count the packages in this repo"   # one-shot task
```

Both need `DEEPSEEK_API_KEY`. DSH reads it from a `.env` at the repository root:

```sh
DEEPSEEK_API_KEY=sk-...
```

Key policy lives in {{src:AGENTS.md#L94-L96|the Secrets / .env section of AGENTS.md}}. Without a key, real-API tests skip themselves and reading source is unaffected, but **this course's open questions need it** for grading.

:::warn Never commit credentials
`AGENTS.md` states it outright: "Never commit credentials." `.env` is already listed in the repo's `.gitignore`.
:::

One more command worth memorizing right now. It is the key to understanding the whole assembly:

```sh
pnpm dsh --profile web --dump-config
```

It prints the **complete plugin tree** your machine actually boots. Every entry it prints can be replaced by your own patch file. Chapter 3 walks through its output.

## Finding things in 200k lines

This is the most practical part of the chapter. DSH's documentation is unusually good, and there are three legitimate paths to any piece of code, in priority order:

### Path 1: subsystem reference pages

{{src:docs/subsystems/README.md|docs/subsystems/}} holds **46** subsystem pages, one per subsystem, in both English and Chinese. Want to know how compaction works? Read `compaction.md`. How the sandbox confines processes? `sandbox.md`.

These pages have a property that is rare elsewhere: their type declarations are verified against source by CI and are not allowed to drift.

```srcref docs/subsystems/README.md#L55-L55
"Type declarations on these pages are equivalent to source and checked for drift by `pnpm run verify-type-equiv`"
```

So you can treat them as authoritative without worrying about staleness. That is also why this course quotes them heavily.

### Path 2: package group READMEs

`packages/<group>/README.md` owns the **package-to-`ctx`-key mapping**. If you see `ctx.shell` in code and want to know who provides it, go to the README in {{src:packages/shell|packages/shell/}}.

{{src:packages/README.md|packages/README.md}} is the index for this layer: all 49 groups in one table.

### Path 3: the search box on the right

The top-bar search box is wired to full-text search over the repository (`Cmd/Ctrl+F` focuses it). In the code view, **clicking any type name or function name** pops up its definition sites. I built both specifically for this course, because the single most time-consuming action when reading DSH is "where is this type actually defined".

:::lab Try it right now
1. Search for `agent/pre-step` in the top bar and see how many producers and consumers this event has.
2. Open the file tree on the right, expand `vendor/cordis/src/`, and open `fiber.ts`.
3. Click any `Context` or `Disposable` inside `fiber.ts` and check that symbol jump takes you to the definition.

Do those three and you know 80% of how to operate this course.
:::

## What a conversation is, on disk

Finally, build a concrete mental image. When you talk to DSH, what is actually stored on disk?

The answer is **an append-only event log**. It lives in the harness home (`~/.dsh`, see {{src:packages/util/home-paths/src/index.ts#L12|DSH_HOME_DIR_NAME}}), laid out as:

```text
<root>/
  --<normalized-project-path>--/
    <session id>/
      session.jsonl.zstd      # default: concatenated checksummed zstd frames
      session.jsonl           # only with compression: 'none'
```

The first line is an immutable `SessionHeader`; every line after it is a `SessionEvent`. Every message you send, every streamed chunk from the model, every tool call and result is one event in that log.

This log is not a by-product of the chat transcript. It is the **sole source of the model's context**. A runtime invariant enforces exactly that:

:::key Model-visible ⟺ logged
Anything that reaches a model request must be reconstructable from the session log. Consequently, "adding a new model-visible input" necessarily requires "adding a new session event type".

That rule is the subject of chapter 4, but remember it now. It explains a lot of designs that otherwise look roundabout.
:::

:::note Want to read the log directly?
It is zstd-compressed by default, so `cat` gives you binary noise. The JSONL backend supports a `compression: 'none'` option (see {{src:packages/session/session-persistence-jsonl/README.md|that package's README}}); switch to plaintext and you can read it directly. Chapter 4's lab uses this trick.
:::

## How to read this course

- **Explanation on the left, source on the right.** Every inline reference marked with ◆ and every blue-bordered card opens the corresponding file on the right, scrolled and highlighted to the exact lines. **Actually click them**. This course assumes you are reading against the source, not just reading my paraphrase.
- **Multiple choice first, then open questions.** Multiple choice checks factual recall and is graded locally; open questions check mechanical understanding and are sent to DeepSeek together with **that question's source context**, so it can tell you what you missed and what you got wrong.
- **Grading is deliberately strict**, especially against answers that use the right vocabulary while describing the mechanism backwards. Wherever you lose points is where you should go back and reread.
