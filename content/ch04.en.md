# The session log: if the model saw it, it was recorded

A conversation in DSH is not a message array. It is an append-only event log, and **the message history the model sees is derived from that log rather than stored a second time**.

That choice yields a sentence you can use as an invariant: if the model saw it, it was recorded. It has two halves, each guaranteed by different code.

- **Structurally**: a message cannot reach the model's view unless it first entered the log as a marked event. The derivation function has no second data source.
- **In time**: before a request goes out, the committed log prefix must be durable. Same before a tool produces side effects.

This chapter walks both halves, and settles what "compaction" means: DSH's context compaction **deletes no history**. It only makes a stretch of history invisible to the model.

## 1. The log is the truth; messages are a derived value

{{src:packages/core/session/src/types.ts#L236-L256|SessionEventMap}} is the event vocabulary. The entries this chapter needs:

| Event | Meaning | Model-visible |
|---|---|---|
| `turn/start` / `turn/end` | opening and closing one turn | no |
| `step/start` / `step/end` | one step (a model call plus the tools it requested) | no |
| `user/message` | a user message (typed, `inject()`ed, or a goal round) | **yes** |
| `assistant/chunk` | raw streaming delta | no |
| `assistant/message` | the assembled assistant message of one step | **yes** |
| `tool/call` | one tool invocation the model requested | no |
| `tool/result` | the result of one tool call | **yes** |
| `todo/write` | todo-list snapshot | no |

Only three rows say yes. Those three types are hardcoded in {{src:packages/core/session/src/surface.ts#L15-L28|SURFACE_EVENT_TYPES}}:

```ts
const SURFACE_EVENT_TYPES = new Set<string>([
  'user/message',
  'assistant/message',
  'tool/result',
])
```

The derivation function {{src:packages/core/session/src/surface.ts#L83-L114|deriveEventMessage}} is one switch over those three:

```ts
switch (event.type) {
  case 'user/message': {
    return event.data
  }
  case 'assistant/message': {
    if (event.data.message.content.length === 0) return null
    return event.data.message
  }
  case 'tool/result': {
    return event.data.message
  }
  default:
    return null
}
```

All three branches **return the message object already stored in the event, verbatim**, with no assembly, wrapping, or rewriting. The comment above `user/message` says so explicitly:

> Do NOT re-add per-type framing (e.g. `<context>`) here: framing is caller-owned.

Wrapping injected context in something like `<system-reminder>` is **the producer's job**, baked into `content` at append time. This layer stays a pure pass-through.

:::key Why the rule matters
If derivation could transform, then what the log stores and what the model receives would not be the same thing, and replaying a log could produce a history that differs from the one that request was actually built from. Keeping it verbatim is what makes the log replayable.
:::

The empty-content check on `assistant/message` covers a real edge: a step that hits max-tokens produces an assistant message with no content that exists only to host usage. It enters the log (the token accounting must be recorded) but not the model history (a content-less assistant turn would pollute the conversation).

## 2. The surface: which log rows the model can see

Type alone is not enough. DSH requires **every surface event to declare at write time how it enters the model's view**, and that declaration is `surfaceOp`.

Look first at how the type system enforces it. {{src:packages/core/session/src/index.ts#L604-L608|append's signature}}:

```ts
append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent] : []
): SessionEvent<T>
```

The third parameter is a **conditional tuple**. Writing `append('user/message', …)` without it is a compile error; writing `append('turn/start', …, { surfaceOp: 'append' })` is also an error, because the tuple in that position is empty. One signature expresses both "required" and "forbidden".

The runtime check lives in {{src:packages/core/session/src/surface.ts#L185-L208|surfaceOpOf}}, and it is symmetric:

```ts
if (!isSurfaceEligibleType(event.type)) {
  if (raw.surfaceOp !== undefined) {
    throw new Error(`session event "${event.type}" is not surface-eligible and cannot carry surfaceOp`)
  }
  if (raw.sourceEventSeqs !== undefined) {
    throw new Error(`session event "${event.type}" is not surface-eligible and cannot carry sourceEventSeqs`)
  }
  return
}
const op = raw.surfaceOp
if (op === undefined) {
  throw new Error(`session event "${event.type}" is surface-eligible and requires a surfaceOp marker`)
}
```

**An ineligible type carrying the marker is an error, and an eligible type missing it is an error.** With both directions closed, surface membership has no default to guess: every message event must answer "are you appending or replacing".

`surfaceOp` has exactly two forms:

- `'append'` joins the surface tail
- `{ op: 'replace', start, end }` replaces the whole surface range from `start` to `end`

The second one is compaction, covered in section 4.

## 3. append: what one commit does

{{src:packages/core/session/src/index.ts#L604-L655|Session.append}} is the entry point of the whole data plane. Piece by piece:

```ts
const dataSnapshot = snapshotJsonValue(data)
if (dataSnapshot === undefined) {
  throw new Error(`session event "${type}" carries non-JSON-serializable data`)
}
```

`snapshotJsonValue` **validates and copies in one traversal**. That is not a shortcut; it closes a specific hole. Validating with `isJsonValue(data)` and then copying with `structuredClone(data)` would let an object with a getter return a legal value on the first read and something else on the second. What was validated and what was stored would differ. One traversal fixes the value as it reads, so the gap does not exist.

Rejected inputs include BigInt, functions, symbols, `undefined`, `-0`, non-finite numbers, cycles, sparse arrays, and exotic prototypes like Map / Set / Date / class instances. The lab hits one on purpose.

```ts
const entry = attachments.get(this)
if (entry?.appending) {
  throw new Error('session append cannot reenter while another append is being published')
}
```

The reentrancy check. If a `session/event` listener appended to the same session while handling an event, seq assignment and the listener snapshot would interleave. Rejected outright.

```ts
const event = deepFreeze({
  type,
  seq: this.log.length,
  time: Date.now(),
  data: dataSnapshot,
  ...(surfaceMetadataSnapshot as { surfaceOp?: unknown; sourceEventSeqs?: unknown }),
} as unknown as SessionEvent<T>)
this.surfaceManager.validateNext(event as SessionEvent)
```

`seq = this.log.length`, so `events[i].seq === i` always holds. That contiguity contract is the foundation persistence and replay stand on.

`validateNext` checks whether the event may join the surface **before the event enters the log**. A validation failure throws and the log does not change by a single byte.

Then comes the part most worth reading:

```ts
let callbacks: SessionCallback[] | undefined
const callbackArgs: unknown[] = [this, event]
if (entry !== undefined) {
  callbacks = collectSessionCallbacks(entry.emitCtx, [entry.carrier, 'session/event', ...callbackArgs])
}
this.log.push(event as SessionEvent)
this.eventsSnapshot = undefined
if (callbacks !== undefined && entry !== undefined) {
  invokeContainedSessionObservers(entry.emitCtx, 'session/event', entry.id, callbackArgs, callbacks)
}
```

**Resolve the listener list, then push, then invoke.** The order of those three steps is deliberate.

The line inside {{src:packages/core/session/src/index.ts#L377-L379|collectSessionCallbacks}} is chapter 2's dispatch:

```ts
return [...ctx.events.dispatch('emit', args)] as SessionCallback[]
```

`dispatch` runs Cordis's internal checks (scope filtering, context validity), and those can throw. Placed before the push, a throw leaves the log unchanged. Placed after, the log would already have changed while an error propagated, and the caller could not tell whether the event landed.

Post-push invocation uses independent containment. {{src:packages/core/session/src/index.ts#L382-L399|invokeContainedSessionObservers}}:

```ts
for (const callback of callbacks) {
  try {
    const returned: unknown = callback(...args)
    void Promise.resolve(returned).catch((error: unknown) => {
      ctx.logger.warn(`session "${id}": ${name} listener rejected: ${String(error)}`)
    })
  } catch (error: unknown) {
    ctx.logger.warn(`session "${id}": ${name} listener threw: ${String(error)}`)
  }
}
```

Synchronous throws and async rejections are both only logged. The reason is in the method's own doc comment:

> Once the event enters the log, the append is committed.

One observer's failure cannot turn a committed append into a failure, and it cannot stop later observers from seeing the same event. **The commit boundary is drawn at the `log.push` line**: every failure before it is fatal, every failure after it is contained.

## 4. Compaction deletes no history

This is the chapter's most important section.

When the context fills up, the intuitive move is to delete early messages. DSH does not. Compaction is **one more append**, whose `surfaceOp` is a replace:

```ts
{ op: 'replace', start: 0, end: 3 }
```

The log keeps growing; the four surface nodes are simply shadowed by this new one. {{src:packages/core/session/src/surface.ts#L362-L379|applySurfacePlan}} is one splice:

```ts
if (plan?.kind === 'append') {
  state.nodes.push(plan.seq)
} else if (plan?.kind === 'replace') {
  state.nodes.splice(plan.startIdx, plan.endIdx - plan.startIdx + 1, plan.seq)
  state.replaceGeneration += 1
}
```

A replacement passes three checks, chained together in {{src:packages/core/session/src/surface.ts#L321-L347|planSurfaceEvent}}.

**First**, the range must actually exist on the current surface ({{src:packages/core/session/src/surface.ts#L246-L266|replacementRange}}):

```ts
const startIdx = state.nodes.indexOf(op.start)
if (startIdx === -1) {
  throw new Error(`surface replace: start seq ${op.start} not found in surface`)
}
```

Note it searches `state.nodes` (the current surface), not the log. A seq already shadowed by an earlier compaction cannot serve as an endpoint for a second one.

**Second**, every shadowed node must appear in `sourceEventSeqs` ({{src:packages/core/session/src/surface.ts#L211-L243|assertProvenance}}):

```ts
const missing = shadowedSeqs.filter(seq => !sources.has(seq))
if (missing.length > 0) {
  throw new Error(`surface replace: sourceEventSeqs must include every shadowed surface node; missing ${missing.join(', ')}`)
}
```

This turns "which messages is this summary made from" into hard data in the log rather than something the compaction plugin privately knows. Anyone holding the log can reconstruct the shadowed stretch.

**Third** applies only to `tool/result` ({{src:packages/core/session/src/surface.ts#L286-L318|assertToolResultRewrite}}): it must replace exactly one current node, and **may change nothing except content**. The implementation hollows out `content` on both sides and deep-compares the rest:

```ts
originalRest['message'] = {
  ...original.data.message,
  content: [{ ...originalResult, content: null }],
}
// ... same for replacementRest
if (!isDeepEqualJson(originalRest, replacementRest)) {
  throw new Error('tool/result surface replacement may change only content')
}
```

The use case is tool-result pruning: a 40k-character file read is swapped for "(content pruned)", while `callId`, the call/result pairing, and the error flag stay identical. The model still sees that the call happened and succeeded, just not its content. Changing any other field would break call/result pairing, so it is forbidden.

### Two surfaces, two readers

Compaction raises a problem: replacing four messages with a summary is right for the model and wrong for the **human**. The user did see those four messages, and the UI must not make them vanish.

DSH's answer is {{src:packages/core/session/src/surface.ts#L41-L55|isAppendSurfaceEvent}}, whose comment states it plainly:

> The model-visible surface deliberately shadows replaced ranges, so it is the wrong source for a human transcript — a landed replacement would erase conversation the user already saw. Append-origin events are that transcript's durable source material; replacement copies stay model-only.

| Reader | Source | After compaction |
|---|---|---|
| model | `session.surface` | sees the summary, not the originals |
| human | every log event with `surfaceOp === 'append'` | sees the originals, not the summary |

Two projections over one log, each taking what it needs. This only works given "the log is the truth and messages are derived". If history were really deleted, one of the two readers would have to lose.

:::key Compaction is addition
`replaceGeneration` only grows and the log only lengthens. No function in DSH removes an event from a session log. "Compacting the context" compacts **the derived value sent to the model**, not the storage.
:::

## 5. Three folds with the same shape

A log can reach tens of thousands of events, so folding from scratch on every read is out. The surface, the messages, and the request header each keep an incremental cache, and all three have the same shape: **a cursor plus an invalidation condition**.

The surface's cursor is `_lastProcessedSeq` ({{src:packages/core/session/src/surface.ts#L398-L459|SurfaceManager}}):

```ts
private _processDelta(): void {
  const tailSeq = this.baseSeq + this.log.length - 1
  for (let seq = this._lastProcessedSeq + 1; seq <= tailSeq; seq++) {
    ...
  }
}
```

Both getters (`nodes`, `replaceGeneration`) check whether the cursor is behind and catch up first.

The message cache has two cursors ({{src:packages/core/session/src/index.ts#L726-L747|deriveMessages}}):

```ts
if (generation !== this.derivedGeneration) {
  this.derived = []
  this.derivedNodes = 0
  this.derivedGeneration = generation
}
for (const seq of nodes.slice(this.derivedNodes)) {
  const msg = this.deriveEventMessage(this.log[seq]!)
  if (msg) this.derived.push(msg)
}
this.derivedNodes = nodes.length
return [...this.derived]
```

`derivedNodes` is the incremental cursor and `derivedGeneration` is the invalidation condition: **one replace throws the whole message cache away and rebuilds it**, because a splice changes the middle and the increment cannot continue. An append only projects the newly added nodes.

The last line returns a fresh array every call. The comment gives the reason: an array a caller already holds must not grow because of a later append. The array is new; the `Message` objects inside are shared and deep-frozen, so no second deep clone is needed.

The request-header fold ({{src:packages/core/session/src/index.ts#L670-L680|requestHeader}}) is the same cursor-plus-delta shape, with one addition:

```ts
this.headerFold = deepFreeze(foldRequestHeader(this.log.slice(this.headerFoldSeq), this.headerFold))
```

The fold result is **frozen before it is stored**. The comment explains: this is session state exposed by reference, and a consumer mutating it in place instead of building a replacement would desync every later comparison against the log.

## 6. When "recorded" actually happens

`append` is synchronous and touches no disk. When it returns, the event is only in memory. Two layers handle durability.

### Write-behind: a 200 ms window by default

{{src:packages/session/session-persistence/src/coordinator.ts#L1086-L1137|installWritePath}} wires the persistence plugin onto session events:

```ts
ctx.on('session/created', (session) => { void this.initFor(session) })
ctx.on('session/event', (session, event) => {
  const live = this.initFor(session)
  live.writes.enqueue(event)
})
ctx.on('session/flush', session => this.flush(session))
ctx.on('session/disposed', (session) => { this.retire(session) })
```

Four listeners: that is the entire interface between a persistence plugin and the core. The top of this function also applies a chapter 1 fact:

```ts
// Register the disposer BEFORE the listeners. Cordis tears effects down in
// reverse registration order, so event admission closes before this final
// drain reaches quiescence and closes the backend.
ctx.effect(() => async () => { ... })
```

**Register the cleanup first, the listeners second.** Because effects tear down in reverse, this order guarantees that unloading closes event admission before the final drain runs. The other way round, new events could still arrive halfway through that last drain.

{{src:packages/session/session-persistence/src/write-behind.ts#L45-L56|enqueue}} does `structuredClone(event)`, so persistence holds its own copy. The window is fixed:

```ts
enqueue(event: SessionEvent): void {
  const wasEmpty = this.pending.length === 0
  this.pending.push(structuredClone(event))
  if (this.barrier !== undefined) return
  ...
  } else if (wasEmpty) {
    this.armTimer()
  }
}
```

The timer arms only when the queue goes **from empty to non-empty**. Later events do not reset it, so 200 ms is an upper bound on batching, not "200 ms after the last event".

Failure handling is in {{src:packages/session/session-persistence/src/write-behind.ts#L139-L158|startWrite}}:

```ts
const batch = this.pending.splice(0)
...
.catch((error: unknown) => {
  this.pending = batch.concat(this.pending)
  ...
})
```

A failed write puts the whole batch **back at the head**: `batch.concat(this.pending)`, not the reverse. The log is ordered, and letting newer events jump ahead of a failed batch would break seq contiguity on disk.

### Checkpoints: three semantic boundaries

Write-behind is best-effort. The actual "recorded" guarantee comes from {{src:packages/session/session-checkpoint-policy/src/index.ts#L63-L83|session-checkpoint-policy}}, a plugin consisting of three listeners:

```ts
ctx.on('llm/stream', (options, next): AsyncIterable<StreamChunk> => {
  if (options.sessionId === undefined) return next()
  const session = ctx.sessions.get(options.sessionId)
  return session === undefined ? next() : afterCheckpoint(ctx, session, next)
})

ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  if (exec.agent === undefined || exec.parent !== undefined) return next()
  await ctx.sessions.flush(exec.agent.session)
  if (exec.signal.aborted) return abortedBeforeDispatchResult()
  return next()
})

ctx.on('agent/pre-step', async ({ agent }, next): Promise<PreStepDecision> => {
  await ctx.sessions.flush(agent.session)
  return next()
})
```

All three are chapter 2's **waterfall onion**, and all three do **pre-**processing: flush first, then `next()`. Chapter 3's `internal/config` was post-processing (call `next()` first, then transform the result); this is the other half.

The first listener is this chapter's title, implemented. {{src:packages/session/session-checkpoint-policy/src/index.ts#L29-L38|afterCheckpoint}}:

```ts
return (async function* (): AsyncIterable<StreamChunk> {
  await ctx.sessions.flush(session)
  yield* next()
})()
```

A generator wrapper puts the flush **before the first chunk is pulled**. For a request to go out, the log prefix must be durable first. If the flush throws, `yield*` is never reached and the adapter is never called.

The second listener does the same at the tool-side-effect boundary, and only for top-level calls (`exec.parent !== undefined` passes straight through; a nested dispatch reuses the outer call's checkpoint).

:::key fail-closed
Both are "checkpoint fails, nothing proceeds". If durability fails, DSH prefers not sending the request and not running the tool over letting an action happen that the log has no record of. That is the time half of "if the model saw it, it was recorded".
:::

`session/flush` dispatches in **parallel** mode, one of chapter 2's five. {{src:packages/core/session/src/index.ts#L1022-L1039|SessionStore.flush}}:

```ts
const results = await Promise.allSettled(callbacks.map((callback) => {
  try {
    return callback(...callbackArgs)
  } catch (error: unknown) {
    return Promise.reject(error)
  }
}))
const failure = results.find((result): result is PromiseRejectedResult => result.status === 'rejected')
if (failure !== undefined) throw failure.reason
```

Every listener starts, and the first failure is reported only after all of them settle. A listener that throws synchronously is converted into a rejected promise so it takes the same path as an async failure. The reasoning matches chapter 3's `EntryGroup.update`: the first failure must not strand everyone else halfway.

## 7. What lands on disk

The JSONL backend writes one file per session: a header line, then one line per event ({{src:packages/session/session-persistence-jsonl/src/format.ts#L30-L44|HeaderLine}}). The lab produces a real one:

```
{"type":"session","version":0,"id":"demo","createdAt":1786852223136,"delegationDepth":0}
{"type":"turn/start","seq":0,"time":…,"data":{"turn":1}}
{"type":"user/message","seq":1,…,"surfaceOp":"append"}
{"type":"assistant/chunk","seq":2,…}
{"type":"assistant/message","seq":3,…,"sourceEventSeqs":[2],"surfaceOp":"append"}
```

Three things to notice:

1. **`seq` is contiguous, chunks included.** Not one `assistant/chunk` is dropped, so a streamed response replays token by token.
2. **`surfaceOp` is on disk.** A reload does not have to guess which messages are on the surface; the log carries the answer.
3. **The header holds `version`.** The version mechanism works together with each event's `ignorable` marker ({{src:packages/session/session-persistence/src/coordinator.ts#L1061-L1066|assertEventsSupported}}):

```ts
for (const event of events) {
  if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue
  throw this.unsupported(meta, `session "${meta.id}" contains event type "${event.type}" (seq ${event.seq}) unknown to this harness and not marked ignorable; …`)
}
```

Meeting an unknown event type **refuses to load the whole session by default**, unless the writer explicitly marked it `ignorable: true`. The type definition's comment explains which way the default leans:

> defaulting to required means a forgotten marker over-refuses (an inconvenience) rather than silently resuming a gutted session.

A forgotten marker over-refuses, which is merely inconvenient; the other default would silently restore a gutted session, which is data corruption. The default falls on the inconvenient side.

Compression defaults to zstd, written as concatenated independent frames: one for the header, then one per durable batch. Listing decodes only the header frame. Runs of consecutive same-block chunks are packed into one line by default, measured at roughly 60% smaller.

## 8. What this means for building on it

`SessionEventMap` is **declaration-mergeable**. One statement in your plugin:

```ts
declare module '@deepseek-ai/dsh-session' {
  interface SessionEventMap {
    'memory/recall': { query: string; hits: string[] }
  }
}
```

adds an event type, and `append`'s type checking, persistence, and replay all cover it automatically. Because it is not in `SURFACE_EVENT_TYPES`, the compiler refuses a `surfaceOp` for it and it never reaches the model's history.

This route is directly usable for all three chapter 12 directions:

| Direction | Use |
|---|---|
| memory | record retrieval and writes as events, so a replay shows how memory was used |
| self-evolution | record policy changes as events; the log is the evolution trace |
| multi-agent | one session per agent; `parentSession` and `delegationDepth` are already in the header |

To make a record **reach** the model's view, only three types qualify today, and distinguishing origins through `user/message`'s `source` field is the established pattern (`agent.inject()` does exactly that).

## Summary

The two halves of "if the model saw it, it was recorded", each with its guarantor:

| Half | Guarantor | Mechanism |
|---|---|---|
| structure | `deriveMessages` + `surfaceOp` | derivation has one source; surface membership must be declared |
| time | `session-checkpoint-policy` | flush before the request and before tool execution; failure stops the chain |

The converse does not hold: not everything in the log is visible to the model. Chunks, turn boundaries, and compaction-shadowed messages all sit in the log and off the surface. **What is recorded is a superset of what the model sees**, and that gap is exactly the room compaction and replay operate in.

Three conclusions:

**Compaction is addition.** No function removes an event from a session log. What gets compacted is the derived value sent to the model. Human and model read different projections of the same log.

**The commit boundary is one line.** Every failure before `log.push` is fatal, every failure after it is contained. That line makes "did this event land" always answerable.

**`inject` declares access and ordering at once.** The `flush participants = false` moment in lab step 2 is the cheapest possible demonstration.

The next chapter covers the agent loop: who appends these events and in what order, and what states one turn passes through from receiving input to ending.
