# 会话日志：模型可见即已记录

一次对话在 DSH 里不是一个消息数组。它是一条只增不减的事件日志，**模型看到的消息历史是从这条日志派生出来的，不是另存一份**。

这个选择带来一句可以当成不变式来用的话：模型可见即已记录。它有两半含义，各由不同的代码保证。

- **结构上**：一条消息进不了模型的视野，除非它先以一条带标记的事件进了日志。派生函数没有第二个数据来源。
- **时间上**：请求发出之前，已提交的日志前缀必须先落盘。工具产生副作用之前也一样。

这一章走完这两半，并把「压缩」这件事讲清楚：DSH 的上下文压缩**不删除任何历史**，它只是让一段历史对模型不可见。

## 一、日志是唯一真相，消息是派生值

{{src:packages/core/session/src/types.ts#L236-L256|SessionEventMap}} 是事件词表。挑出这一章要用的几条：

| 事件 | 含义 | 模型能看见吗 |
|---|---|---|
| `turn/start` / `turn/end` | 一个轮次的开合 | 否 |
| `step/start` / `step/end` | 一个 step（一次模型调用 + 它请求的工具执行） | 否 |
| `user/message` | 用户消息（人打的、`inject()` 注入的、goal 续轮） | **是** |
| `assistant/chunk` | 流式原始分片 | 否 |
| `assistant/message` | 一个 step 拼装完的助手消息 | **是** |
| `tool/call` | 模型请求的一次工具调用 | 否 |
| `tool/result` | 一次工具调用的结果 | **是** |
| `todo/write` | 待办清单快照 | 否 |

右列只有三个「是」。这三个类型写死在 {{src:packages/core/session/src/surface.ts#L15-L28|SURFACE_EVENT_TYPES}}：

```ts
const SURFACE_EVENT_TYPES = new Set<string>([
  'user/message',
  'assistant/message',
  'tool/result',
])
```

派生函数 {{src:packages/core/session/src/surface.ts#L83-L114|deriveEventMessage}} 就是对这三个类型做一次 switch：

```ts
switch (event.type) {
  case 'user/message': {
    return event.data
  }
  case 'assistant/message': {
    if (event.data.message.content.length === 0) return null
    return event.data.message
  }
  case 'tool/result': {
    return event.data.message
  }
  default:
    return null
}
```

三个分支都是**原样返回事件里已经存好的那个 message 对象**，没有任何拼装、包装或改写。`user/message` 上方那段注释专门交代了这一点：

> Do NOT re-add per-type framing (e.g. `<context>`) here: framing is caller-owned.

给注入的上下文加 `<system-reminder>` 之类的外壳是**生产方的事**，在 append 的时候就已经烘进 `content` 里了。派生这一层保持纯粹的透传。

:::key 这条规矩为什么重要
如果派生时可以加工，那么日志里存的和模型收到的就不是同一个东西，重放一条日志得到的历史就可能和当初那次请求不一致。保持透传，日志就是可重放的。
:::

`assistant/message` 那个空内容判断是个真实的边界情况：一个撞上 max-tokens 的 step 会产出一条内容为空、只用来挂 usage 的助手消息。它进日志（因为 token 账要记），但不进模型历史（一条空的助手轮次会污染对话）。

## 二、surface：日志里哪些行模型能看见

光有类型还不够。DSH 要求**每一条 surface 事件在写入时显式声明自己怎么进入模型视野**，这个声明叫 `surfaceOp`。

先看类型层面怎么强制。{{src:packages/core/session/src/index.ts#L604-L608|append 的签名}}：

```ts
append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent] : []
): SessionEvent<T>
```

第三个参数是**条件元组**。写 `append('user/message', …)` 而不给第三个参数，TypeScript 直接报错；写 `append('turn/start', …, { surfaceOp: 'append' })` 也报错，因为那个位置的元组是空的。一个类型签名同时表达了「必须给」和「不许给」。

运行时的检查在 {{src:packages/core/session/src/surface.ts#L185-L208|surfaceOpOf}}，而且是对称的两条：

```ts
if (!isSurfaceEligibleType(event.type)) {
  if (raw.surfaceOp !== undefined) {
    throw new Error(`session event "${event.type}" is not surface-eligible and cannot carry surfaceOp`)
  }
  if (raw.sourceEventSeqs !== undefined) {
    throw new Error(`session event "${event.type}" is not surface-eligible and cannot carry sourceEventSeqs`)
  }
  return
}
const op = raw.surfaceOp
if (op === undefined) {
  throw new Error(`session event "${event.type}" is surface-eligible and requires a surfaceOp marker`)
}
```

**不合格的类型带了标记要报错，合格的类型没带标记也要报错。** 两个方向都堵死，surface 的成员关系就没有默认值可猜：任何一条消息事件都必须回答「你是追加还是替换」。

`surfaceOp` 只有两种取值：

- `'append'` 追加到 surface 末尾
- `{ op: 'replace', start, end }` 替换 surface 上从 `start` 到 `end` 的一整段

第二种就是压缩，第四节细讲。

## 三、append：一次提交做的七件事

{{src:packages/core/session/src/index.ts#L604-L655|Session.append}} 是整个数据面的入口。逐段拆：

```ts
const dataSnapshot = snapshotJsonValue(data)
if (dataSnapshot === undefined) {
  throw new Error(`session event "${type}" carries non-JSON-serializable data`)
}
```

`snapshotJsonValue` **一次遍历同时完成校验和拷贝**。这不是省事，是防一类具体攻击：如果先 `isJsonValue(data)` 校验、再 `structuredClone(data)` 拷贝，一个带 getter 的对象可以在第一次读时返回合法值、第二次读时返回别的东西。校验过的和存下来的就不是同一个值了。一次遍历读完就定型，这个缝隙不存在。

拒绝的东西包括 BigInt、函数、symbol、`undefined`、`-0`、非有限数、循环引用、稀疏数组，以及 Map / Set / Date / 类实例这些外来原型。本章实验会亲手撞一次。

```ts
const entry = attachments.get(this)
if (entry?.appending) {
  throw new Error('session append cannot reenter while another append is being published')
}
```

重入检查。一个 `session/event` 监听器如果在处理事件时又往同一个会话 append，seq 的分配和监听器快照就会交叉。直接拒绝。

```ts
const event = deepFreeze({
  type,
  seq: this.log.length,
  time: Date.now(),
  data: dataSnapshot,
  ...(surfaceMetadataSnapshot as { surfaceOp?: unknown; sourceEventSeqs?: unknown }),
} as unknown as SessionEvent<T>)
this.surfaceManager.validateNext(event as SessionEvent)
```

`seq = this.log.length`，所以 `events[i].seq === i` 永远成立，这条连续性契约是持久化和重放的地基。

`validateNext` 在**事件进日志之前**校验它能不能进 surface。校验失败就抛，日志一个字节都不变。

然后是最值得看的一段：

```ts
let callbacks: SessionCallback[] | undefined
const callbackArgs: unknown[] = [this, event]
if (entry !== undefined) {
  callbacks = collectSessionCallbacks(entry.emitCtx, [entry.carrier, 'session/event', ...callbackArgs])
}
this.log.push(event as SessionEvent)
this.eventsSnapshot = undefined
if (callbacks !== undefined && entry !== undefined) {
  invokeContainedSessionObservers(entry.emitCtx, 'session/event', entry.id, callbackArgs, callbacks)
}
```

**先解析监听器名单，再 push，最后才逐个调用。** 三步的顺序是刻意的。

{{src:packages/core/session/src/index.ts#L377-L379|collectSessionCallbacks}} 里那一句就是第 2 章讲的分发：

```ts
return [...ctx.events.dispatch('emit', args)] as SessionCallback[]
```

`dispatch` 会跑 Cordis 的内部校验（作用域过滤、上下文有效性）。这个校验有可能抛。放在 push 之前，它抛了日志就没变；放在 push 之后，日志已经改了却报了个错，调用方无从判断这条事件到底进没进去。

push 之后的调用则用了独立的容错。{{src:packages/core/session/src/index.ts#L382-L399|invokeContainedSessionObservers}}：

```ts
for (const callback of callbacks) {
  try {
    const returned: unknown = callback(...args)
    void Promise.resolve(returned).catch((error: unknown) => {
      ctx.logger.warn(`session "${id}": ${name} listener rejected: ${String(error)}`)
    })
  } catch (error: unknown) {
    ctx.logger.warn(`session "${id}": ${name} listener threw: ${String(error)}`)
  }
}
```

同步抛和异步 reject 都只记日志。理由在方法注释里：

> Once the event enters the log, the append is committed.

事件一旦进了日志就已经提交了。一个观察者失败不能让已提交的 append 变成失败，也不能让后面的观察者收不到这条事件。**提交边界画在 `log.push` 那一行**，前面的错误全都致命，后面的错误全都容纳。

## 四、压缩不删除历史

这是本章最重要的一节。

上下文满了要压缩，直觉做法是删掉早期消息。DSH 不这么做。压缩是**再 append 一条事件**，它的 `surfaceOp` 是 replace：

```ts
{ op: 'replace', start: 0, end: 3 }
```

日志继续变长，只是 surface 上那四个节点被这一条新节点顶掉了。{{src:packages/core/session/src/surface.ts#L362-L379|applySurfacePlan}} 就是一行 splice：

```ts
if (plan?.kind === 'append') {
  state.nodes.push(plan.seq)
} else if (plan?.kind === 'replace') {
  state.nodes.splice(plan.startIdx, plan.endIdx - plan.startIdx + 1, plan.seq)
  state.replaceGeneration += 1
}
```

替换要过三道校验，都在 {{src:packages/core/session/src/surface.ts#L321-L347|planSurfaceEvent}} 里串起来。

**第一道**，范围必须在当前 surface 上真实存在（{{src:packages/core/session/src/surface.ts#L246-L266|replacementRange}}）：

```ts
const startIdx = state.nodes.indexOf(op.start)
if (startIdx === -1) {
  throw new Error(`surface replace: start seq ${op.start} not found in surface`)
}
```

注意查的是 `state.nodes`（当前 surface）而不是日志。一个已经被前一次压缩顶掉的 seq，不能再被第二次压缩当作端点。

**第二道**，被遮蔽的节点必须一条不落地写进 `sourceEventSeqs`（{{src:packages/core/session/src/surface.ts#L211-L243|assertProvenance}}）：

```ts
const missing = shadowedSeqs.filter(seq => !sources.has(seq))
if (missing.length > 0) {
  throw new Error(`surface replace: sourceEventSeqs must include every shadowed surface node; missing ${missing.join(', ')}`)
}
```

这条把「这条摘要是从哪几条消息来的」变成了日志里的硬数据，而不是压缩插件私下知道的事。任何人拿到日志都能重建被遮蔽的那一段。

**第三道**只对 `tool/result` 生效（{{src:packages/core/session/src/surface.ts#L286-L318|assertToolResultRewrite}}）：它必须恰好替换一个当前节点，而且**除了 content 之外什么都不许改**。做法是把两边的 `content` 挖空再深比：

```ts
originalRest['message'] = {
  ...original.data.message,
  content: [{ ...originalResult, content: null }],
}
// ... 同样处理 replacementRest
if (!isDeepEqualJson(originalRest, replacementRest)) {
  throw new Error('tool/result surface replacement may change only content')
}
```

用途是工具结果裁剪：一个几万字的文件读取结果，压缩时换成一句「（内容已裁剪）」，但 `callId`、配对关系、错误标记全部原样。这样模型仍然看得到「这次调用发生过、成功了」，只是看不到内容。改到别的字段就会破坏工具调用与结果的配对，所以直接禁止。

### 两个 surface，两个读者

压缩带来一个问题：把四条消息换成一条摘要，对模型是对的，对**人**是错的。用户明明看见过那四条消息，界面上不能让它们消失。

DSH 的答案是 {{src:packages/core/session/src/surface.ts#L41-L55|isAppendSurfaceEvent}}，注释把这件事说得很清楚：

> The model-visible surface deliberately shadows replaced ranges, so it is the wrong source for a human transcript — a landed replacement would erase conversation the user already saw. Append-origin events are that transcript's durable source material; replacement copies stay model-only.

| 读者 | 数据来源 | 压缩后 |
|---|---|---|
| 模型 | `session.surface` | 看到摘要，看不到原文 |
| 人 | 日志里所有 `surfaceOp === 'append'` 的事件 | 看到原文，看不到摘要 |

两个投影读的是同一条日志，各取所需。这只有在「日志是唯一真相、消息是派生值」的前提下才成立。如果历史被真的删掉了，人机两边就只能二选一。

:::key 压缩是加法
`replaceGeneration` 只增不减，日志只长不短。DSH 里没有任何一个函数会从会话日志里删除事件。所谓「压缩上下文」压的是**发给模型的那份派生结果**，不是存储。
:::

## 五、三个 fold 长得一样

日志会长到几万条事件。每次要历史都从头折叠一遍显然不行，所以 surface、消息、请求头各有一份增量缓存。三处的形状是一样的：**一个游标 + 一个失效条件**。

surface 的游标是 `_lastProcessedSeq`（{{src:packages/core/session/src/surface.ts#L398-L459|SurfaceManager}}）：

```ts
private _processDelta(): void {
  const tailSeq = this.baseSeq + this.log.length - 1
  for (let seq = this._lastProcessedSeq + 1; seq <= tailSeq; seq++) {
    ...
  }
}
```

三个 getter（`nodes`、`replaceGeneration`）在读之前都先判断游标是否落后，落后就补折叠。

消息缓存有两个游标（{{src:packages/core/session/src/index.ts#L726-L747|deriveMessages}}）：

```ts
if (generation !== this.derivedGeneration) {
  this.derived = []
  this.derivedNodes = 0
  this.derivedGeneration = generation
}
for (const seq of nodes.slice(this.derivedNodes)) {
  const msg = this.deriveEventMessage(this.log[seq]!)
  if (msg) this.derived.push(msg)
}
this.derivedNodes = nodes.length
return [...this.derived]
```

`derivedNodes` 是增量游标，`derivedGeneration` 是失效条件：**一次 replace 会让整份消息缓存作废重建**，因为 splice 改的是中间位置，增量续不上。追加则只投影新增的那几个节点。

最后一行 `return [...this.derived]` 每次返回一个新数组。注释解释了原因：调用方已经拿到的数组不能因为后续 append 而变长。数组是新的，里面的 `Message` 对象是共享且深冻结的，所以不需要第二次深拷贝。

请求头的 fold（{{src:packages/core/session/src/index.ts#L670-L680|requestHeader}}）同样是游标 + 只折叠增量。它多做一件事：

```ts
this.headerFold = deepFreeze(foldRequestHeader(this.log.slice(this.headerFoldSeq), this.headerFold))
```

折叠结果**冻结后**才存。注释说明了理由：这是按引用暴露出去的会话状态，如果调用方原地改它而不是构造一个替换值，后面每一次和日志的比较都会错位。

## 六、「已记录」是什么时候记录的

`append` 是同步的，而且不碰磁盘。它返回时事件只在内存里。真正落盘由两层负责。

### 写回：默认攒 200 毫秒

{{src:packages/session/session-persistence/src/coordinator.ts#L1086-L1137|installWritePath}} 把持久化插件挂到会话事件上：

```ts
ctx.on('session/created', (session) => { void this.initFor(session) })
ctx.on('session/event', (session, event) => {
  const live = this.initFor(session)
  live.writes.enqueue(event)
})
ctx.on('session/flush', session => this.flush(session))
ctx.on('session/disposed', (session) => { this.retire(session) })
```

四行监听，就是持久化插件和 core 之间的全部接口。这个函数开头还有一处第 1 章的知识点：

```ts
// Register the disposer BEFORE the listeners. Cordis tears effects down in
// reverse registration order, so event admission closes before this final
// drain reaches quiescence and closes the backend.
ctx.effect(() => async () => { ... })
```

**先注册清理，再注册监听。** 因为 effect 是倒序清理的，这个顺序保证卸载时先关掉事件接收，再做最后一次排空。反过来的话，最后那次排空进行到一半还可能有新事件涌进来。

{{src:packages/session/session-persistence/src/write-behind.ts#L45-L56|enqueue}} 里 `structuredClone(event)`，持久化持有的是自己的副本。窗口是固定的：

```ts
enqueue(event: SessionEvent): void {
  const wasEmpty = this.pending.length === 0
  this.pending.push(structuredClone(event))
  if (this.barrier !== undefined) return
  ...
  } else if (wasEmpty) {
    this.armTimer()
  }
}
```

只在**队列从空变非空**时起表。后续事件不重置它，所以 200 毫秒是攒批的上界而不是「最后一个事件之后再等 200 毫秒」。

失败处理在 {{src:packages/session/session-persistence/src/write-behind.ts#L139-L158|startWrite}}：

```ts
const batch = this.pending.splice(0)
...
.catch((error: unknown) => {
  this.pending = batch.concat(this.pending)
  ...
})
```

写失败时把整批**放回队首**，`batch.concat(this.pending)` 而不是反过来。日志是有序的，一批写失败后如果让新事件排到它前面，磁盘上的 seq 就断了。

### 检查点：三个语义边界

写回是尽力而为的。真正的「已记录」保证由 {{src:packages/session/session-checkpoint-policy/src/index.ts#L63-L83|session-checkpoint-policy}} 提供，整个插件只有三个监听：

```ts
ctx.on('llm/stream', (options, next): AsyncIterable<StreamChunk> => {
  if (options.sessionId === undefined) return next()
  const session = ctx.sessions.get(options.sessionId)
  return session === undefined ? next() : afterCheckpoint(ctx, session, next)
})

ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  if (exec.agent === undefined || exec.parent !== undefined) return next()
  await ctx.sessions.flush(exec.agent.session)
  if (exec.signal.aborted) return abortedBeforeDispatchResult()
  return next()
})

ctx.on('agent/pre-step', async ({ agent }, next): Promise<PreStepDecision> => {
  await ctx.sessions.flush(agent.session)
  return next()
})
```

三处都是第 2 章讲的 **waterfall 洋葱**，而且都是**前置**加工：先 flush，再 `next()`。第 3 章的 `internal/config` 是后置加工（先 `next()` 再处理结果），这里是另一半。

第一个监听就是本章标题那句话的实现。{{src:packages/session/session-checkpoint-policy/src/index.ts#L29-L38|afterCheckpoint}}：

```ts
return (async function* (): AsyncIterable<StreamChunk> {
  await ctx.sessions.flush(session)
  yield* next()
})()
```

包一层生成器，把 flush 塞在**第一个 chunk 被索取之前**。请求要发出去，日志前缀必须先落盘。flush 抛错，`yield*` 就到不了，适配器根本不会被调用。

第二个监听同理，只是把边界画在工具副作用之前，且只对顶层调用生效（`exec.parent !== undefined` 直接放行，嵌套调用复用外层已经做过的检查点）。

:::key fail-closed
两处都是「检查点失败就不往下走」。落盘失败时宁可这次请求不发、这个工具不跑，也不让一个日志里没有的动作真的发生。这是「模型可见即已记录」的时间那一半。
:::

`session/flush` 的分发模式是 **parallel**，第 2 章五种模式里的一种。{{src:packages/core/session/src/index.ts#L1022-L1039|SessionStore.flush}}：

```ts
const results = await Promise.allSettled(callbacks.map((callback) => {
  try {
    return callback(...callbackArgs)
  } catch (error: unknown) {
    return Promise.reject(error)
  }
}))
const failure = results.find((result): result is PromiseRejectedResult => result.status === 'rejected')
if (failure !== undefined) throw failure.reason
```

每个监听器都会被启动，全部 settle 之后才报第一个失败。同步抛的监听器被转成 rejected promise，和异步失败走同一条路。这和第 3 章 `EntryGroup.update` 用 `allSettled` 的理由是同一个：不能让第一个失败把其他人晾在半路。

## 七、落盘长什么样

JSONL 后端每个会话一个文件，第一行是头，之后每行一条事件（{{src:packages/session/session-persistence-jsonl/src/format.ts#L30-L44|HeaderLine}}）。本章实验会生成一个真的，长这样：

```
{"type":"session","version":0,"id":"demo","createdAt":1786852223136,"delegationDepth":0}
{"type":"turn/start","seq":0,"time":…,"data":{"turn":1}}
{"type":"user/message","seq":1,…,"surfaceOp":"append"}
{"type":"assistant/chunk","seq":2,…}
{"type":"assistant/message","seq":3,…,"sourceEventSeqs":[2],"surfaceOp":"append"}
```

三点值得注意：

1. **`seq` 连续，包括 chunk。** `assistant/chunk` 一条不丢，所以一次流式输出可以逐 token 重放。
2. **`surfaceOp` 落在磁盘上。** 重新加载时不需要猜哪条消息在 surface 上，日志自己带着答案。
3. **头里有 `version`。** 版本机制配合每条事件的 `ignorable` 标记工作（{{src:packages/session/session-persistence/src/coordinator.ts#L1061-L1066|assertEventsSupported}}）：

```ts
for (const event of events) {
  if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue
  throw this.unsupported(meta, `session "${meta.id}" contains event type "${event.type}" (seq ${event.seq}) unknown to this harness and not marked ignorable; …`)
}
```

碰到不认识的事件类型，**默认是拒绝加载整个会话**，除非写入方明确标了 `ignorable: true`。类型定义里的注释解释了这个默认值的方向：

> defaulting to required means a forgotten marker over-refuses (an inconvenience) rather than silently resuming a gutted session.

漏标记会导致过度拒绝，那只是不方便；反过来会静默恢复出一个残缺的会话，那是数据错误。默认值往不方便的那边倒。

默认压缩是 zstd，一个个独立帧拼起来：头一帧，之后每次持久化写入一帧。列表操作只解头帧就够了。默认还会把连续的同类 chunk 打包成一行，实测能省约 60% 体积。

## 八、这对二次开发意味着什么

`SessionEventMap` 是**可声明合并**的。你的插件写一句：

```ts
declare module '@deepseek-ai/dsh-session' {
  interface SessionEventMap {
    'memory/recall': { query: string; hits: string[] }
  }
}
```

就多了一个事件类型，`append` 的类型检查、持久化、重放全部自动覆盖。因为它不在 `SURFACE_EVENT_TYPES` 里，编译器会拒绝你给它传 `surfaceOp`，它也就不会出现在模型历史里。

这条路对第 12 章的三个方向都直接可用：

| 方向 | 用法 |
|---|---|
| 记忆机制 | 检索和写入各记一个事件，重放时能看清记忆是怎么被用的 |
| 自进化 | 策略变更记成事件，日志本身就是演化轨迹 |
| 多智能体 | 每个 agent 一个 session，`parentSession` 和 `delegationDepth` 已经在头里 |

需要让某条记录**进入**模型视野的话，目前只有三个类型能进，走 `user/message` 的 `source` 字段区分来源是既有做法（`agent.inject()` 就是这么干的）。

## 小结

「模型可见即已记录」的两半，各由一处代码保证：

| 半 | 保证者 | 机制 |
|---|---|---|
| 结构 | `deriveMessages` + `surfaceOp` | 派生只有 surface 一个来源，surface 成员必须显式声明 |
| 时间 | `session-checkpoint-policy` | 请求发出前、工具执行前先 flush，失败就不往下走 |

反过来不成立：日志里的东西模型不一定看得到。chunk、轮次边界、被压缩遮蔽的消息都在日志里躺着，但不在 surface 上。**记录是模型可见的超集**，这个方向差正是压缩和重放能工作的空间。

三个结论：

**压缩是加法。** 没有任何函数会从会话日志里删事件。压的是发给模型的派生结果。人机两边读同一条日志的不同投影。

**提交边界画在一行上。** `log.push` 之前的失败全部致命，之后的失败全部容纳。这条线让「事件到底进没进日志」永远有确定答案。

**`inject` 同时是访问声明和时序声明。** 实验第 2 步那个 `flush 参与者 = false` 是最便宜的一次演示。

下一章讲 Agent Loop：这些事件是被谁、按什么顺序 append 的，一次轮次从收到输入到结束经过哪些状态。
