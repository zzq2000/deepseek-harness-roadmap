# Tool registry and the guarded pipeline

Chapter 5 covered how the loop schedules tool calls into the log; chapter 6 covered why tool arguments stay raw JSON strings. This chapter covers the segment in between: what a `tool-call` block passes through between leaving the model's mouth and landing in the log as a `tool/result`.

The answer is seven gates. Lab step 3 prints them one by one:

```
=== one normal call (text="hi") ===
   1. tools/pre-execute  name=echo args={"text":"hi"}
   2. guard  name=echo
   3. tools/execute (before)
   4. the tool body execute()
   5. tools/execute (after) isError=false
   6. tools/post-execute  isError=false
   7. tools/result (emit, read-only) isError=false frozen=true
   → isError=false content=[{"type":"text","text":"HI"}]
```

"Guarded" means something specific, and this chapter takes it apart in three layers:

- **Guarding the model**: arguments, return value, and rendering are all validated, and any violation becomes a structured `isError` result rather than a throw.
- **Guarding the deployment**: two admission levels (`pre-execute` and guards), `restrict` trimming the visible tool set per agent, and `ask` degrading to denial when no approval service is mounted.
- **Guarding the loop**: this pipeline **never throws**. Chapter 5's "tools run concurrently but commit in model order" only holds because every call is guaranteed to produce a result.

## 1. defineTool: one declaration, four uses

{{src:packages/core/tools/src/schema.ts#L545-L617|defineTool()}} takes a compact declaration and produces a `ToolDefinition`. Lab step 1 registers this one:

```js
defineTool({
  name: 'grep',
  description: 'Search files for a pattern.',
  parameters: {
    pattern: { type: 'string', required: true, description: 'the regex to search for' },
    path: { type: 'string', description: 'directory to search in' },
    maxResults: { type: 'number' },
  },
  output: {
    schema: { type: 'object', additionalProperties: false, properties: {
      matches: { type: 'array', required: true, items: { type: 'string' } },
      truncated: { type: 'boolean' },
    } },
    render: (_args, v) => [{ type: 'text', text: v.matches.join('\n') || '(no matches)' }],
  },
  execute: async (args) => ({ matches: [`a.ts: ${args.pattern}`], truncated: false }),
})
```

`parameters` writes `required: true` on each property, and what compiles out is a standard JSON Schema `required` array:

```json
{
  "type": "object",
  "properties": {
    "pattern": { "type": "string", "description": "the regex to search for" },
    "path": { "type": "string", "description": "directory to search in" },
    "maxResults": { "type": "number" }
  },
  "required": ["pattern"]
}
```

That JSON is exactly what chapter 6's `GenerateOptions.tools` sends to the model. {{src:packages/core/tools/src/schema.ts#L449-L458|parameterSchemaSpecToJsonSchema()}} performs the conversion.

One declaration has four consumers:

| Field | Who uses it |
|---|---|
| `parameters` | the schema sent to the model, and the argument validator at the `execute` entry |
| `output.schema` | what the registry validates the tool's **return value** against |
| `output.render` | projects the structured return value into the `ContentBlock[]` the model sees |
| `output.presentationMeta` / `presentCall` / `presentResult` | UI presentation: pure functions, recomputable on replay |

Note that `additionalProperties: false` in `output.schema` is not optional. Omit it and registration fails outright:

```
unsupported JSON schema: schema.additionalProperties must be explicitly true or false
```

And the failure happens **at load**, taking down the whole plugin tree (chapter 3's `EntryGroup.update` full rollback). This is the repo's "misconfiguration fails loud at load when self-contained" rule made concrete: a broken schema is a self-contained error and should not wait for the model's first call to detonate.

### Validation lives at the `execute` entry, not in the registry

The `execute` that `defineTool` generates is a wrapper:

```ts
async execute(args: unknown, exec: ToolRunContext): Promise<JsonValue> {
  const violations = validate(args)
  if (violations.length > 0) throw new ToolArgsError(violations)
  return userExecute(args as InferArgs<S>, exec) as Promise<JsonValue>
},
```

Argument validation is **the tool's own job**, not the registry's. `ToolDefinition`'s JSDoc states it: the registry hands arguments to `execute` as-is, and the tool validates its own schema. Why split it that way? Because a tool need not use `defineTool` at all: hand-writing a `ToolDefinition` is perfectly legal, and such a tool decides its own validation. The registry only forces it to declare `output`.

### Presentation projections never throw

The same `validate` is used differently on the presentation path:

```ts
// Presentation is display-only and may run on REPLAY of arbitrary logged args
// (possibly from an older schema), so it must never throw: validate softly and
// fall back to `undefined` (a generic UI presentation) on any mismatch, rather
// than the hard `ToolArgsError` the execute path raises.
if (userPresentCall) {
  tool.presentCall = (args: unknown): ToolCallView | undefined => {
    if (validate(args).length > 0) return undefined
    return userPresentCall(args as InferArgs<S>)
  }
}
```

The execution path throws on a validation failure; the presentation path returns `undefined`. The comment gives the reason: presentation runs on **replay** against arguments in historical logs, which may come from an older version of the schema. A log from a year ago will not validate against today's schema, yet it should still be displayable.

## 2. Three validations, five failures

Lab step 2 runs five failures side by side. All of them return `isError` results; none reaches the caller as a throw:

```
[missing required argument]
  error = {"message":"invalid arguments: missing required property \"pattern\"",
           "info":{"name":"ToolArgsError","code":"INVALID_ARGS"}}

[wrong argument type]
  error = {"message":"invalid arguments: \"pattern\" must be a string", ... "code":"INVALID_ARGS"}

[tool violates its own output schema]
  error = {"message":"tool \"liar\" returned invalid output: \"value.matches\" must be an array;
           \"value.extra\" is not a declared property (additionalProperties: false)",
           "info":{"name":"ToolOutputError","code":"INVALID_TOOL_OUTPUT"}}

[render throws]
  error = {"message":"tool \"badrender\" returned invalid output: output.render failed: render blew up",
           "info":{"name":"ToolOutputError","code":"INVALID_TOOL_OUTPUT"}}

[unregistered tool]
  error = {"message":"unknown tool \"nope\"","info":{"name":"ToolNotFoundError","code":"UNKNOWN_TOOL"}}
```

The third and fourth come from {{src:packages/core/tools/src/index.ts#L1793-L1823|createSuccessResult()}}, the gate every tool body's return value passes:

```ts
private createSuccessResult(exec: ToolExecution, tool: ToolDefinition, candidate: unknown): ToolExecutionSuccess {
  const detached = snapshotToolValue(tool.name, candidate)
  const violations = validateJsonSchemaValue(tool.output.schema, detached, 'value')
  if (violations.length > 0) throw new ToolOutputError(tool.name, violations)
  const value = deepFreeze(detached)
  let rendered: ContentBlock[]
  try {
    rendered = tool.output.render(exec.arguments, value)
  } catch (error: unknown) {
    throw projectionError(tool.name, 'render', error)
  }
  const content = snapshotProjection(tool.name, 'render', rendered)
  ...
}
```

Four steps: **snapshot** (detaching from references the tool may still hold), **validate**, **freeze**, **project**. The order cannot change. Snapshotting first guarantees that what was validated is what gets used; freezing before `render` means `render` cannot alter it.

`presentationMeta` is computed only for top-level calls:

```ts
if (exec.parent === undefined && tool.output.presentationMeta !== undefined) {
```

A set `exec.parent` means this is a nested sub-call inside `run_code`, which has no place in the UI, so computing it would produce something nobody sees.

:::key A tool's return value is not trusted
Tools are written by plugins, `output.schema` is declared by the tool itself, and the registry validates the tool against its own declaration. This guards against drift, not malice: a tool that changes its return structure and forgets its schema surfaces as `INVALID_TOOL_OUTPUT` on the first call, instead of pushing an object the model cannot read into the log.
:::

## 3. The order of the seven gates, and where each denial stops

The pipeline's skeleton is {{src:packages/core/tools/src/index.ts#L1342-L1344|execute()}}, one line dividing the work into three stages:

```ts
async execute(exec: ToolExecutionInput): Promise<ToolExecutionResult> {
  return this.prepareExecution(exec, prepared => this.completeScheduledExecution(prepared))
}
```

Admission is {{src:packages/core/tools/src/index.ts#L1463-L1507|prepareExecution()}}, dispatch is `dispatchScheduledExecution()`, and settlement is `finalizeScheduledExecution()`. The split into three exists so an external scheduler (`TOOL_RUNTIME_SCHEDULER`) can drive the stages individually; `execute()` is the convenience entry that chains them.

The admission segment is this section's subject:

```ts
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)
const askResolution: ToolAskResolution = gate.kind === 'ask'
  ? await this.serviceAsk(exec, gate)
  : { decision: gate, approvalCancelled: false }
const { decision } = askResolution
if (this.callerCancelled(exec) && askResolution.approvalCancelled) {
  return await next({ kind: 'post-result', exec, result: toolAbortedBeforeDispatchResult() })
}
const denialReason = decision.kind === 'allow'
  ? this.guardReason(exec)
  : decision.reason
if (denialReason !== undefined) { ... }
```

Three judgments in order: the waterfall's verdict, approval's verdict, the guards' verdict. The last condition is worth reading closely: **only an `allow` consults the guards**. An already-denied call needs no second opinion, and guards have no power to overturn one.

Lab step 3's output marks where each path stops:

| Scenario | Gates reached | Skipped |
|---|---|---|
| normal | 1→2→3→4→5→6→7 | nothing |
| `pre-execute` denies | 1→6→7 | guards, `tools/execute`, the body |
| a guard denies | 1→2→6→7 | `tools/execute`, the body |
| `ask` with no approval service | 1→6→7 | same as a pre-execute denial |
| `post-execute` blocks | 1→2→3→4→5→6→7 | nothing, but the result becomes `isError` |

One invariant: **however a call is denied, `post-execute` and `tools/result` still run**. A denial is a result too, and observers (audit, billing, UI) see it.

### What separates a guard from pre-execute

Both can deny; they differ in power:

```ts
/**
 * Register a monotonic guard after the extensible `tools/pre-execute`
 * waterfall. A plain-context guard applies globally; one registered through
 * `agent.ctx` applies only to that agent. Any matching guard may deny by
 * returning a reason, while no guard can force-allow a call another guard
 * denied.
 */
guard(guard: ToolGuard): () => void {
```

**Monotonic** is the key word: a guard can only deny, never allow. {{src:packages/core/tools/src/index.ts#L1119-L1128|guardReason()}} walks the global layer then the scope chain, stopping at the first string returned:

```ts
private guardReason(exec: ToolExecution): string | undefined {
  const globalReason = this.layers.global.guardReason(exec)
  if (globalReason !== undefined) return globalReason
  if (exec.agent === undefined) return undefined
  for (const layer of this.layers.chainLayers(exec.agent)) {
    const reason = layer.guardReason(exec)
    if (reason !== undefined) return reason
  }
  return undefined
}
```

`tools/pre-execute`, by contrast, is a waterfall: a listener that does not call `next()` decides for everyone, including **allowing** for everyone. So the two have different jobs: policy negotiation goes in pre-execute, hard prohibition goes in a guard. Chapter 9's security boundary lands almost entirely on guards.

`guard()` also passes one extra option:

```ts
{ label: 'tools.guard()', notify: false }
```

`notify: false` means registering a guard **does not fire `tools/change`**. A guard does not change tool visibility, the schema list the model sees is unchanged, and there is no reason to make every agent reassemble its prompt. `register()` and `restrict()` both do fire it.

### ask degrades to denial

{{src:packages/core/tools/src/index.ts#L1689-L1729|serviceAsk()}} handles `{ kind: 'ask' }`:

```ts
const approval = this.ctx.get('approval')
if (approval === undefined) {
  return {
    decision: { kind: 'deny', reason: ask.reason ?? `tool "${exec.name}" requires approval (not yet supported)` },
    approvalCancelled: false,
  }
}
```

`ctx.get('approval')` rather than a declared injection, because the approval service is optional (chapter 2 covered the difference between the two reads). Without it, `ask` becomes `deny`. That is fail-closed: a call that says "a human must confirm this" must never allow itself in a deployment where nobody can confirm.

With the service present, four outcomes map to three distinct denial reasons:

```ts
case 'allowed-once': return { decision: { kind: 'allow' }, approvalCancelled: false }
case 'rejected': return { decision: { kind: 'deny', reason: `the user rejected tool "${exec.name}"` }, ... }
case 'cancelled': return { decision: { kind: 'deny', reason: `approval for tool "${exec.name}" was cancelled` }, approvalCancelled: true }
case 'unavailable': return { decision: { kind: 'deny', reason: `tool "${exec.name}" requires approval, but no approval channel is available` }, ... }
```

The JSDoc explains why the wording differs: `so the model can tell a human "no" from an absent approval channel`. A human explicitly saying no and there being nobody to ask should lead the model to different next steps. The first calls for a different approach; the second calls for telling the user this deployment has no approval channel configured.

## 4. The registry is layered

`ToolRuntime` uses the same `ScopedLayers` as chapter 7: one global layer plus per-agent scoped layers.

{{src:packages/core/tools/src/index.ts#L1037-L1062|register()}} files into the **caller's scope**: the global `ctx` registers a global tool, and `agent.ctx` registers one belonging to that agent alone. Lab step 5 verifies the same-name behavior:

```
[duplicate registration in one layer]
  tool "read" is already registered (for a per-agent variant, register through that agent's `agent.ctx` instead)
[same-name shadow in the agent layer] no error
```

A duplicate in one layer throws; the same name across layers is **shadowing**. The same pattern as chapter 7's `PERSONA_SECTION`.

### restrict trims only what is inherited

{{src:packages/core/tools/src/index.ts#L1071-L1098|restrict()}} has four validations, and lab step 5 triggers all of them:

```
[restrict on the global ctx]
  tools.restrict() requires a scoped context (agent.ctx): a context-global restriction
  would mask every agent — deny the tool for the intended agent instead
[empty filter]
  tools.restrict({}) is a no-op: pass `allow` and/or `deny`
  (an empty filter is almost always a materialized-empty-config bug)
[restricting a name that does not exist]
  tools.restrict() names unknown global tool "nosuch"; known global tools: read
[restricting the reserved run_code]
  tools.restrict() cannot name reserved Code Mode presentation transport "run_code";
  restrict end-capability tools instead
```

The second one's phrase, "an empty filter is almost always a materialized-empty-config bug", is worth remembering: `restrict({})` is syntactically legal and semantically harmless, yet it is almost always the symptom of a config field materialized to an empty object. Better to fail than to silently do nothing.

The genuinely subtle part is the comment on {{src:packages/core/tools/src/index.ts#L1152-L1193|view()}}, which records a failure that actually happened:

> A restriction filters what a scope inherits — the global layer and every ancestor layer on its chain — and never what its OWN layer registers. That exemption is what a per-child capability filter has to keep intact: the delegation runtime registers a child's reporting and structured-output tools into the child's own layer, and a filter naming the capabilities the child may use must not strip the machinery it answers through.
>
> Reading the exempt set as "the global layer" instead of "not mine" held only while every model-facing tool sat in the host composition. Once presets moved them onto the agent plane they became an ANCESTOR contribution, so a child's filter silently stopped constraining anything it was given.

A restriction applies to what is inherited; what is exempt is what the scope registers itself. An earlier implementation read the exempt set as "the global layer", which is equivalent as long as every model-facing tool lives in the host composition. Once agent presets moved tools onto the agent plane, they became an **ancestor** contribution, and a subagent's capability filter **silently stopped constraining anything**. Chapter 10 returns to this when it covers subagents.

### A restricted tool does not exist, as far as the model is concerned

Lab step 4:

```
--- after restrict({deny:[bash,write]}) ---
   agent : flaky, read, search, slow
   global: bash, flaky, read, search, slow, write
   get("bash") in the agent = undefined
   the agent calls bash → {"message":"unknown tool \"bash\"","info":{"name":"ToolNotFoundError","code":"UNKNOWN_TOOL"}}
```

Not "you are not permitted to call bash", but `unknown tool "bash"`. It is absent from the schema list, and calling it errors exactly like calling a misspelled name. The model has no way to infer from the error that this deployment has bash and merely withholds it.

There is one deliberate exception: the Code Mode collapse. In {{src:packages/core/tools/src/index.ts#L1364-L1451|createExecution()}}:

```ts
// The name IS visible here, so the denial carries the route the model
// must take instead. Without it the model reads a bare `unknown tool`
// for a tool the prompt just declared and concludes the deployment is
// broken rather than correcting itself.
return {
  kind: 'final-result',
  exec: execution,
  result: toolErrorResult(new ToolNotFoundError(
    name,
    `only \`${RUN_CODE_NAME}\` is callable directly — call \`${name}\` from inside a \`${RUN_CODE_NAME}\` program instead`,
  )),
}
```

The name did appear in the prompt; it just cannot be called directly. A bare `unknown tool` here would make the model conclude the deployment is broken rather than correct its own calling convention. So this denial **carries the right route**.

A comment just above explains why the collapse terminates **before** the pipeline:

> A collapsed call is deterministically denied, so it terminates BEFORE the extensible policy pipeline: pre-execute listeners, approval `ask`, and guards must never observe — or worse, approve — a call that can only fail.

A call doomed to fail should never reach approval. Otherwise the user is asked "allow bash?", clicks allow, and the call fails anyway.

## 5. tools/execute wrappers: who owns the signal

{{src:packages/guard/timeout-policy/src/index.ts#L55-L81|timeout-policy}} is 27 lines and is the model `tools/execute` wrapper:

```ts
ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs
  if (timeoutMs === undefined) return next()

  using d = deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)
  const upstream = exec.signal
  exec.signal = d.signal
  try {
    const result = await next()
    if (timeoutOf(d.signal, TOOL_TIMEOUT) !== undefined) {
      return toolTimeoutResult(timeoutMs)
    }
    return result
  } finally {
    exec.signal = upstream
  }
})
```

Four things, each matching one clause of the event contract.

**One: only `exec.signal` may change.** The event JSDoc: `wrappers may change only exec.signal, while call identity remains immutable`. callId, name, and arguments are off limits. Changing identity forges a call.

**Two: it must be restored.** `exec.signal = upstream` in the `finally`. The comment says why: `so post-execute listeners never see this plugin's (possibly already-aborted) timeout signal`. A post-execute listener handed an already-aborted signal would conclude the whole call was cancelled.

**Three: the registry fuses the caller's original signal back in.** A wrapper cannot undo this:

```ts
/**
 * Dispatch the registered body with the original caller signal fused back
 * into any around-wrapper replacement. Cancellation never abandons the body:
 * a started promise reaches quiescence before its outcome becomes `ABORTED`.
 */
private async dispatchToolBody(exec: MutableToolRunContext): Promise<ToolExecutionResult> {
  const state = this.cancellationStates.get(exec)
  const wrapperSignal = exec.signal
  const fused = fuseToolSignals(state.callerSignal, wrapperSignal)
  const signal = fused.signal
```

{{src:packages/core/tools/src/index.ts#L1532-L1560|dispatchToolBody()}} fuses the wrapper's signal with the **original caller signal**. The event declaration states it: `The registry re-fuses the original caller signal before the body, so replacement cannot detach caller cancellation`. A wrapper cannot make a tool deaf to the user's cancel by swapping the signal.

**Four: replace the result only when its own timer fired.** `timeoutOf(d.signal, TOOL_TIMEOUT)` tests by **code**:

```ts
/**
 * The code owned by this plugin, used BOTH as the internal deadline
 * classification code AND as the structured error `code` on the replacement
 * tool result. Scoping timeoutOf to it keeps a nested outer deadline
 * (another `tools/execute` wrapper's timer that fired first) from being misread
 * as this plugin's own timeout — it reads as an ordinary upstream cancel.
 */
```

When two timeout wrappers nest, the outer timer fires first, and the inner one must not report it as its own timeout. Testing by code lets each wrapper recognize only its own.

Lab step 4's result: a tool body that sleeps 3000ms and declares `timeoutMs: 200` returns in 203ms with:

```
{"isError":true,"error":{"message":"tool call timed out after 200ms",
 "info":{"name":"ToolTimeoutError","code":"TOOL_TIMEOUT"}}}
```

Note that the tool body itself **returned normally** (it observes `exec.signal` and, once aborted, does `return 'finished anyway'`). The wrapper saw its own timer fire and replaced that return value with the structured timeout. The tool's promise was neither abandoned nor raced, which is the comment's `without racing or abandoning the tool promise`.

## 6. Result normalization: canonicalResults

A `tools/execute` wrapper may **replace the result**, not just the signal. That raises a question: does a success result a wrapper fabricated bypass section 2's `output.schema` validation?

It does not. {{src:packages/core/tools/src/index.ts#L1826-L1844|normalizeDispatchResult()}}:

```ts
private normalizeDispatchResult(exec: ToolExecution, result: ToolExecutionResult): ToolExecutionResult {
  if (this.canonicalResults.get(result) === exec.token) return result
  if (result.isError) { ... }
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (tool === undefined) throw new ToolNotFoundError(exec.name)
  const normalized = this.createSuccessResult(exec, tool, result.value)
  ...
}
```

The first line consults a `WeakMap<object, ToolExecutionToken>`: results the registry built itself are stamped by {{src:packages/core/tools/src/index.ts#L1787-L1790|markCanonical()}} with this execution's token. A returned result that the registry did **not** build (a fresh object from a wrapper) goes through `createSuccessResult` again, meaning revalidation and re-rendering.

The key is worth looking at:

```ts
private markCanonical<T extends ToolExecutionResult>(exec: ToolExecution, result: T): T {
  this.canonicalResults.set(result, exec.token)
  return result
}
```

What it records is "this result object belongs to **this** execution", not "this result object is canonical". The token is minted with `Symbol()` in {{src:packages/core/tools/src/index.ts#L1364-L1451|createExecution()}} and differs on every execution. So a wrapper that caches a previous call's result object and returns it fails the token check and is revalidated.

`tools/post-execute`'s `accept` may also carry a `value` to replace the return value, and it likewise goes through `createSuccessResult`:

```ts
if (Object.hasOwn(decision, 'value')) {
  if (result.isError) {
    throw new TypeError('tools/post-execute cannot replace the value of a failed result')
  }
  ...
  const replaced = this.createSuccessResult(exec, tool, decision.value)
```

The `Object.hasOwn(decision, 'content') && Object.hasOwn(decision, 'value')` check lives in the same function: replacing both is refused, because `content` is a projection of `value` and supplying both is self-contradictory.

The last gate is {{src:packages/core/tools/src/index.ts#L1847-L1862|materializeFinalResult()}}, which freezes the result before `tools/result`. The `frozen=true` printed in lab step 3 is that. Observers can only look.

## 7. Cancellation: whether the body started decides the code

The pipeline has two cancellation constants:

```ts
export const TOOL_ABORTED = 'ABORTED'
export const TOOL_ABORTED_BEFORE_DISPATCH = 'ABORTED_BEFORE_DISPATCH'
```

Which one applies is decided by one line in {{src:packages/core/tools/src/index.ts#L1518-L1525|cancellationResult()}}:

```ts
return state.bodyInvoked
  ? toolAbortedResult(prior)
  : toolAbortedBeforeDispatchResult(prior)
```

`bodyInvoked` is set in `dispatchToolBody` immediately before `tool.execute()`. The distinction has real consequences: **`ABORTED_BEFORE_DISPATCH` means this tool produced no side effects**, so replay and retry may safely treat it as never having happened; `ABORTED` means part of the body ran and its side effects are unknown.

`execute()`'s JSDoc states the whole cancellation contract:

> Cancellation arriving after entry and before final result materialization skips a not-yet-started body with `ABORTED_BEFORE_DISPATCH` or replaces a successful started outcome with `ABORTED`; already-started work is still drained and may retain a tool-owned structured error.

Three clauses, three rules. The last is the important one: **already-started work is still awaited to completion**. This layer never races and never abandons a promise. Chapter 5's "when cancellation arrives after a tool has started, `runGroup` drains the started calls and commits their results normally" rests on exactly this.

Note also the `!postResult.isError` condition:

```ts
this.callerCancelled(exec) && !postResult.isError
  ? this.cancellationResult(exec, postResult)
  : postResult,
```

Cancellation replaces only **successful** results. A structured error the tool reported itself survives, because it carries more information than "cancelled".

## 8. Concurrency: exclusive by default

Chapter 5 walked the loop-side scheduling. Here is the one missing criterion. {{src:packages/core/tools/src/index.ts#L1276-L1285|executionMode()}}:

```ts
executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
```

All three paths lead to the conservative side: no `isConcurrencySafe` means exclusive, a declared predicate returning anything but `true` means exclusive, and a predicate that **throws** also means exclusive. Lab step 4:

```
--- executionMode (exclusive by default) ---
   read    {"kind":"exclusive"}
   search  {"kind":"parallel"}
   flaky   {"kind":"exclusive"}
```

`flaky`'s predicate is `throw new Error('boom')`, and the verdict is exclusive rather than a failure. The `catch {}` has no logging and no rethrow, because this is not error handling: it is a **default**. A call that cannot be shown safe is treated as unsafe.

Note also that the predicate receives `arguments`: one tool can decide per call. Reading a file is safe; writing the same file is not. A `bash` tool can return `true` for read-only commands and `false` otherwise.

Attach a print to each of the four extension points, plus a guard:

1. **Guards come after pre-execute.** The `DENY` run never reaches the guard: an already-denied call is not put to the guards.

## Summary

One tool call's full chain:

```
createExecution   snapshot args → freeze → mint a token; collapses and non-JSON args stop here
  ↓
tools/pre-execute (waterfall)  allow / deny / ask
  ↓ only allow continues
guards (monotonic)  any layer returning a string denies; nobody can force-allow
  ↓
tools/execute (around)  may swap exec.signal and the result; finally must restore
  ↓
dispatchToolBody  fuse the caller signal back → bodyInvoked = true → tool.execute()
  ↓
createSuccessResult  snapshot → validate output.schema → freeze → render → presentationMeta
  ↓
tools/post-execute (waterfall)  accept / +content / +value (revalidated) / block
  ↓
materializeFinalResult → deep freeze → tools/result (emit, read-only)
```

Three conclusions:

**This pipeline never throws.** Bad arguments, a bad return value, a crashing render, an unknown tool, a timeout, a cancellation: all six become structured `isError` results with stable machine codes. Chapter 5's "tools run concurrently but commit in model order" holds precisely because every call is guaranteed to yield a committable result.

**Denial has two levels with different powers.** `tools/pre-execute` is a waterfall that can deny and can also allow for everyone; a `guard` is monotonic and can only deny. Policy negotiation goes to the former, hard prohibition to the latter. Neither prevents `post-execute` and `tools/result` from running, which is what makes denials auditable.

**When unsure, fall to the conservative side.** No approval service means `ask` becomes `deny`; an undeclared, non-`true`, or even throwing `isConcurrencySafe` means exclusive; a return value that violates its own schema errors rather than entering the log. None of these is error handling; each is a choice about which way the default falls.

The next chapter follows the guards downward into capability seams and the security boundary: how genuinely dangerous capabilities like the filesystem, the shell, and the network are wrapped, and where DSH draws the line of trust.
