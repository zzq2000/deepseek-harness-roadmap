# Prompt assembly, skills, and compaction

Chapters 5 and 6 covered how a request goes out. This chapter covers where its **content** comes from.

A model call's input has two halves: the system prompt in the `system` slot, and the conversation history in `messages`. The first is composed by the registry in section 1. The second holds, besides what the user actually said, three kinds of plugin-injected material: dynamic runtime context, the skill catalog and skill bodies, and compaction summaries.

Those three look unrelated, yet in code they share one entry point: chapter 5's {{src:packages/core/agent-loop/src/agent.ts#L225-L242|preStep()}}.

```ts
const claimed = this.inbox.claim(target, position.turn)
const assembly = await this.loopCtx.systemPrompt.assemble(assembleContextFor(this, signal))
signal.throwIfAborted()
const sections = renderContextSections(assembly)
const context = this.runtimeContext.project(joinContextSections(sections), sections)
const decision = await this.dispatch.waterfall(
  'agent/pre-step', { messages: claimed, ...position, signal },
  (): Promise<PreStepDecision> => Promise.resolve<PreStepDecision>({
    kind: 'enter',
    messages: context === undefined ? claimed : [...claimed, context],
  }),
)
```

Eight lines. `assemble()` produces the system prompt, `project()` produces the runtime snapshot, then the `agent/pre-step` waterfall lets every plugin append to that list. The skill catalog, skill bodies, and compaction all hook this one point.

One criterion runs through the chapter, carried over from chapter 4: **whatever the model can see must be reconstructable from the log**. The system prompt is not logged because `request/header` already records it in full; the other three are genuine `user/message` events, every one of them in the log.

## 1. Four registrations, one assemble

{{src:packages/core/system-prompt/src/index.ts#L337-L543|SystemPrompt}} is a registry accepting four things:

| Method | Registers | Goes to |
|---|---|---|
| {{src:packages/core/system-prompt/src/index.ts#L373-L390\|`section()`}} | an ordered prompt section | the `system` slot |
| {{src:packages/core/system-prompt/src/index.ts#L392-L407\|`context()`}} | ordered dynamic context | one user message |
| {{src:packages/core/system-prompt/src/index.ts#L423-L436\|`tools()`}} | a tool-schema provider | the request's `tools` field |
| {{src:packages/core/system-prompt/src/index.ts#L438-L455\|`variable()`}} | a `{{variable}}` value | interpolation |

Section order follows a convention stated in {{src:packages/core/system-prompt/src/index.ts#L52-L75|PromptSection}}'s JSDoc:

> Convention: `-100` is the harness identity, `0` the deployment persona, tool guidance uses 100–199; other negative orders also render before the persona.

The constructor registers the first two itself:

```ts
if (config.includeHarnessIdentity ?? true) {
  this.section({
    name: 'harness:identity',
    order: -100,
    text: 'You are an AI agent powered by DeepSeek Harness.',
  })
}
this.section({
  name: PERSONA_SECTION,
  order: PERSONA_ORDER,
  text: config.persona ?? '',
})
```

{{src:packages/core/system-prompt/src/index.ts#L122-L131|PERSONA_SECTION}} is exported, and the comment says why:

> Exported because a composition can replace this slot — an agent preset shadows the deployment's persona with its own — and both sides naming the same section is what makes the replacement work rather than duplicate.

An agent preset that wants a different persona registers a section with the **same name**. Same name means replacement; a different name means two sections side by side. So the name has to be a public constant rather than a string each side writes out.

### Layers and shadowing

Which layer a registration lands in depends on the `ctx` that called `section()`. {{src:packages/core/system-prompt/src/index.ts#L303-L335|PromptLayer}} is one layer's whole content, and `ScopedLayers` manages the global layer plus scoped ones. {{src:packages/core/system-prompt/src/index.ts#L457-L542|assemble()}} merges them with a nearest-wins rule:

```ts
for (const [name, provider] of this.layers.global.variables.entries()) {
  variables[name] = provider(context)
}
// Scope-chain variables, farthest first, so the nearest scope wins a name.
for (const layer of scopeLayers) {
  for (const [name, provider] of layer.variables.entries()) {
    variables[name] = provider(context)
  }
}
```

Global first, then the scope chain from farthest to nearest. A duplicate within one layer throws, and the message names the right move:

```ts
`prompt section "${name}" is already registered (for a per-agent override, register through that agent's \`agent.ctx\` instead)`
```

The error text says what you probably meant to do: to override for one agent, register through that agent's `ctx` instead of colliding in the global layer.

### The complete section is restored after the waterfall

`PromptSection` carries a `complete` flag meaning "this section is the entire system prompt". The tail of `assemble()` looks odd at first:

```ts
const transformed = await this.ctx.waterfall(
  scopeTarget(this, scope), 'system-prompt/assemble', assembly, context,
  () => Promise.resolve(assembly),
)
if (completeSection === undefined && !runtimeContextSuppressed) return transformed
return {
  ...transformed,
  sections: completeSection === undefined ? transformed.sections : [completeSection],
  contexts: runtimeContextSuppressed ? [] : transformed.contexts,
}
```

The waterfall runs, `transformed` comes back, and then `sections` is replaced with the single complete section. The event JSDoc states it plainly:

> A registered complete section is restored after this waterfall, so listeners cannot add to or replace that scope's system prompt.

Why run the waterfall at all? Because tools, contexts, and variables still need listener participation. So the design is: **the waterfall runs, but its edits to `sections` are discarded**. `suppressRuntimeContext()` behaves the same way, forcing `contexts` empty. Both are declared intent overriding procedural edits.

More than one complete section throws, and that check happens before any text is resolved.

## 2. Interpolation: deliberately strict

{{src:packages/core/system-prompt/src/index.ts#L257-L295|interpolate()}} is 38 lines scanning for `{{name}}`. Its strictness is worth walking clause by clause, because each clause prevents something specific.

**One: it is malformed only if a `}}` follows; otherwise it is prose.**

```ts
const group = GROUP_AT.exec(text.slice(open))
if (group === null) {
  // A later closing brace makes this malformed; otherwise it is literal prose.
  if (text.indexOf('}}', open + 2) >= 0) {
    throw new Error(`malformed prompt variable reference at ...`)
  }
  result += text.slice(last, open + 2)
  last = open + 2
  continue
}
```

Prompts contain code samples, and `{{` may just be part of a Handlebars example. The test is whether a `}}` appears later. If not, it is literal text kept verbatim; if so, it is a broken reference and throws.

**Two: an unregistered name throws, with the registered list attached.**

```ts
// Do not resolve unregistered names through Object.prototype.
if (!Object.hasOwn(variables, name)) {
  const known = Object.keys(variables)
  throw new Error(`unknown prompt variable "{{${name}}}" in ${kind} "${input.name}"; registered variables: ...`)
}
```

`Object.hasOwn` rather than `variables[name] !== undefined`, and the comment gives the reason: names like `{{constructor}}` or `{{tostring}}` would resolve through the prototype chain to a function. The `VARIABLE_NAME` pattern (`/^[a-z][a-z0-9_]*$/`) already excludes uppercase, but `constructor` is all lowercase and passes it.

**Three: registered but valueless for this assembly also throws.**

```ts
const value = variables[name]
if (value === undefined) {
  throw new Error(`prompt variable "{{${name}}}" has no value for this assembly (${kind} "${input.name}")`)
}
```

A `variable()` provider may return `undefined`, but a section referencing it then fails to render. That is intentional: a `{{workspace_root}}` with no workspace should make assembly **fail loudly** rather than render `undefined` or an empty string into a model request.

**Four: substituted values are not rescanned.**

```ts
result += text.slice(last, open) + value
last = open + group[0].length
```

`result` only appends, and `last` skips past the whole reference. The JSDoc says `substituted values are not scanned again`. A `{{other}}` inside a variable's value is a literal. This is the most direct injection defense: variable values routinely come from the user's environment (cwd, git branch, file contents), and they must not trigger another round of resolution.

## 3. Tool order: why it has to be deterministic

Tool ordering lives in {{src:packages/core/system-prompt/src/index.ts#L159-L178|orderTools()}} and a three-line comparator:

```ts
/** Lexicographic (code-unit) name comparison — locale-independent, so the order is identical on every machine. */
function compareToolNames(a: ToolSchema, b: ToolSchema): number {
  return a.name < b.name ? -1 : a.name > b.name ? 1 : 0
}
```

No `localeCompare`. The comment says `locale-independent, so the order is identical on every machine`. This is not fastidiousness: tool schemas are part of the request prefix, and one differing byte invalidates the provider's whole KV cache. A locale-dependent sort would give one session two different prefixes when resumed on two machines.

A deployment may set `toolOrder`, but it must contain a {{src:packages/core/system-prompt/src/index.ts#L139-L140|TOOL_ORDER_REST}} marker:

```ts
if (!seen.has(TOOL_ORDER_REST)) {
  throw new Error(`toolOrder must contain the "${TOOL_ORDER_REST}" rest entry (where unlisted tools are inserted)`)
}
```

`<unlisted-tools>` is the slot where unlisted tools go. Requiring it exists because otherwise a newly installed plugin's tools would have no defined position.

Two deliberately asymmetric validations:

```ts
const unknown = toolOrder.filter(name => name !== TOOL_ORDER_REST && !knownNames.has(name))
if (unknown.length > 0) {
  throw new Error(`toolOrder lists unregistered tool${...} ...; known tools: ...`)
}
```

A name in `toolOrder` that was **never registered** throws. A name that is registered but invisible in this assembly due to a restriction may be absent. The distinction rests on `knownNames`: {{src:packages/core/system-prompt/src/index.ts#L103-L109|ToolProviderResult}} lets a provider declare its pre-restriction name universe separately, so config validation runs against the universe rather than this assembly's visible subset. Otherwise a global `toolOrder` would fail inexplicably inside an agent that restricts tools.

:::key Every byte of the prompt is cache prefix
Section order, tool order, variable values: any nondeterminism there invalidates the KV cache on session resume. Every fastidious-looking sort and check in this layer points at that one fact.
:::

## 4. Dynamic context is a user message

What `context()` registers does not go into the `system` slot. Look at the text {{src:packages/core/system-prompt/src/index.ts#L228-L240|joinContextSections()}} builds:

```ts
return `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n${body}`
```

That first sentence is a meta-instruction for the model: **this snapshot supersedes every earlier runtime-context snapshot**.

Why say it? Because snapshots are never deleted. The session log only grows (chapter 4), so the old cwd and old git branch are still in history and the model can see them. Newer supersedes older by prose, not by rewriting history. Rewriting would invalidate the KV cache from the rewrite point onward, a far higher cost than a few stale snapshots.

So when is a new one emitted? {{src:packages/core/agent-loop/src/runtime-context.ts#L58-L75|RuntimeContextProjection.project()}}:

```ts
project(current: string, sections: readonly ContextSnapshotSection[]): UserMessage | undefined {
  if (this.retained === undefined && current.length === 0) return
  const snapshot = current.length === 0 ? CLEARED : current
  if (this.retained?.text === snapshot) return
  return createUserMessage({
    content: [{ type: 'text', text: snapshot }],
    source: sections.length === 0
      ? { kind: 'plugin', plugin: SOURCE }
      : { kind: 'plugin', plugin: SOURCE, form: 'snapshot', sections },
  })
}
```

Two early returns. The first: never emitted one and there is nothing now, so do nothing. The second: **the text is identical to last time, so do not emit**.

`retained` is a three-state field, documented on the declaration:

```ts
/** `undefined` means no snapshot ever existed; `null` means none is retained. */
private retained: { seq: number; text: string | undefined } | null | undefined
```

`undefined` is "never existed", `null` is "existed but is gone". The distinction exists for `CLEARED`:

```ts
const CLEARED = 'Current runtime context: none. Earlier runtime-context snapshots no longer apply.'
```

When context goes from present to absent, a "there is none now" message must be emitted, because the old snapshot is still in history and the model would keep acting on it. A session that never had context needs no such message.

Where does `null` come from? The listener in the {{src:packages/core/agent-loop/src/runtime-context.ts#L29-L56|constructor}}:

```ts
} else if (this.retained
  && isReplacementSurfaceEvent(event)
  && event.sourceEventSeqs?.includes(this.retained.seq) === true) {
  this.retained = null
}
```

The retained snapshot was swallowed by a surface replacement, which means it was compacted. `retained` goes to `null` and the next assembly republishes, because a compaction summary makes no promise to restate the cwd and branch. **That line is the interface between section 4 and section 6.**

The constructor also scans the log backwards on startup: find the most recent `user/message` this plugin owns, set `retained ??= null` on the first hit (proving one once existed), and if it is still on the surface record it and stop. A restarted plugin does not republish an identical snapshot.

## 5. Skills: catalog, gesture, body

Skills reach the model three ways, all installed by the single `apply()` in {{src:packages/skill/tool-skill/src/index.ts#L79-L252|tool-skill}}.

### The catalog republishes only on change

The second pre-step listener publishes the catalog. Its core is a digest comparison:

```ts
const entries = catalogSourceEntries(skills, catalogDescriptionMaxLength)
const digest = digestCatalogEntries(entries)
const history = catalogHistory(agent)
const existing = catalogMessage(decision.messages)
if (history.visibleDigest === digest) {
  return existing === undefined
    ? decision
    : { kind: 'enter', messages: decision.messages.filter(message => message.id !== existing.message.id) }
}
```

Unchanged content is not published, and if someone already placed an identical catalog in this step's message list, it is **removed**. The reason matches the previous section's snapshot: every redundant catalog burns tokens and adds one more chance to confuse the model.

When it does publish, the wording differs. The first time is {{src:packages/skill/tool-skill/src/index.ts#L254-L277|renderCatalogMessage}}, phrased "the following skills are available in this session". Afterwards it is {{src:packages/skill/tool-skill/src/index.ts#L279-L311|renderCatalogUpdate}}:

> The available skill catalog changed. This complete catalog replaces every earlier available-skills list in this session

Prose superseding history again, the same technique as the runtime snapshot. When the catalog empties, the wording changes once more: `Do not use names from earlier skill catalogs.`

The catalog is also tied to tool visibility:

```ts
const toolVisible = ctx.tools.get(skillTool.name, agent) === skillTool
```

The comparison is against the **definition object**, not the name. The comment explains:

> Exact definition identity prevents a scoped shadow merely named `skill` from inheriting this catalog.

An agent that shadows this tool with its own `skill` should not inherit this catalog. Same name does not mean same thing. When the tool is restricted away, the schema and its call guidance disappear together, so there is never a state where the model is told to call a tool absent from the schema list.

### The `/name` gesture reads only genuine user input

The first pre-step listener scans for gestures like `/rebuttal`. The defense is one line:

```ts
if ((message.source as { kind?: unknown }).kind !== 'user') continue
```

Only `source.kind === 'user'` messages are scanned. A `/deploy-prod` in a tool result, a `/skill-name` the model emitted itself, a slash inside text another plugin injected: none of them count. The comment says `no other source can forge a gesture`.

An unrecognized name stays plain prose rather than failing:

```ts
// Unknown names and user-disabled skills stay plain prose: the
// gesture was never a claim this boundary recognizes.
if (skill === undefined || !isUserInvocable(skill)) continue
```

A slash in `/tmp/foo`, or chat about a command that does not exist, must not fail the turn.

### Order: background first, the thing to act on last

The two listeners' registration order carries meaning. From the source:

> The rendered body enters this step as injected instructions context appended after every other injection — background first (workspace rules, runtime policy, the catalog), the material the model must act on last, closest to its answer. Registration order makes that placement deterministic: this listener registers before the catalog listener, so the waterfall hands it the catalog-bearing list to extend.

Both listeners `await next()` before appending their own material. In a waterfall the first-registered listener is outermost, so the first-registered **appends last**. The skill body registers first, so it lands after the catalog, right next to where the model answers.

Lab step 3 prints the order directly: seq 4 is the user's sentence, seq 5 the catalog, seq 6 the `<skill_content>`.

### Three escaping boundaries

{{src:packages/skill/skill/src/index.ts#L162-L184|renderSkillContent()}} frames the skill body in pseudo-XML, and treats three positions differently:

```ts
return [
  `<skill_content name="${escapeAttr(skill.name)}">`,
  '<skill_resources>',
  ...resourceHint,
  '</skill_resources>',
  '',
  '<skill_instructions>',
  skill.content,
  '</skill_instructions>',
  '</skill_content>',
].join('\n')
```

The name goes through `escapeAttr` (`&`, `"`, `<`), paths in the resource hint go through {{src:packages/skill/skill/src/index.ts#L220-L229|escapeText}} (`&`, `<`, `>`), and the **body is embedded verbatim**. The JSDoc gives the reason:

> the body is embedded verbatim (skills are trusted local content, and user-supplied invocation text stays outside this wrapper)

A skill body is trusted local content that is supposed to contain Markdown and code blocks; escaping it would break it. The user's own words after `/rebuttal` sit **outside** this wrapper as a separate user message. Trusted content goes in verbatim, untrusted content never enters the frame, and the boundary is drawn at the message level rather than the character level.

## 6. Compaction: one logged transaction

Compaction exists because the context runs out. Its three triggers live in {{src:packages/compaction/compaction-basic/src/index.ts#L137-L224|_registerAutomaticCompaction()}} and the manual command:

| Trigger | Hook | Character |
|---|---|---|
| `pressure` | `agent/pre-step` | measure before each step, act only above the threshold |
| `context-overflow` | `agent/request-error` | the provider said it overflowed: force one reduction, then retry |
| manual | `compactNow()` | requires an idle agent, runs through `runMaintenance` |

The second is notable: it hooks the same `agent/request-error` as `llm-retry` from chapters 5 and 6. On success it returns `{ kind: 'retry' }`, so `step()`'s inner while takes a second lap with the shortened history. **Context overflow is a recoverable error in DSH.**

### Selecting a range: accumulate backwards from the tail

{{src:packages/compaction/compaction-basic/src/region.ts#L98-L134|selectCompactableRange()}} is the whole retention policy in about thirty lines:

```ts
let accumulated = 0
let keepFromIdx = pricedNodes.length
for (let index = pricedNodes.length - 1; index >= 0; index -= 1) {
  accumulated += pricedNodes[index]!.tokens
  keepFromIdx = index
  if (accumulated >= retainTokens) break
}
if (keepFromIdx === 0) return null

while (keepFromIdx > 0) {
  if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
  keepFromIdx -= 1
}
if (keepFromIdx === 0) return null
```

The first loop accumulates tokens backwards from the last node until it reaches `retainTokens`; those are the recent tail kept **verbatim**. The second loop walks the cut point further back until it sits at a tool-pairing-balanced position. Either loop can push `keepFromIdx` to 0, which returns `null`: no safe compactable range exists.

The returned range is always `{ start: first node, end: node before the cut }`, meaning **head through the cut**. Compaction never punches a hole in the middle.

### Tool pairing: why not step markers

{{src:packages/compaction/compaction/src/tool-pairing.ts#L28-L38|eventDelta()}} recognizes exactly two event kinds:

```ts
switch (event.type) {
  case 'assistant/message':
    return event.data.message.content.filter(block => block.type === 'tool-call').length
  case 'tool/result':
    return -1
  default:
    return 0
}
```

Add one per tool-call block in an assistant message, subtract one per tool result. Positions where the running total is zero are balanced cuts. The module JSDoc explains why step markers are not used:

> Compaction changes surface positions, so safe cuts are derived from tool-call/result content in current surface order rather than step markers.

Compaction moves surface positions, and `step/start` / `step/end` are log events rather than surface nodes, so their correspondence with the surface breaks after a compaction. The criterion has to be derived from **what is currently on the surface**, not from historical markers.

Cutting at an unbalanced position yields an assistant message with a tool call and no matching result, which most providers reject outright with a 400.

### The transaction: start is the lock

{{src:packages/compaction/compaction-basic/src/region.ts#L152-L251|compactSurfaceRegion()}} opens with the point:

> Idle/log validation and `compaction/start` are synchronously adjacent, so the durable opening marker is the compaction lock before summarization yields.

There is **no await** between validation and `session.append('compaction/start', ...)`. That one log event is the lock: any later compaction attempt finds a `compaction/start` with no matching `compaction/end` via `assertCompactionInactive` and is refused. The lock lives in the log, not in memory, so an unclosed start survives a process restart and stays visible.

Summarization is async, and the surface can change meanwhile. On return there is a stability check, in two strictnesses:

```ts
const assertStable: StabilityCheck = options.stability === 'whole-surface'
  ? assertWholeSurfaceUnchanged
  : assertSelectedSpanStable
```

{{src:packages/compaction/compaction-basic/src/region.ts#L387-L396|assertWholeSurfaceUnchanged}} demands the entire surface be byte-identical, which automatic compaction uses because it runs inside a turn where nobody else should be writing. {{src:packages/compaction/compaction-basic/src/region.ts#L398-L423|assertSelectedSpanStable}} demands only that the selected span be unchanged; manual compaction uses it because the user may keep talking during it, and those new messages sit outside the span and should not invalidate the summary.

The commit stage, {{src:packages/compaction/compaction-basic/src/region.ts#L427-L478|commitCompactionBody()}}, is documented `without yielding`: no await between the two appends.

```ts
const summaryEvent = session.append('compaction/summary', { ... })
session.append('user/message', checkpointMessage, {
  surfaceOp: { op: 'replace', start, end },
  sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
})
```

That adjacency is contractual, stated on the `compaction/summary` event declaration:

> That adjacency is contractual — the shadowed pricing fields are the replacement's shadow price, so a consumer may pair a replacement with the metering event directly before it.

A `replace` surface event is **priced** by the metering event immediately before it. A pure consumer (a token-counting projection, say) sees the replace, looks one event back, and knows what the replaced content cost, without retaining a price per node.

### The summarization call reuses the conversation's own prefix

{{src:packages/compaction/compaction-basic/src/region.ts#L498-L514|buildSummarizationInput()}} and {{src:packages/compaction/compaction-basic/src/summarizer.ts#L110-L182|summarizeWithLlm()}} together do something careful:

```ts
const messages: Message[] = [
  ...input.messages,
  createUserMessage({
    content: [{ type: 'text', text: COMPACTION_INSTRUCTION }],
    source: { kind: 'plugin', plugin: 'dsh-compaction-basic' },
  }),
]
const options: GenerateOptions = {
  provider: target.provider,
  model: target.model,
  messages,
  ...input.system === undefined ? {} : { system: input.system },
  ...input.tools === undefined ? {} : { tools: [...input.tools] },
  maxTokens: config.maxTokens,
  sessionId: agent.session.id,
  purpose: 'compaction',
  ...
}
```

The compaction directive is the **final user message**, not a dedicated summarizer system prompt. The comment above {{src:packages/compaction/compaction-basic/src/summarizer.ts#L24-L66|COMPACTION_INSTRUCTION}} gives the motive:

> Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call a genuine prefix of the last routed request, so the provider's KV cache is reused instead of invalidated.

The conversation's own system prompt and tools ride along unchanged, the messages being compacted ride along unchanged, and only one instruction is appended at the end. That makes the auxiliary call a **genuine prefix** of the last real request, so the provider's KV cache hits. A dedicated summarizer system prompt would differ from the first token and discard the whole cached prefix.

The `purpose: 'compaction'` field appeared in chapter 6: the DeepSeek adapter maps it to the `x-deepseek-harness-compact: 1` request header.

Lab step 4 prints that call's envelope:

```
[compaction call] system="You are an AI agent powered by DeepSeek Harness.\n\nYou are a lab agent." tools=undefined messages=4
```

4 messages = the 3 being compacted plus 1 instruction, and `system` is the conversation's own.

### Surface position is not seq order

{{src:packages/compaction/compaction/src/types.ts#L106-L114|CompactionResult.shadowedRange}}'s JSDoc contains a counterintuitive sentence:

> A surface-POSITION span, not a numeric seq interval — after a prior replace lands a fresh high-seq summary node at an older range's position, `start` can be GREATER than `end`.

A replace puts a **new high-seq** summary node at an **old range's position**. Surface order and seq order come apart. The final surface after six turns in lab step 4:

```
[79, 71, 82, 87]
```

79 precedes 71. Any code that rebuilds the surface by sorting on seq breaks here, which is why `shadowedSeqs` is explicitly declared as the authoritative list, in surface order.

## 7. The model-free half: tool-result pruning

Not every compaction calls a model. {{src:packages/compaction/compaction-tool-result-pruner/src/index.ts#L136-L184|ToolResultPruner.pruneSession()}} does purely mechanical work: an over-long tool result keeps its head and tail, and the middle becomes a marker.

```ts
export const PRUNE_MARKER = '\n\n[... tool result middle pruned ...]\n\n'
export const DEFAULTS = {
  thresholdChars: 8192,
  headChars: 4096,
  tailChars: 1024,
}
```

By default it prunes above 8192 code points, keeping 4096 leading and 1024 trailing. The head is larger because tool output usually starts with structure (file headers, command echoes, table headers) and ends with conclusions.

Its relationship to summarizing compaction is **prune first, summarize second**. {{src:packages/compaction/compaction-basic/src/index.ts#L258-L332|compactIfNeeded()}} remeasures twice:

```ts
if (prune !== undefined) {
  prune.pruneSession(agent.session)
  measurement = meter.measure(agent.session)
}
if (measurement.totalTokens < spec.thresholdTokens) return null
```

Do the free half first, measure, and if that suffices no model call happens. `ctx.get('toolResultPruner')` uses the optional-service read (chapter 2 covered `ctx.get` versus `ctx.<name>`), and the comment states why: `Pruning is optional so compaction-basic remains independently composable.`

Pruning obeys the same shadow-price protocol:

```ts
session.append('compaction/prune', {
  shadowedRange: { start: seq, end: seq },
  shadowedSeqs: [seq],
  shadowedTokenCount: this.ctx.tokenMeter.estimateMessage(event.data.message),
})
const replacement = session.append('tool/result', { ...event.data, message }, {
  surfaceOp: { op: 'replace', start: seq, end: seq },
  sourceEventSeqs: [seq],
})
```

The metering event sits immediately before the replace, exactly where `compaction/summary` sits in a summarizing compaction. Different output, same protocol.

The replacement keeps **every field** of the original event and swaps only `content`: `{ ...event.data, message }`. turn, step, callId, error, meta all ride through unchanged. This is chapter 4's "a replace changes content, not identity" in the concrete.

## Summary

A request's content converges from four sources:

```
systemPrompt.assemble()
  ├─ sections (sorted by order → interpolated)  → the system slot, unlogged (request/header records it)
  ├─ tools (toolOrder / lexicographic)          → the tools field
  ├─ contexts                                   → RuntimeContextProjection → one user message
  └─ variables                                  → used during interpolation

preStep's agent/pre-step waterfall
  ├─ default: claimed messages + the runtime snapshot
  ├─ tool-skill: the skill catalog (silent when the digest is unchanged)
  ├─ tool-skill: the skill body a /name gesture injects (appended last)
  └─ compaction-basic: appends nothing, rewrites the surface
```

Three conclusions:

**History is superseded by prose, not by rewriting.** The runtime snapshot says it supersedes earlier snapshots; the skill catalog says it replaces earlier catalogs; the compaction checkpoint says to treat its content as established background. All three could have rewritten the log, and none of them do, because the log only grows (chapter 4) and because a rewrite invalidates the entire KV cache after the rewrite point. The one thing that genuinely rewrites the surface is compaction, and it pays for that with a full transaction: a lock, a stability check, and a synchronously adjacent commit.

**Nothing redundant is sent twice.** The snapshot compares text, the catalog compares a digest, compaction compares a threshold. All three live in the same pre-step, and all three first ask whether this is actually needed. What they save is tokens, and also the model's attention.

**The model-free half runs first.** Compaction goes prune, measure, and only then call a model if still over. A tool result's middle is the easiest thing to drop and the least missed, and dropping it may mean no model call at all.
