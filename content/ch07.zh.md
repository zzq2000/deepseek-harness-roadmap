# 提示词组装、skill 与压缩

第 5、6 章讲的是请求怎么被发出去。这一章讲请求里的**内容**是怎么来的。

一次模型调用的输入分两部分：`system` 槽里的系统提示词，和 `messages` 里的对话历史。前者由本章第一节的注册表拼出来，后者除了用户真正说的话之外，还混着三类插件塞进去的东西：动态运行时上下文、skill 目录与 skill 正文、压缩摘要。

这三件事看起来毫不相干，代码里却共用同一个入口：第 5 章那个 {{src:packages/core/agent-loop/src/agent.ts#L225-L242|preStep()}}。

```ts
const claimed = this.inbox.claim(target, position.turn)
const assembly = await this.loopCtx.systemPrompt.assemble(assembleContextFor(this, signal))
signal.throwIfAborted()
const sections = renderContextSections(assembly)
const context = this.runtimeContext.project(joinContextSections(sections), sections)
const decision = await this.dispatch.waterfall(
  'agent/pre-step', { messages: claimed, ...position, signal },
  (): Promise<PreStepDecision> => Promise.resolve<PreStepDecision>({
    kind: 'enter',
    messages: context === undefined ? claimed : [...claimed, context],
  }),
)
```

八行。`assemble()` 出系统提示词，`project()` 出运行时快照，然后 `agent/pre-step` waterfall 让所有插件往这个列表后面追加。skill 目录、skill 正文、压缩，全部挂在这一个点上。

本章有一条贯穿的判据，来自第 4 章：**模型能看到的，必须能从日志重建**。系统提示词不进日志，因为 `request/header` 已经完整记下了它；其余三类都是货真价实的 `user/message`，每一条都在日志里。

## 一、四种注册，一次 assemble

{{src:packages/core/system-prompt/src/index.ts#L337-L543|SystemPrompt}} 是个注册表，收四种东西：

| 方法 | 注册什么 | 去哪 |
|---|---|---|
| {{src:packages/core/system-prompt/src/index.ts#L373-L390\|`section()`}} | 有序的提示词段落 | `system` 槽 |
| {{src:packages/core/system-prompt/src/index.ts#L392-L407\|`context()`}} | 有序的动态上下文 | 一条 user 消息 |
| {{src:packages/core/system-prompt/src/index.ts#L423-L436\|`tools()`}} | 工具 schema 提供者 | 请求的 `tools` 字段 |
| {{src:packages/core/system-prompt/src/index.ts#L438-L455\|`variable()`}} | `{{变量}}` 的值 | 插值时用 |

`section` 的 order 有一套约定，写在 {{src:packages/core/system-prompt/src/index.ts#L52-L75|PromptSection}} 的 JSDoc 里：

> Convention: `-100` is the harness identity, `0` the deployment persona, tool guidance uses 100–199; other negative orders also render before the persona.

`-100` 是 harness 身份，`0` 是部署方的人格，`100` 到 `199` 留给工具指引。构造函数里就注册了前两个：

```ts
if (config.includeHarnessIdentity ?? true) {
  this.section({
    name: 'harness:identity',
    order: -100,
    text: 'You are an AI agent powered by DeepSeek Harness.',
  })
}
this.section({
  name: PERSONA_SECTION,
  order: PERSONA_ORDER,
  text: config.persona ?? '',
})
```

{{src:packages/core/system-prompt/src/index.ts#L122-L131|PERSONA_SECTION}} 这个常量被导出，注释解释了为什么：

> Exported because a composition can replace this slot — an agent preset shadows the deployment's persona with its own — and both sides naming the same section is what makes the replacement work rather than duplicate.

一个 agent preset 想换掉人格，办法是注册一个**同名**的 section。同名才是替换，不同名就是并列两段。所以这个名字必须是公开常量，不能各写各的字符串。

### 层与遮蔽

注册落在哪一层，取决于调用 `section()` 的那个 `ctx`。{{src:packages/core/system-prompt/src/index.ts#L303-L335|PromptLayer}} 是一层的全部内容，`ScopedLayers` 管全局层和 scoped 层。{{src:packages/core/system-prompt/src/index.ts#L457-L542|assemble()}} 合并时的规则是**近的赢**：

```ts
for (const [name, provider] of this.layers.global.variables.entries()) {
  variables[name] = provider(context)
}
// Scope-chain variables, farthest first, so the nearest scope wins a name.
for (const layer of scopeLayers) {
  for (const [name, provider] of layer.variables.entries()) {
    variables[name] = provider(context)
  }
}
```

全局先写，然后按 scope 链从远到近覆盖。同一层里重名直接抛，错误信息还专门指路：

```ts
`prompt section "${name}" is already registered (for a per-agent override, register through that agent's \`agent.ctx\` instead)`
```

这句话把「你想干的事应该怎么做」写进了报错里：想给某个 agent 单独改，用那个 agent 的 `ctx` 注册，别在全局层撞名字。

### complete section：waterfall 之后被强行恢复

`PromptSection` 有个 `complete` 标记，语义是「这一段就是完整的系统提示词」。`assemble()` 结尾有一段看起来很怪的代码：

```ts
const transformed = await this.ctx.waterfall(
  scopeTarget(this, scope), 'system-prompt/assemble', assembly, context,
  () => Promise.resolve(assembly),
)
if (completeSection === undefined && !runtimeContextSuppressed) return transformed
return {
  ...transformed,
  sections: completeSection === undefined ? transformed.sections : [completeSection],
  contexts: runtimeContextSuppressed ? [] : transformed.contexts,
}
```

waterfall 跑完了，拿到 `transformed`，然后把 `sections` 换回那唯一一段 complete。事件声明的 JSDoc 说得很直白：

> A registered complete section is restored after this waterfall, so listeners cannot add to or replace that scope's system prompt.

为什么不干脆跳过 waterfall？因为工具、上下文、变量还得让监听器参与解析。所以设计是：**waterfall 照跑，但它对 sections 的修改会被丢弃**。同理，`suppressRuntimeContext()` 生效时 `contexts` 也被强制清空。两处都是「声明式的意图压过程序式的修改」。

多于一个 complete section 直接抛错，这个检查在解析文本之前就做了。

## 二、插值：为什么故意这么严格

{{src:packages/core/system-prompt/src/index.ts#L257-L295|interpolate()}} 38 行，扫 `{{name}}`。它的严格程度值得逐条看，因为每一条都在防一件具体的事。

**一、有后续 `}}` 才算格式错误，否则是散文。**

```ts
const group = GROUP_AT.exec(text.slice(open))
if (group === null) {
  // A later closing brace makes this malformed; otherwise it is literal prose.
  if (text.indexOf('}}', open + 2) >= 0) {
    throw new Error(`malformed prompt variable reference at ...`)
  }
  result += text.slice(last, open + 2)
  last = open + 2
  continue
}
```

提示词里写代码示例是常事，`{{` 可能只是 Handlebars 教程的一部分。判据是：这个 `{{` 后面还有没有 `}}`。没有就是纯文本，原样保留；有就是写坏了的引用，报错。

**二、未注册的名字报错，而且带上已注册列表。**

```ts
// Do not resolve unregistered names through Object.prototype.
if (!Object.hasOwn(variables, name)) {
  const known = Object.keys(variables)
  throw new Error(`unknown prompt variable "{{${name}}}" in ${kind} "${input.name}"; registered variables: ...`)
}
```

用 `Object.hasOwn` 而不是 `variables[name] !== undefined`，注释给了理由：`{{constructor}}` 或者 `{{tostring}}` 这类名字会通过原型链解析到一个函数上。虽然 `VARIABLE_NAME` 正则（`/^[a-z][a-z0-9_]*$/`）已经挡掉了大写，`constructor` 全小写却是合法名字。

**三、注册了但这次没值，也报错。**

```ts
const value = variables[name]
if (value === undefined) {
  throw new Error(`prompt variable "{{${name}}}" has no value for this assembly (${kind} "${input.name}")`)
}
```

`variable()` 的 provider 允许返回 `undefined`，但引用了它的 section 渲染就会失败。这是有意的：一个 `{{workspace_root}}` 在没有工作区时应该让组装**响亮地失败**，而不是渲染成 `undefined` 或者空字符串发给模型。

**四、替换进去的值不再扫描。**

```ts
result += text.slice(last, open) + value
last = open + group[0].length
```

`result` 只往前追加，`last` 直接跳过整个引用。函数签名上方的 JSDoc 写了 `substituted values are not scanned again`。这意味着变量值里如果含 `{{other}}`，它就是字面量。这是最直接的注入防线：变量值经常来自用户环境（cwd、git 分支、文件内容），不能让它们再触发一轮解析。

## 三、工具顺序：为什么必须确定

工具的排序逻辑在 {{src:packages/core/system-prompt/src/index.ts#L159-L178|orderTools()}} 和一个三行的比较函数里：

```ts
/** Lexicographic (code-unit) name comparison — locale-independent, so the order is identical on every machine. */
function compareToolNames(a: ToolSchema, b: ToolSchema): number {
  return a.name < b.name ? -1 : a.name > b.name ? 1 : 0
}
```

不用 `localeCompare`。注释写的是 `locale-independent, so the order is identical on every machine`。这不是洁癖：工具 schema 是请求前缀的一部分，前缀一个字节不同，provider 的 KV cache 就全部作废。如果排序依赖机器 locale，同一个会话在两台机器上恢复会产生两个不同的前缀。

配置项 `toolOrder` 允许部署方指定顺序，但必须包含一个 {{src:packages/core/system-prompt/src/index.ts#L139-L140|TOOL_ORDER_REST}} 标记：

```ts
if (!seen.has(TOOL_ORDER_REST)) {
  throw new Error(`toolOrder must contain the "${TOOL_ORDER_REST}" rest entry (where unlisted tools are inserted)`)
}
```

`<unlisted-tools>` 这个位置就是「没列出来的工具插在哪」。强制要求它出现，是因为没有它的话，新装一个插件带来的新工具就没有确定的位置。

两条不对称的校验规则：

```ts
const unknown = toolOrder.filter(name => name !== TOOL_ORDER_REST && !knownNames.has(name))
if (unknown.length > 0) {
  throw new Error(`toolOrder lists unregistered tool${...} ...; known tools: ...`)
}
```

`toolOrder` 里出现**没注册过**的名字，抛。但注册过、这次因为限制而不可见的名字，允许缺席。区分靠的是 `knownNames`：{{src:packages/core/system-prompt/src/index.ts#L103-L109|ToolProviderResult}} 让 provider 单独申报「限制前的名字全集」，就是为了让配置校验对着全集做，而不是对着这次可见的子集做。否则在一个限制了工具的 agent 里，全局的 `toolOrder` 会莫名其妙地报错。

:::key 提示词的每一个字节都是缓存前缀
section 顺序、工具顺序、变量值，任何一处不确定，KV cache 就会在恢复会话时失效。这一层里所有看起来过于讲究的排序和校验，最终都指向这一件事。
:::

## 四、动态上下文：它是一条 user 消息

`context()` 注册的东西不进 `system` 槽。看 {{src:packages/core/system-prompt/src/index.ts#L228-L240|joinContextSections()}} 拼出来的文本：

```ts
return `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n${body}`
```

第一句是给模型看的元指令：**这份快照取代之前所有的运行时上下文快照**。

为什么要这句话？因为快照不会被删除。会话日志只增长（第 4 章），历史里那条旧的 cwd、旧的 git 分支还在，模型能看到。让新的压过旧的，靠的是这一句散文，不是改写历史。改写历史会让 KV cache 从改写点之后全部作废，代价远大于多留几条过期快照。

那么什么时候发一条新的？{{src:packages/core/agent-loop/src/runtime-context.ts#L58-L75|RuntimeContextProjection.project()}}：

```ts
project(current: string, sections: readonly ContextSnapshotSection[]): UserMessage | undefined {
  if (this.retained === undefined && current.length === 0) return
  const snapshot = current.length === 0 ? CLEARED : current
  if (this.retained?.text === snapshot) return
  return createUserMessage({
    content: [{ type: 'text', text: snapshot }],
    source: sections.length === 0
      ? { kind: 'plugin', plugin: SOURCE }
      : { kind: 'plugin', plugin: SOURCE, form: 'snapshot', sections },
  })
}
```

两个提前返回。第一个：从来没发过、现在也是空的，什么都不做。第二个：**文本和上次一模一样，不发**。

`retained` 是个三态字段，注释写在声明上：

```ts
/** `undefined` means no snapshot ever existed; `null` means none is retained. */
private retained: { seq: number; text: string | undefined } | null | undefined
```

`undefined` 是「从来没有过」，`null` 是「有过但已经不在了」。区分这两者是为了 `CLEARED`：

```ts
const CLEARED = 'Current runtime context: none. Earlier runtime-context snapshots no longer apply.'
```

上下文从有变成无的时候，要发一条「现在没有了」的消息，因为历史里那条旧快照还在，不说一声模型会继续按它行事。而从来没有过上下文的会话，不需要发这条。

`null` 从哪来？{{src:packages/core/agent-loop/src/runtime-context.ts#L29-L56|构造函数}}里那个监听器：

```ts
} else if (this.retained
  && isReplacementSurfaceEvent(event)
  && event.sourceEventSeqs?.includes(this.retained.seq) === true) {
  this.retained = null
}
```

保留的那条快照被一次 surface 替换吃掉了，也就是被压缩了。这时 `retained` 归 `null`，下一次组装会重发一条。因为压缩摘要不保证复述 cwd 和分支。**这一行是本章第六节和第四节的接口**。

构造函数还有一段从日志倒着扫的恢复逻辑：从后往前找最近一条本插件产的 `user/message`，第一条命中就 `retained ??= null`（说明历史上存在过），若它还在 surface 上则记下并停止。插件重启后不会重复发一条相同的快照。

## 五、skill：目录、手势、正文

skill 有三条进入模型视野的路径，全部由 {{src:packages/skill/tool-skill/src/index.ts#L79-L252|tool-skill}} 这一个插件的 `apply()` 装好。

### 目录：只有变化时才重发

第二个 pre-step 监听器发布目录。核心是一个摘要比较：

```ts
const entries = catalogSourceEntries(skills, catalogDescriptionMaxLength)
const digest = digestCatalogEntries(entries)
const history = catalogHistory(agent)
const existing = catalogMessage(decision.messages)
if (history.visibleDigest === digest) {
  return existing === undefined
    ? decision
    : { kind: 'enter', messages: decision.messages.filter(message => message.id !== existing.message.id) }
}
```

目录内容没变就不发，而且如果这一步的消息列表里已经有人放了一条同样的目录，还要把它**摘掉**。理由和上一节的快照一样：每多一条重复的目录，就多烧一次 token，也多一次让模型困惑的机会。

发的时候分两种措辞。首次是 {{src:packages/skill/tool-skill/src/index.ts#L254-L277|renderCatalogMessage}}，措辞是「本会话可用的 skill 如下」；之后是 {{src:packages/skill/tool-skill/src/index.ts#L279-L311|renderCatalogUpdate}}，措辞变成：

> The available skill catalog changed. This complete catalog replaces every earlier available-skills list in this session

又是靠散文取代历史，和运行时快照同一个手法。目录变空时措辞再变一次：`Do not use names from earlier skill catalogs.`

目录还和工具的可见性绑定：

```ts
const toolVisible = ctx.tools.get(skillTool.name, agent) === skillTool
```

比较的是**定义对象本身**，不是名字。注释解释了为什么：

> Exact definition identity prevents a scoped shadow merely named `skill` from inheriting this catalog.

某个 agent 用自己的 `skill` 工具遮蔽了这一个，那它不该继承这份目录。名字相同不代表是同一件东西。工具被限制掉的时候，schema 和调用指引一起消失，不会出现「告诉模型有个工具可以调，但那个工具不在 schema 里」的状态。

### `/name` 手势：只认真正的用户输入

第一个 pre-step 监听器扫描 `/rebuttal` 这样的手势。防线在一行判断上：

```ts
if ((message.source as { kind?: unknown }).kind !== 'user') continue
```

只扫 `source.kind === 'user'` 的消息。工具结果里出现 `/deploy-prod`、模型自己输出 `/skill-name`、别的插件注入的文本里带斜杠，全都不算。注释写的是 `no other source can forge a gesture`。

认不出的名字保持普通散文，不报错：

```ts
// Unknown names and user-disabled skills stay plain prose: the
// gesture was never a claim this boundary recognizes.
if (skill === undefined || !isUserInvocable(skill)) continue
```

`/tmp/foo` 里的斜杠、聊到某个不存在的命令，都不该让轮次失败。

### 顺序：背景在前，要执行的在后

两个监听器的注册顺序有语义。源码注释：

> The rendered body enters this step as injected instructions context appended after every other injection — background first (workspace rules, runtime policy, the catalog), the material the model must act on last, closest to its answer. Registration order makes that placement deterministic: this listener registers before the catalog listener, so the waterfall hands it the catalog-bearing list to extend.

两个监听器都是先 `await next()` 再追加自己的东西。waterfall 里先注册的在外层，所以先注册的**最后追加**。skill 正文注册在前，于是它排在目录后面，紧挨着模型要作答的位置。

本章实验第 3 步把这个顺序直接印出来了：seq 4 是用户那句话，seq 5 是目录，seq 6 是 `<skill_content>`。

### 三种转义边界

{{src:packages/skill/skill/src/index.ts#L162-L184|renderSkillContent()}} 用伪 XML 框住 skill 正文，三个位置的处理各不相同：

```ts
return [
  `<skill_content name="${escapeAttr(skill.name)}">`,
  '<skill_resources>',
  ...resourceHint,
  '</skill_resources>',
  '',
  '<skill_instructions>',
  skill.content,
  '</skill_instructions>',
  '</skill_content>',
].join('\n')
```

名字走 `escapeAttr`（转 `&` `"` `<`），资源提示里的路径走 {{src:packages/skill/skill/src/index.ts#L220-L229|escapeText}}（转 `&` `<` `>`），而**正文原样嵌入**。JSDoc 给了理由：

> the body is embedded verbatim (skills are trusted local content, and user-supplied invocation text stays outside this wrapper)

skill 正文是本地可信内容，它本来就要写 Markdown 和代码块，转义了就没法用。而用户跟在 `/rebuttal` 后面的那句话待在这个 wrapper **外面**，是一条独立的 user 消息。可信的东西原样进，不可信的东西不进这个框，边界画在消息层面而不是字符层面。

## 六、压缩：一次有日志的事务

压缩要解决的是上下文装不下了。它的三条触发路径都在 {{src:packages/compaction/compaction-basic/src/index.ts#L137-L224|_registerAutomaticCompaction()}} 和手动命令里：

| 触发 | 挂在哪 | 特点 |
|---|---|---|
| `pressure` | `agent/pre-step` | 每步前测量，超阈值才动 |
| `context-overflow` | `agent/request-error` | provider 说超了，绕过阈值强行压一次然后 retry |
| 手动 | `compactNow()` | 要求 agent 空闲，走 `runMaintenance` |

第二条值得注意：它挂的是第 5、6 章那个 `agent/request-error`，和 `llm-retry` 同一个点。压缩成功后返回 `{ kind: 'retry' }`，于是 `step()` 的内层 while 转第二圈，用缩短后的历史重发。**上下文溢出在 DSH 里是一种可恢复的错误**。

### 选范围：从尾巴倒着攒

{{src:packages/compaction/compaction-basic/src/region.ts#L98-L134|selectCompactableRange()}} 是全部的范围策略，三十几行：

```ts
let accumulated = 0
let keepFromIdx = pricedNodes.length
for (let index = pricedNodes.length - 1; index >= 0; index -= 1) {
  accumulated += pricedNodes[index]!.tokens
  keepFromIdx = index
  if (accumulated >= retainTokens) break
}
if (keepFromIdx === 0) return null

while (keepFromIdx > 0) {
  if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
  keepFromIdx -= 1
}
if (keepFromIdx === 0) return null
```

第一个循环从最后一条往前累加 token，攒够 `retainTokens` 就停，这些是要**原样保留**的近期尾巴。第二个循环把切点往前挪，直到它是一个「工具配对平衡」的位置。两个循环都可能把 `keepFromIdx` 顶到 0，那就返回 `null`：没有安全的可压缩范围。

返回的永远是 `{ start: 第一个节点, end: 切点前一个 }`，也就是**从头压到切点**。压缩不做中间挖洞。

### 工具配对：为什么不看 step 标记

{{src:packages/compaction/compaction/src/tool-pairing.ts#L28-L38|eventDelta()}} 只认两种事件：

```ts
switch (event.type) {
  case 'assistant/message':
    return event.data.message.content.filter(block => block.type === 'tool-call').length
  case 'tool/result':
    return -1
  default:
    return 0
}
```

assistant 消息里有几个 tool-call 就加几，每条 tool/result 减一。累计值归零的位置就是平衡切点。模块 JSDoc 说明了为什么不用 `step/start` 这类标记：

> Compaction changes surface positions, so safe cuts are derived from tool-call/result content in current surface order rather than step markers.

压缩会改变 surface 的位置，`step/start` 和 `step/end` 是日志事件而不是 surface 节点，压完之后它们和 surface 的对应关系就断了。所以判据必须从**当前 surface 上的内容**推出来，不能依赖历史标记。

切在不平衡的位置会产生一条「有 tool-call 但没有对应 result」的 assistant 消息，绝大多数 provider 会直接 400。

### 事务：start 是锁

{{src:packages/compaction/compaction-basic/src/region.ts#L152-L251|compactSurfaceRegion()}} 的注释开门见山：

> Idle/log validation and `compaction/start` are synchronously adjacent, so the durable opening marker is the compaction lock before summarization yields.

校验和 `session.append('compaction/start', ...)` 之间**没有 await**。这一条日志就是锁：之后任何一次压缩进来，`assertCompactionInactive` 会看到一个没有配对 `compaction/end` 的 start，直接拒绝。锁住在日志里，不住在内存里，所以进程重启后未闭合的 start 仍然可见。

摘要是异步的，这期间 surface 可能变。回来之后要做稳定性检查，有两种严格程度：

```ts
const assertStable: StabilityCheck = options.stability === 'whole-surface'
  ? assertWholeSurfaceUnchanged
  : assertSelectedSpanStable
```

{{src:packages/compaction/compaction-basic/src/region.ts#L387-L396|assertWholeSurfaceUnchanged}} 要求整个 surface 一个字节都没动，自动压缩用它（它跑在轮次内部，本来就不该有别人写入）。{{src:packages/compaction/compaction-basic/src/region.ts#L398-L423|assertSelectedSpanStable}} 只要求被选中的那一段没变，手动压缩用它，因为手动压缩期间用户可能继续说话，那些新消息在选中段之外，不该让摘要作废。

提交阶段 {{src:packages/compaction/compaction-basic/src/region.ts#L427-L478|commitCompactionBody()}} 的函数名注释是 `without yielding`：两次 `append` 之间不能有 await。

```ts
const summaryEvent = session.append('compaction/summary', { ... })
session.append('user/message', checkpointMessage, {
  surfaceOp: { op: 'replace', start, end },
  sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
})
```

相邻是有契约的，写在 `compaction/summary` 的事件声明里：

> That adjacency is contractual — the shadowed pricing fields are the replacement's shadow price, so a consumer may pair a replacement with the metering event directly before it.

一条 `replace` 的 surface 事件，它的**价格**由紧挨在它前面的那条计量事件给出。这样一个纯消费者（比如 token 计数的投影）只要看到 replace，往前一条就知道被换掉的内容值多少 token，不需要为每个节点保存价格。

### 摘要调用复用会话自己的前缀

{{src:packages/compaction/compaction-basic/src/region.ts#L498-L514|buildSummarizationInput()}} 和 {{src:packages/compaction/compaction-basic/src/summarizer.ts#L110-L182|summarizeWithLlm()}} 一起做了一件很讲究的事：

```ts
const messages: Message[] = [
  ...input.messages,
  createUserMessage({
    content: [{ type: 'text', text: COMPACTION_INSTRUCTION }],
    source: { kind: 'plugin', plugin: 'dsh-compaction-basic' },
  }),
]
const options: GenerateOptions = {
  provider: target.provider,
  model: target.model,
  messages,
  ...input.system === undefined ? {} : { system: input.system },
  ...input.tools === undefined ? {} : { tools: [...input.tools] },
  maxTokens: config.maxTokens,
  sessionId: agent.session.id,
  purpose: 'compaction',
  ...
}
```

压缩指令是**最后一条 user 消息**，不是一个专门的 summarizer system prompt。{{src:packages/compaction/compaction-basic/src/summarizer.ts#L24-L66|COMPACTION_INSTRUCTION}} 上方的注释解释了动机：

> Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call a genuine prefix of the last routed request, so the provider's KV cache is reused instead of invalidated.

会话自己的 system prompt 和 tools 原样带上，被压缩的那些消息原样带上，只在最后追加一句指令。这样这次辅助调用是上一次真实请求的**真前缀**，provider 的 KV cache 直接命中。换一个 summarizer 专用的 system prompt，前缀从第一个 token 就不同，整段缓存作废。

`purpose: 'compaction'` 这个字段第 6 章见过：DeepSeek 适配器把它映射成 `x-deepseek-harness-compact: 1` 请求头。

本章实验第 4 步把这次调用的信封打印了出来：

```
[压缩调用] purpose=compaction system="You are an AI agent powered by DeepSeek Harness.\n\nYou are a lab agent." tools=undefined messages=4
```

4 条消息 = 被压缩的 3 条 + 1 条指令，system 就是会话自己那个。

### surface 位置不是 seq 顺序

{{src:packages/compaction/compaction/src/types.ts#L106-L114|CompactionResult.shadowedRange}} 的 JSDoc 有一句反直觉的话：

> A surface-POSITION span, not a numeric seq interval — after a prior replace lands a fresh high-seq summary node at an older range's position, `start` can be GREATER than `end`.

一次 replace 会把一个**新的高 seq** 摘要节点放在**旧范围的位置**上。于是 surface 的顺序和 seq 的大小关系就脱钩了。实验第 4 步跑六轮之后的最终 surface：

```
[79, 71, 82, 87]
```

79 排在 71 前面。任何按 seq 排序来重建 surface 的代码都会在这里出错，这就是为什么 `shadowedSeqs` 被显式声明为「权威的、按 surface 顺序的」那一份。

## 七、model-free 的那一半：工具结果剪枝

不是所有压缩都要调模型。{{src:packages/compaction/compaction-tool-result-pruner/src/index.ts#L136-L184|ToolResultPruner.pruneSession()}} 干的是纯机械的活：超长的工具结果，留头留尾，中间换成一个标记。

```ts
export const PRUNE_MARKER = '\n\n[... tool result middle pruned ...]\n\n'
export const DEFAULTS = {
  thresholdChars: 8192,
  headChars: 4096,
  tailChars: 1024,
}
```

默认 8192 个码点以上才剪，留前 4096 后 1024。头比尾长，因为工具输出的开头通常是结构（文件头、命令回显、表头），结尾是结论。

它和摘要压缩的关系是**先剪枝，后摘要**。{{src:packages/compaction/compaction-basic/src/index.ts#L258-L332|compactIfNeeded()}} 里连着两次重新测量：

```ts
if (prune !== undefined) {
  prune.pruneSession(agent.session)
  measurement = meter.measure(agent.session)
}
if (measurement.totalTokens < spec.thresholdTokens) return null
```

先做不花钱的那一半，测一下，够了就不用调模型了。`ctx.get('toolResultPruner')` 用的是可选服务读法（第 2 章讲过 `ctx.get` 和 `ctx.<name>` 的区别），注释也写明了原因：`Pruning is optional so compaction-basic remains independently composable.`

剪枝也遵守同一套 shadow price 协议：

```ts
session.append('compaction/prune', {
  shadowedRange: { start: seq, end: seq },
  shadowedSeqs: [seq],
  shadowedTokenCount: this.ctx.tokenMeter.estimateMessage(event.data.message),
})
const replacement = session.append('tool/result', { ...event.data, message }, {
  surfaceOp: { op: 'replace', start: seq, end: seq },
  sourceEventSeqs: [seq],
})
```

计量事件紧挨着 replace，和摘要压缩里 `compaction/summary` 的位置完全对应。两种压缩产出不同，协议相同。

替换事件保留了原事件的**全部字段**，只换 `content`：`{ ...event.data, message }`。turn、step、callId、error、meta 全部原样。这是第 4 章那条「replace 只改内容，不改身份」的直接体现。

## 小结

一次请求的内容，由四路汇合而成：

```
systemPrompt.assemble()
  ├─ sections（order 排序 → 插值）      → system 槽，不进日志（request/header 记它）
  ├─ tools（toolOrder / 字典序）        → tools 字段
  ├─ contexts                          → RuntimeContextProjection → 一条 user 消息
  └─ variables                         → 插值时用

preStep 的 agent/pre-step waterfall
  ├─ 默认：claimed 消息 + 运行时快照
  ├─ tool-skill：skill 目录（digest 没变就不发）
  ├─ tool-skill：/name 手势注入的 skill 正文（追加在最后）
  └─ compaction-basic：不追加，改写 surface
```

三个结论：

**取代历史靠散文，不靠改写。** 运行时快照说「本快照取代之前所有快照」，skill 目录说「本目录替换之前所有目录」，压缩 checkpoint 说「把这段当作已确立的背景」。三处都可以选择去改写日志，三处都没有。因为日志是只增的（第 4 章），也因为改写会作废改写点之后的全部 KV cache。唯一真正改写 surface 的是压缩，而它付出的代价是一次完整的事务：锁、稳定性检查、同步相邻的提交。

**重复的东西一律不发第二遍。** 快照比文本，目录比 digest，压缩比阈值。三处都在同一个 pre-step 里，三处都先问「这次真的需要吗」。省下来的是 token，也是模型的注意力。

**model-free 的那一半先做。** 压缩的顺序是先剪枝、再测量、还超才调模型。工具结果的中段是最容易删又最不心疼的东西，删完可能就不用花钱了。
