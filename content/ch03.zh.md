# 启动链：从 `dsh web` 到一棵插件树

前两章讲的是机制：fiber 怎么活、服务怎么找、事件怎么分发。这一章讲装配。

先给一个数字。跑一次 `dsh --profile web --dump-config`，输出 **129 行插件条目**。这 129 行没有一行写在 TypeScript 里，全部是 YAML 补丁叠出来的，起点是一个空数组 `[]`。

这一章走完那条从 argv 到 129 个 fiber 的链，并在最后让你自己造一个 profile、自己写一个插件、自己把它 patch 进树里。这就是第 12 章大作业的最小形态。

```

## 一、启动器只认自己的四个 flag

{{src:apps/cli/src/bin.ts#L27-L53|bin.ts:27-53}} 是全部的入口逻辑：

```ts
const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({
      environment: loadLayeredEnv('dsh'),
      profile: invocation.profile,
      patchFiles: invocation.patches,
      args: invocation.args,
    })
```

三种模式各自 `await import()`，一次调用只加载它这条路径要用的模块。`dsh plugin add foo` 不会把整个 boot 链拉进内存。

真正值得看的是 `parseDshArgs` 怎么划边界。{{src:apps/cli/src/args.ts#L122-L134|args.ts:122-134}}：

```ts
    .exitOverride()
    // The launcher's flags come first and end at the first token it does not
    // know; everything from there on belongs to the booted app, including
    // its -h. `dsh -h` with no profile still prints this help, below.
    .helpOption(false)
    .allowUnknownOption()
    .passThroughOptions()
    .enablePositionalOptions()
```

四个 commander 开关合起来只表达一件事：**启动器解析到第一个自己不认识的 token 就停手，剩下的原样交给树。**

`helpOption(false)` 是其中最容易被忽略的一个。它把 `-h` 也让了出去，所以 `dsh --profile web --help` 打印的是 web app 自己的帮助，不是启动器的。启动器只在完全没有 profile 可交接时才打印自己的（{{src:apps/cli/src/args.ts#L138-L141|args.ts:138-141}}）。

启动器认识的 flag 只有四个：`--profile`、`--patch`、`--dump-config`、`--dump-default-config`。除此之外它对 DSH 的功能一无所知。

那 app 的参数怎么到达插件？靠一个服务。{{src:packages/boot/cmdline/src/index.ts#L68-L72|provideCmdline}}：

```ts
export function provideCmdline(ctx: Context, host: CmdlineHost): void {
  const snapshot: readonly string[] = Object.freeze([...host.args])
  ctx.provide('cmdlineArgs', { get: () => snapshot })
  ctx.provide('appExit', host.exit)
}
```

两个 `provide`，就是第 2 章讲的那个 `provide`。命令行在 DSH 里没有任何特权，它就是一个普通服务，任何插件 `inject: ['cmdlineArgs']` 就能读。

:::key 这条边界的意义
启动器不知道 `--resume`、`--print`、`--model` 是什么意思，也不需要知道。一个新 app 插件想要新 flag，不用改启动器，注入 `cmdlineArgs` 自己解析即可。

第 12 章要加的东西如果需要命令行开关，走的就是这条路。
:::

## 二、profile：一个目录，两个文件

`--profile web` 指向 `$DSH_HOME/profiles/web/`。这个目录里只有两个文件是启动器关心的：

| 文件 | 作用 |
|---|---|
| `package.json` | `dsh.profile.bundles`：有序的 bundle 包名列表 |
| `cordis.patch.yml` | 你自己的补丁层，叠在所有 bundle 之上 |

还有一个 `cordis.yml`，内容永远是空数组。{{src:apps/cli/src/profile-boot.ts#L59-L64|PROFILE_ROOT_CONFIG}} 的注释解释了它为什么存在：

```
# dsh profile root — an empty entry list. The tree is composed as patches:
# each bundle in package.json's dsh.profile.bundles, then cordis.patch.yml, then any
# --patch overlays. Edit cordis.patch.yml, not this file.
[]
```

它存在只是因为 Include 插件需要一个真实文件来锚定 `baseUrl`。而且每次启动都会**重写**它（{{src:apps/cli/src/profile-boot.ts#L98-L103|prepareProfile}}）：

```ts
export function prepareProfile(name: string, userLayer = true): Profile {
  healProfilesModuleFallback(INSTALL_ANCHOR)
  const profile = loadProfile(NAME, name, INSTALL_ANCHOR, undefined, { userLayer })
  writeFileSync(join(profile.dir, PROFILE_ROOT_FILENAME), PROFILE_ROOT_CONFIG)
  return profile
}
```

无条件覆盖，原因写在函数注释里：Loader 有回写机制（一个插件自我销毁时会把当前树写回文件），如果不重置，下次启动会在已经有内容的根上再叠一遍 bundle 的 insert，每个插件出现两次。

### bundle 从哪里来

{{src:packages/boot/app-boot/src/profile.ts#L344-L355|resolveBundleDir}} 的解析顺序是硬约定：

```ts
for (const anchor of [installAnchor, join(profileDir, 'package.json')]) {
  const dir = packageDirFromAnchor(anchor, packageName)
  if (dir !== undefined) return dir
}
```

**先从 dsh 安装位置找，再从 profile 目录找。** 这保证 `@deepseek-ai/dsh-base` 永远和正在跑的 dsh 来自同一份安装，profile 里就算有个同名副本也压不过它。

反过来，用户自己 `pnpm add` 装进 profile 的第三方插件，Node 从 profile 目录的 `node_modules` 就能找到。两类插件各走各的路。

### 让站外插件也能 import 框架包

一个装在 profile 里的第三方插件，`import { Service } from '@deepseek-ai/cordis'` 要能解析到**同一份 cordis 实例**，否则第 1 章讲的那些 symbol 全部对不上。

{{src:packages/boot/app-boot/src/profile.ts#L223-L255|healProfilesModuleFallback}} 干这件事：在 `$DSH_HOME/profiles/node_modules/` 下为 dsh 依赖闭包里的每个包建一个软链。

```ts
const queue: { anchor: string; manifest: ProfileManifest }[] = [{ anchor: installAnchor, manifest: appManifest }]
for (let next = queue.shift(); next !== undefined; next = queue.shift()) {
  for (const dep of [...Object.keys(next.manifest.dependencies ?? {}), ...Object.keys(next.manifest.peerDependencies ?? {})]) {
    if (links.has(dep)) continue
    const dir = packageDirFromAnchor(next.anchor, dep)
    if (dir === undefined) continue
    links.set(dep, dir)
```

三处细节值得注意：

1. **是 BFS 闭包，不是直接依赖。** 注释给了原因：站外插件的 peer 依赖会点名 `dsh-compaction`、`dsh-invariants` 这类纯定义包，而 app 只通过实现包间接够到它们。只链直接依赖会漏。
2. **`peerDependencies` 一起参与。** 在 DSH 里「服务定义包」永远是实现包的 peer，不是 dependency。
3. **`links` 本身就是 visited 集**，先解析先赢，和 Node 自己的就近优先一致。

这个目录在 `profiles/` 下、每个 profile 目录的旁边，所以 Node 从任意 profile 向上走父目录时，第二站就能命中。pnpm 完全不管理它。

## 三、补丁栈：四层叠成一棵树

{{src:apps/cli/src/profile-boot.ts#L142-L171|composeProfile}} 决定叠加顺序，{{src:apps/cli/src/profile-boot.ts#L122-L129|allPatches}} 把它写死成一个数组：

```ts
function allPatches(composed: ComposedProfile): PatchOptions[] {
  return [
    ...composed.bundlePatches,
    ...composed.profile.patches,
    ...composed.homePatches,
    ...composed.overlays,
  ]
}
```

| 层 | 来源 | 谁写的 |
|---|---|---|
| 1 | 每个 bundle 的 `cordis.patch.yml`，按 `bundles` 顺序 | DSH 官方 |
| 2 | `$DSH_HOME/profiles/<name>/cordis.patch.yml` | 你，针对这个 profile |
| 3 | `$DSH_HOME/cordis.patch.yml` | 你，针对这台机器 |
| 4 | `--patch` 覆盖层 + 启动器派生的开关 | 本次调用 |

第 3 层压过第 2 层是刻意的：机器级偏好（比如「这台机器上一律关掉遥测」）应该对所有 profile 生效，所以它排在单个 profile 的设置后面。

第 4 层里有两个由代码派生的补丁，不来自任何文件。{{src:apps/cli/src/profile-boot.ts#L159-L169|profile-boot.ts:159-169}}：

```ts
if (rows.has('agent-presets')) {
  composedOverlays.push({
    id: 'agent-presets',
    config: { ...(rows.get('agent-presets')?.config ?? {}), roots: [{ path: SHIPPED_PRESET_ROOT, trust: 'system' }] },
  })
}
const telemetryPatch = resolveTelemetryPatch(process.env.DSH_TELEMETRY_DISABLED, rows.has(TELEMETRY_ROW_ID))
if (telemetryPatch !== undefined) composedOverlays.push(telemetryPatch)
```

两个都先判断 `rows.has(...)`，也就是**先把前三层合成一遍看看有没有这一行，再决定要不要补**。{{src:apps/cli/src/profile-boot.ts#L80-L83|resolveTelemetryPatch}} 的注释说明了理由：一个自定义 profile 可能根本没挂遥测，那么 `DSH_TELEMETRY_DISABLED` 就是天然满足的，不该为了它生造一个打不中的补丁。

顺带看一眼这个开关的判定：

```ts
if ((disabledEnv ?? '') === '' || !hasRow) return undefined
```

**任何非空值都算关闭**，包括 `'0'` 和 `'false'`。注释写得很直白：隐私开关宁可误关，不可误开。

### applyEntryPatches：补丁到底怎么打

所有层最后汇成一个扁平列表，交给 {{src:vendor/include/src/index.ts#L58-L128|applyEntryPatches}}。它是 Include 插件的核心，也是 `--dump-config` 用的同一个函数，所以 dump 出来的和真正挂载的不可能有偏差。

先建 id 索引：

```ts
const entryMap = new Map<string, EntryOptions>()
const buildMap = (entries: EntryOptions[]) => {
  for (const entry of entries) {
    if (entry.id) entryMap.set(entry.id, entry)
    if (entry.group && Array.isArray(entry.config)) {
      buildMap(entry.config)
    }
  }
}
```

group 行的 `config` 是子行数组，所以索引要递归下去。group 里的行同样能被外层补丁按 id 命中。

然后逐条应用。`insert` 分支：

```ts
if (insert) {
  if (id) {
    const target = entryMap.get(id)
    if (!target) { warn('patch insert: entry %C not found', id); continue }
    if (!target.group) { warn('patch insert: entry %C is not a group', id); continue }
    if (!Array.isArray(target.config)) target.config = []
    target.config.push(...insert)
  } else {
    data.push(...insert)
  }
  buildMap(insert)
  continue
}
```

最后那句 `buildMap(insert)` 是整个函数里最值得记的一行，注释也专门解释了它：

> Index what this patch added so a LATER patch in the same list can target it.

**刚插入的行要立刻进索引，否则后面的层动不了它。** 这正是 `dsh-web-app` 能覆盖 `dsh-base` 插入的行的原因：base 层用一个 `insert` 塞进 100 多行，web-app 层紧接着按 id 改其中几行。没有这一行，bundle 之间就完全无法互相配置。

非 insert 分支的最后三行是最容易踩的坑：

```ts
for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value
}
```

**整个 `config` 被替换，不是深合并。** `dsh-base` 的注释把这条规矩的后果写在了文件开头（{{src:packages/bundle/base/cordis.patch.yml#L1-L13|base bundle 的开头注释}}）：

> A patch replaces the targeted row's whole `config` rather than merging into it, so a row whose value differs by mode does NOT live here: it belongs to each mode bundle.

所以 base 里只放各模式通用的中性默认值，凡是按模式不同的配置，由每个模式 bundle 完整重述一遍。这样任何一行的最终值最多经过「一个 bundle 层 + 用户层」两次写入，追起来简单。

:::warn 写自己的补丁时
`config:` 里只写你要改的那个键，其余键会全部消失，因为它替换的是整个 config 对象。改一行之前先 `--dump-config` 看清它当前的完整配置。
:::

## 四、boot()：主干只有八行

补丁算完，进 {{src:packages/boot/app-boot/src/index.ts#L757-L802|boot()}}。剥掉注释和错误处理，主干是这样：

```ts
const ctx = new Context()
let stage = 'host preparation failed'
try {
  ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + '/'
  ctx.provide('dshHomePath', dshHomePath)
  await ctx.plugin(Loader)
  await prepare?.(ctx)
  stage = 'plugin tree failed to load'
  await mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)
  await ctx.get('loader')?.await()
  if (ctx.get('loader') === undefined) return ctx
  await assertEntriesActivated(ctx, binName)
  return ctx
}
```

`new Context()` 就是第 1 章那个根 Context。整个 DSH 的 129 个插件，全部挂在这一个根下面。

几个设计点：

**`stage` 变量分两段。** `prepare` 在任何配置行挂载之前跑，所以它失败是 host 装配的问题，不是插件树的问题。两个标签让错误信息一眼分清是谁的错。

**`prepare` 就是命令行注入的时机。** {{src:apps/cli/src/profile-boot.ts#L248-L259|profile-boot.ts:248-259}} 传进来的回调里只有三个 `provide`：环境快照、`cmdlineArgs`、`appExit`。注释说明了为什么必须在这里：

> Before any config-tree entry mounts, so plugins resolve all launch-time environment values from the same immutable provenance snapshot.

**每个 `await` 之后都重新检查 `ctx.get('loader')`。** 因为一个 app 可以在启动还没跑完时就要求退出（比如 `--help` 打印完就调 `appExit`），那时整棵树连同 Loader 服务已经被销毁。此时读 `ctx.loader` 会抛 TypeError，而实际上程序是完全按要求退出的。这个检查在 boot 里出现两次，在 `runProfile` 里还有一次。

**错误链会被展开。** {{src:packages/boot/app-boot/src/index.ts#L796-L800|index.ts:796-800}}：

```ts
let deepest: unknown = cause
while (deepest instanceof Error && deepest.cause !== undefined) deepest = deepest.cause
const stack = deepest instanceof Error && deepest !== cause ? `\n${deepest.stack ?? deepest.message}` : ''
```

Loader 每穿过一层树就包一层 `failed to apply loader entry ...`，最外层的 message 只是包装链。这段把最深处那个真正的异常抠出来附在后面，所以你看到的堆栈指向出错的插件本身。本章实验第二步会看到这个链的真实样子。

### mountRootInclude 挂了什么

{{src:packages/boot/app-boot/src/index.ts#L486-L529|mountRootInclude}} 只创建一个条目：

```ts
const rootInclude: EntryOptions = {
  id: 'include',
  name: 'cordis:include',
  config: includeConfig,
}
const includeId = await ctx.loader.create(rootInclude)
```

`cordis:` 前缀走的是 {{src:vendor/loader/src/config/tree.ts#L144-L162|EntryTree.import}} 的短路分支，直接从 `loader.builtins` 取对象，不经过任何模块解析。挂进 builtins 的有两个：`include` 和 `group`。

group 也在里面的理由写在注释里：

> a group row is how a composition gives one `isolate` realm to a provider and its consumers together, and an agent preset living outside this workspace cannot resolve `@deepseek-ai/cordis-plugin-group` by name.

这就是第 2 章讲的 isolate realm 落到配置层的样子：**group 行是给一组插件划一个隔离域的语法。** 一个装在 profile 外面的 agent preset 没法按包名解析到 group 插件，所以把它做成 builtin。

`id: 'include'` 是写死的，注释解释：这个 include 是 app 胶水而不是配置行，它的 id 会出现在 Loader 的失败链里，随机 id 会让启动诊断在每次运行之间都不一样。

## 五、Include 挂上去之后

{{src:vendor/include/src/index.ts#L273-L289|Include 的 Service.init}} 是一个生成器，第 1 章讲过这种写法：`yield` 出来的函数就是清理函数。

```ts
async* [Service.init]() {
  let candidate: ReadCandidate
  try {
    candidate = (await this.read(true))!
  } catch (error) {
    if (!(error instanceof ConfigFileError) || error.stage !== 'read' || (error.cause as NodeJS.ErrnoException)?.code !== 'ENOENT') throw error
    if (this.config.initial) {
      await this._writeFile(this.config.initial as any)
      candidate = (await this.read(true))!
    } else {
      throw new Error(`config file not found: ${this.filename}`)
    }
  }

  yield () => this.stop()
  await this.apply(candidate)
}
```

注意 `yield` 的位置：**读文件在 yield 之前，挂载子树在 yield 之后。**

这个顺序是有意的。读文件失败时还没有任何东西需要清理，直接抛就行。而 `apply()` 会创建一大批子 fiber，它们必须被 `stop()` 覆盖到，所以清理函数要在 apply 之前就注册好。第 1 章讲 `ctx.effect()` 保证「清理恰好执行一次」，这里是它在真实代码里的用法：**注册清理的时机决定了哪些东西会被清理。**

`_apply` 三行：

```ts
const data = this.applyPatches(candidate.data, this.config.patches)
await this.root.update(data)
this.content = candidate.content
```

补丁在这里打，然后交给 EntryGroup。

构造函数里还挂了一个 `internal/update` 监听（{{src:vendor/include/src/index.ts#L206-L213|include/index.ts:206-213}}），这是热重载的入口：外面更新 Include 的 config（换一批 patches），它就用**缓存的原始文件数据**重新打一遍补丁再 `root.update`。文件本身不用重读。第 2 章讲的 `cordis.patch.yml` 热更新走的就是这条路。

## 六、EntryGroup.update：并发创建，全量回滚

{{src:vendor/loader/src/config/group.ts#L59-L106|EntryGroup.update}} 是 129 行变成 129 个 fiber 的地方。

```ts
const outcomes = await Promise.allSettled(config.map(options => this.create(options)))
if (this.ctx.fiber.uid === null) return
const failures = outcomes
  .filter((outcome): outcome is PromiseRejectedResult => outcome.status === 'rejected')
  .map(outcome => outcome.reason)
if (failures.length === 1) throw failures[0]
if (failures.length > 1) throw new AggregateError(failures, 'loader entries failed to apply')
```

**`Promise.allSettled` 而不是 `Promise.all`。** 差别在于：`all` 会在第一个失败时立刻返回，剩下的插件还在半途中启动，没人管它们。`allSettled` 等所有条目都有结果，然后一次性收集全部失败，多个失败包成 `AggregateError`。

中间那句 `if (this.ctx.fiber.uid === null) return` 是第 1 章的知识点在这里的应用：`uid` 变成 `null` 意味着这个 fiber 已经被销毁。注释：

> Disposal owns termination: sibling starts can still be settling after the containing tree has gone away, but their failures no longer describe a live update to roll back.

树都没了，再谈回滚没有意义。

失败路径是完整回滚：

```ts
for (const id of Object.keys(newMap).reverse()) {
  if (oldMap[id]) continue
  try { await this.remove(id, true) } catch (rollbackError) { rollbackErrors.push(rollbackError) }
}
for (const options of oldConfig) {
  try { await this.create(options) } catch (rollbackError) { rollbackErrors.push(rollbackError) }
}
this.data = oldConfig
```

先倒序拆掉新建的（倒序，和第 1 章的清理顺序一致），再把旧配置逐条重建。回滚过程中的错误不会掩盖原始错误，而是一起塞进 `AggregateError`。

启动时 `oldConfig` 是空的，所以任何一行插件启动失败，整棵树都不留：新建的全部拆掉，什么也不恢复，然后 `boot()` 抛错。**DSH 没有「部分启动」这个状态。**

## 七、Entry.update：什么时候重启，什么时候只改配置

{{src:vendor/loader/src/config/entry.ts#L142-L246|Entry.update}} 有 100 行，但骨架是一个四分支的判定。先算 diff：

```ts
const diff = Object
  .keys({ ...candidate, ...legacy })
  .filter(key => !deepEqual(candidate[key], legacy[key]))
if (!diff.length && !force) return
```

然后按 diff 的内容分流。最关键的一行是：

```ts
const replace = diff.some(key => key === 'name' || key === 'inject' || key === 'group')
```

**只有 `name`、`inject`、`group` 三个字段变了才需要重启插件。** 其余的（主要是 `config`）走 `_patchContext`，插件对象本身不动，只调 `fiber.update(config)`。

理由是清楚的：`name` 换了要重新 import 一个模块；`inject` 换了会改变第 2 章讲的 `fiber.store` 快照内容和 epoch 指纹；`group` 换了整个节点的性质变了。`config` 变了则是插件自己该处理的事，Cordis 有 `internal/update` 事件专门通知它。

这就是为什么你改 `cordis.patch.yml` 里某一行的 `config`，那个插件是热更新而不是重启；而把它的 `inject` 列表改一下，它会整个重来。

四个分支各自都有回滚。以最复杂的 replace 分支为例：

```ts
try {
  await this._start(plugin)
} catch (error) {
  this.options = previousOptions
  try {
    await this._start(previousPlugin)
  } catch (rollbackError) {
    throw updateError('rollback', legacy, new AggregateError([error, rollbackError]))
  }
  this.context.emit('loader/partial-dispose', this, candidate, true)
  throw updateError('apply', candidate, error)
}
```

新插件启动失败就把旧的原样启回来。`previousPlugin` 在 dispose 之前就已经存好了引用，就是为了这一步。

### 接回第 1 章

链条的终点在 {{src:vendor/loader/src/config/entry.ts#L291-L302|Entry._start}}：

```ts
private async _start(plugin: any) {
  let fiber: Fiber | undefined
  try {
    await this._patchContext([])
    this.loader.showLog(this, 'apply')
    fiber = this.fiber = this.ctx.registry.plugin(plugin, this.options.config, this.getOuterStack)
    await fiber.await()
  } catch (error) {
    await this._dispose(fiber)
    throw error
  }
}
```

`this.ctx.registry.plugin(...)` 就是第 1 章逐行走读过的那个函数。**从 argv 到 fiber 的整条链，到这一行接上。** 一个 YAML 行最终就是一次 `registry.plugin()` 调用。

:::key 整条链
`dsh web` → `parseDshArgs` → `composeProfile`（四层补丁）→ `applyEntryPatches`（129 行）→ `mountRootInclude` → `Include[Service.init]` → `EntryGroup.update`（并发）→ `Entry._start` → `registry.plugin()` → fiber

再往下就是第 1 章的内容：`_reload` / `effect` / epoch。
:::

## 八、`!!js` 是惰性的

dump 出来的配置里有这样几行：

```yaml
- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject:
    - webStartup
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080
```

`!!js` 是 Include 定义的 YAML 标签（{{src:vendor/include/src/index.ts#L9-L23|JsExpr 类型与 entryListSchema}}），它把字符串包成 `{ __jsExpr: '...' }`，**解析时不求值**。

求值发生在 Loader 的一个事件监听里。{{src:vendor/loader/src/index.ts#L92-L101|internal/config 钩子}}：

```ts
ctx.on('internal/config', function (this: Fiber, _config, next) {
  const config = next()
  if (!this.entry || this.parent.fiber?.entry === this.entry) return config
  // Tree carriers (Group, Include) keep their configs literal
  const plugin = this.runtime?.callback as Record<PropertyKey, unknown> | undefined
  if (plugin?.[EntryGroup.key]) return config
  return interpolate(this.ctx, config)
}, { global: true })
```

这是第 2 章讲的 **waterfall 洋葱**的真实用例，而且是标准形态：先 `next()` 拿到内层结果，再对结果做加工。函数用的是 `function` 而不是箭头函数，因为它要 `this`（当前 fiber），这也是第 2 章讲过的作用域机制。

中间那个 `EntryGroup.key` 判断是必须的：Group 和 Include 的 config 里装的是**别的行的 config**，那些 `!!js` 属于别的行的 fiber，不能在这一层就求值。所以带这个标记的插件的 config 保持字面量。

求值本身是 {{src:vendor/loader/src/config/utils.ts#L5-L22|utils.ts:5-22}}：

```ts
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`)
```

`with (ctx)` 让表达式里可以直接写 `dshHomePath('sessions')` 而不用写 `ctx.dshHomePath(...)`，也可以直接写 `process.env.X`（从外层作用域来）。

### 为什么命令行能打赢配置文件

现在把这几件事拼起来：

1. `web-startup` 行提供 `webStartup` 服务，它在自己的 commander action 里解析 `--port` 之类的 flag。
2. `webserver` 行声明 `inject: [webStartup]`。第 1 章讲过，声明了依赖的 fiber 在依赖就绪前处于 PENDING，不会激活。
3. 激活时才触发 `internal/config`，此时 `ctx.webStartup` 已经存在，`!!js ctx.webStartup.port ?? 3080` 求值成功。

**没有任何一行代码在实现「命令行优先级高于配置文件」。** 这个行为是「服务解析 + 惰性求值 + inject 调度」三个已有机制的组合结果。{{src:packages/boot/cmdline/src/index.ts#L1-L17|cmdline 的模块注释}}把这条设计写成了一句话：

> No row has launcher-level command-line status.

:::key 这是 DSH 最典型的扩展点形状
想让你的插件被一个新 flag 控制，做法是：提供一个服务解析你的 flag，然后在配置里写 `inject` + `!!js`。不需要改启动器，不需要改任何已有代码。

第 12 章会用到这个形状。
:::

## 九、行序不是加载顺序

`dsh-base` 的 patch 文件开头有一句容易读漏的话（{{src:packages/bundle/base/cordis.patch.yml#L12-L13|base bundle 的最后两行注释}}）：

> Row order carries no load semantics (activation is service-availability driven); the grouping is for readers.

129 行的顺序对启动毫无影响。原因在第 1 章：fiber 的激活由 epoch 驱动，一个插件在它 `inject` 的服务全部就绪时才激活。`EntryGroup.update` 用 `Promise.allSettled` 把 129 行**同时**扔出去，谁先谁后由依赖关系自己决定。

所以你往树里加一行插件时，不用考虑放在哪一行。你只需要把 `inject` 写对。

## 十、启动失败长什么样

{{src:packages/boot/app-boot/src/index.ts#L692-L725|assertEntriesActivated}} 是最后一道关。树 settle 之后，它遍历每个条目查 fiber 状态：

```ts
if (state === FIBER_ACTIVE) continue
if (state === FIBER_FAILED) {
  try {
    await fiber.await()
  } catch (error) {
    rejectionReasons.push(error)
    failures.push(`${entry.options.name}: ${formatActivationError(error)}`)
  }
  continue
}
if (state === FIBER_PENDING) {
  const missing = Object.keys(fiber.inject).filter(service => fiber.ctx.get(service) === undefined)
  const subject = missing.length === 1 ? 'service' : 'services'
  failures.push(`${entry.options.name}: pending (waiting for ${subject}: ${missing.join(', ') || 'unknown'})`)
}
```

两类失败的诊断方式完全不同：

- **FAILED**：插件自己抛了异常。异常存在 fiber 私有状态里，只有 `await fiber.await()` 才能拿到，所以这里故意 await 一个已知会 rejected 的 promise，把原因捞出来。
- **PENDING**：插件没抛异常，它只是永远等不到依赖。这种情况没有异常可报，所以现算一遍**哪些 inject 的服务至今是 undefined**，把服务名列出来。

PENDING 这一支是新手最常撞到的：插件写得没问题，就是永远不启动，也没有任何报错。这个诊断把「在等谁」直接印出来。本章实验第四步会造一个出来看。

:::note 为什么只 await FAILED 的 fiber
ACTIVE 的不用等，PENDING 的一等就永远不返回。只有 FAILED 的 fiber 有一个已经 settle 的 rejected promise，await 它会立刻抛出。
:::

:::lab 动手实验：造一个自己的 profile

四步。前两步只看不写，后两步你自己造一个能跑的插件。

**第 1 步：看清 129 行**

用一个临时的 `$DSH_HOME`，不碰你自己的 `~/.dsh`：

```sh
cd deepseek-harness
export LAB=/tmp/dsh-lab
mkdir -p $LAB
DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile web --dump-config > $LAB/web.yml
grep -c '^- id:' $LAB/web.yml     # 129
grep '^# ==' $LAB/web.yml | head  # 每段来自哪个 bundle
```

`# ==` 注释是 `renderConfigDump` 生成的溯源标记。留意 `patched by @deepseek-ai/dsh-web-app` 那几段，那就是第三节讲的「后层按 id 改前层插入的行」。

顺便看一眼刚被创建出来的 profile：

```sh
cat $LAB/profiles/web/package.json   # bundles: [dsh-base, dsh-web-app]
cat $LAB/profiles/web/cordis.yml     # []
```

第一次跑 `web` 这个名字时，`loadProfile` 从 `PROFILE_TEMPLATES` 自动初始化了它。

**第 2 步：造一个只有你自己插件的 profile**

自定义 profile 名字没有模板，所以手写 `package.json`。bundles 留空，整棵树完全由你决定：

```sh
mkdir -p $LAB/profiles/lab
cat > $LAB/profiles/lab/package.json <<'EOF'
{
  "name": "dsh-profile-lab",
  "private": true,
  "dsh": { "profile": { "bundles": [] } }
}
EOF

cat > $LAB/profiles/lab/hello.mjs <<'EOF'
export const inject = ['cmdlineArgs', 'appExit']
export function apply(ctx, config) {
  console.log('[hello] config =', JSON.stringify(config))
  console.log('[hello] args   =', JSON.stringify(ctx.cmdlineArgs.get()))
  ctx.appExit(0)
}
EOF

cat > $LAB/profiles/lab/cordis.patch.yml <<'EOF'
- insert:
    - id: hello
      name: ./hello.mjs
      config:
        greeting: hi
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --some-app-flag 42
```

输出：

```
[hello] config = {"greeting":"hi"}
[hello] args   = ["--some-app-flag","42"]
```

这就是全部。一个导出 `apply` 的模块 + 一条 YAML 行 = 一个 DSH 插件。

两点值得停下来看：

- `--some-app-flag 42` 启动器完全不认识，原样进了 `cmdlineArgs`。这就是第一节那条边界。
- 用 `.mjs` 后缀是因为 profile 目录的 `package.json` 没有 `"type": "module"`，Node 会按 CJS 处理 `.js`。真实插件是独立的 npm 包，各自声明自己的 type。

**第 3 步：用 `--patch` 覆盖它**

```sh
cat > $LAB/over.yml <<'EOF'
- id: hello
  config:
    greeting: overridden
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml --dump-config
DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml
```

dump 的溯源注释变成：

```
# == …/profiles/lab/cordis.patch.yml, patched by …/over.yml
- id: hello
  name: ./hello.mjs
  config:
    greeting: overridden
```

启动输出 `greeting: overridden`。第 4 层压过第 2 层，和第三节的表一致。

**第 4 步：造一个永远等不到依赖的插件**

```sh
cat > $LAB/profiles/lab/broken.mjs <<'EOF'
export const inject = ['workspace']
export function apply(ctx) {
  console.log('[broken] never reached')
}
EOF

cat > $LAB/profiles/lab/cordis.patch.yml <<'EOF'
- insert:
    - id: hello
      name: ./hello.mjs
      config:
        greeting: hi
    - id: broken
      name: ./broken.mjs
EOF

cat > $LAB/over.yml <<'EOF'
- id: hello
  disabled: true
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml
```

`workspace` 服务在这个 profile 里没人提供，所以 `broken` 永远停在 PENDING。输出：

```
Error: dsh: plugin tree failed to load: dsh: 1 entry did not activate
./broken.mjs: pending (waiting for service: workspace)
    at boot (…/app-boot/src/index.ts:800:11)
```

这就是第十节讲的 PENDING 诊断。`waiting for service: workspace` 是现场算出来的，不是插件报的错。

这一步顺便验证了另一件事：这里必须先用 `disabled: true` 关掉 `hello`。否则 `hello` 会调 `appExit(0)`，整棵树在 `assertEntriesActivated` 跑到之前就被销毁了，`boot()` 在 `ctx.get('loader') === undefined` 那一行提前返回，你根本看不到这个诊断。第四节讲的那个检查，就是这个场景。

```sh

```

## 小结

这一章的链条：

| 阶段 | 代码 | 产物 |
|---|---|---|
| 解析 argv | `parseDshArgs` | 启动器的四个 flag + 剩下的原样透传 |
| 找 profile | `loadProfile` / `resolveBundleDir` | bundle 列表 + 用户补丁层 |
| 叠补丁 | `composeProfile` / `applyEntryPatches` | 129 行条目 |
| 装配 | `boot` / `mountRootInclude` | 一个根 Context + 一个 Include |
| 展开 | `EntryGroup.update` / `Entry._start` | 129 次 `registry.plugin()` |
| 验收 | `assertEntriesActivated` | 全 ACTIVE，或者一条指名道姓的诊断 |

三个结论：

**配置即代码结构。** 没有中心化的 app 装配文件，一棵树完全由补丁栈决定。要改 DSH 的组成，改 YAML 就够了，第二步实验里那个 profile 是从零构造的。

**补丁替换整个 config，不合并。** 这条规矩逼着 bundle 之间保持「一行的值最多两层写入」，代价是写补丁时必须重述整行配置。

**优先级不是特判出来的。** 命令行打赢配置文件，靠的是 `inject` 让 fiber 等到服务就绪、`!!js` 让配置惰性求值。第 12 章要接的所有扩展点，形状都和它一样。

下一章讲会话日志：DSH 怎么记录一次对话，为什么「模型可见即已记录」这条约束会反过来决定数据结构的形状。
