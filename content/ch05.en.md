# The agent loop: one turn from start to finish

The previous chapter covered how events get recorded. This one covers who appends them.

The `dsh-agent-loop` README opens with a sentence worth memorizing:

> This is the only package in the harness that contains concrete loop logic. Everything else is an abstract service or a plugin against extension points.

**Exactly one package in the harness holds concrete loop logic.** Of 219 packages, every other one is an abstract service or a plugin hanging off an extension point. So the final answer to "where is DSH's control flow" is the 496 lines this chapter walks.

Start with what one run produces. The lab uses a fake model adapter (tool call first, text second) to drive a real agent, and the log is these 23 events:

```

 1 turn/start                 the turn opens
```

## 1. Three nested loops

The driver is three nested `while`s, each with a different exit condition.

**The outermost** is {{src:packages/core/agent-loop/src/agent.ts#L210-L223|kick}}:

```ts
private async kick(): Promise<void> {
  try {
    while (await this.turn()) {}
  } catch (_error) {
    // Reported failures and cancellation are contained at the driver boundary.
  } finally {
    if (this.phase.kind === 'running') {
      const { turn, wakeRequested } = this.phase
      this.setPhase({ kind: 'idle', lastTurn: turn })
      if (wakeRequested && this.inbox.hasPending) this.wakeDriver()
    }
  }
}
```

`while (await this.turn()) {}` with an empty body. `turn()` returning `true` means the queue still holds work, so another turn opens; `false` stops and goes idle.

The empty `catch` is not swallowing errors: the failure was already reported deeper down through the `agent/error` event, and this only keeps it from escaping the driver boundary. Chapter 4 established that a committed thing cannot be un-committed by an observer's failure; this is the other half of the same idea. **The driver is where failures stop.**

**The middle layer** is the `while (true)` inside {{src:packages/core/agent-loop/src/agent.ts#L246-L330|turn()}}, one iteration per step.

**The innermost** is the `while (true)` inside {{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}}, which exists for exactly one purpose: retrying a failed request.

## 2. Phase: three states and one latch

{{src:packages/core/agent-loop/src/agent.ts#L38-L46|Phase}} is a three-way union:

```ts
type Phase =
  | { kind: 'idle'; lastTurn: number }
  | { kind: 'maintenance'; abort: AbortController; lastTurn: number; wakeRequested: boolean }
  | { kind: 'running'; abort: AbortController; turn: number; step: number; wakeRequested: boolean }
```

The externally visible `status` has only two values: both `maintenance` and `idle` report `'idle'`. Maintenance is the "exclusive but not a model turn" state, and work like compaction runs inside it.

The interesting part is the `wakeRequested` latch. In {{src:packages/core/agent-loop/src/agent.ts#L172-L193|wakeDriver}}:

```ts
private wakeDriver(wakeAfterAbort = false): void {
  if (this.phase.kind !== 'idle') {
    const reason = this.phase.abort.signal.reason as AgentCancelCause | undefined
    if (reason?.kind !== 'disposed' && (this.phase.kind === 'maintenance' || wakeAfterAbort)) {
      this.phase.wakeRequested = true
    }
    return
  }
  ...
}
```

When new input arrives while the driver is busy, usually nothing is needed: a live driver claims the queue itself at the next step boundary. But two situations mean it will never come and take it:

1. the phase is **maintenance**, which has no step boundaries;
2. the current driver is **already aborted** and is on its way out.

Those two set `wakeRequested`, and the convergence point (`kick`'s `finally`, or `runMaintenance`'s) replays the wake.

`reason?.kind !== 'disposed'` is the exception to the exception: **disposal never latches.** Otherwise unloading would start a fresh model turn.

### An ordering the comment calls out

{{src:packages/core/agent-loop/src/agent.ts#L113-L120|send()}} is six lines, and every one matters:

```ts
send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
  // Waking input cannot join an aborted activity, so it starts the next turn.
  // Captured before the insertion so a reentrant cancel from a splice observer cannot reclassify it.
  const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
  const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
  this.inbox.splice(resolvedTarget, Infinity, 0, [message])
  if (wakeup) this.wakeDriver(wakingAfterAbort)
}
```

`wakingAfterAbort` is **computed before the insertion**. The reason is in the second comment line: `inbox.splice` appends an `agent/inbox/spliced` event, and chapter 4 established that an append synchronously invokes a batch of `session/event` listeners. Any one of them could call `agent.cancel()` in turn. Computing the classification after the insertion would let one observer's side effect flip the same message from "joins the current turn" to "starts a new one".

Classify first, insert second, and the classification is locked.

## 3. The inbox: two queues

{{src:packages/core/agent/src/inbox.ts#L28-L40|Inbox}} holds two queues with quite different semantics:

| Queue | How it is consumed | Purpose |
|---|---|---|
| `next-turn` | **one** at a time (FIFO) | queued user prompts, one turn each |
| `next-step` | the **whole batch** | between-step input: steering, tool-produced context, injections |

The three public methods are fixed presets of one `send()`, differing only along (target × wakeup):

| Method | target | wakeup | Effect |
|---|---|---|---|
| `followup()` | `next-turn` | yes | queue a new turn and wake |
| `steer()` | `next-step` | yes | slip into the next step boundary and wake |
| `inject()` | `next-step` | no | slip into the next step boundary without waking |

That `inject()` does not wake matters: file-change notices, AGENTS.md, and skill content all go through `inject()`, and they only make sense when a turn is **already active**. Injecting context into an idle agent and thereby spending a model call is nobody's intent.

{{src:packages/core/agent/src/inbox.ts#L71-L78|claim()}} is the pickup at a step boundary:

```ts
claim(target: InboxTarget, turn: number): UserMessage[] {
  const claimed = this.mutate('next-step', 0, this.nextStep.length, [], false)
  if (target === 'next-turn') {
    claimed.push(...this.mutate('next-turn', 0, 1, [], false))
  }
  for (const message of claimed) this.notifications.claimed(message, turn)
  return claimed
}
```

All of `next-step`, exactly one of `next-turn`. That trailing `false` is `discardRemoved`: **a claim is a pure deletion, not a cancellation.** On disk the difference is whether the event carries `outcome: 'canceled'`, so a replay can tell "this message was consumed" from "this message was withdrawn".

### The inbox is a log projection too

The last lines of {{src:packages/core/agent/src/inbox.ts#L158-L193|mutate()}}:

```ts
this.validate(splice)
const event = this.session.append('agent/inbox/spliced', splice)
const removed = inbox.splice(actualStart, actualDeleteCount, ...event.data.inserted)
```

**Log first, mutate memory second.** The method comment explains:

> The durable event commits before the live projection mutates, so synchronous `session/event` observers see the pre-splice lists and can reconstruct the removed messages from the normalized coordinates.

A synchronous observer sees the **pre-change** queues plus normalized coordinates, and subtracting one from the other yields what was removed. The event does not need to redundantly store the removed messages.

The constructor goes the other way, replaying memory state from the log:

```ts
for (const event of session.events.slice(session.header.seedLength ?? 0)) {
  if (event.type !== 'agent/inbox/spliced') continue
  this.apply(event.data)
}
```

So resuming a persisted session brings back the prompts that were queued but never processed. The inbox and chapter 4's surface are the same kind of thing: **an incremental projection of the log.**

## 4. turn(): boundaries always pair

{{src:packages/core/agent-loop/src/agent.ts#L246-L330|turn()}} is the function in this chapter most worth reading line by line. The skeleton:

```ts
const turn = phase.turn + 1
this.session.append('turn/start', { turn })
phase.turn = turn
let turnEnds: TurnEndReason | null = null
let target: InboxTarget = 'next-turn'
try {
  while (true) { /* one lap per step */ }
} catch (error) {
  ...
} finally {
  this.session.append('turn/end', { turn, reason: turnEnds! })
}
```

**`turn/end` is appended in `finally`.** Whether the turn ends normally, is rejected, throws, or is cancelled, that event lands. `step/end` likewise:

```ts
try {
  for (const message of decision.messages) {
    this.session.append('user/message', message, { surfaceOp: 'append' })
  }
  const stepEnd = await this.step(decision.assembly)
  if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
} finally {
  this.session.append('step/end', { turn, step })
}
```

So `turn/start`/`turn/end` and `step/start`/`step/end` nest strictly in the log, and a replayer never has to handle "opened but never closed".

### Where turnEnds gets assigned

This variable decides what reason `turn/end` records, and its four assignment sites are the four possible endings:

```ts
if (decision.kind === 'reject') {
  turnEnds = { kind: 'blocked' }
  return false
}
```

`agent/pre-step` rejected: the turn opened and no step ran. Lab step 3 produces one, with a four-event log.

```ts
if (phase.step === 0 && decision.messages.length === 0) {
  turnEnds = { kind: 'completed' }
  return false
}
```

**The waking message was withdrawn, or a plugin rewrote the decision to empty.** The comment states the tradeoff:

> A removed waking message or an enter decision rewritten to empty still owns the initial turn boundary, but it spends no model call.

An opened turn boundary must be closed, but it costs no model call.

```ts
if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
```

**max-tokens is sticky.** Once any step hits the output ceiling, later steps that complete normally must not downgrade the turn's conclusion, because "something in this turn was truncated" is a fact the caller must know.

```ts
} catch (error: unknown) {
  if (signal.aborted) {
    turnEnds = { kind: 'aborted', reason: signal.reason as AgentCancelCause }
    throw error
  }
  turnEnds = {
    kind: 'error',
    error: error instanceof LlmError ? error.failure : { message: errorChain(error), code: 'UNKNOWN' },
  }
  this.throwError(error)
}
```

Cancellation and failure are separated. Cancellation stores `signal.reason` verbatim, so a replay can tell a user stop from a hook block from a parent shutdown. Failure is always structured: an `LlmError` keeps its facts, anything else flattens to `errorChain` text under `UNKNOWN`. **An unstructured error never reaches the log.**

### When the next step runs

```ts
if (turnEnds && this.inbox.nextStep.length === 0) {
  await this.dispatch.serial('agent/turn-stopping', { turn, signal })
  signal.throwIfAborted()
}
if (turnEnds && this.inbox.nextStep.length === 0) break
target = 'next-step'
```

The same condition is tested twice with one `agent/turn-stopping` in between. Not a typo: a `turn-stopping` listener **may push into `next-step`** and thereby keep the turn going. The first test decides whether to ask; the second, after asking, is the one that counts. This is the "last chance to continue" extension point, and goal-mode continuation hangs off it.

Note `target = 'next-step'`: **from the second step on, queued prompts are no longer consumed.** In the opening 23 lines, the `step/start` at seq 15 has no `user/message` after it for exactly this reason; the second step's input is the `tool/result` the previous step left on the surface.

Finally:

```ts
if (!this.inbox.hasPending) return false
phase.abort = new AbortController()
phase.wakeRequested = false
phase.step = 0
return true
```

**A fresh AbortController.** If the previous turn was cancelled, that controller is already aborted, and reusing it would make the new turn throw immediately. The latch is cleared at the same time, as the comment explains: a live driver claims the queue itself, so a latch on the old controller is stale.

## 5. step(): one model call

One lap of {{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}}:

```ts
const { request, preparedCall } = await this.buildRequest(
  turn, step, assembly.tools, system, this.session.deriveMessages(), signal,
)
```

The fifth argument is chapter 4's `deriveMessages()`. **Every step re-derives**, and the driver keeps no message array of its own. That is the direct consequence of "the log is the truth" on the calling side: a compaction plugin appending a replace event between two steps automatically changes the next step's request, with nobody notifying the driver.

```ts
const assembler = new BlockAssembler()
const chunkSeqs: number[] = []
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
for await (const chunk of stream) {
  signal.throwIfAborted()
  chunkSeqs.push(this.session.append('assistant/chunk', { turn, step, chunk }).seq)
  assembler.push(chunk)
}
```

Every chunk lands in the log, and `append`'s return value supplies the seq, accumulating into `chunkSeqs`. Seqs 7-10 in the opening log are those four, and the `assistant/message` at seq 11 carries `sourceEventSeqs: [7,8,9,10]`. Chapter 4's provenance chain is filled in here.

`signal.throwIfAborted()` is the first line of the loop body, **checked once per chunk**. Cancellation takes effect anywhere in the stream, and chunks already logged are not rolled back.

```ts
const finish = assembler.finish
if (finish.kind === 'error' || finish.kind === 'aborted') {
  const action = await this.dispatch.waterfall('agent/request-error', { ... },
    () => Promise.resolve<RequestErrorAction>(undefined))
  if (action?.kind !== 'retry') {
    throw new LlmError(finish.failure.message, finish.failure.code, finish.failure)
  }
  continue
}
```

**No retry by default.** The built-in behaviour returns `undefined`, and only a plugin explicitly answering `{ kind: 'retry' }` takes a second lap. Chapter 2's waterfall onion shows up again in the "deny by default, capability supplied by plugins" shape, the mirror image of `tools/pre-execute` (which allows by default). `dsh-llm-retry` is the plugin on this point.

```ts
this.session.append('assistant/message', { turn, step, message, ...usage },
  { surfaceOp: 'append', sourceEventSeqs: chunkSeqs })
if (finish.kind === 'max-tokens') return { kind: 'max-tokens' }

const toolCalls = message.content.filter(block => block.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }
const { concluded } = await executeToolCalls(
  this.loopCtx, turn, step, toolCalls, signal,
  context => this.inbox.splice('next-step', this.inbox.nextStep.length, 0, [context]),
)
return concluded ? { kind: 'completed' } : null
```

Three return values define the outer loop's behaviour:

| Return | Meaning | What turn() does |
|---|---|---|
| `{ kind: 'max-tokens' }` | hit the output ceiling | record as the ending reason (and it sticks) |
| `{ kind: 'completed' }` | no tool calls, or a tool declared the turn concluded | record as the ending reason |
| `null` | tools ran, the model must be asked again | run another step |

`null` is the ReAct loop's "keep going". The `React` in `ReactLoopAgent` is reason-act alternation.

That last arrow function is **where tool-produced context goes**: straight into the `next-step` queue. So a tool may attach a user-role context message alongside its result, and it gets claimed at the next step boundary.

## 6. buildRequest: the header is written only when it changes

{{src:packages/core/agent-loop/src/agent.ts#L407-L495|buildRequest}} is 88 lines doing four things.

**One, compute this call's config proposal and let plugins edit it.**

```ts
const seedConfig = deepFreeze(structuredClone(
  this.requestHeaderLogged ? requestProposal(persistedHeader!) : { ...route, ...reasoningEffort, ...maxTokens }
))
const proposedConfig = await this.dispatch.waterfall('agent/request', { turn, step, signal },
  () => Promise.resolve(seedConfig))
```

That small `requestProposal` helper is worth reading:

```ts
function requestProposal(header: EpochHeader): LlmCallConfig {
  if (header.adapterDefaults === undefined) return header.config
  const proposal = { ...header.config }
  if (header.adapterDefaults.reasoningEffort === true) delete proposal.reasoningEffort
  if (header.adapterDefaults.maxTokens === true) delete proposal.maxTokens
  return proposal
}
```

**Adapter-supplied defaults are stripped before plugins see the proposal.** Chapter 4 mentioned the `adapterDefaults` marker map, which distinguishes "the user set this" from "the adapter filled it in for that exact model". Without stripping, a plugin would see a config already frozen by the previous resolution, and switching models would carry the old model's defaults along.

**Two, hand the proposal to the adapter.**

```ts
try {
  preparedCall = await this.loopCtx.llm.prepareCall(proposedConfig, signal)
  config = preparedCall.config
} catch (error) {
  if (!(error instanceof LlmError) || error.code !== 'NO_ADAPTER') throw error
  config = proposedConfig
}
```

`NO_ADAPTER` alone passes through, and the comment explains: middleware may serve a route with no registered adapter. Only terminal dispatch actually requires one.

**Three, write the request header, but only when it changes.**

```ts
const baseline = this.session.requestHeader()
if (!this.requestHeaderLogged) {
  this.session.append('request/header', { header, reason: baseline === undefined ? 'initial' : 'resume' })
  this.requestHeaderLogged = true
} else if (baseline === undefined || !headerEquals(baseline, header)) {
  this.session.append('request/header', { header, reason: 'change' })
}
```

The three reasons each mean something: `initial` is a brand-new session's first header, `resume` is this loop instance's first header over an existing log (process restart, fork seed), and `change` is a later request that used a different config. `baseline` comes from chapter 4's incremental fold `session.requestHeader()`.

A request header contains the full system prompt and every tool schema, so writing one per step would balloon the log. Writing only on change and folding to the latest on replay is cheap on both sides. In the opening log, seq 5 appears once and the second step does not rewrite it.

**Four, freeze and mark.**

```ts
const request = markAgentLoopRequest(deepFreeze({ ...header.config, messages: boundaryMessages, ... }))
```

`markAgentLoopRequest` registers the request object in a process-local identity set owned by `dsh-llm`. The invariant companion uses it to tell "a loop-built request" from "a plugin's direct one-shot call", because only the former should be reconstructible from the log.

## 7. Tool scheduling: concurrent execution, model-ordered commits

{{src:packages/core/agent-loop/src/tool-calls.ts#L59-L101|executeToolCalls}} cuts a step's tool calls into groups:

```ts
while (next < planned.length) {
  const first = planned[next]!
  const mode = ctx.tools.executionMode(first.exec).kind
  const group = mode === 'parallel' ? planned.slice(next) : [first]
  const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
  next += outcome.consumed
  ...
}
```

A `parallel` call takes everything from here to the end (subdivided later); anything else takes exactly one and forms a barrier. Writing files and running commands are exclusive; reads and searches are parallel.

{{src:packages/core/agent-loop/src/tool-calls.ts#L121-L246|runGroup}} is this section's core, held up by two invariants.

**Invariant one: commits advance only along contiguous model order.**

{{src:packages/core/agent-loop/src/tool-calls.ts#L146-L160|commitReady}}:

```ts
const commitReady = async (): Promise<void> => {
  while (committed < group.length) {
    const slot = slots[committed]
    if (slot === undefined) break
    ...
    appendToolResult(session, turn, step, call!.block, result, callSeqs[committed]!)
    for (const context of result.additionalContexts ?? []) acceptContext(context)
    concluded ||= result.concludesTurn === true
    committed++
  }
}
```

Three calls run concurrently, and the third finishing first still waits: `slots[committed]` is undefined, so the loop breaks. Only once the first and second land does it commit through.

**Execution may be out of order; the log must not be.** If the `tool/result` sequence the model sees next differs from the `tool/call` order it emitted, the same set of calls would produce two different histories across two runs, and replay would stop being deterministic.

**Invariant two: a registry change can create a barrier mid-group.**

{{src:packages/core/agent-loop/src/tool-calls.ts#L198-L213|fillPool}}:

```ts
while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
  const nextCall = group[nextToStart]!
  if (nextToStart > 0 && mode === 'parallel'
    && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
  await startCall(nextToStart)
  nextToStart++
  ...
}
```

`executionMode` is **re-read before starting each new call**, because an earlier tool may have just changed the registry (a tool switching permission mode, say), and calls that were parallel should immediately become exclusive. After the `break`, the outer `executeToolCalls` regroups with the new mode.

### How cancellation ends

The tail of {{src:packages/core/agent-loop/src/tool-calls.ts#L237-L245|runGroup}}:

```ts
if (aborted) {
  for (const call of group.slice(started)) appendSkippedToolCall(session, turn, step, call.block)
  return { consumed: group.length, aborted: true, concluded }
}
```

Already-started calls drain and commit their results normally, while **unstarted ones get a synthetic call/result pair** ({{src:packages/core/agent-loop/src/tool-calls.ts#L249-L259|appendSkippedToolCall}}):

```ts
appendToolResult(session, turn, step, block, {
  content: [{ type: 'text', text: 'Error: tool call aborted before dispatch' }],
  isError: true,
  error: { message: 'tool call aborted before dispatch', info: { name: 'AbortError', code: TOOL_ABORTED_BEFORE_DISPATCH } },
}, callSeq)
```

The module comment gives the reason:

> Abort records synthetic error results for skipped calls so replay stays valid.

The model emitted 5 tool calls, so the log must hold 5 results. One short, and the replayed history contains a dangling call that confuses the model. So a cancellation fabricates a "cancelled" result rather than break the pairing.

A scheduler failure is the opposite: it **fabricates nothing**, keeping only the `tool/call` events already recorded. That is not the fact "a call was cancelled" but "the harness itself broke", and a fabricated result would hide it.

Lab step 4 shows what cancellation actually looks like: the tool had started, its result commits normally, and `turn/end` records `{"kind":"aborted","reason":{"kind":"user"}}`.

## 8. Five extension points

Every `dispatch.waterfall` / `dispatch.serial` in the driver is the complete set of loop-level extension points DSH exposes:

| Event | Mode | When | What it can do | Default |
|---|---|---|---|---|
| {{src:packages/core/agent/src/runtime-types.ts#L222-L231\|`agent/pre-step`}} | waterfall | before each step | reject the whole turn, or rewrite the messages entering the step | allow, messages unchanged |
| {{src:packages/core/agent/src/runtime-types.ts#L236-L244\|`agent/request`}} | waterfall | while assembling the request | change provider / model / sampling params | use the seed config |
| `agent/request-error` | waterfall | after a failed request | ask for a retry | no retry, throw |
| {{src:packages/core/agent/src/runtime-types.ts#L270-L278\|`agent/turn-stopping`}} | serial | as the turn is about to end | push into `next-step` to continue it | nothing |
| `agent/error` | emit | when a failure occurs | observe | none |

These five cover "block a step, swap the model, retry, extend a turn, watch". Chapter 4's `session-checkpoint-policy` hangs off `agent/pre-step` for its durability checkpoint; lab step 3 uses the same point for a content block.

:::key There is no sixth loop extension point
Changing loop behaviour means picking one of these five. Tool-level extension (new tools, execution policy, approval) goes through the `tools/*` events of chapters 8 and 9, which are a separate set.

For chapter 12's multi-agent direction, `agent/pre-step` and `agent/turn-stopping` are the two most direct handles.
:::

## Summary

One turn end to end:

```
followup() → inbox.splice → wakeDriver → kick
  → turn(): turn/start → preStep → claim → step/start → user/message
      → step(): buildRequest → llm.stream → chunk×N → assistant/message
          → executeToolCalls → tool/call / tool/result
      → step/end → next step, or turn-stopping → turn/end
  → queue empty → idle
```

Three conclusions:

**Boundary events are written in `finally`.** `turn/end` and `step/end` land however the code exits, so a replayer never handles "opened but never closed". Cancellation and failure each put a structured reason into `turn/end`.

**Execution may be out of order; the log must not be.** Tools run concurrently, but `commitReady` commits only along contiguous model order, and cancellation fabricates results for unstarted calls to preserve pairing. Both exist so one set of calls yields one history on every replay.

**Every step re-derives with `deriveMessages()`.** The driver holds no message array. That is what lets compaction, injection, and steering take effect without notifying the driver, and it is chapter 4's design paying off on the calling side.

The next chapter goes one layer down into the LLM layer: the streaming protocol behind `llm.stream()`, the adapter contract, and how `BlockAssembler` reassembles a run of deltas into message blocks.
