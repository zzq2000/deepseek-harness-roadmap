## 一、`ctx.tools` 不是属性，是一次查找

第 1 章讲过 `ctx` 是个 Proxy。现在看那个 Proxy 的 `get` 陷阱到底做了什么。{{src:vendor/cordis/src/reflect.ts#L136-L171|ReflectService.handler.get}}：

```ts
get: (target, prop, ctx: Context) => {
  if (isSpecialProperty(prop)) {
    return Reflect.get(target, prop, ctx)
  }
  if (Reflect.has(target, prop)) {
    return getTraceable(ctx, Reflect.get(target, prop, ctx))
  }

  const error = new Error(`cannot get property "${prop}" without inject`)
  ...
```

开头两个分支是快速通道。{{src:vendor/cordis/src/reflect.ts#L86-L91|isSpecialProperty}} 定义了什么叫「特殊」：

```ts
// - is a symbol
// - is a reserved word (prototype, then)
// - is a number string (0, 1, 2, ...)
// - starts with `_`
function isSpecialProperty(prop: string | symbol): prop is symbol {
  return typeof prop === 'symbol'
    || RESERVED_WORDS.includes(prop)
    || parseInt(prop).toString() === prop
    || prop.startsWith('_')
}
```

`then` 在保留字里，这一条直接关系到第 1 章讲过的 `await ctx.plugin(...)`：如果 `ctx.then` 也走服务解析，那么任何 `await ctx` 都会触发一次查找并抛错。把它划进特殊属性，`ctx` 就永远不会被误认成 thenable。

注意第三行那个 `error` 对象：它在**查找开始前**就被创建了。这不是浪费，而是为了**在这里捕获调用方的栈**。等到查找失败时再 `new Error()`，栈顶就变成框架内部了，用户只会看到一堆 cordis 的帧。这种「提前造错误对象只为留栈」的手法，第 1 章在 `buildOuterStack` 里已经见过一次。

### 真正的查找

跳过 accessor 分支，核心是这段循环（{{src:vendor/cordis/src/reflect.ts#L153-L167|reflect.ts:153-167}}）：

```ts
return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
  const key = target[symbols.isolate][prop]
  let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber
  while (true) {
    const impl = fiber.store?.[prop]
    if (impl) return getTraceable(ctx, impl.value)
    if (prop in fiber.inject) {
      error.message = `cannot get required service "${prop}" in inactive context`
      throw error
    }
    if (!fiber.runtime) throw error
    if (fiber.parent[symbols.isolate][prop] !== key) throw error
    fiber = fiber.parent.fiber
  }
})
```

**读一个服务名，是沿着 fiber 链向上走。** 逐句拆这个循环：

1. `const key = target[symbols.isolate][prop]` 取出这个服务名在当前上下文的**隔离标签**。第四节会讲它。
2. `fiber.store?.[prop]` 查当前 fiber 的服务快照。命中就返回。
3. `if (prop in fiber.inject)` 这一条最关键：**声明了依赖，但快照里没有**。这只可能发生在 fiber 还没激活的时候（第 1 章：`store` 是在 `_reload` 时从 `_store` 快照来的）。此时不能继续向上找，因为向上找会拿到别人的实现，而这个插件明确声明了「我要的是我自己那份」。所以直接报错，且措辞是 `in inactive context` 而不是 `without inject`。
4. `if (!fiber.runtime) throw error` 走到根 fiber 了（第 1 章讲过根 fiber 的 `runtime` 是 `null`），没找到，报最初那句 `without inject`。
5. `if (fiber.parent[symbols.isolate][prop] !== key) throw error` 父级的隔离标签和我不同，**说明这里是一道隔离边界**，不能跨过去。
6. `fiber = fiber.parent.fiber` 都不满足才向上一层。

:::key 为什么必须 `inject`
`fiber.store` 里只有这个插件**声明过 `inject`** 的服务（第 1 章 `_refresh` 逐个 `_checkImpl` 填的就是它）。没声明就没进快照，循环一路向上走到根，最后抛 `cannot get property "x" without inject`。

所以 `inject` 不只是「等依赖就绪」的调度提示，它同时是**访问权限声明**。这两件事由同一份 `inject` 表承担。
:::

## 二、provide：把实现放进注册表

反方向。{{src:vendor/cordis/src/reflect.ts#L277-L305|ReflectService.provide()}}：

```ts
provide(name: string, value?: any, check?: () => boolean) {
  return this.ctx.fiber.effect(() => {
    ...
    this.ctx.root[symbols.isolate][name] ??= Symbol(name)
    const key = this.ctx[symbols.isolate][name]
    const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
    if (this.store[key]) {
      throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
    }
    this.store[key] = impl
    this.ctx.fiber.store![name] = impl
    if (this.ctx.fiber.state === FiberState.ACTIVE) {
      this.notify([name])
    }
    return async () => {
      delete this.store[key]
      const fibers = this.notify([name])
      await Promise.allSettled(fibers.map(fiber => fiber.await()))
      // ensure self access before dependencies cleanup
      delete this.ctx.fiber.store![name]
    }
  }, `ctx.provide(${JSON.stringify(name)})`)
}
```

第一行就是第 1 章那条硬规则的兑现：**整个注册包在 `ctx.fiber.effect()` 里**。插件卸载时，`store[key]` 自动被删。

几处细节：

**`root[symbols.isolate][name] ??= Symbol(name)`** 把默认隔离标签建在**根上下文**上。所以没有任何 isolate 声明时，全树共享同一个标签，`store` 里一个名字只有一份实现。

**重复 provide 直接抛错**，错误信息里带上先注册者的 fiber 名字。这是「misconfiguration fails loud」的一个实例：两个插件抢同一个服务名是配置错误，不能让后来者静默覆盖。

**disposer 里的顺序值得注意**。先 `delete this.store[key]`（别人立刻看不到我了），再 `notify` 唤醒依赖者去卸载，`await` 它们全部结束，**最后**才删自己的 `fiber.store[name]`。源码注释解释了为什么：`ensure self access before dependencies cleanup`。依赖者在卸载过程中可能还要读这个服务做清理工作，如果先删自己这份，它们的清理代码就会拿不到实现而报错。

### Service 基类只是 provide 的糖

{{src:vendor/cordis/src/service.ts#L42-L59|Service 的构造函数}}：

```ts
constructor(protected ctx: Context, name: string) {
  name ??= this.constructor['provide'] as string
  let self = this
  const tracker: Tracker = { associate: name, property: 'ctx' }
  if (self[symbols.invoke]) {
    self = createCallable(name, joinPrototype(Object.getPrototypeOf(this), Function.prototype), tracker)
  }
  self.ctx = ctx
  self.name = name
  defineProperty(self, symbols.tracker, tracker)

  self.ctx.reflect.provide(name, self, this[symbols.check])
  return self
}
```

最后两行是全部要点：`super(ctx, 'myService')` 就是一次 `provide`，而且**构造函数返回的可能不是 `this`**（第 1 章在 `Context` 里见过同样的手法）。当服务定义了 `[symbols.invoke]` 时，它被包装成一个可调用对象，这就是 `ctx.logger('name')` 这种「服务本身能当函数用」的来源。

DSH 里的服务都是这么写的。看一个真的（{{src:packages/core/tools/src/index.ts#L787-L794|ToolRuntime}}）：

```ts
export class ToolRuntime extends Service {
  static inject = ['systemPrompt']

  static Config: z<Config> = z.object({
    mode: z.union(['native', 'code', 'both'] as const).default('native'),
    maxParallelSubCalls: z.natural().min(1).default(10),
  })
```

`static inject` 和 `static Config` 都是第 1 章讲过的插件元数据，`Service` 子类同时也是类插件。

## 三、notify：服务变了，谁被唤醒

第 1 章讲了 epoch 机制：依赖指纹变了就重载。但**谁去改指纹**当时没说。答案是 {{src:vendor/cordis/src/reflect.ts#L314-L336|notify()}}：

```ts
notify(names: string[], filter = (ctx, name) => ctx[symbols.isolate][name] === this.ctx[symbols.isolate][name]) {
  const fibers: Fiber[] = []
  for (const runtime of this.ctx.registry.values()) {
    for (const fiber of runtime.fibers) {
      let hasUpdate = false
      for (const name of names) {
        if (!(name in fiber.inject)) continue
        if (!filter(fiber.ctx, name)) continue
        hasUpdate = true
        fiber._checkImpl(name)
      }
      if (!hasUpdate) continue
      fiber._refresh()
      fibers.push(fiber)
    }
  }
  ...
}
```

它遍历注册表里**每一个** fiber，挑出「声明了这个依赖」且「隔离标签匹配」的，逐个 `_checkImpl` 更新快照，然后 `_refresh` 重算 epoch。

至此第 1 章的循环闭合了：

```text
某插件 provide('llm', impl)
  → notify(['llm'])
    → 每个 inject 了 llm 的 fiber：_checkImpl('llm')  更新 _store
    → _refresh()          重算 epoch 指纹
      → _setEpoch()       指纹变了
        → _reload()       插件重新加载，这次能拿到 llm 了
```

**这个链条是 Cordis 里唯一的「自动调度」。** 没有依赖注入容器，没有拓扑排序，只有「谁 provide 了什么」触发「谁 inject 了它」重算。第 1 章说插件在配置文件里的顺序不决定加载顺序，就是因为顺序由这条链条在运行时决定。

## 四、isolate：同名服务的多份实现

到目前为止 `store` 是按隔离标签存的，但我们一直假设标签只有一个。{{src:vendor/cordis/src/context.ts#L121-L125|Context.isolate()}} 打破这个假设：

```ts
isolate(name: string, label?: symbol) {
  const shadow = Object.create(this[symbols.isolate])
  shadow[name] = label ?? Symbol(name)
  return this.extend({ [symbols.isolate]: shadow })
}
```

三行。造一个继承父级隔离表的新表，把 `name` 改成新标签，用 `extend` 派生子上下文（第 1 章讲过 `extend` 是原型继承、不改父级）。

效果是：在返回的上下文之下，`ctx[isolate]['tools']` 指向一个新 Symbol。于是

- `provide('tools', ...)` 写进 `store[新Symbol]`，和外面那份互不覆盖；
- 第一节那个查找循环走到边界时，`fiber.parent[symbols.isolate]['tools'] !== key` 成立，**停止向上**，看不见外面的实现。

在 `cordis.yml` 里，这是条目的一个选项（{{src:vendor/loader/src/config/isolate.ts#L5-L13|loader 的 EntryOptions}}）：

```yaml
- name: my-plugin
  isolate:
    tools: true          # 局部 realm：只有这个条目自己
    llm: shared-label    # 具名 realm：所有写同一 label 的条目共享
```

`true` 生成 {{src:vendor/loader/src/config/isolate.ts#L47-L56|LocalRealm}}（标签后缀是 `#<条目 id>`），字符串生成具名的 `GlobalRealm`。

### DSH 拿它做什么

这是「让某个会话拥有不同的能力集合」的实现方式。{{src:packages/preset/agent-presets/src/index.ts#L418-L428|agent-presets 的注释}}写得很直接：

> A preset publishes services behind `isolate` realms, which are invisible outside the group that declares them, including to the host.

一个 agent preset 把自己那套工具、提示词、模型适配器挂在 isolate realm 里。于是**同一个进程里，两个 agent 可以各有一套 `ctx.tools`，互相看不见**。

:::key 这对多智能体研究意味着什么
「给不同 agent 配不同工具集」在 DSH 里不需要改 agent-loop，也不需要在工具注册表里加 agent 字段做过滤。它是一行配置：把服务行放进 isolate realm。

第 10 章讲 subagent 时会回到这里，第 12 章你要做的多智能体排布，落点也在这里。
:::

## 五、事件：五种分发模式

服务解决「拿到谁的实现」。剩下一半是「我的决定谁能拦」。

Cordis 的事件总线有五种分发模式，区别只在**怎么处理监听器的返回值**：

| 模式 | 同步性 | 何时停 | 返回 | 典型用途 |
|---|---|---|---|---|
| {{src:vendor/cordis/src/events.ts#L194-L196\|`emit`}} | 同步，不等 Promise | 全跑完 | 无 | 广播通知 |
| {{src:vendor/cordis/src/events.ts#L183-L187\|`parallel`}} | 并发，await 全部 | 全跑完 | 无（错误汇总成 AggregateError） | 需要等所有观察者处理完 |
| {{src:vendor/cordis/src/events.ts#L204-L209\|`serial`}} | 顺序 await | 首个 bail 值 | 该值 | 异步的「谁先认领」 |
| {{src:vendor/cordis/src/events.ts#L217-L222\|`bail`}} | 同步顺序 | 首个 bail 值 | 该值 | 同步的「谁先认领」 |
| {{src:vendor/cordis/src/events.ts#L234-L243\|`waterfall`}} | 由监听器决定 | 谁不调 `next()` | 最外层返回值 | 可拦截、可改写的决策链 |

什么叫「bail 值」由 {{src:vendor/cordis/src/events.ts#L13-L15|isBailed}} 定义：

```ts
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

返回 `null` / `false` / `undefined` 表示「我不管，交给下一个」，返回别的都算「我认领了，停」。所以监听器**不写 return** 就是自动放行。

### waterfall 是本章第二个重点

`emit` 到 `bail` 都好懂。`waterfall` 值得逐行读（{{src:vendor/cordis/src/events.ts#L234-L243|events.ts:234-243}}）：

```ts
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()
  const next = () => {
    const cb = cbs.shift() ?? inner
    return cb(...args)
  }
  args.push(next)
  return next()
}
```

十行做成了一个洋葱模型：

1. `const inner = args.pop()` 把最后一个参数摘下来。**调用方传进来的最后一个参数是「内置行为」**，也就是没有任何监听器时该干什么。
2. `next` 闭包每次调用都 `cbs.shift()` 取走一个监听器。**这是破坏性的**，所以链只会前进不会回头；取空了就用 `inner`。
3. `args.push(next)` 把 `next` 放回参数列表末尾。于是每个监听器收到的最后一个参数都是 `next`。
4. `return next()` 启动。

**监听器不调 `next()`，链就断在那里，包括内置行为也不执行。** 这就是否决。DSH 的规范把它列为硬规则：

> **Waterfall listeners MUST call `next()`** to delegate; returning without it short-circuits the chain.

### 事件过滤

{{src:vendor/cordis/src/events.ts#L165-L175|dispatch()}} 在派发前会筛一遍监听器：

```ts
dispatch(type: string, args: any[]) {
  const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
  const name: string = args.shift()
  if (!name.startsWith('internal/')) {
    this.emit('internal/dispatch', type, name, args, thisArg)
  }
  const filter = thisArg?.[Context.filter]
  return (this._hooks[name] || [])
    .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
    .map(hook => hook.callback.bind(thisArg))
}
```

第一行是个可选参数技巧：如果第一个参数是对象或函数，就当作 `thisArg` 取走，否则第一个参数就是事件名。这让 `ctx.emit('foo', a)` 和 `ctx.emit(carrier, 'foo', a)` 两种写法都成立。

`thisArg[Context.filter]` 是过滤器。第四节讲的 isolate 之所以不会让事件串台，就是因为 {{src:vendor/cordis/src/service.ts#L61-L63|Service 默认的 filter}} 比较隔离标签：

```ts
protected [symbols.filter](ctx: Context) {
  return ctx[symbols.isolate][this.name] === this.ctx[symbols.isolate][this.name]
}
```

`global: true` 的监听器无视过滤，用于真正需要看全局的诊断类插件。

最后，{{src:vendor/cordis/src/events.ts#L254-L260|register()}} 一如既往包在 effect 里：

```ts
register(label: string, hooks: Hook[], callback: any, options: EventOptions): () => void {
  const method = options.prepend ? 'unshift' : 'push'
  return this.ctx.fiber.effect(() => {
    hooks[method]({ ctx: this.ctx, callback, ...options })
    return () => this.unregister(hooks, callback)
  }, label)
}
```

**`ctx.on()` 注册的监听器随插件卸载自动移除。** 这是第 1 章那条规则在事件侧的兑现。

## 六、回到 DSH：一次工具调用的审批

把这一章的两半合起来看一个真实场景。DSH 在派发工具前，会走一次 waterfall（{{src:packages/core/tools/src/index.ts#L1474-L1478|tools/index.ts:1474}}）：

```ts
const carrier = scopeTarget(this, exec.agent)
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)
```

对照第五节的实现读这四行：

- `carrier` 是 `thisArg`，由 `scopeTarget(this, exec.agent)` 造出来，**携带按 agent 划分的过滤器**。于是只绑到这个 agent 的监听器会收到事件。
- `exec` 是参数，待执行的工具调用。
- 最后那个箭头函数是 `inner`，**默认放行**。

这个 `inner` 的存在解释了一个设计选择：**DSH 的默认行为是允许，而拒绝能力完全由插件提供**。没装任何审批插件时，链上没有监听器，`next()` 直接落到 `inner`，返回 `{ kind: 'allow' }`。装了审批插件后，它监听这个事件，可以返回 `{ kind: 'ask' }` 或 `{ kind: 'deny' }` 而不调 `next()`，把整条链短路掉。

事件的类型声明里写明了这一切（{{src:packages/core/tools/src/index.ts#L144-L152|事件声明}}）：

```ts
/**
 * Allow, deny, or ask before dispatch. `next()` delegates to allow; missing
 * approval support turns `ask` into denial. ...
 * @mode waterfall
 */
'tools/pre-execute'(this: Scoped<ToolRuntime>, exec: ToolExecution, next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
```

`@mode waterfall` 是 DSH 强制的 JSDoc 标注，因为**光看签名分不出这个事件该用哪种分发模式**，而用错模式会让监听器行为完全不同。

```ts
import type { Context } from '@deepseek-ai/cordis'
```

预期输出 `[consumer] hello from outer`。然后依次验证三件事：

1. **把 `consumer.ts` 里的 `export const inject` 那行注释掉**，再跑。进程会直接崩掉：

   ```text
   Error: failed to apply loader entry b141926e (@deepseek-ai/cordis-plugin-include):
     failed to apply loader entry 968fbe06 (./consumer.ts):
       cannot get property "greeter" without inject
   ```

   ```yaml
   - name: './consumer.ts'
   ```

   ```yaml
     config:
       name: inner
     isolate:
       greeter: shared
   ```

第 3 步就是 DSH 给不同 agent 配不同工具集的机制原型。

## 七、回看：这两章讲的是一篇论文

到这里 Cordis 的两半都讲完了：第 1 章的可撤销副作用，第 2 章的服务解析与通知。这套机制不是攒出来的，它有一篇论文。

DSH 的 {{src:README.zh.md#L7|README 第 7 行}} 就写着：

> 它采用**一切皆插件**的架构，并由 Cordis 驱动，其设计参见论文 _A Programming Paradigm for Spatiotemporal Composability_。

论文在 [github.com/cordiverse/paper](https://github.com/cordiverse/paper)（[直接下载 PDF](https://github.com/cordiverse/paper/blob/main/paper.pdf)）。作者 Yifan Shi、Wei Zhang、Tianyi Cui，北京大学与 DeepSeek-AI，88 页，2026 年 8 月 13 日草稿，标注为仍在修订的预印本。摘要第一句就点明了动机：

> Modern software—from plugin systems to self-evolving agent harnesses—increasingly requires *dynamic composition*, yet its formal foundations remain underdeveloped.

**从插件系统到自进化的 agent harness。** 论文 §1.2.2 的标题就是 Self-Evolving Agent Harnesses，DSH 是这篇论文的应用场景，不是反过来。

### 两个维度

论文把动态组合拆成两个正交维度，正好是这两章：

| 维度 | 要求 | 静态情形下退化成 | 本课 |
|---|---|---|---|
| **时间可组合性** | 卸载一个组件时，它对共享环境的全部修改必须被完整、安全地撤销 | 词法作用域（RAII、bracket 模式） | 第 1 章 |
| **空间可组合性** | 组件之间的依赖必须能声明、发现、并在运行时响应变化 | 模块 import 解析 | 第 2 章 |

难点在于「动态」。静态情形下这两件事都由编译期解决，而插件在部署之后才到达，没有词法作用域框得住它，也没有编译期上下文能预知它的依赖。论文的做法是把效应（effect，程序如何**修改**环境）和余效应（coeffect，程序如何**依赖**环境）这两套本来用于静态分析的理论，抬成运行时机制。

论文用 VSCode 做反例，两个数字很说明问题：安装量前 100 的扩展里，**87 个含有可执行代码**，因此卸载任何一个都要重启整个扩展宿主；而声明了 `extensionDependencies` 的**只有 7 个**。前者是时间维度的缺失，后者是空间维度的缺失。

### 三处论文说清了、只读代码看不出来的地方

**一、为什么倒序清理不需要前提，而并发清理需要。**

第 1 章讲了两种清理顺序：一个 `effect` 内部是倒序**串行**，一个 fiber 的多个 effect 之间是倒序**并发**（`Promise.all`）。当时只能说「代码就是这么写的」。

论文给出了区别的来源。Definition 1 定义了 twisted composition：

```
(f₁, g₁) ∘ (f₂, g₂) := (f₁ ∘ f₂, g₂ ∘ g₁)
```

正向变换按顺序复合，逆向变换**按相反顺序累积**。这就是 `ctx.effect()` 里把新逆 prepend 到累加器上的那一行的代数形式。Theorem 16 由此得出：按施加的相反顺序撤销，**不需要任何附加假设**，因为每个逆恰好遇到自己那次施加所产生的状态。

但并发撤销不是严格倒序。要让任意顺序都成立，需要 Definition 19 的**独立性**：两个 effect 独立，当且仅当各自的变换互相交换，且谁都不干扰对方产出的逆。Corollary 21 才给出结论：一族两两独立的 effect，按**任意排列**撤销都回到初始状态。

所以第 1 章那两种顺序不是随手选的：单个 effect 内部串行倒序，拿的是 Theorem 16 的无条件保证；跨 effect 并发，押的是独立性假设。论文 §6.1 专门讨论了这个义务落在谁头上：**运行时不验证逆是否真的撤销了它对应的效应，这是组件作者的义务。**

**二、`notify` 的三分类在论文里有名字。**

Definition 24 给出满足谓词，Definition 26 给出分类：

```
σ ⊨ d  :=  ∀k ∈ d. k ∈ dom(σ)

notify_d(σ, σ') = activating    若 σ ⊭ d 且 σ' ⊨ d
                | deactivating  若 σ ⊨ d 且 σ' ⊭ d
                | neutral       其余
```

「activating 触发组件的效应执行，deactivating 触发用累加器恢复」——这正是第 1 章的 `_reload` 与 effect 撤销，由第 2 章的 {{src:vendor/cordis/src/reflect.ts#L314-L336|notify()}} 驱动。论文 Algorithm 3 的伪代码和这个函数逐行同构：遍历所有 fiber，检查 `key ∈ fiber.inject` 且隔离标签相同，命中就 refresh。

第 2 章讲的 epoch 在论文里叫 `target`，定义是把每个声明键解析到的**提供者 fiber 的 uid** 打包成摘要。论文特意解释了为什么用 uid 而不是值：uid 永不复用，所以「换了一个提供者」和「同一个提供者改了值」能被区分开，而后者按设计**不触发重载**。

**三、isolate 和 intercept 是一对，不是两件事。**

第 2 章讲了 isolate realm，只在旁边提了一句 intercept。论文 §3.2.3 把它们放在同一节，标题是 Isolation and Interception，并说明了它们为什么成对。

Definition 28 把带隔离的余效应上下文定义成二层映射：

```
Σ^iso := (K ⇀ R) × ((r : R) ⇀ V_r)
```

先用 realm 表 ρ 把键 k 映射到 realm 标识 r，再用值表 σ 查 σ(ρ(k))。这就是第 2 章那个 `ctx[symbols.isolate][name]` 取标签、再 `store[key]` 取实现的两步。

Definition 27 是关键区分：一个上下文变换有两种**实现方式**。*in-place* 改共享表并返回一个非平凡的逆；*derived* 不动共享表，而是派生一个子上下文，逆是恒等。`provide` 是前者（所以它是 effect，需要撤销），**isolate 和 intercept 都是后者**——它们只改「键怎么解析」，不改表本身，所以丢掉子上下文就等于撤销，不需要跟踪任何逆。这解释了为什么第 1 章的 `ctx.isolate()` 返回的是一个新 context 而不是一个 disposer。
