# LLM 层：流式协议与适配器契约

上一章的 {{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}} 里有一行是黑箱：

```ts
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
```

拿到的东西是 `AsyncIterable<StreamChunk>`，循环 `for await` 它，一边落日志一边喂给 `BlockAssembler`。这一章把这行展开：chunk 是谁造的，它从什么变过来，以及为什么循环可以完全不知道对面是 DeepSeek 还是别的什么。

这一层只做一件事：**把某个厂商的线上格式翻译成一套 harness 自己的词汇，再翻译回去**。翻译之外的一切，重试、路由、缓存、回放，全都不在适配器里。这句话有两个保证机制，本章分别拆开：

- 词汇的统一由 `StreamChunk` 这七个变体和适配器契约保证；
- 适配器不做决策，由 {{src:packages/llm/llm/src/index.ts#L838-L900|adapterStream()}} 的归一化和 `llm/stream` waterfall 两个机制共同保证。

## 一、七种 chunk 就是全部词汇

{{src:packages/llm/llm/src/types.ts#L283-L303|StreamChunk}} 是个七变体的联合：

```ts
export type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: CallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | {
    type: 'finish'
    reason: FinishReason
    /** Adapter-private lossless-JSON state for replaying a successful response. */
    replayState?: unknown
  }
```

前五个带 `index`，那是**块序号**。同一个 index 的所有 delta 属于同一块，不同 index 的 delta 可以交错到达。这就是「流式」在这套词汇里的全部含义：一次响应是若干块，块可以并行长出来。

类型声明上面那段 JSDoc 不是说明文字，它是**适配器必须遵守的契约**，逐句拆开：

> Block indexes correlate interleaved deltas, and `block-end` carries the assembled block.

`block-end` 要带上装好的块。这条让下游有两条路可走：自己按 delta 拼，或者直接采信 `block-end`。第三节会看到 `BlockAssembler` 两条都留着。

> Adapters emit usage before the terminal finish and nothing afterward.

`usage` 在 `finish` 之前，`finish` 之后什么都没有。这条保证了消费者可以把 `finish` 当作真正的终止信号，不用为了等 usage 再多读一轮。

> tool arguments remain raw JSON strings.

工具参数保持原始 JSON 字符串，不解析。适配器不许替模型把 `{"city":"北京"}` 解析成对象。原因在第 8 章会展开：参数校验是工具层的事，提前解析等于提前丢掉「模型到底吐了什么」这个事实。

> An adapter implementation may throw, but `LlmRuntime.stream()` normalizes that failure to a terminal `error` or `aborted` finish before exposing it to consumers.

适配器可以抛，但抛出来的东西**到不了消费者手上**，它会被换成一个终止 chunk。这条是第四节的主题。

配套的两个联合也是 merge-extensible 的映射类型：{{src:packages/llm/llm/src/types.ts#L95-L110|ContentBlockMap}} 有 text / reasoning / image / tool-call / tool-result 五种块，{{src:packages/llm/llm/src/types.ts#L112-L125|FinishReasonMap}} 有 stop / tool-calls / max-tokens / aborted / error 五种结束理由。写成 `interface` 的映射再取 `keyof`，插件就能用声明合并往里加自己的成员，这是第 2 章讲过的手法。

:::key 循环认识的只有这七个词
`ReactLoopAgent` 全文没有一处 provider 判断。它认识 chunk，不认识 DeepSeek。所以第 12 章要接一个新模型厂商，需要写的是一个 `LlmAdapter` 子类，循环一行都不用动。
:::

## 二、从 SSE 字节到 chunk：三段流水线

DeepSeek 适配器把线上响应变成 chunk，走的是三段：

```
Response.body  →  parseSse()  →  translate()  →  StreamChunk
   字节流          SSE data 载荷      翻译
```

代码在 {{src:packages/llm/llm-deepseek/src/adapter.ts#L271-L345|request()}} 的最后一行：

```ts
yield* translate(parseSse(response.body, onComment))
```

### parseSse：只守一件事

{{src:packages/llm/llm-deepseek/src/sse.ts#L28-L40|parseSse}} 一共 12 行有效代码：

```ts
const events = stream
  .pipeThrough(new TextDecoderStream())
  .pipeThrough(new EventSourceParserStream({ onComment }))
for await (const { data } of events) {
  yield data
  if (data === DONE) return
}
throw new LlmError('SSE stream ended without [DONE]', 'STREAM_CLOSED')
```

分帧交给了 `eventsource-parser`。模块头的 JSDoc 明确列出了让出去的是什么：chunk 重组、UTF-8 与 CRLF 与 BOM 处理、注释与非 data 字段跳过、多行 `data:` 合并。这是仓库那条「有维护的依赖优于手写」的直接体现。

它自己只守两件 DeepSeek 协议层面的事：`[DONE]` 原样 yield 出去交给上层决定怎么收尾；**流在 `[DONE]` 之前结束就抛 `STREAM_CLOSED`**。

第二条值得停一下。一个被截断的 SSE 流，在字节层面看没有任何异常，它只是读完了。如果这里不抛，上层会拿到一个「正常结束但内容不全」的响应，然后把半截答案当成完整答案写进日志。所以模块 JSDoc 写的是 `truncated response — the model call cannot be trusted`。分帧还是 spec-strict 的：事件只在空行终止符处派发，所以 EOF 处没终止的尾巴算截断，不算可以冲刷的载荷。

### translate：块序号是自己发的

{{src:packages/llm/llm-deepseek/src/translate.ts#L86-L185|translate()}} 是有状态的。它维护 `textBlock` / `reasoningBlock` 两个可选块和一张 `toolBlocks` 表，序号从 `nextIndex++` 发：

```ts
function open(kind: OpenBlock['kind']): OpenBlock {
  const block: OpenBlock = { index: nextIndex++, kind, text: '' }
  order.push(block)
  return block
}
```

注意 harness 的 index 和线上的 index 不是一回事。DeepSeek 的 `tool_calls[].index` 是工具调用在这一轮里的下标，从 0 开始；harness 的 index 是**块**的下标，文本块、思考块、工具调用块共享一个号段。所以一个「先思考、再说话、再调工具」的响应里，工具调用块的 harness index 是 2，而它的线上 index 是 0。`toolBlocks` 这张 `Map<number, OpenBlock>` 就是这两套编号之间的转换表。

三个开块规则各有讲究：

```ts
const reasoning = delta?.reasoning_content
if (typeof reasoning === 'string' && reasoning.length > 0) {
```

思考内容放在最前面判断，注释写了原因：thinking 模式下它先于正文到达。`length > 0` 那个判断也有注释：`The empty-string first chunk must not open a block.` DeepSeek 在思考模式开启时会先发一个 `reasoning_content: ""` 的空 delta。如果按「字段存在就开块」写，每次响应都会多出一个空的 reasoning 块，而这个块会一路写进会话日志、再序列化回给模型。

第三条规则在工具调用上：

```ts
if (call.id !== undefined) block.callId = call.id
if (call.function?.name !== undefined) block.name = call.function.name
```

id 和 name 只在第一帧出现，后续帧只带 `arguments` 片段。所以这里是「有就更新，没有就保持」，而不是每帧覆盖。

### 三样东西全部推迟到 `[DONE]`

这是 `translate` 最反直觉的设计。`block-end`、`usage`、`finish` 都不在收到时发出，而是攒到 `[DONE]` 那一刻一起发：

```ts
if (payload === DONE) {
  for (const block of order) {
    yield { type: 'block-end', index: block.index, block: closeBlock(block) }
  }
  if (pendingUsage) yield { type: 'usage', usage: pendingUsage }
  const reason = pendingFinish ?? { kind: 'stop' as const }
  yield {
    type: 'finish',
    reason: reason.kind === 'stop' && order.length === 0
      ? { kind: 'error', failure: { message: 'model returned a completed response with no content', code: EMPTY_RESPONSE_CODE } }
      : reason,
  }
  return
}
```

为什么？因为 OpenAI 兼容协议里 usage 有两种到达方式：挂在带 `finish_reason` 的那一帧上，或者作为一个 `choices: []` 的尾帧单独发。模块 JSDoc 说的 `covering both finish-attached and trailing usage-only shapes while ensuring no chunk follows finish` 就是这个意思。如果收到 `finish_reason` 就立刻发 `finish`，那么尾随的 usage 帧就会排在 `finish` 之后，直接违反第一节那条契约。推迟到 `[DONE]` 让两种形状统一，代价是块的关闭时刻晚一点，而这没有代价：delta 早就流出去了。

顺带一个决策也塞在这里：**结束理由是 stop 但一个块都没开，改判为 `EMPTY_RESPONSE` 错误**。{{src:packages/llm/llm/src/error.ts#L30-L39|EMPTY_RESPONSE_CODE}} 的注释解释了为什么这不算成功：

> an empty message silently ends the turn with nothing for the user or the loop to act on. The attempt produced nothing durable, so retry policy treats it as safe to repeat.

一条空的 assistant 消息会让轮次静悄悄地结束，用户和循环都没有东西可做。改判成错误之后，它就落进了默认可重试码表，第八节会看到。

### 口径换算

{{src:packages/llm/llm-deepseek/src/translate.ts#L53-L62|mapUsage()}} 只有六行，但它解决的是一个口径冲突：

```ts
const cacheRead = usage.prompt_tokens_details?.cached_tokens ?? usage.prompt_cache_hit_tokens
return {
  inputTokens: usage.prompt_tokens - (cacheRead ?? 0),
  ...
}
```

DeepSeek 的 `prompt_tokens` **包含**缓存命中，而 {{src:packages/llm/llm/src/types.ts#L127-L141|TokenUsage}} 的约定是三个计数互不相交（计费输入 = 三者之和）。所以这里要减出去。本章实验里这个转换是可见的：线上 `prompt_tokens: 1180`、`prompt_cache_hit_tokens: 1024`，出来是 `inputTokens: 156, cacheReadTokens: 1024`。

## 三、BlockAssembler：容忍协议缺陷的那几行

{{src:packages/llm/llm/src/assembler.ts#L36-L164|BlockAssembler}} 是循环把 chunk 拼回消息的唯一算法。它 164 行，真正有意思的是四处「不按理想协议来也要能活」的处理。

**一、没有 `block-start` 也能开块。** {{src:packages/llm/llm/src/assembler.ts#L96-L104|ensure()}} 在 delta 到达时按需建 partial：

```ts
private ensure(index: number, blockType: string): PartialBlock {
  let partial = this.partials.get(index)
  if (!partial) {
    partial = { blockType, text: '', toolCallArguments: '' }
    this.partials.set(index, partial)
    this.order.push(index)
  }
  return partial
}
```

类 JSDoc 说的 `Tolerant of delta-only protocols (no block-start/end)` 就是这条。适配器可以只发 delta。

**二、`block-end` 之后的迟到 delta 被丢弃。** 三个 case 里各有一行：

```ts
if (partial.block) return // closed by block-end; ignore stragglers
```

类注释给了理由：`so a misbehaving adapter cannot grow memory or corrupt a completed block`。一个坏适配器不断发迟到 delta，不会把内存撑爆，也不会改掉已完成的块。

**三、重复的 `block-end` 第一次赢。**

```ts
// First close wins; ignoring re-close stragglers keeps streamed output
// and the final assembled block in agreement.
if (partial.block) return
```

理由是「保持流式输出和最终块一致」。用户在界面上看到的是逐字流出来的那份，如果第二个 `block-end` 能覆盖，最终写进日志的就和用户看到的不是同一段文字了。这是第 4 章那条「模型可见即已记录」在渲染侧的对偶。

**四、`max-tokens` 时丢掉所有工具调用。** {{src:packages/llm/llm/src/assembler.ts#L128-L139|blocks()}}：

```ts
blocks(): ContentBlock[] {
  const blocks = this.order.map(index => this.assemble(this.mustGet(index), index))
  return this.finish.kind === 'max-tokens'
    ? blocks.filter(block => block.type !== 'tool-call')
    : blocks
}
```

这一行不是格式处理，是**安全决策**。输出被 token 上限截断时，最后一个工具调用的 `arguments` 很可能是半截 JSON。半截 JSON 解析失败还算好的，糟糕的是它恰好能解析：`{"path":"/tmp/a","recursive":true` 截成 `{"path":"/tmp/a"` 之后仍是合法 JSON，只是参数变了。JSDoc 写的 `drops tool calls that cannot be executed safely` 就是这个意思。

本章实验第 3 步把它显示出来了。喂进一个文本块和一个截断的工具调用，然后 `finish: max-tokens`：

```
blocks: [{"type":"text","text":"好的，我来"}]
```

工具调用整块消失。回到第 5 章：`step()` 收到 `max-tokens` 会直接 `return { kind: 'max-tokens' }`，不进工具调度。两处配合，被截断的调用既不在消息里，也不会被执行。

还有一个小设计：{{src:packages/llm/llm/src/assembler.ts#L146-L149|finish}} 的 getter 在没收到 `finish` chunk 时返回 `{ kind: 'stop' }`。流断了但没说为什么，按正常结束处理，因为「流断了」这件事本身已经由 `parseSse` 的 `STREAM_CLOSED` 或者 `adapterStream` 的归一化管了，这里再猜一次只会掩盖上游的判断。

## 四、抛出的异常怎么变成 chunk

第一节那条契约说「适配器可以抛，但抛出来的到不了消费者手上」。执行这条的是 {{src:packages/llm/llm/src/index.ts#L838-L900|adapterStream()}}。它的 JSDoc 一句话划了边界：

> Adapter selection, dispatch, iterator construction, and iteration failures become one terminal failure chunk. Middleware and downstream consumer failures remain thrown plugin or consumer errors.

**适配器侧的失败变 chunk，中间件和消费者侧的失败照样抛。** 这条线怎么在代码里画出来，是这个函数全部的技巧。

第一段 try 包住选适配器、解析 config、拿迭代器：

```ts
try {
  const registration = prepared?.registration ?? this.registration(options.provider)
  ...
  const stream = adapter.stream(this.forAdapter(resolvedOptions, adapter))
  iterator = stream[Symbol.asyncIterator]()
} catch (error: unknown) {
  yield adapterFailureChunk(error, options.signal)
  return
}
```

第二段是逐条读，注意 try 包住的只有 `iterator.next()`：

```ts
try {
  const next = await iterator.next()
  item = next.done ? { done: true } : { done: false, value: next.value }
} catch (error: unknown) {
  completed = true
  yield adapterFailureChunk(error, options.signal)
  return
}
if (item.done) { completed = true; return }
// End the adapter-owned try before yielding: consumer/middleware
// failures resumed into this generator must remain thrown.
yield item.value
```

`yield item.value` 写在 try **外面**。注释解释了为什么：generator 的 `yield` 会挂起，消费者在这里抛的异常会以 `throw()` 的形式**回灌进这个 generator**，落在 yield 那一行。如果 yield 在 try 里面，消费者自己的 bug 就会被当成适配器失败，被包成一个 `error` finish chunk 吞掉。挪出一行，责任归属就对了。

失败到 chunk 的转换是 {{src:packages/llm/llm/src/index.ts#L930-L939|adapterFailureChunk()}}：

```ts
function adapterFailureChunk(error: unknown, signal?: AbortSignal): StreamChunk {
  const failure = normalizeLlmFailure(error)
  return {
    type: 'finish',
    reason: signal?.aborted || failure.code === 'ABORTED'
      ? { kind: 'aborted', failure }
      : { kind: 'error', failure },
  }
}
```

`aborted` 和 `error` 分开，因为下游对它们的处理不同：取消不该触发重试，也不该记成失败。判定看两处，调用方的 signal 和失败码本身，任一成立就算取消。

{{src:packages/llm/llm/src/adapter-failure.ts#L16-L28|normalizeLlmFailure()}} 处理的是另一个问题：跨包的 Error 实例 `instanceof` 会失效（打包后类身份不同）。它的做法是读 own data property，并且要求 `failure.code` 和 `error.code` 两者一致才采信：

```ts
const carried = ownFailureSnapshot(error)
if (carried !== undefined && carried.code === ownErrorCode(error)) return carried
```

整个文件里 `Object.getOwnPropertyDescriptor` 出现了三次，每次都配一句「不要触发 SDK 定义的 accessor」的注释。原因是第三方 SDK 的 error 上可能挂着会抛的 getter，而这段代码运行在「已经出错」的路径上，再抛一次就没人接了。

最后是 `finally` 里的收尾：

```ts
} finally {
  if (!completed) {
    const close = iterator.return?.bind(iterator)
    if (close) await close()
  }
}
```

`completed` 标记只在正常读完或读到失败时置位。消费者提前 break 掉 `for await`，走的就是 `!completed` 这条路，适配器的 generator 会收到 `return()`，从而执行它自己的 `finally`，也就是 {{src:packages/llm/llm-deepseek/src/adapter.ts#L214-L269|DeepSeekAdapter.stream()}} 里那句 `consumer.abort(...)`，HTTP 连接才会真的断开。

## 五、回程：序列化

去程讲完了，回程是 {{src:packages/llm/llm-deepseek/src/serialize.ts#L151-L187|serializeRequest()}}，把 harness 的消息变回 OpenAI 兼容的请求体。四个地方值得单独看。

**一、assistant 的 `content` 永远是字符串，绝不是 null。** {{src:packages/llm/llm-deepseek/src/serialize.ts#L71-L102|serializeAssistant()}} 那段注释是全仓库最长的注释之一：

```ts
// Text-less turns send "" — NEVER null. Pure tool-call turns: the
// official samples replay message.content verbatim (which is "") and
// some gateways reject null outright. Reasoning-ONLY turns (the model
// can answer entirely in the reasoning channel, e.g. a v4-flash
// greeting): the live API rejects null-content/no-tool_calls assistant
// messages with a 400 ("content or tool_calls must be set"), and since
// the message sits durably in the session log, a null here bricks every
// later turn of that session.
content: text,
```

最后一句是重点：**这条消息会持久化进会话日志**。一个 null 不是让这一次请求失败，是让这个 session 之后的每一轮都失败，因为每一轮都要把这条历史重新序列化发上去。日志是只增的，这条坏消息删不掉。第 4 章那条「日志只会增长」在这里变成了一个约束。

**二、`reasoning_content` 只在有工具调用时回传。**

```ts
...toolCalls.length > 0 && reasoning.length > 0 ? { reasoning_content: reasoning } : {},
```

注释指了官方文档：thinking 模式要求工具调用轮必须回传 reasoning_content，普通轮它会被忽略，所以那里省掉省 token。

**三、工具结果从 user 消息里展开成独立的 tool 消息。** harness 的词汇里工具结果是一个 `tool-result` 块，装在 user 角色的消息里（第 4 章讲过）；DeepSeek 要的是 `role: 'tool'` 的独立消息。{{src:packages/llm/llm-deepseek/src/serialize.ts#L112-L141|serializeMessages()}} 做展开：

```ts
const toolResults = message.content.filter(block => block.type === 'tool-result')
const text = flattenText(message.content)
if (text.length > 0 || toolResults.length === 0) {
  wire.push({ role: 'user', content: text })
}
for (const result of toolResults) {
  wire.push({ role: 'tool', tool_call_id: result.toolCallId, content: flattenText(result.content) || '(no output)' })
}
```

那个 `if` 条件读起来别扭，展开就是：纯工具结果的消息不发 user 消息（否则会多一条空的 user），混合消息先发文本再发结果。末尾的 `|| '(no output)'` 是因为空字符串在这个字段上会被拒。

**四、图片是显式拒绝的，不是被静默丢掉的。** {{src:packages/llm/llm-deepseek/src/serialize.ts#L64-L68|assertTextOnly()}}：

```ts
function assertTextOnly(blocks: readonly ContentBlock[]): void {
  if (contentHasImage(blocks)) {
    throw new LlmError('The DeepSeek chat-completions adapter does not support image content.', 'UNSUPPORTED_CONTENT')
  }
}
```

它在 `serializeMessages` 的循环开头调用，也就是在 `flattenText` 之前。因为 `flattenText` 只挑 `type === 'text'` 的块，图片块会**无声地消失**：请求发出去了，模型看不到图，用户也不知道。模块 JSDoc 写的 `rejected explicitly because this wire route is text-only` 就是拒绝这种静默。

配套的是 `resolveModel` 里那个 `inputModalities: ['text']`，连没在目录里的模型也声明。那段注释说清了动机：写 unknown 会让宿主接受并持久化一张图片，然后序列化器必须拒绝它，而那时图片已经在日志里了。

本章实验第 5 步能直接看到完整的请求体，包括 `stream: true` 和 `stream_options: { include_usage: true }` 这两个恒定字段。这一层不提供非流式路径。

## 六、prepareCall：为什么不直接 stream

`LlmRuntime` 上有两个入口。{{src:packages/llm/llm/src/index.ts#L902-L915|stream()}} 是一步到位的；{{src:packages/llm/llm/src/index.ts#L771-L814|prepareCall()}} 先解析、后派发，中间隔着一段异步。循环走的是后者：

```ts
preparedCall = await this.loopCtx.llm.prepareCall(proposedConfig, signal)
config = preparedCall.config
```

JSDoc 给的理由很具体：

> The returned one-shot handle keeps that registration across header logging and dispatch, so HMR cannot combine one adapter's capability result with another adapter.

中间隔的那段异步里，`resolveModel()` 要问适配器要 contextWindow、defaultMaxTokens、支持哪些 reasoning effort。这期间 Cordis 的热重载完全可能把这个 provider 的适配器换掉。如果派发时再查一次注册表，就会拿 A 适配器算出来的能力去调 B 适配器。`prepareCall` 把 `registration` 闭包捕获住，堵的是这个缝。

返回的 handle 有三道锁：

```ts
if (dispatched) throw new LlmError('a prepared LLM call can only be dispatched once', 'INVALID_PREPARED_CALL')
if (!callConfigEquals(options, resolvedConfig)) throw new LlmError('prepared LLM call config changed before adapter dispatch', 'INVALID_PREPARED_CALL')
```

一次性，配置必须一致，以及 config 本身是 `deepFreeze(structuredClone(...))` 出来的。

`adapterDefaults` 这个字段要联系第 5 章看。{{src:packages/llm/llm/src/index.ts#L734-L769|resolveCallFor()}} 会把适配器配的默认值填进 config：调用方没给 `maxTokens` 就用模型的 `defaultMaxTokens`，没给 `reasoningEffort` 就用 `defaultEffort`。填了之后，config 里就分不清哪些是调用方要的、哪些是适配器补的。`adapterDefaults` 记的就是这个区别：

```ts
...config.reasoningEffort === undefined && resolvedConfig.reasoningEffort !== undefined
  ? { reasoningEffort: true } : {},
```

第 5 章 {{src:packages/core/agent-loop/src/agent.ts#L407-L495|buildRequest()}} 里那段读起来费解的条件，用的就是它：

```ts
const reasoningEffort = persistedConfig?.provider === route.provider
  && persistedConfig.model === route.model
  && persistedHeader?.adapterDefaults?.reasoningEffort !== true
  ? persistedConfig.reasoningEffort
  : undefined
```

恢复一个会话时，日志里记着上次的 reasoningEffort。如果那个值是用户选的，应该恢复；如果是适配器当时补的默认值，就不该恢复，要重新问一次适配器，因为默认值可能已经改了。没有 `adapterDefaults` 这个标记，这个区分做不出来。

同样的道理还有 `resolveCallFor` 里的这条：不支持的 effort 直接抛 `UNSUPPORTED_REASONING_EFFORT`，**不做夹取也不做别名**。悄悄把 `max` 降级成 `high`，用户会以为自己用着 max。

## 七、llm/stream：策略住在这里

{{src:packages/llm/llm/src/index.ts#L917-L927|streamWithRegistration()}} 的全部内容是一个 waterfall：

```ts
return this.ctx.waterfall(this, 'llm/stream', options, () => this.adapterStream(options, prepared))
```

第 2 章讲过 waterfall 的语义：监听器拿到 `next`，调它就往下走，不调就短路。放在这里，含义是**每一次模型调用都可以被插件整个换掉**。

事件声明的 JSDoc 写明了参数的约束：

```ts
/**
 * @param options - the full request. A LOOP-built request carries the
 *   process-local {@link markAgentLoopRequest} identity and arrives deep-frozen
 *   (mutation throws): its content is a pure function of the session log (the
 *   reconstructability Agent Note), so listeners read it, never rewrite it.
 * @mode waterfall
 */
```

**循环建的请求是只读的**，理由是它的内容是会话日志的纯函数。第 4 章那条「模型可见即已记录」要成立，就不能允许一个监听器在日志之后、发送之前偷偷改内容，那样日志重放出来的请求和真正发出去的就不是同一个了。所以循环在 {{src:packages/core/agent-loop/src/agent.ts#L486-L493|buildRequest 的最后一步}} 就把它冻上：

```ts
const request = markAgentLoopRequest(deepFreeze({ ...header.config, messages: boundaryMessages, ... }))
```

本章实验里可以直接验证这两件事：

```
[拦截] 请求是冻结的？ true 消息数组也冻结？ true
[拦截] 改写请求 -> TypeError: Cannot add property 1, object is not extensible
```

{{src:packages/llm/llm/src/call-config.ts#L88-L117|deepFreeze()}} 有一个刻意的例外：

```ts
if (node instanceof AbortSignal) continue
```

AbortSignal 是请求的取消通道，冻上它 abort 就坏了。这一行下面 JSDoc 明说了 `freezing them breaks abort`。

那么 `markAgentLoopRequest` 又是干什么的？{{src:packages/llm/llm/src/call-config.ts#L66-L69|它}} 往一个模块级的 `WeakSet` 里放这个请求对象：

```ts
const AGENT_LOOP_REQUESTS = new WeakSet<GenerateOptions>()
export function markAgentLoopRequest<T extends GenerateOptions>(request: T): T {
  AGENT_LOOP_REQUESTS.add(request)
  return request
}
```

为什么不在请求上加个字段？因为字段会被序列化，会被 `structuredClone` 复制，也可能被伪造。用 WeakSet 记的是**对象身份**，进程内唯一且不可伪造，一份拷贝不算数。这个标记的用处是让监听器区分「这是循环建的、来自日志的请求」和「这是某个插件手搓的一次性请求」，前者只读，后者没有这个约束。

最后一处是 {{src:packages/llm/llm/src/index.ts#L822-L836|forAdapter()}}，它在派发前擦掉不属于当前适配器的 `replayState`：

```ts
if (message.role !== 'assistant' || source.kind !== 'model' || source.replayState === undefined) return message
if (this.adapters.get(source.provider)?.adapter === adapter) return message
return freezeMessage({ ...message, source: { kind: 'model', provider: source.provider, model: source.model } })
```

`replayState` 是适配器私有的、无损 JSON 的回放状态（第一节 `finish` chunk 上那个可选字段）。一个会话可能中途换过 provider，历史消息上就带着别的适配器的回放状态。判定条件写的是**适配器实例相同**，不是 provider 名字相同：同一个适配器实例可以注册多条路由，那种情况下回放状态是通用的。

:::key llm/stream 和 agent/request 不是一回事
第 5 章那个 `agent/request` waterfall 改的是**配置**：provider、model、采样参数。这里的 `llm/stream` 换的是**整次调用**。想做 A/B 路由用前者，想做回放、录制、缓存用后者。
:::

## 八、重试不在这一层

`dsh-llm-retry` 是一个独立插件，226 行。第一个值得问的问题是：它挂在哪？

不是 `llm/stream`。看 {{src:packages/llm/llm-retry/src/index.ts#L210-L219|监听器注册}}：

```ts
const disposeListener = ctx.on('agent/request-error', (payload, next) => { ... })
```

挂的是第 5 章那个 `agent/request-error`，也就是 `step()` 里那个内层 `while` 的重试判定点。为什么不在 LLM 层重试？因为重试需要两样 LLM 层拿不到的东西：**会话日志**（往里写 `llm/retry` 事件）和**轮次坐标**（turn / step）。而 `step()` 那个 `while (true)` 已经是天然的重试循环了，它只要一个「要不要再来一次」的答案。

再看它怎么数「这是第几次重试」。不是内存计数器：

```ts
const priorPolicyRetry = agent.session.events.findLast((event): event is SessionEvent<'llm/retry'> =>
  event.type === 'llm/retry'
  && event.data.turn === turn
  && event.data.step === step
  && event.data.provider === provider
  && event.data.policyKey === policyKey,
)
const previousRetry = priorPolicyRetry?.data.retry ?? 0
```

**从会话日志里 findLast 出来的。** 这是第 4 章那条原则的又一次应用：状态住在日志里，插件本身无状态。带来的直接好处是，重启后恢复一个会话，重试计数不会归零。

四个匹配条件里 `policyKey` 最有意思。{{src:packages/llm/llm-retry/src/index.ts#L65-L76|retryPolicyKey()}} 把整个策略序列化成一个字符串。用它匹配的意思是：**策略变了，计数就重新开始**。用户把 maxRetries 从 2 改成 5 并热重载，不会因为「之前已经重试过 2 次」而立刻放弃。

{{src:packages/llm/llm-retry/src/index.ts#L111-L154|backoff()}} 里有一个顺序值得看：

```ts
agent.session.append('llm/retry', eventData)
if (!await cancellableDelay(delayMs, fusedSignal)) return
agent.session.append('llm/retry-started', { retryId, turn, step, retry })
return { kind: 'retry' }
```

两条事件夹着那段等待：`llm/retry` 在等之前写，`llm/retry-started` 在等之后写。模块 JSDoc 一句话概括为 `Each scheduled retry is durable before its cancellable wait`。**决定重试这件事，在开始等待之前就已经持久化了。** 如果只在等完之后写一条，那么等待期间进程崩掉，日志里就完全看不出曾经计划过重试。而两条分开写还有第二个作用：界面可以在这两条之间显示倒计时。

延迟怎么算，{{src:packages/llm/llm-retry/src/index.ts#L58-L63|localDelay()}} 是标准的指数退避加对称抖动，`Math.min(retry - 1, 1024)` 那个封顶是防 `2 ** n` 溢出。真正的分支在服务端给了 `Retry-After` 的时候：

```ts
if (failure.providerRetryAfterMs > policy.maxDelayMs) {
  if (policy.mode === 'normal') return next()
  delayMs = localDelay(policy, retry, random)
}
```

服务端要求的等待超过了本地上限，`normal` 模式**放弃重试**（`return next()` 把决定权交给链上的下家），`always` 模式改用本地退避继续。这个分岔体现了两种模式的定位差别：`normal` 是「有限次的瞬时故障恢复」，服务端说要等 10 分钟就不该傻等；`always` 是「永远重试直到成功、取消或卸载」，那就自己定节奏。

默认的可重试码表在 {{src:packages/llm/llm/src/retry-policy.ts#L18-L24|retry-policy.ts}}：

```ts
const DEFAULT_RETRYABLE_CODES = Object.freeze([
  EMPTY_RESPONSE_CODE, 'RATE_LIMIT', 'SERVER', 'TIMEOUT', 'TRANSPORT',
])
```

`AUTH` 和 `INVALID_REQUEST` 不在里面，重试它们只是把同一个错误再犯一遍。`EMPTY_RESPONSE` 在里面，理由第二节引过：那次尝试没产生任何持久的东西。`INVALID_CREDENTIAL` 的注释也专门说明了为什么被排除在外：格式坏掉的凭据每次都会以同样的方式失败。

import { LlmAdapter, createUserMessage } from '@deepseek-ai/dsh-llm'

export const inject = ['agents', 'agentLoop', 'llm', 'tools', 'appExit']

class RealAdapter extends LlmAdapter {
  calls = 0
  async *stream() {
    this.calls++
    yield { type: 'block-start', index: 0, blockType: 'text' }
    yield { type: 'text-delta', index: 0, text: '来自真适配器' }
    yield { type: 'block-end', index: 0, block: { type: 'text', text: '来自真适配器' } }

  }
}

export async function apply(ctx) {
  const adapter = new RealAdapter()
  ctx.llm.registerAdapter(['lab'], adapter)

  ctx.on('llm/stream', async function* (options, next) {
    const text = options.messages.at(-1).content
      .filter(b => b.type === 'text').map(b => b.text).join('')
    console.log('[拦截] 请求是冻结的？', Object.isFrozen(options),
      '消息数组也冻结？', Object.isFrozen(options.messages))
    try { options.messages.push(1) } catch (e) { console.log('[拦截] 改写 ->', e.message) }
    console.log('[拦截] signal 没被冻结：', Object.isFrozen(options.signal))
    if (!text.includes('缓存')) return yield* next()
    yield { type: 'block-start', index: 0, blockType: 'text' }
    yield { type: 'text-delta', index: 0, text: '（缓存命中，没有发出网络请求）' }
    yield { type: 'block-end', index: 0, block: { type: 'text', text: '（缓存命中，没有发出网络请求）' } }
    yield { type: 'finish', reason: { kind: 'stop' } }
  })

    sessionId: 'lab-1', agentOptions: { provider: 'lab', model: 'lab-model' },
  })
  const agent = handle.agent
  agent.followup(createUserMessage({
    content: [{ type: 'text', text: '走缓存吧' }], source: { kind: 'human' },

  for (const e of agent.session.events) {
    if (e.type === 'assistant/message') console.log('assistant/message:', JSON.stringify(e.data.message.content))
  }
  console.log('adapter.stream 被调用次数 =', adapter.calls)
  ctx.appExit(0)
}

## 小结

一次模型调用穿过这一层的完整路径：

```
step() → prepareCall(config)         捕获适配器注册，解析 exact-model 能力
      → preparedCall.stream(request) 请求已 deep-frozen
        → ctx.waterfall('llm/stream')  插件可以整个换掉
          → adapterStream()             throw → 终止 chunk
            → DeepSeekAdapter.stream()
              → fetch → parseSse → translate → StreamChunk
      ← for await：一条 chunk 一条日志，同一条喂给 BlockAssembler
      ← finish 是 error/aborted？ → agent/request-error → llm-retry 决定重试
      ← 否则 assembler.blocks() → createAssistantMessage()
```

三个结论：

**厂商相关的代码被压进一个类里。** 适配器要做的就是 `stream()`：把线上格式变成七种 chunk，把 harness 消息变回线上格式。剩下的注册表、能力解析、冻结、拦截、失败归一化，全在 `LlmRuntime` 里，接新厂商时一行都不用改。

**「适配器可以抛，但抛不到消费者手上」是靠一行 `yield` 的位置实现的。** `adapterStream` 里那句 `yield item.value` 在 try 外面，把适配器的失败和消费者的失败分到了两条路上。这行注释值得记住：`consumer/middleware failures resumed into this generator must remain thrown`。

**策略全部住在日志里，不住在内存里。** 重试计数从 `session.events.findLast` 出来，重试决定在等待之前就持久化，失败的那次尝试本身也是一条 `assistant/chunk`。第 4 章那条原则在这一层没有例外。
