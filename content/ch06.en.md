# The LLM layer: streaming protocol and the adapter contract

One line inside last chapter's {{src:packages/core/agent-loop/src/agent.ts#L332-L401|step()}} was a black box:

```ts
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
```

What comes back is an `AsyncIterable<StreamChunk>`. The loop `for await`s it, logging each chunk and feeding the same chunk to a `BlockAssembler`. This chapter opens that line: who makes the chunks, what they were translated from, and why the loop can be completely unaware of whether the other side is DeepSeek or something else.

This layer does exactly one thing: **translate one vendor's wire format into a vocabulary the harness owns, and translate back**. Everything that is not translation, retry, routing, caching, replay, lives outside the adapter. Two mechanisms guarantee that sentence, and this chapter takes them apart separately:

- the shared vocabulary is guaranteed by `StreamChunk`'s seven variants and the adapter contract;
- adapters making no decisions is guaranteed jointly by {{src:packages/llm/llm/src/index.ts#L838-L900|adapterStream()}}'s normalization and the `llm/stream` waterfall.

## 1. Seven chunks are the entire vocabulary

{{src:packages/llm/llm/src/types.ts#L283-L303|StreamChunk}} is a union of seven variants:

```ts
export type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: CallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | {
    type: 'finish'
    reason: FinishReason
    /** Adapter-private lossless-JSON state for replaying a successful response. */
    replayState?: unknown
  }
```

The first five carry an `index`, which is a **block number**. Every delta with the same index belongs to the same block, and deltas for different indexes may interleave. That is all "streaming" means in this vocabulary: one response is several blocks, and blocks may grow in parallel.

The JSDoc above the declaration is not description, it is **the contract every adapter must obey**, clause by clause:

> Block indexes correlate interleaved deltas, and `block-end` carries the assembled block.

`block-end` must carry the finished block. This clause leaves the consumer two routes: assemble from deltas itself, or trust `block-end`. Section 3 shows `BlockAssembler` keeping both.

> Adapters emit usage before the terminal finish and nothing afterward.

`usage` before `finish`, nothing after. This lets consumers treat `finish` as a genuine terminator instead of reading one more round in case usage is still coming.

> tool arguments remain raw JSON strings.

Tool arguments stay raw JSON, unparsed. An adapter may not helpfully turn `{"city":"Beijing"}` into an object. Chapter 8 develops the reason: argument validation belongs to the tool layer, and parsing early throws away the fact of what the model actually emitted.

> An adapter implementation may throw, but `LlmRuntime.stream()` normalizes that failure to a terminal `error` or `aborted` finish before exposing it to consumers.

An adapter may throw, but what it throws **never reaches the consumer**; it is replaced with a terminal chunk. This clause is section 4's subject.

The two companion unions are merge-extensible map types too. {{src:packages/llm/llm/src/types.ts#L95-L110|ContentBlockMap}} has five block kinds (text / reasoning / image / tool-call / tool-result) and {{src:packages/llm/llm/src/types.ts#L112-L125|FinishReasonMap}} has five finish reasons (stop / tool-calls / max-tokens / aborted / error). Writing the map as an `interface` and deriving the union with `keyof` is what lets a plugin add its own member by declaration merging, the technique from chapter 2.

:::key The loop knows only these seven words
`ReactLoopAgent` contains not one provider check anywhere. It knows chunks; it does not know DeepSeek. So adding a new vendor in chapter 12 means writing one `LlmAdapter` subclass, with no change to the loop.
:::

## 2. From SSE bytes to chunks: a three-stage pipeline

The DeepSeek adapter turns a wire response into chunks in three stages:

```
Response.body  →  parseSse()  →  translate()  →  StreamChunk
   byte stream     SSE data payloads   translation
```

The code is the last line of {{src:packages/llm/llm-deepseek/src/adapter.ts#L271-L345|request()}}:

```ts
yield* translate(parseSse(response.body, onComment))
```

### parseSse guards exactly one thing

{{src:packages/llm/llm-deepseek/src/sse.ts#L28-L40|parseSse}} has twelve lines of real code:

```ts
const events = stream
  .pipeThrough(new TextDecoderStream())
  .pipeThrough(new EventSourceParserStream({ onComment }))
for await (const { data } of events) {
  yield data
  if (data === DONE) return
}
throw new LlmError('SSE stream ended without [DONE]', 'STREAM_CLOSED')
```

Framing is delegated to `eventsource-parser`. The module JSDoc enumerates exactly what was handed off: chunk reassembly, UTF-8 / CRLF / BOM handling, comment and non-data field skipping, multi-`data:` joining. This is the repo's "maintained dependencies over hand-rolling" rule in the concrete.

It keeps two DeepSeek-protocol facts for itself: `[DONE]` is yielded verbatim so the caller owns final flushing, and **a stream that ends before `[DONE]` throws `STREAM_CLOSED`**.

The second one deserves a pause. A truncated SSE stream looks like nothing unusual at the byte level; it just ran out. Without this throw, the layer above receives a response that "completed normally with incomplete content", then writes half an answer into the log as a whole one. Hence the module JSDoc: `truncated response — the model call cannot be trusted`. Framing is spec-strict as well: an event dispatches only on its blank-line terminator, so an unterminated tail at EOF is truncation, not a flushable payload.

### translate issues its own block numbers

{{src:packages/llm/llm-deepseek/src/translate.ts#L86-L185|translate()}} is stateful. It holds an optional `textBlock` and `reasoningBlock` plus a `toolBlocks` map, and hands out numbers from `nextIndex++`:

```ts
function open(kind: OpenBlock['kind']): OpenBlock {
  const block: OpenBlock = { index: nextIndex++, kind, text: '' }
  order.push(block)
  return block
}
```

The harness index and the wire index are not the same thing. DeepSeek's `tool_calls[].index` is the tool call's position within this turn, starting at 0; the harness index numbers **blocks**, with text, reasoning, and tool-call blocks sharing one counter. So in a response that thinks, then speaks, then calls a tool, the tool-call block's harness index is 2 while its wire index is 0. The `Map<number, OpenBlock>` named `toolBlocks` is the translation table between the two numbering schemes.

Each of the three open rules is deliberate:

```ts
const reasoning = delta?.reasoning_content
if (typeof reasoning === 'string' && reasoning.length > 0) {
```

Reasoning is checked first, and the comment says why: in thinking mode it arrives before the visible text. The `length > 0` test has its own comment: `The empty-string first chunk must not open a block.` With thinking enabled, DeepSeek leads with a `reasoning_content: ""` delta. Written as "open a block when the field is present", every response would grow an extra empty reasoning block, and that block would travel into the session log and be serialized back to the model on every later turn.

The third rule is on tool calls:

```ts
if (call.id !== undefined) block.callId = call.id
if (call.function?.name !== undefined) block.name = call.function.name
```

`id` and `name` appear only in the first frame; later frames carry only `arguments` fragments. So this is "update if present, otherwise keep", not overwrite per frame.

### Three things are all deferred to `[DONE]`

This is `translate`'s least intuitive design. `block-end`, `usage`, and `finish` are not emitted when they arrive; they are held until `[DONE]` and emitted together:

```ts
if (payload === DONE) {
  for (const block of order) {
    yield { type: 'block-end', index: block.index, block: closeBlock(block) }
  }
  if (pendingUsage) yield { type: 'usage', usage: pendingUsage }
  const reason = pendingFinish ?? { kind: 'stop' as const }
  yield {
    type: 'finish',
    reason: reason.kind === 'stop' && order.length === 0
      ? { kind: 'error', failure: { message: 'model returned a completed response with no content', code: EMPTY_RESPONSE_CODE } }
      : reason,
  }
  return
}
```

Why? Because in the OpenAI-compatible protocol usage arrives two ways: attached to the frame carrying `finish_reason`, or as a separate trailing frame with `choices: []`. The module JSDoc's `covering both finish-attached and trailing usage-only shapes while ensuring no chunk follows finish` names exactly this. Emitting `finish` the moment `finish_reason` arrives would put the trailing usage frame after `finish`, violating section 1's contract outright. Deferring to `[DONE]` unifies both shapes, at the cost of closing blocks slightly later, which costs nothing: the deltas went out long ago.

One decision rides along here too: **a stop finish with zero opened blocks is reclassified as an `EMPTY_RESPONSE` error**. {{src:packages/llm/llm/src/error.ts#L30-L39|EMPTY_RESPONSE_CODE}}'s comment explains why that is not a success:

> an empty message silently ends the turn with nothing for the user or the loop to act on. The attempt produced nothing durable, so retry policy treats it as safe to repeat.

An empty assistant message ends the turn quietly with nothing for the user or the loop to do. Reclassified as a failure, it lands in the default retryable code set, which section 8 covers.

### Unit conversion

{{src:packages/llm/llm-deepseek/src/translate.ts#L53-L62|mapUsage()}} is six lines, and it resolves a conflict of convention:

```ts
const cacheRead = usage.prompt_tokens_details?.cached_tokens ?? usage.prompt_cache_hit_tokens
return {
  inputTokens: usage.prompt_tokens - (cacheRead ?? 0),
  ...
}
```

DeepSeek's `prompt_tokens` **includes** cache hits, while {{src:packages/llm/llm/src/types.ts#L127-L141|TokenUsage}} declares its three counts disjoint (billed input is their sum). So the cache read is subtracted out. The lab makes the conversion visible: wire `prompt_tokens: 1180` and `prompt_cache_hit_tokens: 1024` come out as `inputTokens: 156, cacheReadTokens: 1024`.

## 3. BlockAssembler: the few lines that tolerate a broken protocol

{{src:packages/llm/llm/src/assembler.ts#L36-L164|BlockAssembler}} is the loop's single assembly algorithm. Of its 164 lines, four handle "survive an adapter that does not follow the ideal protocol".

**One: a block can open without `block-start`.** {{src:packages/llm/llm/src/assembler.ts#L96-L104|ensure()}} creates the partial on demand when a delta arrives:

```ts
private ensure(index: number, blockType: string): PartialBlock {
  let partial = this.partials.get(index)
  if (!partial) {
    partial = { blockType, text: '', toolCallArguments: '' }
    this.partials.set(index, partial)
    this.order.push(index)
  }
  return partial
}
```

The class JSDoc's `Tolerant of delta-only protocols (no block-start/end)` is this. An adapter may emit deltas alone.

**Two: deltas arriving after `block-end` are dropped.** One line in each of three cases:

```ts
if (partial.block) return // closed by block-end; ignore stragglers
```

The class comment gives the reason: `so a misbehaving adapter cannot grow memory or corrupt a completed block`. An adapter that keeps emitting stragglers cannot exhaust memory, and cannot rewrite a finished block.

**Three: a repeated `block-end` loses to the first.**

```ts
// First close wins; ignoring re-close stragglers keeps streamed output
// and the final assembled block in agreement.
if (partial.block) return
```

The reason is keeping the streamed output and the final block in agreement. What the user watched appear character by character is the first version; if a second `block-end` could overwrite it, the text committed to the log would not be the text the user read. This is the rendering-side dual of chapter 4's "model-visible means already recorded".

**Four: on `max-tokens`, every tool call is dropped.** {{src:packages/llm/llm/src/assembler.ts#L128-L139|blocks()}}:

```ts
blocks(): ContentBlock[] {
  const blocks = this.order.map(index => this.assemble(this.mustGet(index), index))
  return this.finish.kind === 'max-tokens'
    ? blocks.filter(block => block.type !== 'tool-call')
    : blocks
}
```

That line is not formatting, it is a **safety decision**. When output is cut off at the token cap, the last tool call's `arguments` is very likely half a JSON document. Half a document failing to parse is the good case; the bad case is that it parses: `{"path":"/tmp/a","recursive":true` truncated to `{"path":"/tmp/a"` is still valid JSON, just with different arguments. The JSDoc's `drops tool calls that cannot be executed safely` names exactly this.

Lab step 3 shows it. Feed one text block plus a truncated tool call, then `finish: max-tokens`:

```
blocks: [{"type":"text","text":"OK, let me"}]
```

The tool call disappears entirely. Back in chapter 5: `step()` receiving `max-tokens` returns `{ kind: 'max-tokens' }` immediately without entering tool scheduling. Together the two mean a truncated call is neither in the message nor executed.

One smaller design: {{src:packages/llm/llm/src/assembler.ts#L146-L149|the finish getter}} returns `{ kind: 'stop' }` when no `finish` chunk arrived. A stream that ended without saying why is treated as a normal ending, because "the stream broke" is already handled upstream by `parseSse`'s `STREAM_CLOSED` or `adapterStream`'s normalization; guessing again here would only mask that judgment.

## 4. How a throw becomes a chunk

Section 1's contract said an adapter may throw but the throw never reaches the consumer. {{src:packages/llm/llm/src/index.ts#L838-L900|adapterStream()}} enforces it. Its JSDoc draws the line in one sentence:

> Adapter selection, dispatch, iterator construction, and iteration failures become one terminal failure chunk. Middleware and downstream consumer failures remain thrown plugin or consumer errors.

**Adapter-side failures become chunks; middleware- and consumer-side failures stay thrown.** How that line is drawn in code is this function's entire craft.

The first `try` wraps adapter selection, config resolution, and getting the iterator:

```ts
try {
  const registration = prepared?.registration ?? this.registration(options.provider)
  ...
  const stream = adapter.stream(this.forAdapter(resolvedOptions, adapter))
  iterator = stream[Symbol.asyncIterator]()
} catch (error: unknown) {
  yield adapterFailureChunk(error, options.signal)
  return
}
```

The second is the read loop, and notice the `try` wraps only `iterator.next()`:

```ts
try {
  const next = await iterator.next()
  item = next.done ? { done: true } : { done: false, value: next.value }
} catch (error: unknown) {
  completed = true
  yield adapterFailureChunk(error, options.signal)
  return
}
if (item.done) { completed = true; return }
// End the adapter-owned try before yielding: consumer/middleware
// failures resumed into this generator must remain thrown.
yield item.value
```

`yield item.value` sits **outside** the try. The comment says why: a generator suspends at `yield`, and an exception the consumer throws there is **resumed back into this generator** as a `throw()`, landing on the yield line. With the yield inside the try, the consumer's own bug would be classified as an adapter failure and swallowed into an `error` finish chunk. Moving one line assigns responsibility correctly.

The failure-to-chunk conversion is {{src:packages/llm/llm/src/index.ts#L930-L939|adapterFailureChunk()}}:

```ts
function adapterFailureChunk(error: unknown, signal?: AbortSignal): StreamChunk {
  const failure = normalizeLlmFailure(error)
  return {
    type: 'finish',
    reason: signal?.aborted || failure.code === 'ABORTED'
      ? { kind: 'aborted', failure }
      : { kind: 'error', failure },
  }
}
```

`aborted` and `error` are separated because downstream treats them differently: cancellation should not trigger retry, and should not be recorded as a failure. The test reads two places, the caller's signal and the failure code itself; either one suffices.

{{src:packages/llm/llm/src/adapter-failure.ts#L16-L28|normalizeLlmFailure()}} handles a different problem: `instanceof` fails across package copies, since bundling gives the class a different identity. Its approach is to read own data properties, and to trust them only when `failure.code` and `error.code` agree:

```ts
const carried = ownFailureSnapshot(error)
if (carried !== undefined && carried.code === ownErrorCode(error)) return carried
```

`Object.getOwnPropertyDescriptor` appears three times in that file, each with a comment about not triggering an SDK-defined accessor. The reason is that a third-party SDK error may carry a throwing getter, and this code runs on the already-failed path, where a second throw has nobody to catch it.

Finally the cleanup in `finally`:

```ts
} finally {
  if (!completed) {
    const close = iterator.return?.bind(iterator)
    if (close) await close()
  }
}
```

`completed` is set only on a clean end or a read failure. A consumer that breaks out of its `for await` early takes the `!completed` path, so the adapter's generator receives `return()` and runs its own `finally`, which is the `consumer.abort(...)` in {{src:packages/llm/llm-deepseek/src/adapter.ts#L214-L269|DeepSeekAdapter.stream()}}. That is what actually closes the HTTP connection.

## 5. The return trip: serialization

The outbound half is done; the return trip is {{src:packages/llm/llm-deepseek/src/serialize.ts#L151-L187|serializeRequest()}}, turning harness messages back into an OpenAI-compatible body. Four places are worth reading closely.

**One: an assistant `content` is always a string, never null.** The comment in {{src:packages/llm/llm-deepseek/src/serialize.ts#L71-L102|serializeAssistant()}} is one of the longest in the repo:

```ts
// Text-less turns send "" — NEVER null. Pure tool-call turns: the
// official samples replay message.content verbatim (which is "") and
// some gateways reject null outright. Reasoning-ONLY turns (the model
// can answer entirely in the reasoning channel, e.g. a v4-flash
// greeting): the live API rejects null-content/no-tool_calls assistant
// messages with a 400 ("content or tool_calls must be set"), and since
// the message sits durably in the session log, a null here bricks every
// later turn of that session.
content: text,
```

The last sentence is the point: **this message is persisted to the session log**. A null does not fail one request, it fails every subsequent turn of that session, because every turn reserializes that history and sends it again. The log is append-only, so the bad message cannot be deleted. Chapter 4's "the log only grows" becomes a constraint here.

**Two: `reasoning_content` is replayed only on tool-call turns.**

```ts
...toolCalls.length > 0 && reasoning.length > 0 ? { reasoning_content: reasoning } : {},
```

The comment cites the official guide: thinking mode requires reasoning_content on tool-call turns; on plain turns it is ignored, so it is dropped there to save tokens.

**Three: tool results are expanded out of user messages into standalone tool messages.** In the harness vocabulary a tool result is a `tool-result` block inside a user-role message (chapter 4); DeepSeek wants a standalone `role: 'tool'` message. {{src:packages/llm/llm-deepseek/src/serialize.ts#L112-L141|serializeMessages()}} does the expansion:

```ts
const toolResults = message.content.filter(block => block.type === 'tool-result')
const text = flattenText(message.content)
if (text.length > 0 || toolResults.length === 0) {
  wire.push({ role: 'user', content: text })
}
for (const result of toolResults) {
  wire.push({ role: 'tool', tool_call_id: result.toolCallId, content: flattenText(result.content) || '(no output)' })
}
```

That `if` reads awkwardly; unfolded it says: a pure tool-result message emits no user message (which would be an extra empty one), and a mixed message emits its text first and its results after. The trailing `|| '(no output)'` exists because an empty string is rejected in that field.

**Four: images are refused explicitly, not dropped silently.** {{src:packages/llm/llm-deepseek/src/serialize.ts#L64-L68|assertTextOnly()}}:

```ts
function assertTextOnly(blocks: readonly ContentBlock[]): void {
  if (contentHasImage(blocks)) {
    throw new LlmError('The DeepSeek chat-completions adapter does not support image content.', 'UNSUPPORTED_CONTENT')
  }
}
```

It is called at the top of `serializeMessages`'s loop, before `flattenText`. Because `flattenText` keeps only `type === 'text'` blocks, an image block would **vanish without a sound**: the request goes out, the model never sees the image, and the user is never told. The module JSDoc's `rejected explicitly because this wire route is text-only` refuses that silence.

Its companion is the `inputModalities: ['text']` in `resolveModel`, declared even for models absent from the catalog. That comment states the motive: writing "unknown" would let the host accept and persist an image the serializer must then reject, by which point the image is already in the log.

Lab step 5 prints the whole request body, including the two constant fields `stream: true` and `stream_options: { include_usage: true }`. This layer offers no non-streaming path.

## 6. prepareCall: why not just stream

`LlmRuntime` has two entry points. {{src:packages/llm/llm/src/index.ts#L902-L915|stream()}} is one-shot; {{src:packages/llm/llm/src/index.ts#L771-L814|prepareCall()}} resolves first and dispatches later, with an await in between. The loop uses the latter:

```ts
preparedCall = await this.loopCtx.llm.prepareCall(proposedConfig, signal)
config = preparedCall.config
```

The JSDoc's reason is concrete:

> The returned one-shot handle keeps that registration across header logging and dispatch, so HMR cannot combine one adapter's capability result with another adapter.

During that await, `resolveModel()` asks the adapter for the context window, the default max tokens, and the supported reasoning efforts. Cordis hot reload can perfectly well swap this provider's adapter meanwhile. If dispatch looked the registry up again, adapter A's capability result would be used to call adapter B. `prepareCall` captures `registration` in a closure, closing that gap.

The returned handle has three locks:

```ts
if (dispatched) throw new LlmError('a prepared LLM call can only be dispatched once', 'INVALID_PREPARED_CALL')
if (!callConfigEquals(options, resolvedConfig)) throw new LlmError('prepared LLM call config changed before adapter dispatch', 'INVALID_PREPARED_CALL')
```

One dispatch only, config must match, and the config itself came out of `deepFreeze(structuredClone(...))`.

The `adapterDefaults` field connects back to chapter 5. {{src:packages/llm/llm/src/index.ts#L734-L769|resolveCallFor()}} materializes adapter-configured defaults into the config: no `maxTokens` from the caller means the model's `defaultMaxTokens`, no `reasoningEffort` means its `defaultEffort`. Once materialized, the config no longer distinguishes what the caller asked for from what the adapter filled in. `adapterDefaults` records that distinction:

```ts
...config.reasoningEffort === undefined && resolvedConfig.reasoningEffort !== undefined
  ? { reasoningEffort: true } : {},
```

The condition in chapter 5's {{src:packages/core/agent-loop/src/agent.ts#L407-L495|buildRequest()}} that reads so awkwardly uses exactly this:

```ts
const reasoningEffort = persistedConfig?.provider === route.provider
  && persistedConfig.model === route.model
  && persistedHeader?.adapterDefaults?.reasoningEffort !== true
  ? persistedConfig.reasoningEffort
  : undefined
```

When resuming a session, the log holds last time's reasoning effort. If the user chose it, restore it; if the adapter supplied it as a default, do not, and ask the adapter again, because the default may have changed. Without the `adapterDefaults` marker the distinction cannot be made.

The same spirit governs another line in `resolveCallFor`: an unsupported effort throws `UNSUPPORTED_REASONING_EFFORT`, with **no clamping and no aliasing**. Quietly downgrading `max` to `high` would leave the user believing they are running max.

## 7. llm/stream: policy lives here

{{src:packages/llm/llm/src/index.ts#L917-L927|streamWithRegistration()}} is entirely one waterfall:

```ts
return this.ctx.waterfall(this, 'llm/stream', options, () => this.adapterStream(options, prepared))
```

Chapter 2 covered waterfall semantics: a listener receives `next`, calling it continues down the chain, not calling it short-circuits. Here that means **every model call can be replaced wholesale by a plugin**.

The event declaration's JSDoc states the parameter constraint:

```ts
/**
 * @param options - the full request. A LOOP-built request carries the
 *   process-local {@link markAgentLoopRequest} identity and arrives deep-frozen
 *   (mutation throws): its content is a pure function of the session log (the
 *   reconstructability Agent Note), so listeners read it, never rewrite it.
 * @mode waterfall
 */
```

**A loop-built request is read-only**, because its content is a pure function of the session log. For chapter 4's "model-visible means already recorded" to hold, no listener may quietly alter content after logging and before sending; otherwise the request replayed from the log is not the request that went out. So the loop freezes it as {{src:packages/core/agent-loop/src/agent.ts#L486-L493|buildRequest's last step}}:

```ts
const request = markAgentLoopRequest(deepFreeze({ ...header.config, messages: boundaryMessages, ... }))
```

The lab verifies both facts directly:

```
[intercept] frozen? true  messages array frozen? true
[intercept] rewrite -> TypeError: Cannot add property 1, object is not extensible
```

{{src:packages/llm/llm/src/call-config.ts#L88-L117|deepFreeze()}} has one deliberate exception:

```ts
if (node instanceof AbortSignal) continue
```

An AbortSignal is the request's live cancellation channel, and freezing it breaks abort. The JSDoc says so outright: `freezing them breaks abort`.

So what is `markAgentLoopRequest` for? {{src:packages/llm/llm/src/call-config.ts#L66-L69|It}} puts the request object into a module-level `WeakSet`:

```ts
const AGENT_LOOP_REQUESTS = new WeakSet<GenerateOptions>()
export function markAgentLoopRequest<T extends GenerateOptions>(request: T): T {
  AGENT_LOOP_REQUESTS.add(request)
  return request
}
```

Why not a field on the request? Because a field would be serialized, copied by `structuredClone`, and forgeable. A WeakSet records **object identity**: unique within the process, unforgeable, and a copy does not count. The marker lets listeners tell "this is a loop-built request derived from the log" from "this is a one-off request some plugin assembled by hand", where the former is read-only and the latter carries no such constraint.

The last piece is {{src:packages/llm/llm/src/index.ts#L822-L836|forAdapter()}}, which strips `replayState` that does not belong to the current adapter before dispatch:

```ts
if (message.role !== 'assistant' || source.kind !== 'model' || source.replayState === undefined) return message
if (this.adapters.get(source.provider)?.adapter === adapter) return message
return freezeMessage({ ...message, source: { kind: 'model', provider: source.provider, model: source.model } })
```

`replayState` is adapter-private lossless-JSON replay state (the optional field on section 1's `finish` chunk). A session may have switched providers midway, leaving historical messages carrying another adapter's replay state. The test compares **adapter instances**, not provider names: one adapter instance may register several routes, and in that case the replay state is shared.

:::key llm/stream and agent/request are different things
Chapter 5's `agent/request` waterfall rewrites the **config**: provider, model, sampling. `llm/stream` here replaces the **entire call**. Use the former for A/B routing, the latter for replay, recording, and caching.
:::

## 8. Retry is not in this layer

`dsh-llm-retry` is a standalone plugin of 226 lines. The first question worth asking is where it hooks in.

Not `llm/stream`. See {{src:packages/llm/llm-retry/src/index.ts#L210-L219|the listener registration}}:

```ts
const disposeListener = ctx.on('agent/request-error', (payload, next) => { ... })
```

It hooks chapter 5's `agent/request-error`, the retry decision point of the inner `while` in `step()`. Why not retry in the LLM layer? Because retry needs two things the LLM layer cannot reach: **the session log** (to write `llm/retry` events into) and **turn coordinates** (turn / step). And `step()`'s `while (true)` is already a retry loop; all it needs is a yes-or-no answer.

Then look at how it counts which retry this is. Not an in-memory counter:

```ts
const priorPolicyRetry = agent.session.events.findLast((event): event is SessionEvent<'llm/retry'> =>
  event.type === 'llm/retry'
  && event.data.turn === turn
  && event.data.step === step
  && event.data.provider === provider
  && event.data.policyKey === policyKey,
)
const previousRetry = priorPolicyRetry?.data.retry ?? 0
```

**It is `findLast`ed out of the session log.** This is chapter 4's principle applied once more: state lives in the log, the plugin itself is stateless. The immediate benefit is that resuming a session after a restart does not reset the retry count.

Of the four match conditions, `policyKey` is the interesting one. {{src:packages/llm/llm-retry/src/index.ts#L65-L76|retryPolicyKey()}} serializes the whole policy into a string. Matching on it means **the count restarts when the policy changes**. A user raising maxRetries from 2 to 5 and hot-reloading will not immediately give up because "we already retried twice".

{{src:packages/llm/llm-retry/src/index.ts#L111-L154|backoff()}} contains an ordering worth noticing:

```ts
agent.session.append('llm/retry', eventData)
if (!await cancellableDelay(delayMs, fusedSignal)) return
agent.session.append('llm/retry-started', { retryId, turn, step, retry })
return { kind: 'retry' }
```

Two events bracket the wait: `llm/retry` before, `llm/retry-started` after. The module JSDoc puts it in one line: `Each scheduled retry is durable before its cancellable wait`. **The decision to retry is persisted before the waiting starts.** Writing only after the wait would mean a crash during the wait leaves no trace that a retry was ever planned. Splitting them has a second use too: a UI can show a countdown between the two.

For the delay, {{src:packages/llm/llm-retry/src/index.ts#L58-L63|localDelay()}} is standard exponential backoff with symmetric jitter; the `Math.min(retry - 1, 1024)` cap guards `2 ** n` against overflow. The real branch is when the server supplied `Retry-After`:

```ts
if (failure.providerRetryAfterMs > policy.maxDelayMs) {
  if (policy.mode === 'normal') return next()
  delayMs = localDelay(policy, retry, random)
}
```

When the server's requested wait exceeds the local ceiling, `normal` mode **gives up** (`return next()` hands the decision to the next listener in the chain) while `always` mode falls back to local backoff and continues. The fork expresses the two modes' different jobs: `normal` is bounded recovery from transient faults, and waiting ten minutes because a server said so is not that; `always` retries until success, cancellation, or disposal, so it sets its own pace.

The default retryable set is in {{src:packages/llm/llm/src/retry-policy.ts#L18-L24|retry-policy.ts}}:

```ts
const DEFAULT_RETRYABLE_CODES = Object.freeze([
  EMPTY_RESPONSE_CODE, 'RATE_LIMIT', 'SERVER', 'TIMEOUT', 'TRANSPORT',
])
```

`AUTH` and `INVALID_REQUEST` are absent: retrying them just repeats the same mistake. `EMPTY_RESPONSE` is present for the reason quoted in section 2: that attempt produced nothing durable. `INVALID_CREDENTIAL`'s comment likewise explains its exclusion: a malformed credential fails identically every time.

class RealAdapter extends LlmAdapter {
  calls = 0
  async *stream() {
    this.calls++
    yield { type: 'block-start', index: 0, blockType: 'text' }
    yield { type: 'text-delta', index: 0, text: 'from the real adapter' }
    yield { type: 'block-end', index: 0, block: { type: 'text', text: 'from the real adapter' } }
    yield { type: 'finish', reason: { kind: 'stop' } }
  }
}

export async function apply(ctx) {
  const adapter = new RealAdapter()
  ctx.llm.registerAdapter(['lab'], adapter)

  ctx.on('llm/stream', async function* (options, next) {
    const text = options.messages.at(-1).content
      .filter(b => b.type === 'text').map(b => b.text).join('')
    console.log('[intercept] frozen?', Object.isFrozen(options),
      ' messages array frozen?', Object.isFrozen(options.messages))

    if (!text.includes('cache')) return yield* next()

    yield { type: 'block-end', index: 0, block: { type: 'text', text: '(cache hit, no network request)' } }

    if (e.type === 'assistant/message') console.log('assistant/message:', JSON.stringify(e.data.message.content))
  }
  console.log('adapter.stream call count =', adapter.calls)

## Summary

One model call's full path through this layer:

```
step() → prepareCall(config)         capture the adapter registration, resolve exact-model capability
      → preparedCall.stream(request) the request is already deep-frozen
        → ctx.waterfall('llm/stream')  a plugin may replace the whole call
          → adapterStream()             throw → terminal chunk
            → DeepSeekAdapter.stream()
              → fetch → parseSse → translate → StreamChunk
      ← for await: one chunk, one log event; the same chunk goes to BlockAssembler
      ← is finish error/aborted? → agent/request-error → llm-retry decides
      ← otherwise assembler.blocks() → createAssistantMessage()
```

Three conclusions:

**Vendor-specific code is compressed into one class.** An adapter's job is `stream()`: wire format into seven chunk kinds, harness messages back into wire format. The registry, capability resolution, freezing, interception, and failure normalization all live in `LlmRuntime`, and none of it changes when a new vendor arrives.

**"An adapter may throw, but the throw never reaches the consumer" is implemented by where one `yield` sits.** `yield item.value` in `adapterStream` lives outside the try, splitting adapter failures from consumer failures onto two paths. That comment is worth remembering: `consumer/middleware failures resumed into this generator must remain thrown`.

**Policy lives in the log, not in memory.** The retry count comes from `session.events.findLast`, the retry decision is persisted before the wait, and the failed attempt is itself an `assistant/chunk`. Chapter 4's principle has no exception in this layer.
