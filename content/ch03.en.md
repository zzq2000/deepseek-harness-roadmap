# The boot chain: from `dsh web` to a plugin tree

The first two chapters covered mechanism: how a fiber lives, how a service is found, how an event is dispatched. This chapter covers assembly.

Start with a number. Run `dsh --profile web --dump-config` and you get **129 plugin rows**. Not one of them is written in TypeScript. They are composed entirely out of YAML patches, starting from an empty array `[]`.

This chapter walks the chain from argv to 129 fibers, and ends by having you build your own profile, write your own plugin, and patch it into the tree. That is the smallest possible version of the chapter 12 capstone.

## 1. The launcher knows only its own four flags

{{src:apps/cli/src/bin.ts#L27-L53|bin.ts:27-53}} is the entire entry logic:

```ts
const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({
      environment: loadLayeredEnv('dsh'),
      profile: invocation.profile,
      patchFiles: invocation.patches,
      args: invocation.args,
    })
```

Each mode does its own `await import()`, so one invocation loads only the modules on its own path. `dsh plugin add foo` never pulls the boot chain into memory.

What is worth reading is how `parseDshArgs` draws its boundary. {{src:apps/cli/src/args.ts#L122-L134|args.ts:122-134}}:

```ts
    .exitOverride()
    // The launcher's flags come first and end at the first token it does not
    // know; everything from there on belongs to the booted app, including
    // its -h. `dsh -h` with no profile still prints this help, below.
    .helpOption(false)
    .allowUnknownOption()
    .passThroughOptions()
    .enablePositionalOptions()
```

Four commander switches expressing one thing: **the launcher stops at the first token it does not recognize and hands the rest to the tree verbatim.**

`helpOption(false)` is the one that is easy to miss. It gives away `-h` too, so `dsh --profile web --help` prints the web app's help, not the launcher's. The launcher prints its own only when there is no profile to hand it to ({{src:apps/cli/src/args.ts#L138-L141|args.ts:138-141}}).

The launcher recognizes four flags: `--profile`, `--patch`, `--dump-config`, `--dump-default-config`. Beyond those it knows nothing about what DSH does.

So how do an app's arguments reach a plugin? Through a service. {{src:packages/boot/cmdline/src/index.ts#L68-L72|provideCmdline}}:

```ts
export function provideCmdline(ctx: Context, host: CmdlineHost): void {
  const snapshot: readonly string[] = Object.freeze([...host.args])
  ctx.provide('cmdlineArgs', { get: () => snapshot })
  ctx.provide('appExit', host.exit)
}
```

Two `provide` calls, the same `provide` from chapter 2. The command line has no privilege in DSH. It is an ordinary service, and any plugin that declares `inject: ['cmdlineArgs']` can read it.

:::key What this boundary buys
The launcher does not know what `--resume`, `--print`, or `--model` mean, and does not need to. A new app plugin that wants a new flag injects `cmdlineArgs` and parses it itself, with no launcher change.

Anything in chapter 12 that needs a command-line switch takes this same route.
:::

## 2. A profile: one directory, two files

`--profile web` points at `$DSH_HOME/profiles/web/`. Only two files there matter to the launcher:

| File | Role |
|---|---|
| `package.json` | `dsh.profile.bundles`: the ordered bundle package list |
| `cordis.patch.yml` | your own patch layer, applied over every bundle |

There is also a `cordis.yml`, and its content is always an empty array. {{src:apps/cli/src/profile-boot.ts#L59-L64|PROFILE_ROOT_CONFIG}} explains why it exists at all:

```
# dsh profile root — an empty entry list. The tree is composed as patches:
# each bundle in package.json's dsh.profile.bundles, then cordis.patch.yml, then any
# --patch overlays. Edit cordis.patch.yml, not this file.
[]
```

It exists because the Include plugin needs a real file to anchor `baseUrl` on. And it is **rewritten** on every launch ({{src:apps/cli/src/profile-boot.ts#L98-L103|prepareProfile}}):

```ts
export function prepareProfile(name: string, userLayer = true): Profile {
  healProfilesModuleFallback(INSTALL_ANCHOR)
  const profile = loadProfile(NAME, name, INSTALL_ANCHOR, undefined, { userLayer })
  writeFileSync(join(profile.dir, PROFILE_ROOT_FILENAME), PROFILE_ROOT_CONFIG)
  return profile
}
```

Unconditional overwrite, and the reason is in the function's own comment: the Loader has a write-back path (a plugin disposing itself persists the current tree). Without the reset, the next boot would apply every bundle's insert on top of an already-populated root, and every plugin would appear twice.

### Where a bundle comes from

The resolution order in {{src:packages/boot/app-boot/src/profile.ts#L344-L355|resolveBundleDir}} is a hard contract:

```ts
for (const anchor of [installAnchor, join(profileDir, 'package.json')]) {
  const dir = packageDirFromAnchor(anchor, packageName)
  if (dir !== undefined) return dir
}
```

**The dsh installation first, the profile directory second.** This guarantees `@deepseek-ai/dsh-base` always comes from the same installation as the running dsh; a same-named copy inside a profile cannot outrank it.

Conversely, a third-party plugin the user `pnpm add`s into a profile resolves from that profile's own `node_modules`. The two classes of plugin take different paths.

### Letting out-of-tree plugins import the framework

A third-party plugin installed inside a profile writes `import { Service } from '@deepseek-ai/cordis'` and must resolve to the **same cordis instance**, otherwise none of the symbols from chapter 1 line up.

{{src:packages/boot/app-boot/src/profile.ts#L223-L255|healProfilesModuleFallback}} handles that: under `$DSH_HOME/profiles/node_modules/` it maintains one symlink per package in the dsh dependency closure.

```ts
const queue: { anchor: string; manifest: ProfileManifest }[] = [{ anchor: installAnchor, manifest: appManifest }]
for (let next = queue.shift(); next !== undefined; next = queue.shift()) {
  for (const dep of [...Object.keys(next.manifest.dependencies ?? {}), ...Object.keys(next.manifest.peerDependencies ?? {})]) {
    if (links.has(dep)) continue
    const dir = packageDirFromAnchor(next.anchor, dep)
    if (dir === undefined) continue
    links.set(dep, dir)
```

Three details worth noting:

1. **It is a BFS closure, not direct dependencies.** The comment gives the reason: an out-of-tree plugin's peer dependencies name pure definition packages like `dsh-compaction` and `dsh-invariants`, which the app only reaches through implementation packages. Linking direct dependencies alone would miss them.
2. **`peerDependencies` participate.** In DSH a Service Definition package is always a peer of its implementation, never a plain dependency.
3. **`links` is itself the visited set**, so first resolution wins, matching Node's own nearest-wins rule.

The directory sits under `profiles/`, next to each profile directory, so Node's parent-directory walk from any profile hits it on the second stop. pnpm never manages it.

## 3. The patch stack: four layers into one tree

{{src:apps/cli/src/profile-boot.ts#L142-L171|composeProfile}} decides the stacking order, and {{src:apps/cli/src/profile-boot.ts#L122-L129|allPatches}} writes it out as one array:

```ts
function allPatches(composed: ComposedProfile): PatchOptions[] {
  return [
    ...composed.bundlePatches,
    ...composed.profile.patches,
    ...composed.homePatches,
    ...composed.overlays,
  ]
}
```

| Layer | Source | Author |
|---|---|---|
| 1 | each bundle's `cordis.patch.yml`, in `bundles` order | DSH upstream |
| 2 | `$DSH_HOME/profiles/<name>/cordis.patch.yml` | you, for this profile |
| 3 | `$DSH_HOME/cordis.patch.yml` | you, for this machine |
| 4 | `--patch` overlays plus launcher-derived switches | this invocation |

Layer 3 outranking layer 2 is deliberate: a machine-level preference ("telemetry off on this box, always") should apply to every profile, so it goes after the per-profile setting.

Layer 4 contains two patches derived in code rather than read from a file. {{src:apps/cli/src/profile-boot.ts#L159-L169|profile-boot.ts:159-169}}:

```ts
if (rows.has('agent-presets')) {
  composedOverlays.push({
    id: 'agent-presets',
    config: { ...(rows.get('agent-presets')?.config ?? {}), roots: [{ path: SHIPPED_PRESET_ROOT, trust: 'system' }] },
  })
}
const telemetryPatch = resolveTelemetryPatch(process.env.DSH_TELEMETRY_DISABLED, rows.has(TELEMETRY_ROW_ID))
if (telemetryPatch !== undefined) composedOverlays.push(telemetryPatch)
```

Both check `rows.has(...)` first, meaning **the first three layers are composed once to see whether the row exists at all, and only then is a patch added**. The comment on {{src:apps/cli/src/profile-boot.ts#L80-L83|resolveTelemetryPatch}} gives the reason: a custom profile may not mount telemetry at all, in which case `DSH_TELEMETRY_DISABLED` is trivially satisfied and there is no point manufacturing a patch that matches nothing.

Look at the switch's own test while you are here:

```ts
if ((disabledEnv ?? '') === '' || !hasRow) return undefined
```

**Any non-empty value disables**, including `'0'` and `'false'`. The comment is blunt about it: a privacy switch prefers off-by-mistake over on-by-mistake.

### applyEntryPatches: how a patch actually lands

Every layer flattens into one list handed to {{src:vendor/include/src/index.ts#L58-L128|applyEntryPatches}}. It is the core of the Include plugin, and it is the same function `--dump-config` uses, so a dump can never drift from what actually mounts.

First it builds an id index:

```ts
const entryMap = new Map<string, EntryOptions>()
const buildMap = (entries: EntryOptions[]) => {
  for (const entry of entries) {
    if (entry.id) entryMap.set(entry.id, entry)
    if (entry.group && Array.isArray(entry.config)) {
      buildMap(entry.config)
    }
  }
}
```

A group row's `config` is an array of child rows, so the index recurses. Rows inside a group can be targeted by an outer patch just as well.

Then it applies patches one at a time. The `insert` branch:

```ts
if (insert) {
  if (id) {
    const target = entryMap.get(id)
    if (!target) { warn('patch insert: entry %C not found', id); continue }
    if (!target.group) { warn('patch insert: entry %C is not a group', id); continue }
    if (!Array.isArray(target.config)) target.config = []
    target.config.push(...insert)
  } else {
    data.push(...insert)
  }
  buildMap(insert)
  continue
}
```

That last `buildMap(insert)` is the single most worthwhile line in the function, and it has its own comment:

> Index what this patch added so a LATER patch in the same list can target it.

**A freshly inserted row must enter the index immediately, or later layers cannot touch it.** This is exactly why `dsh-web-app` can override rows that `dsh-base` inserted: the base layer pushes 100+ rows with one `insert`, and the web-app layer then edits several of them by id. Without this line, bundles could not configure each other at all.

The last three lines of the non-insert branch are the easiest trap:

```ts
for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value
}
```

**The whole `config` is replaced, not deep-merged.** The `dsh-base` bundle states the consequence at the top of its own file ({{src:packages/bundle/base/cordis.patch.yml#L1-L13|the base bundle's opening comment}}):

> A patch replaces the targeted row's whole `config` rather than merging into it, so a row whose value differs by mode does NOT live here: it belongs to each mode bundle.

So base carries only neutral defaults shared across modes, and any value that differs by mode is restated in full by each mode bundle. Any single row's final value passes through at most "one bundle layer plus the user's", which keeps it traceable.

:::warn When you write your own patch
Under `config:`, write only the key you want to change and every other key disappears, because what gets replaced is the whole config object. Run `--dump-config` first to see the row's current full configuration.
:::

## 4. boot(): eight lines of trunk

With patches computed, control enters {{src:packages/boot/app-boot/src/index.ts#L757-L802|boot()}}. Stripped of comments and error handling, the trunk is:

```ts
const ctx = new Context()
let stage = 'host preparation failed'
try {
  ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + '/'
  ctx.provide('dshHomePath', dshHomePath)
  await ctx.plugin(Loader)
  await prepare?.(ctx)
  stage = 'plugin tree failed to load'
  await mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)
  await ctx.get('loader')?.await()
  if (ctx.get('loader') === undefined) return ctx
  await assertEntriesActivated(ctx, binName)
  return ctx
}
```

`new Context()` is the root Context from chapter 1. All 129 DSH plugins hang under this one root.

Several design points:

**The `stage` variable splits the run in two.** `prepare` runs before any config row mounts, so its failure is host setup, not the plugin tree. Two labels make it obvious at a glance whose fault it was.

**`prepare` is where the command line is injected.** The callback {{src:apps/cli/src/profile-boot.ts#L248-L259|profile-boot.ts:248-259}} passes in contains exactly three `provide` calls: the environment snapshot, `cmdlineArgs`, and `appExit`. The comment says why it must be here:

> Before any config-tree entry mounts, so plugins resolve all launch-time environment values from the same immutable provenance snapshot.

**Every `await` is followed by a fresh `ctx.get('loader')` check.** An app can request exit while startup is still in flight (`--help` prints and calls `appExit`), and by then the whole tree, Loader service included, is gone. Reading `ctx.loader` would throw a TypeError over a program that exited exactly as asked. The check appears twice inside boot and once more in `runProfile`.

**The error chain is unwrapped.** {{src:packages/boot/app-boot/src/index.ts#L796-L800|index.ts:796-800}}:

```ts
let deepest: unknown = cause
while (deepest instanceof Error && deepest.cause !== undefined) deepest = deepest.cause
const stack = deepest instanceof Error && deepest !== cause ? `\n${deepest.stack ?? deepest.message}` : ''
```

The Loader wraps a `failed to apply loader entry ...` message around every tree layer it crosses, so the outermost message is only the wrapper chain. This digs out the deepest real exception and appends it, so the stack you read points at the plugin that actually failed. Step 2 of this chapter's lab shows the real chain.

### What mountRootInclude mounts

{{src:packages/boot/app-boot/src/index.ts#L486-L529|mountRootInclude}} creates exactly one entry:

```ts
const rootInclude: EntryOptions = {
  id: 'include',
  name: 'cordis:include',
  config: includeConfig,
}
const includeId = await ctx.loader.create(rootInclude)
```

The `cordis:` prefix takes the short-circuit branch in {{src:vendor/loader/src/config/tree.ts#L144-L162|EntryTree.import}}, reading the object straight out of `loader.builtins` with no module resolution. Two things go into builtins: `include` and `group`.

The comment explains why group is there:

> a group row is how a composition gives one `isolate` realm to a provider and its consumers together, and an agent preset living outside this workspace cannot resolve `@deepseek-ai/cordis-plugin-group` by name.

That is chapter 2's isolate realm arriving at the config layer: **a group row is the syntax for giving a set of plugins their own isolation realm.** An agent preset installed outside the profile cannot resolve the group plugin by package name, so it is made a builtin.

`id: 'include'` is pinned, and the comment says why: this include is app glue rather than a config row, its id shows up in Loader failure chains, and a random id would make startup diagnostics differ between runs.

## 5. After Include is mounted

{{src:vendor/include/src/index.ts#L273-L289|Include's Service.init}} is a generator, the pattern chapter 1 covered: the function it yields is the cleanup function.

```ts
async* [Service.init]() {
  let candidate: ReadCandidate
  try {
    candidate = (await this.read(true))!
  } catch (error) {
    if (!(error instanceof ConfigFileError) || error.stage !== 'read' || (error.cause as NodeJS.ErrnoException)?.code !== 'ENOENT') throw error
    if (this.config.initial) {
      await this._writeFile(this.config.initial as any)
      candidate = (await this.read(true))!
    } else {
      throw new Error(`config file not found: ${this.filename}`)
    }
  }

  yield () => this.stop()
  await this.apply(candidate)
}
```

Note where the `yield` sits: **reading the file happens before it, mounting the subtree after it.**

That ordering is intentional. If reading fails, nothing exists yet that needs cleaning up, so throwing is correct. But `apply()` creates a large batch of child fibers, and they must be covered by `stop()`, so the cleanup function has to be registered before apply runs. Chapter 1 established that `ctx.effect()` guarantees cleanup runs exactly once; here is that guarantee in production code: **when you register cleanup decides what gets cleaned up.**

`_apply` is three lines:

```ts
const data = this.applyPatches(candidate.data, this.config.patches)
await this.root.update(data)
this.content = candidate.content
```

Patches land here, and the result goes to EntryGroup.

The constructor also registers an `internal/update` listener ({{src:vendor/include/src/index.ts#L206-L213|include/index.ts:206-213}}), which is the hot-reload entry: update the Include's config from outside (a new patch list) and it re-applies patches over the **cached raw file data** and calls `root.update` again. The file itself is not re-read. Chapter 2's live `cordis.patch.yml` reloading takes this path.

## 6. EntryGroup.update: concurrent creation, all-or-nothing rollback

{{src:vendor/loader/src/config/group.ts#L59-L106|EntryGroup.update}} is where 129 rows become 129 fibers.

```ts
const outcomes = await Promise.allSettled(config.map(options => this.create(options)))
if (this.ctx.fiber.uid === null) return
const failures = outcomes
  .filter((outcome): outcome is PromiseRejectedResult => outcome.status === 'rejected')
  .map(outcome => outcome.reason)
if (failures.length === 1) throw failures[0]
if (failures.length > 1) throw new AggregateError(failures, 'loader entries failed to apply')
```

**`Promise.allSettled`, not `Promise.all`.** The difference: `all` returns on the first failure while the remaining plugins are still mid-startup with nobody minding them. `allSettled` waits for every entry to settle, then collects all failures at once, packing several into an `AggregateError`.

The line in the middle, `if (this.ctx.fiber.uid === null) return`, applies a chapter 1 fact: `uid` becoming `null` means this fiber has been disposed. The comment:

> Disposal owns termination: sibling starts can still be settling after the containing tree has gone away, but their failures no longer describe a live update to roll back.

With the tree gone, rollback is meaningless.

The failure path is a full rollback:

```ts
for (const id of Object.keys(newMap).reverse()) {
  if (oldMap[id]) continue
  try { await this.remove(id, true) } catch (rollbackError) { rollbackErrors.push(rollbackError) }
}
for (const options of oldConfig) {
  try { await this.create(options) } catch (rollbackError) { rollbackErrors.push(rollbackError) }
}
this.data = oldConfig
```

First tear down what was newly created, in reverse (the same ordering as chapter 1's cleanup), then rebuild the old configuration row by row. Errors during rollback do not mask the original error; they all go into one `AggregateError`.

At boot `oldConfig` is empty, so if any single row fails to start, nothing of the tree survives: everything created is torn down, nothing is restored, and `boot()` throws. **DSH has no partially-started state.**

## 7. Entry.update: restart, or just reconfigure

{{src:vendor/loader/src/config/entry.ts#L142-L246|Entry.update}} runs 100 lines, but its skeleton is a four-way decision. First the diff:

```ts
const diff = Object
  .keys({ ...candidate, ...legacy })
  .filter(key => !deepEqual(candidate[key], legacy[key]))
if (!diff.length && !force) return
```

Then it branches on the diff's contents. The critical line is:

```ts
const replace = diff.some(key => key === 'name' || key === 'inject' || key === 'group')
```

**Only `name`, `inject`, and `group` force a plugin restart.** Everything else (mainly `config`) goes through `_patchContext`: the plugin object itself is untouched and only `fiber.update(config)` runs.

The reasoning is clear. A changed `name` means importing a different module. A changed `inject` alters both the `fiber.store` snapshot from chapter 2 and the epoch fingerprint. A changed `group` changes what kind of node this is. A changed `config` is the plugin's own business, and Cordis has the `internal/update` event to tell it.

That is why editing one row's `config` in `cordis.patch.yml` hot-updates that plugin instead of restarting it, while editing its `inject` list restarts it entirely.

All four branches roll back. Take the replace branch, the most involved:

```ts
try {
  await this._start(plugin)
} catch (error) {
  this.options = previousOptions
  try {
    await this._start(previousPlugin)
  } catch (rollbackError) {
    throw updateError('rollback', legacy, new AggregateError([error, rollbackError]))
  }
  this.context.emit('loader/partial-dispose', this, candidate, true)
  throw updateError('apply', candidate, error)
}
```

If the new plugin fails to start, the old one is started back up as it was. `previousPlugin` is captured before the dispose precisely for this step.

### Back to chapter 1

The chain terminates in {{src:vendor/loader/src/config/entry.ts#L291-L302|Entry._start}}:

```ts
private async _start(plugin: any) {
  let fiber: Fiber | undefined
  try {
    await this._patchContext([])
    this.loader.showLog(this, 'apply')
    fiber = this.fiber = this.ctx.registry.plugin(plugin, this.options.config, this.getOuterStack)
    await fiber.await()
  } catch (error) {
    await this._dispose(fiber)
    throw error
  }
}
```

`this.ctx.registry.plugin(...)` is the function chapter 1 walked line by line. **The whole chain from argv to fiber joins up on this line.** One YAML row is, in the end, one `registry.plugin()` call.

:::key The whole chain
`dsh web` → `parseDshArgs` → `composeProfile` (four patch layers) → `applyEntryPatches` (129 rows) → `mountRootInclude` → `Include[Service.init]` → `EntryGroup.update` (concurrent) → `Entry._start` → `registry.plugin()` → fiber

Below that is chapter 1: `_reload` / `effect` / epoch.
:::

## 8. `!!js` is lazy

The dumped config contains rows like this:

```yaml
- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject:
    - webStartup
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080
```

`!!js` is a YAML tag Include defines ({{src:vendor/include/src/index.ts#L9-L23|the JsExpr type and entryListSchema}}). It wraps the string as `{ __jsExpr: '...' }` and **does not evaluate it at parse time**.

Evaluation happens inside one Loader event listener. {{src:vendor/loader/src/index.ts#L92-L101|the internal/config hook}}:

```ts
ctx.on('internal/config', function (this: Fiber, _config, next) {
  const config = next()
  if (!this.entry || this.parent.fiber?.entry === this.entry) return config
  // Tree carriers (Group, Include) keep their configs literal
  const plugin = this.runtime?.callback as Record<PropertyKey, unknown> | undefined
  if (plugin?.[EntryGroup.key]) return config
  return interpolate(this.ctx, config)
}, { global: true })
```

This is chapter 2's **waterfall onion** in production, in its textbook form: call `next()` first, then post-process the inner result. It uses `function` rather than an arrow because it needs `this` (the current fiber), which is chapter 2's scoping mechanism.

The `EntryGroup.key` check in the middle is required: a Group's or Include's config holds **other rows' configs**, whose `!!js` expressions belong to those rows' fibers and must not be evaluated at this level. So a plugin carrying that marker keeps its config literal.

Evaluation itself is {{src:vendor/loader/src/config/utils.ts#L5-L22|utils.ts:5-22}}:

```ts
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`)
```

`with (ctx)` lets an expression write `dshHomePath('sessions')` instead of `ctx.dshHomePath(...)`, and `process.env.X` still resolves from the outer scope.

### Why the command line beats the config file

Put the pieces together:

1. The `web-startup` row provides the `webStartup` service, parsing flags like `--port` in its own commander action.
2. The `webserver` row declares `inject: [webStartup]`. Chapter 1 established that a fiber declaring a dependency stays PENDING until it is available.
3. Activation triggers `internal/config`, and by then `ctx.webStartup` exists, so `!!js ctx.webStartup.port ?? 3080` evaluates.

**Not one line of code implements "the command line outranks the config file."** The behaviour falls out of three existing mechanisms: service resolution, lazy evaluation, and inject-driven scheduling. {{src:packages/boot/cmdline/src/index.ts#L1-L17|The cmdline module comment}} states it in one sentence:

> No row has launcher-level command-line status.

:::key The canonical DSH extension point shape
To make your plugin controllable by a new flag: provide a service that parses your flag, then write `inject` plus `!!js` in the config. No launcher change, no change to any existing code.

Chapter 12 uses this shape.
:::

## 9. Row order is not load order

The `dsh-base` patch file opens with a line that is easy to skim past ({{src:packages/bundle/base/cordis.patch.yml#L12-L13|the last two lines of the base bundle's comment}}):

> Row order carries no load semantics (activation is service-availability driven); the grouping is for readers.

The order of the 129 rows has no effect on startup. The reason is in chapter 1: fiber activation is epoch-driven, and a plugin activates once every service it injects is available. `EntryGroup.update` throws all 129 rows out **at once** and dependencies sort out the order themselves.

So when you add a row to the tree, where you put it does not matter. Getting `inject` right does.

## 10. What a failed boot looks like

{{src:packages/boot/app-boot/src/index.ts#L692-L725|assertEntriesActivated}} is the last gate. Once the tree settles, it walks every entry and checks its fiber state:

```ts
if (state === FIBER_ACTIVE) continue
if (state === FIBER_FAILED) {
  try {
    await fiber.await()
  } catch (error) {
    rejectionReasons.push(error)
    failures.push(`${entry.options.name}: ${formatActivationError(error)}`)
  }
  continue
}
if (state === FIBER_PENDING) {
  const missing = Object.keys(fiber.inject).filter(service => fiber.ctx.get(service) === undefined)
  const subject = missing.length === 1 ? 'service' : 'services'
  failures.push(`${entry.options.name}: pending (waiting for ${subject}: ${missing.join(', ') || 'unknown'})`)
}
```

The two failure classes are diagnosed in completely different ways:

- **FAILED**: the plugin threw. The exception lives in fiber-private state and only `await fiber.await()` recovers it, so this deliberately awaits a promise known to be rejected in order to extract the reason.
- **PENDING**: the plugin threw nothing. It is simply waiting forever for a dependency. There is no exception to report, so the code computes **which injected services are still undefined** and names them.

The PENDING branch is what beginners hit most: the plugin is written correctly, it just never starts, and nothing is reported. This diagnostic prints who it is waiting for. Step 4 of the lab builds one.

:::note Why only FAILED fibers are awaited
ACTIVE ones need no wait, and awaiting a PENDING one never returns. Only a FAILED fiber holds an already-settled rejected promise, so awaiting it throws immediately.
:::

:::lab Hands-on: build your own profile

Four steps. The first two are read-only; in the last two you build a plugin that actually runs.

**Step 1: see the 129 rows**

Use a throwaway `$DSH_HOME` so your real `~/.dsh` is untouched:

```sh
cd deepseek-harness
export LAB=/tmp/dsh-lab
mkdir -p $LAB
DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile web --dump-config > $LAB/web.yml
grep -c '^- id:' $LAB/web.yml     # 129
grep '^# ==' $LAB/web.yml | head  # which bundle each run came from
```

The `# ==` comments are provenance markers generated by `renderConfigDump`. Look at the `patched by @deepseek-ai/dsh-web-app` runs: that is section 3's "a later layer edits a row an earlier layer inserted."

Look at the profile that was just created for you:

```sh
cat $LAB/profiles/web/package.json   # bundles: [dsh-base, dsh-web-app]
cat $LAB/profiles/web/cordis.yml     # []
```

The first time the name `web` is used, `loadProfile` initializes it from `PROFILE_TEMPLATES`.

**Step 2: a profile containing only your own plugin**

A custom profile name has no template, so write `package.json` by hand. Leave bundles empty and the whole tree is yours:

```sh
mkdir -p $LAB/profiles/lab
cat > $LAB/profiles/lab/package.json <<'EOF'
{
  "name": "dsh-profile-lab",
  "private": true,
  "dsh": { "profile": { "bundles": [] } }
}
EOF

cat > $LAB/profiles/lab/hello.mjs <<'EOF'
export const inject = ['cmdlineArgs', 'appExit']
export function apply(ctx, config) {
  console.log('[hello] config =', JSON.stringify(config))
  console.log('[hello] args   =', JSON.stringify(ctx.cmdlineArgs.get()))
  ctx.appExit(0)
}
EOF

cat > $LAB/profiles/lab/cordis.patch.yml <<'EOF'
- insert:
    - id: hello
      name: ./hello.mjs
      config:
        greeting: hi
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --some-app-flag 42
```

Output:

```
[hello] config = {"greeting":"hi"}
[hello] args   = ["--some-app-flag","42"]
```

That is all of it. A module exporting `apply` plus one YAML row is a DSH plugin.

Two things worth pausing on:

- `--some-app-flag 42` means nothing to the launcher and arrives verbatim in `cmdlineArgs`. That is the boundary from section 1.
- The `.mjs` suffix is needed because the profile directory's `package.json` has no `"type": "module"`, so Node would treat `.js` as CJS. Real plugins are standalone npm packages that declare their own type.

**Step 3: override it with `--patch`**

```sh
cat > $LAB/over.yml <<'EOF'
- id: hello
  config:
    greeting: overridden
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml --dump-config
DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml
```

The dump's provenance comment becomes:

```
# == …/profiles/lab/cordis.patch.yml, patched by …/over.yml
- id: hello
  name: ./hello.mjs
  config:
    greeting: overridden
```

and the boot prints `greeting: overridden`. Layer 4 beats layer 2, matching section 3's table.

**Step 4: a plugin that waits forever**

```sh
cat > $LAB/profiles/lab/broken.mjs <<'EOF'
export const inject = ['workspace']
export function apply(ctx) {
  console.log('[broken] never reached')
}
EOF

cat > $LAB/profiles/lab/cordis.patch.yml <<'EOF'
- insert:
    - id: hello
      name: ./hello.mjs
      config:
        greeting: hi
    - id: broken
      name: ./broken.mjs
EOF

cat > $LAB/over.yml <<'EOF'
- id: hello
  disabled: true
EOF

DSH_HOME=$LAB node --import tsx/esm apps/cli/src/bin.ts --profile lab --patch $LAB/over.yml
```

Nobody provides `workspace` in this profile, so `broken` stays PENDING forever. Output:

```
Error: dsh: plugin tree failed to load: dsh: 1 entry did not activate
./broken.mjs: pending (waiting for service: workspace)
    at boot (…/app-boot/src/index.ts:800:11)
```

That is the PENDING diagnostic from section 10. `waiting for service: workspace` is computed on the spot, not reported by the plugin.

This step also demonstrates something else: `hello` has to be disabled first. Otherwise it calls `appExit(0)`, the whole tree is disposed before `assertEntriesActivated` runs, `boot()` returns early at `ctx.get('loader') === undefined`, and you never see the diagnostic. That is exactly the check from section 4.

Clean up:

```sh
rm -rf /tmp/dsh-lab
```

## Summary

This chapter's chain:

| Stage | Code | Product |
|---|---|---|
| parse argv | `parseDshArgs` | four launcher flags, everything else passed through |
| find the profile | `loadProfile` / `resolveBundleDir` | bundle list plus user patch layer |
| stack patches | `composeProfile` / `applyEntryPatches` | 129 rows |
| assemble | `boot` / `mountRootInclude` | one root Context, one Include |
| expand | `EntryGroup.update` / `Entry._start` | 129 `registry.plugin()` calls |
| accept | `assertEntriesActivated` | all ACTIVE, or one diagnostic naming names |

Three conclusions:

**Config is the code structure.** There is no centralized app assembly file; a tree is entirely determined by its patch stack. Changing what DSH consists of means changing YAML, as the profile built from scratch in lab step 2 shows.

**A patch replaces the whole config, it does not merge.** The rule forces bundles to keep any single row down to two layers of writes, at the cost of restating a full row's config when you patch it.

**Priority is not special-cased.** The command line beating the config file works because `inject` makes a fiber wait for its service and `!!js` makes config evaluate lazily. Every extension point chapter 12 hooks into has this same shape.

The next chapter covers the session log: how DSH records a conversation, and why the constraint "if the model saw it, it was recorded" ends up dictating the shape of the data structure.
